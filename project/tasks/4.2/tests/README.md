# Тесты занятия 4.2

Три файла. `os_handle_tests.cpp` — про фабрику границы и правило пяти,
`parse_view_tests.cpp` — про разбор без владения, `rule_loader_tests.cpp` —
про загрузчик правил и номера строк в диагностике.

Первый трогает границу: ему нужен настоящий сценарий, путь передаётся
сборкой. Остальные два не трогают ни диск, ни симулятор.

## Подключение

```bash
cmake --preset windows -D NANO_EDR_LESSON=4.2
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Правки в вашем `CMakeLists.txt` не нужны:
тесты линкуются с библиотекой `nano_edr_core`, а она собирается сама из всех
`.cpp` в `src/`, кроме `main.cpp`.

Наборы прошлых занятий приходят вместе с этим и обязаны проходить: какие
именно и почему не все — в `tasks/lessons.cmake`.

С этого занятия из набора 2.1 выпадают тесты бросающего конструктора
`OsHandle` — почему, сказано ниже. Отдельного ключа для этого нет: номер
занятия знает сам.

Взявшись за продвинутую часть — виды правил `sequence` и `threshold`
в файле, — добавьте ключ:

```bash
cmake --preset windows -D NANO_EDR_LESSON=4.2 -D NANO_EDR_RULE_KINDS=ON
```

Без неё два случая загрузчика из пятнадцати не собираются. Так и задумано:
тест, требующий того, что базовая часть делать не просит, сообщал бы
о несделанном как о сломанном, и чинить вы стали бы не то.

## Один файл из набора 2.1 отключается, и это часть занятия

`tasks/2.1/tests/os_handle_tests.cpp` проверял, что конструктор обёртки
бросает на несуществующем файле и что сообщение исключения называет путь.
На 4.2 конструктор уезжает в приватные, и эти проверки перестают
компилироваться.

Это не «тесты устарели». Проверялся контракт; контракт заменён сознательно,
значит проверка заменяется тоже — на тесты фабрики из этого набора. Цена
смены канала отказа ровно такая: один файл из пяти. Остальные четыре
(событие, разбор, условия, окно) на 4.2 нужны так же, как на 2.1.

Из старого файла сюда переехали не все случаи, а те, у которых остался смысл:
запрет копирования, повторный `Stop`, доведение потока до конца. Добавились
четыре, которых не было и быть не могло.

## Что проверяется и почему именно так

### Фабрика вместо конструктора

| тест | что сломалось бы без него |
|---|---|
| `правило пяти: копирования нет, перемещение есть` | `Open` не собирается: возвращать объект нечем |
| `конструктор недоступен снаружи` | остаётся второй путь создания, мимо проверки |
| `несуществующий файл — ошибка, а не исключение` | отказ можно не заметить |
| `перемещение не освобождает хендл дважды` | двойной `os_free` |

Четвёртый тест сам по себе ничего не ловит — его смысл в прогоне под
`-fsanitize=address`. Перемещающий конструктор, забывший обнулить источник,
собирается, проходит все тесты и падает на чужой машине. Без санитайзера этот
случай проверяет только то, что код скомпилировался.

Тест `отказ действия несёт вид, а не только текст` стоит отдельно. На нём
держится всё реагирование: `kNoSuchProcess`, `kPidReused` и `kAccessDenied` —
три разных последствия, и различать их надо перечислением, а не поиском
подстроки в сообщении.

### Разбор без владения

Проверяется два разных утверждения, и путать их не надо.

**Что разбирает то же самое.** Смотрящая и владеющая формы сравниваются
на одной строке поле за полем. Если у вас окажутся два разных алгоритма
разбора одного формата, они разойдутся — не сразу, а на первой правке
формата, и разойдутся молча. Владеющая форма обязана быть переходником.

**Что действительно не копирует.** Проверяется сравнением адресов: `view`
на подстроку обязан указывать внутрь исходного буфера. Это единственный
способ проверить отсутствие аллокации, не заглядывая в аллокатор.

Тест `переиспользование не оставляет следов прошлой строки` — про то, как
эту функцию положено звать: один `EventPartsView` на весь цикл. Заводить
новый на каждую строку значит вернуть ту самую аллокацию, ради которой всё
затевалось.

Тест `событие из view владеет своими строками` затирает исходный буфер после
конструирования события. Событие обязано это пережить: буфер — одна строка
журнала, а событие живёт дольше.

### Загрузчик правил

Проверяется не то, разбирается ли правильный файл, — это самая лёгкая часть.
Проверяется, что на битой конфигурации загрузчик **отказывает** и называет
**номер строки**.

Тринадцать случаев — про базовую часть, то есть про правила вида `match`.
Ещё два (`три вида правил разбираются` и `порог больше вместимости буфера`)
открываются флагом `NANO_EDR_RULE_KINDS` вместе с продвинутой частью.

| битая строка | ожидаемый номер |
|---|---|
| неизвестный ключ (`severiti`) | строка ключа |
| неизвестный оператор (`startswith`) | строка условия |
| неизвестный тип события (`proces_start`) | строка условия |
| правило без `kind` или без условий | строка **заголовка правила** |
| пустой файл, файла нет | ноль: к строке не привязано |

Последние две строки таблицы стоит прочитать вместе. Отказ про правило
целиком указывает на его заголовок, а не на место, где правило кончилось:
человек читает про правило, а не про его границу. А ноль означает честное
«строки тут нет» — выдумывать её было бы враньём.

Отдельно проверяется `слово or внутри кавычек не режет условие`. Разбор,
не знающий про кавычки, сломает `cmdline contains "a or b"` на два
бессмысленных куска и примет битое правило за исправное. Молча.

## Если не собирается

**`'os_error.h' file not found`** — заготовки взяты из среза `l4.1`. Нужен
`l4.2`.

**`no member named 'Open' in 'nano_edr::OsHandle'`** — то же самое.

**`calling a private constructor of class 'nano_edr::OsHandle'`** в тестах
2.1 — конфигурация осталась на прежнем занятии. С `-D NANO_EDR_LESSON=4.2`
старый файл из набора 2.1 выпадает сам.

**`no viable conversion from 'std::vector<Field>' to 'std::vector<FieldView>'`** —
перегрузка выбирается по типу выходного параметра, а не входного. У вас,
скорее всего, осталась одна форма вместо двух.

**`ignoring return value of function declared with 'nodiscard'`** — это
не придирка компилятора, а смысл занятия: результат обязан быть посмотрен.
