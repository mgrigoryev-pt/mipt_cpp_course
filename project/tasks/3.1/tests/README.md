# Тесты занятия 3.1

Кольцевой буфер, пороговое правило, комбинаторы на шаблонах, типизированный
доступ к полям.

## Как подключить

```bash
cmake --preset windows -D NANO_EDR_LESSON=3.1
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Правки в вашем `CMakeLists.txt` не нужны:
тесты линкуются с библиотекой `nano_edr_core`, а она собирается сама из всех
`.cpp` в `src/`, кроме `main.cpp`.

Наборы занятий 2.1 и 2.3 остаются подключёнными и обязаны проходить. Кольцевой
буфер заменил список **в агенте**, но сам список остался в коде — на нём
построен примитив занятия, — и его тесты продолжают работать.

## «Не аллоцирует вообще» — проверяемое утверждение

Критерий занятия сформулирован так, и проверяется он буквально: тест подменяет
глобальный `operator new` и считает вызовы. Десять тысяч вставок и полный обход
дают **ноль**.

Проверяется на `Timestamp`, а не на `Event`: у события внутри строки, они
аллоцируют сами по себе, и утверждение о буфере на нём не проверить.

## Границы порогового правила

Три случая из критерия, и все три существенные:

- **девятнадцать** — не срабатывает;
- **ровно двадцать** — срабатывает;
- **двадцать за одиннадцать секунд** — не срабатывает.

Третий важнее первых двух: порог не в количестве, а в скорости. Двадцать
записей за одиннадцать секунд — обычная работа, за десять — уже нет.

Плюс три случая, о которых легко забыть:

**Порог считается по ключу.** Иначе десять безобидных процессов складываются
в одну сработку, и правило начинает ловить активность хоста, а не процесса.

**После сработки счёт начинается заново.** Иначе одно превышение порога даёт
сработку на каждом следующем событии, и на потоке это превращается в шум.

**Порог больше вместимости буфера не срабатывает никогда.** Буфер помнит N
отметок; правило с `count > N` физически не может их набрать. Правильное
поведение — молчать: правило, которое не может сработать, лучше правила,
которое срабатывает не так. `static_assert` тут не поможет — `count` задаётся
во время работы.

## Пустые комбинаторы

`AllOfStatic<>` — истина, `AnyOfStatic<>` — ложь. То же соглашение, что
у динамических с занятия 2.3, и по той же причине: это нейтральные элементы
для `&&` и `||`. В шаблонной версии асимметрия даже не выдумана — она прямо
следует из fold-выражения: `(... && )` даёт `true`, `(... || )` даёт `false`.

## Мост между статикой и динамикой

Комбинатор на шаблонах не реализует `ICondition` и не должен: реализовав,
он потерял бы ровно то, за чем создан — отсутствие виртуальных вызовов внутри.

Поэтому есть `MakeCondition`, который заворачивает любой вызываемый объект
в `ICondition`. Виртуальный вызов остаётся **один** — на весь составной
комбинатор, а не на каждое условие внутри. Это и есть предмет замера
в продвинутой части.

## Типизированный доступ

`FieldTraits<T>` объявлен, но не определён — только специализации. Попытка
взять поле как тип, для которого разбора не написано, **не должна собираться**.
Молча сделать что-то похожее на правду хуже, чем не собраться.

Канал отказа не изменился с занятия 1.3: `false`, если поля нет или оно
не разбирается. Битые внешние данные — обычное дело, а не исключение.
