# Тесты занятия 3.3

Два файла. `move_tests.cpp` — про цену копий, `response_tests.cpp` — про план
реагирования. Ни один не запускает симулятор.

## Подключение

```bash
cmake --preset windows -D NANO_EDR_LESSON=3.3
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Правки в вашем `CMakeLists.txt` не нужны:
тесты линкуются с библиотекой `nano_edr_core`, а она собирается сама из всех
`.cpp` в `src/`, кроме `main.cpp`.

Наборы прошлых занятий приходят вместе с этим и обязаны проходить: какие
именно и почему не все — в `tasks/lessons.cmake`.

## Что проверяется и почему именно так

### Половина тестов — `static_assert`

Правило пяти и правило нуля проверяются компилятором, а не запуском. Это
не стилистический выбор: утверждение «у Event перемещение не бросает» либо
верно во время компиляции, либо неверно, и проверять его во время выполнения
нечем.

| проверка | что она означает |
|---|---|
| `is_nothrow_move_constructible_v<Event>` | `vector` при росте переместит события, а не скопирует |
| `!is_copy_constructible_v<Detection>` | сработку нельзя размножить, а значит нельзя доложить о ней дважды |
| `!is_default_constructible_v<Event>` | инвариант держится: «пустого события» не существует |

Обратите внимание, что у `Event` **ни одна** из пяти функций не написана,
а у `Detection` объявлены **все пять**. Это не два стиля, а два случая, и
файлы лежат рядом специально.

### Вторая половина — счётчик копий

Компилятор не скажет, какая перегрузка выбралась на вашей строке. Забытый
`std::move` не даёт ни ошибки, ни предупреждения: код работает, просто делает
вдвое больше аллокаций. Единственное, что это ловит, — число.

Тесты фиксируют числа, которые обязаны получиться:

| строка кода | `event_strings_copied` | `event_strings_moved` |
|---|---|---|
| `Event(parts)` | 7 | 0 |
| `Event(std::move(parts))` | 0 | 7 |
| `Event(MakeParts(...))` | 0 | 7 |

Семь — это три строки шапки плюс по две на каждое из двух полей. Если
у вас другие числа, сначала посчитайте свои поля, и только потом ищите
пропущенный `std::move`.

### Тест, который стоит прочитать целиком

`битая строка не портит части до проверки`. Перемещающий конструктор обязан
сначала проверить инвариант и только потом забирать строки. Обратный
порядок — сначала забрать, потом бросить — даёт ошибку, которую не поймает
ни один тест счастливого пути: вызывающий остаётся с пустым объектом вместо
своих данных и об этом не узнаёт.

Это безопасность относительно исключений в самом простом виде: операция либо
делает всё, либо не делает ничего.

## Про `response_tests.cpp`: здесь нет симулятора

Ни одного вызова `os.h`, ни одного файла на диске, ни одного сценария. Только
модель, сработка и план.

Это проверка дизайна, а не экономия. Если план нельзя построить, не убив
по дороге настоящий процесс, значит планирование и исполнение не разделены —
и режим `--dry-run` в таком агенте будет работать «почти всегда».

Отдельно стоят три теста, каждый про ошибку, которая дорого стоит:

**`потомки убиваются раньше родителя`.** Живой родитель успевает породить
нового потомка взамен убитого.

**`переименованные файлы не удаляются`.** Шифровальщик «создаёт» сорок путей
вида `quarterly.xlsx.locked`, и создаёт по-настоящему: этих путей не было.
Планировщик, удаляющий всё созданное, удалит документы жертвы — единственную
копию, которая у неё осталась.

**`системный файл не изолируется никогда`.** Правило вправе ошибиться
и попросить изолировать образ, который лежит в `System32`. Предохранитель
стоит в планировщике, потому что правил много, а место исполнения одно.

## Если не собирается

**`use of deleted function 'Detection::Detection(const Detection&)'`** —
где-то сработка копируется. Скорее всего в получателе, который складывал
её в вектор. Складывать надо снимок, а не сработку.

**`no matching function for call to 'Event::Event(EventParts)'`** — у вас
один конструктор вместо двух. Занятие требует двух: копирующей формы
и перемещающей.

**Не находится `copy_stats.h` или `window_entry.h`** — заготовки взяты
из среза `l3.2`. Нужен `l3.3`.
