# Проект практикума: агент nano-edr

Это заготовка, из которой за двенадцать занятий вырастает агент: он получает
поток событий от операционной системы, находит в нём атаки и реагирует.

**Ваш код живёт в `src/`. Всё остальное дано.**

Что делать на каждом занятии — в постановках, [`practice/`](../practice/README.md).
Здесь — всё про работу с проектом: как собрать, как запустить, как прогнать
тесты, что где лежит, что менять нельзя и что делать, когда не собирается.

---

## Что нужно установить

| | |
|---|---|
| компилятор C++23 | g++ 14+, clang 19+ или Visual Studio 2022 17.10+ |
| CMake 3.21 и новее | проверить: `cmake --version` |
| Windows | Visual Studio 2022, нагрузка «Разработка классических приложений на C++» |
| Linux | `g++-14`, `make` |

Компилятор старее конфигурация отвергает сразу и с внятным сообщением,
а не падает посреди сборки.

## Собрать и запустить

Проект собирается **двумя шагами**, и путать их не стоит: половина
непонятных ошибок берётся из того, что забыт первый.

**Шаг 1, конфигурация.** Читает `CMakeLists.txt` — описание проекта: какие
файлы компилировать, с какими флагами, что с чем линковать, — и создаёт
в `build/` файлы для настоящей сборочной системы: проект Visual Studio
на Windows, `Makefile` на Linux. Ни один `.cpp` здесь ещё не компилируется.

**Шаг 2, сборка.** Запускает эту сборочную систему: компилирует изменившееся
и линкует результат.

```bash
cmake --preset windows -D NANO_EDR_LESSON=1.1
cmake --build --preset windows
```

На Linux вместо `windows` — `linux`. Результат:
`build/windows/Release/nano-edr.exe` или `build/linux/nano-edr`.

```bash
./build/windows/Release/nano-edr scenarios/phishing_macro.log
```

Запускать из корня `project/` — пути к сценариям относительные.

`--preset` — именованный набор настроек из `CMakePresets.json`: генератор,
каталог сборки, профиль, версия стандарта. Без пресета то же самое пришлось бы
перечислять флагами при каждом запуске.

**К шагу 1 возвращаться надо, только когда меняется описание проекта:**
добавлен новый `.cpp` в `src/`, сменился номер занятия, обновился комплект.
Правка кода — это всегда только шаг 2. Заголовки CMake не перечисляет,
из-за нового `.h` переконфигурация не нужна.

## Номер занятия

Одно значение задаёт всё остальное:

```bash
cmake --preset windows -D NANO_EDR_LESSON=1.2
```

Из него берутся **две** вещи.

1. Каталог заготовок `kit/include/l1.2/` встаёт на include-путь, и
   `#include "event.h"` начинает находить выданный интерфейс.
2. Подключаются наборы выданных тестов, действующие на этом занятии.

Номер запоминается в кэше сборки, поэтому набирается один раз за занятие.
После его смены проект надо **пере**конфигурировать — это шаг 1, и без него
ни новые заготовки, ни новые тесты не появятся.

Какие наборы тестов действуют на каком занятии — в `tasks/lessons.cmake`.
Переписывать оттуда в командную строку нечего; там написано, **почему** набор
прошлого занятия иногда уходит, а не копится дальше. Уходит он тогда, когда
занятие меняет сам контракт, который тот набор проверял.

## Тесты

`ctest` — программа из комплекта CMake: запускает объявленные в проекте тесты
и печатает итог.

```bash
ctest --preset windows
ctest --preset windows -R 1.1          # только набор занятия 1.1
ctest --preset windows --output-on-failure
```

**В начале занятия тесты падают, и так и должно быть:** они описывают то, чего
ещё нет. Занятие закрыто, когда они зелёные.

Тесты появляются только при конфигурации с `NANO_EDR_LESSON`; без номера их нет
вовсе. Правки в вашем `CMakeLists.txt` не нужны никогда: тесты линкуются
с библиотекой `nano_edr_core`, которая собирается из всех `.cpp` в `src/`,
кроме `main.cpp`.

Часть тестов запускает вашего агента целиком и сравнивает вывод с эталоном
побайтово. Такому тесту нужна цель `nano-edr`; если ваша называется иначе,
имя задаётся ключом `NANO_EDR_AGENT`. При расхождении тест печатает первую
разошедшуюся строку — с неё и начинайте.

**Набор прошлого занятия обычно остаётся подключённым.** Это не довесок:
рефакторинг, задевший чужое, обязан провалить старый набор сразу, а не через
три занятия.

## Перед сдачей

**Предупреждения.** `-Wall -Wextra` (на MSVC — `/W4`) включены всегда, но
ошибками не считаются: посреди задания это мешало бы отлаживать. Приёмка
требует чистой сборки, поэтому проверьте заранее пресетом, где предупреждения
становятся ошибками:

```bash
cmake --preset strict-windows
cmake --build --preset strict-windows
```

На Linux — `strict`.

**Санитайзеры.** Половина ошибок с указателями видна только под ними:

```bash
cmake --preset asan-windows
cmake --build --preset asan-windows
ctest --preset asan-windows
```

На Linux — `asan`, и разница между системами в его пользу: у GCC и clang это
ASan **и** UBSan, у MSVC только ASan. Неопределённое поведение, которое ловит
UBSan — переполнение знакового, сдвиг на слишком много, разыменование
невыровненного указателя, — на Windows придётся искать иначе.

## Что где лежит

| | |
|---|---|
| `src/` | **ваш код**; новый `.cpp` подхватывается сам, править CMake не нужно |
| `include/os.h`, `include/edr.h` | границы: вход от системы и выход к серверу |
| `SPEC.md` | контракт границ: что гарантировано, а что нет |
| `lib/<платформа>/` | готовые `os` и `edr` — библиотеки, а не исходники |
| `kit/include/<занятие>/` | заготовки интерфейсов занятия, полный снимок |
| `tasks/<занятие>/tests/` | выданные тесты; они же прогоняются при сдаче |
| `tasks/<занятие>/exercise/` | отдельная программа занятия: упражнение или стенд для замера |
| `tasks/<занятие>/handout/` | код, который выдан готовым, — копируется в `src/` |
| `scenarios/` | журналы, конфигурации и приёмочные секции |
| `tools/<платформа>/sim_verify` | сверяет отчёт симулятора с ожиданиями |
| `tools/<платформа>/gen_stress` | генератор нагрузочного журнала |
| `examples/minimal_agent.cpp` | полный цикл работы с `os.h`, цель `minimal_agent` |

Свой код пишется **только в `src/`**. Остальные каталоги обновляются вместе
с курсом, и правки в них потеряются при следующем обновлении. `src/`
не перезаписывается никогда.

## Заготовки: что это и что с ними можно

`kit/include/<занятие>/` — публичные интерфейсы между модулями проекта.
На них опираются выданные тесты и следующие занятия.

**Это часть постановки, а не пример оформления. Имена и подписи менять
нельзя:** выданные тесты собираются с вашим кодом без правок, а эталонная
реализация после проверочной подключается на место вашего модуля — и то,
и другое держится на совпадении интерфейсов. Всё, что не видно снаружи, ваше.

Реализаций в заготовках нет: только объявления. Заголовок, который собирается,
но не линкуется, — это нормально, тела функций пишете вы.

**Каталог на занятие, и в сборку идёт ровно один** — тот, номер которого задан.
Так получается потому, что интерфейсы растут вместе с пройденным материалом:
в части 1 нет ни классов, ни шаблонов, значит `Event` там агрегат, а таблица
правил живёт на указателях на функции; к 2.1 у `Event` появляются инварианты
и приватные поля, к 2.3 правило становится интерфейсом с виртуальными
функциями, к 3.1 условия — вариадическими шаблонами. Заголовок, написанный
сразу «как надо», был бы выдачей ответа на четыре занятия вперёд.

Каждый каталог — **полный снимок**, а не добавка к предыдущему. Отсюда
полезный приём: `diff -r kit/include/l1.2 kit/include/l1.3` показывает ровно
то, что занятие добавляет к интерфейсу.

| Каталог | Новое | Выросло |
|---|---|---|
| `l1.2` | `event.h`, `event_list.h`, `parse.h` | — |
| `l1.3` | `fields.h`, `rules.h` | `parse.h` |
| `l2.1` | `conditions.h`, `os_handle.h` | `event.h`, `event_list.h`, `fields.h`, `parse.h` |
| `l2.2` | `rule.h` | `conditions.h`, `rules.h` |
| `l2.3` | `event_source.h`, `rule_engine.h` | `conditions.h`, `event.h`, `rule.h` |
| `l3.1` | `combinators.h`, `field_traits.h` | `rule.h` |
| `l3.2` | `alert_sink.h`, `detection.h`, `edr_handle.h`, `entity_model.h` | пять файлов |
| `l3.3` | `copy_stats.h`, `response.h`, `window_entry.h` | восемь файлов |
| `l4.1` | — | `entity_model.h`, `response.h`, `rule.h`, `rule_engine.h` |
| `l4.2` | `os_error.h`, `rule_loader.h` | `event.h`, `os_handle.h`, `parse.h` |
| `l4.3` | `reporter.h` | пять файлов |

Две вещи в этой таблице стоит заметить заранее.

**Не всё, что вы пишете, объявлено в заготовках.** Кольцевой буфер с занятия
3.1, свой `Function` и получатель с подавлением дубликатов с 3.2 своего
заголовка в комплекте не имеют вовсе: их вы кладёте в `src/` сами. Работает
это потому, что `src/` стоит на include-пути **раньше** комплекта, — выданные
тесты и заготовки находят ваш файл без единой правки в них.

**`event_list.h` в `l4.1` отсутствует.** Рукописный список к части 4
заменяется стандартным контейнером — это и есть занятие 4.1, и заготовка
исчезает вместе с надобностью в ней.

### Пометка «ВЫДАН ГОТОВЫМ»

Иногда критерий занятия требует того, что по программе ещё не пройдено. Тогда
код выдан написанным, а в заголовке стоит пометка `ВЫДАН ГОТОВЫМ` с причиной.
Так выдана специализация `std::formatter` для `Event` в `l2.1`: критерий
требует работающего `std::print("{}\n", event)`, а специализация шаблона —
лекция 8. Помеченное читать полезно, трогать не надо.

## Материалы занятия: `tasks/<занятие>/`

Внутри бывает три вида содержимого, и не у каждого занятия есть все три.

**`tests/` — выданные тесты.** Те самые, которые надо довести до зелёного;
они же прогоняются при сдаче. Подключаются номером занятия, руками ничего
перечислять не нужно.

**`exercise/` — отдельная программа.** Упражнение или стенд для замера:
в проект не входит, на сдачу не влияет, собирается вручную одной командой
из своего каталога.

```bash
g++ -std=c++23 -O2 -Wall -Wextra -I ../../../src -o window window.cpp
./window
```

На Windows — из «x64 Native Tools Command Prompt for VS 2022», чтобы `cl` был
на `PATH`:

```
cl /nologo /std:c++latest /O2 /W4 /EHsc /I ..\..\..\src window.cpp
```

Ключ `-I ../../../src` нужен там, где стенд берёт ваш заголовок. **Стенды
собираются только в Release:** в отладочной сборке ничего не встроено, и замер
меряет работу отладочных проверок, а не то, что вы сравниваете.

**`handout/` — выдано готовым.** Код, который не надо писать: копируется
в `src/` вашего проекта и дальше живёт как ваш — вы правите его на следующих
занятиях. Появление нового `.cpp` — изменение описания проекта, поэтому после
копирования нужна переконфигурация.

## Сценарии и проверка результата

`scenarios/` — журналы событий, конфигурации и приёмочные секции. Семь
открытых сценариев: атаки и чистые, на которых детектов быть не должно.

С занятия 3.3 проверяется не текст вывода, а состояние мира: агент
по-настоящему завершает процессы и изолирует файлы в симулируемой системе,
а `tools/<платформа>/sim_verify` читает отчёт симулятора и сверяет, кого агент
действительно завершил и какой файл действительно перенёс.

### Нагрузочный журнал

Замеры делаются не на семи сценариях — они слишком короткие, — а на журнале
из двух миллионов строк. В комплекте он не лежит (двести мегабайт),
а генерируется:

```bash
./tools/win-x64/gen_stress.exe
```

На Linux — `./tools/linux-x64/gen_stress`. По умолчанию журнал ложится
в `scenarios/stress.log`; атак в нём нет, он нужен только для замеров. Журнал
воспроизводим: при одном зерне получается побайтово тот же файл на любой
платформе.

## Если не собирается

**`unresolved external symbol` (на Linux `undefined reference`)** — заголовок
есть, реализации нет. Так выглядит начало занятия: заготовка объявила, вы ещё
не написали.

**`'что-то.h' file not found` или `no member named ...`** — почти всегда
настроен не тот номер занятия. Заготовки взяты из чужого снимка: файла,
который появится позже, ещё нет, или у типа ещё нет метода, который дорастёт
на следующем занятии. Проверьте `NANO_EDR_LESSON` и **пере**конфигурируйте.

Тот же симптом бывает и обратным: файл из прошлого снимка исчез намеренно —
так `event_list.h` пропадает на 4.1.

**Тесты не появились вовсе** — конфигурация прошла без `NANO_EDR_LESSON`.

**Изменения в коде не подхватились** — правился заголовок, а сборка
инкрементальная; либо добавлен новый `.cpp` и нужен шаг 1.

**`цель 'nano_edr' не найдена`** — набор тестов подключён, а библиотеки
из `src/` ещё нет: в `src/` нет ни одного `.cpp`, кроме `main.cpp`.

**`'jthread' is not a member of 'std'` или подобное про библиотеку** —
компилятор старше, чем требует курс. Версии в таблице выше.

**`undefined reference to 'pthread_create'`** — на Linux не подключены потоки.

## Чего в комплекте нет

**Исходников симулятора.** `os` и `edr` поставляются собранными: агент обязан
работать с системой через контракт, а не через знание о том, как она устроена
внутри. Всё, что нужно знать, — в `include/os.h`, `include/edr.h` и `SPEC.md`,
включая то, чего API не делает и делать не будет.

**Решений.** Три состояния эталонного агента выдаются после проверочных.
