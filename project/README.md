# Проект практикума: агент nano-edr

Это заготовка, из которой за двенадцать занятий вырастает агент. Ваш код
живёт в `src/`, всё остальное дано.

Постановки занятий — в [`practice/`](../practice/README.md).

## Что нужно установить

| | |
|---|---|
| компилятор C++23 | g++ 14+, clang 19+ или Visual Studio 2022 17.10+ |
| CMake 3.21 и новее | проверить: `cmake --version` |
| Windows | Visual Studio 2022, нагрузка «Разработка классических приложений на C++» |
| Linux | `g++-14`, `make` |

Компилятор старее конфигурация отвергает сразу и с внятным сообщением,
а не падает посреди сборки непонятной ошибкой.

## Получить проект

```bash
git clone <репозиторий курса>
cd cpp_course/project
```

Свой код пишется **только в `src/`**. Остальные каталоги комплекта обновляются
вместе с курсом, и правки в них потеряются при следующем обновлении. `src/`
не перезаписывается никогда.

## Собрать и запустить

### Что делает CMake

Проект собирается не одной командой компилятора, а двумя шагами.

**Шаг 1, конфигурация.** `cmake --preset windows` читает `CMakeLists.txt` —
описание проекта: какие файлы компилировать, с какими флагами, что с чем
линковать — и создаёт в `build/windows/` файлы для настоящей сборочной
системы: проект Visual Studio на Windows, `Makefile` на Linux. Ни один `.cpp`
на этом шаге ещё не компилируется.

**Шаг 2, сборка.** `cmake --build --preset windows` запускает эту сборочную
систему. Она компилирует изменившиеся файлы и линкует результат.

Возвращаться к шагу 1 нужно, только когда меняется описание проекта: добавлен
файл в `src/`, изменены настройки занятия (ниже), обновлён комплект. Правка
кода — это всегда только шаг 2.

`--preset` — именованный набор настроек из `CMakePresets.json`: генератор,
каталог сборки, профиль, версия стандарта. Без пресета то же самое пришлось бы
перечислять флагами при каждом запуске.

### Команды

```bash
cmake --preset windows
cmake --build --preset windows
```

На Linux вместо `windows` — `linux`. Результат:
`build/windows/Release/nano-edr.exe` или `build/linux/nano-edr`.

```bash
./build/windows/Release/nano-edr scenarios/phishing_macro.log
```

Запускать из корня `project/`: пути к сценариям относительные. Заготовка
считает строки журнала и отличает комментарии от событий. Детектов она
не ищет — это занятие 1.1.

## Настройки занятия

Одно значение — номер занятия:

```bash
cmake --preset windows -D NANO_EDR_LESSON=1.2
```

Из него берётся всё остальное. Каталог заготовок `kit/include/l1.2/` попадает
на include-путь, и `#include "event.h"` начинает находить выданный интерфейс;
подключаются наборы выданных тестов, которые на этом занятии действуют.

Каких наборов сколько — расписано в `tasks/lessons.cmake`. Заглядывать туда
надо не для того, чтобы что-то оттуда переписать в командную строку: там
написано, **почему** набор прошлого занятия иногда уходит, а не копится
дальше. Уходит он тогда, когда занятие меняет сам контракт, который тот набор
проверял.

Номер запоминается в кэше сборки, поэтому набирается один раз за занятие.
А вот после его смены проект надо **пере**конфигурировать: это шаг 1, и без
него ни новые заготовки, ни новые тесты не появятся.

## Тесты

`ctest` — программа из комплекта CMake: запускает тесты, объявленные
в проекте, и печатает итог.

```bash
ctest --preset windows
ctest --preset windows -R 1.1      # только тесты занятия 1.1
```

Тесты появляются при конфигурации с `NANO_EDR_LESSON`; без него их нет вовсе.
В начале занятия его тесты **падают**, и так и должно быть: они описывают то,
что ещё не написано. Занятие закрыто, когда они зелёные.

## Перед сдачей

**Предупреждения.** `-Wall -Wextra` (на MSVC — `/W4`) включены всегда, но
ошибками не считаются: на середине задания это мешает отлаживать. Приёмка
требует чистой сборки, поэтому проверьте заранее пресетом, где предупреждения
становятся ошибками:

```bash
cmake --preset strict-windows
cmake --build --preset strict-windows
```

На Linux — `strict`.

**Санитайзеры.** Половина ошибок с указателями видна только под ними, и критерий
К1 требует чистого прогона:

```bash
cmake --preset asan-windows
cmake --build --preset asan-windows
ctest --preset asan-windows
```

На Linux — `asan`. Разница между системами есть и она в пользу Linux: у GCC
и clang это ASan **и** UBSan, у MSVC только ASan. Неопределённое поведение,
которое ловит UBSan — переполнение знакового, сдвиг на слишком много,
разыменование невыровненного указателя, — на Windows придётся искать иначе.

## Что где лежит

| | |
|---|---|
| `src/` | **ваш код**; новый `.cpp` подхватывается сам, править CMake не нужно |
| `include/os.h`, `include/edr.h` | границы: вход от системы и выход к серверу |
| `SPEC.md` | контракт границ: что гарантировано, а что нет |
| `lib/<платформа>/` | готовые `os` и `edr` — библиотеки, а не исходники |
| `kit/include/<занятие>/` | заготовки интерфейсов занятия, полный снимок |
| `tasks/<занятие>/tests/` | выданные тесты; они же прогоняются при сдаче |
| `tasks/<занятие>/exercise/` | отдельная программа занятия: упражнение или стенд для замера |
| `scenarios/` | журналы, конфигурации и приёмочные секции |
| `tools/<платформа>/sim_verify` | сверяет отчёт симулятора с ожиданиями |
| `tools/<платформа>/gen_stress` | генератор нагрузочного журнала |
| `examples/minimal_agent.cpp` | полный цикл работы с `os.h`, цель `minimal_agent` |

## Чего в комплекте нет

Исходников симулятора. `os` и `edr` поставляются собранными: агент обязан
работать с системой через контракт, а не через знание о том, как она устроена
внутри. Всё, что нужно знать, — в `include/os.h`, `include/edr.h` и `SPEC.md`,
включая то, чего API не делает и делать не будет.

Решений. Три состояния эталонного агента выдаются после проверочных.
