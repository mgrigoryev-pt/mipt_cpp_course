# Настройка окружения: VS Code, Windows, Linux и macOS

Здесь описано окружение, на котором собирается проект курса, и его установка
с нуля. Оно не обязательно: захочется работать в другом — работайте, но тогда
ошибки сборки и компиляции разбираются своими силами.

## Из чего состоит окружение

- **clang** — компилятор: превращает `.cpp` в объектные файлы и собирает
  из них программу. Он же выдаёт предупреждения и ошибки, и он же
  инструментирует код санитайзерами.
- **CMake** — описание проекта. В `CMakeLists.txt` записано, какие файлы
  компилировать, с какими флагами и что с чем линковать; CMake читает это
  описание и создаёт из него файлы для сборочной системы. Сам он ничего
  не компилирует. Через него же подключается занятие и запускаются тесты
  (`ctest`).
- **Ninja** — сборочная система: берёт то, что сгенерировал CMake, и вызывает
  компилятор — только для изменившихся файлов. Она же побочно пишет
  `compile_commands.json`: список того, чем и с какими флагами собирается
  каждый файл.
- **clangd** — языковой сервер для редактора: переход к определению, поиск
  использований, автодополнение, подчёркивание ошибок. Работает он не догадками
  по тексту, а тем же разбором, что и компилятор, и флаги для этого берёт
  из `compile_commands.json` — то есть из настоящей сборки.
- **CMake Tools** — расширение VS Code, которое запускает CMake и Ninja
  за вас: выбор пресета, конфигурация, сборка по F7, запуск, тесты в панели
  Testing. Всё то же самое делается командами в терминале; расширение просто
  избавляет от набора.

Цепочка получается такая: **CMake** описывает проект → **Ninja** ведёт сборку →
**clang** компилирует, а **clangd** подключается к тому же описанию и потому
показывает в редакторе ровно то, что скажет сборка. Подробно про два шага
CMake — конфигурацию и сборку — написано в [`project/README.md`](project/README.md).

## Что такое пресет комплекта

CMake нужно сообщать многое: каким генератором собирать, каким компилятором,
куда класть результат, с какими ключами. Набирать это при каждом запуске
означало бы длинные команды, в которых один ключ из десяти рано или поздно
теряется. Поэтому наборы настроек записаны заранее — в файле
`CMakePresets.json` в корне `project/`, — и у каждого набора есть имя. Такой
именованный набор и называется **пресетом**; «пресет комплекта» — это пресет,
который приехал вместе с курсом, а не написан вами.

Отсюда вид всех команд курса: вместо ключей называется пресет.

```
cmake --preset windows          # конфигурация
cmake --build --preset windows  # сборка
ctest --preset windows          # тесты
```

Имена разделены по назначению:

| | |
|---|---|
| `windows`, `linux`, `macos` | обычная работа: clang, Ninja, профиль `Release` |
| `debug-windows`, `debug`, `debug-macos` | то же, но профиль `Debug`: для отладки по шагам |
| `asan-windows`, `asan`, `asan-macos` | прогон под санитайзерами |
| `strict-windows`, `strict`, `strict-macos` | сборка, где предупреждение считается ошибкой |
| `msvc`, `gcc` | сверка другим компилятором, в обычной работе не нужны |

Список того, что доступно на вашей системе, печатает `cmake --list-presets`;
что внутри каждого — видно в самом `CMakePresets.json`, файл текстовый.

**Правило: пресеты комплекта не правятся.** Файл обновляется вместе с курсом,
и правки в нём потеряются при следующем обновлении. Своего в них дописывать
и не приходится: единственное, что задаёт студент, — номер занятия, и он
передаётся ключом при конфигурации (шаг 4 в разделе «Порядок работы
в VS Code»).

## Компилятор один — clang

Курс идёт на C++23, и требования к версиям не формальность: `std::print`,
`std::expected`, `<=>` и прочее из лекций в более старых компиляторах просто
отсутствует.

Компилятор берётся один и тот же на всех трёх системах — **clang 19
или новее**. Причин три, и все практические:

- **Одинаковые сообщения об ошибках.** Диагностика clang одна и та же
  на Windows, на Linux и на macOS, и разбор непонятной ошибки на паре
  не превращается в «а у меня написано другое».
- **Одинаковый набор санитайзеров.** У clang это ASan **и** UBSan на всех
  трёх. У MSVC UBSan нет вообще, то есть переполнение знакового или сдвиг
  на слишком много под Windows не находились бы ничем.
- **Навигация совпадает со сборкой.** clangd читает те же флаги, которыми
  собирается проект, и подсвечивает то же, что скажет компилятор. Расхождения
  «в редакторе чисто, а сборка падает» не бывает.

Настраивать это не нужно: **пресеты комплекта уже собирают clang'ом** — и те,
что для обычной работы, и санитайзерные, и строгие. Команды из постановок
занятий работают как написаны. Пресеты `msvc` и `gcc` из таблицы выше
оставлены для сверки другим компилятором и в обычной работе не набираются.

**Подвох на macOS: `clang++` в системе уже есть, и он не тот.** Компилятор
от Apple отстаёт от LLVM на несколько выпусков, и C++23 в нём неполный —
`std::print` из комплекта он не соберёт. Требование «clang 19 или новее»
на macOS означает clang из Homebrew, и различить их несложно: свой печатает
`Homebrew clang version …`, системный — `Apple clang version …`. Конфигурация
проверяет это сама и на системном отказывается с текстом «clang … слишком
старый», так что незаметно собраться не тем не получится.

## Windows

### 1. clang и то, без чего он на Windows не работает

clang на Windows не самодостаточен. Он собирает под ABI MSVC (цель
`x86_64-pc-windows-msvc`), заголовки стандартной библиотеки берёт у MSVC,
а системные — из Windows SDK. Поэтому **Build Tools 2022 ставятся всё равно**;
компилятором `cl.exe` из их состава курс при этом не пользуется.

Скачать «Build Tools for Visual Studio 2022» со страницы загрузок
[visualstudio.microsoft.com/downloads](https://visualstudio.microsoft.com/downloads/)
(раздел «Tools for Visual Studio»), запустить установщик и отметить:

- нагрузку **«Разработка классических приложений на C++»** (Desktop
  development with C++) — это Windows SDK и стандартная библиотека;
- в списке отдельных компонентов — **«C++ Clang tools for Windows»**. Это
  и есть компилятор: clang, clangd и компоновщик lld одним компонентом.

Компонент «C++ AddressSanitizer» из состава Visual Studio при этом **не нужен**:
под clang рантайм санитайзеров приезжает вместе с LLVM.

**Подвох:** clang из Build Tools в PATH не попадает. Каталог надо добавить
руками («Изменение системных переменных среды» → «Переменные среды» → `Path`):

```
C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Tools\Llvm\x64\bin
```

Для установленной Visual Studio Community путь другой:
`C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\Llvm\x64\bin`.

### 2. CMake, Ninja, git, VS Code

Три установщика и один архив, все с сайтов своих проектов:

- **CMake** — [cmake.org/download](https://cmake.org/download/), файл
  `cmake-*-windows-x86_64.msi`. В установщике обязательно выбрать
  **«Add CMake to the system PATH»**: без этой галки `cmake` не найдётся
  из терминала.
- **Ninja** —
  [github.com/ninja-build/ninja/releases](https://github.com/ninja-build/ninja/releases),
  архив `ninja-win.zip` из раздела «Assets» последнего релиза. Внутри один
  файл `ninja.exe`; его надо положить в постоянный каталог (например
  `C:\tools\ninja`) и добавить этот каталог в `Path` — тем же способом,
  что и каталог clang выше.
- **git** — [gitforwindows.org](https://gitforwindows.org/), настройки
  установщика по умолчанию.
- **VS Code** — [code.visualstudio.com](https://code.visualstudio.com/).

### 3. Проверка

Новое окно PowerShell — переменную PATH подхватывают только заново запущенные
процессы:

```
clang++ --version
cmake --version
ninja --version
```

clang должен быть 19 или новее, CMake — 3.21 или новее. В выводе clang есть
строка `Target: x86_64-pc-windows-msvc` — это норма, именно так он и должен
собирать под Windows.

Если команда не найдена, а инструмент установлен, дело в PATH: для clang —
каталог из шага 1, для CMake — `C:\Program Files\CMake\bin`. После правки
терминал открывается заново.

## Linux

Команды даны для Ubuntu 26.04 LTS: там всё нужное есть в штатных репозиториях
(раздел universe).

```bash
sudo apt update
sudo apt install clang g++ cmake ninja-build git gdb
```

Номеров версий в именах пакетов нет, и это не небрежность: `clang` без номера
ставит тот clang, который в системе считается основным (в Ubuntu 26.04 —
21-й), и он же отзывается на имя `clang++`, которым его вызывают пресеты
комплекта. Ставить более старый нарочно смысла нет, а нижнюю границу проверяет
сам комплект: на clang старее 19-го конфигурация отказывает сообщением
«clang … слишком старый».

Зачем `g++`, если курс собирается clang: clang приносит компилятор, но не
стандартную библиотеку — на Linux он берёт libstdc++ от GCC, а `std::print`,
которым пользуется комплект, появился в libstdc++ 14. Пакет `g++` тянет
библиотеку за собой, и это единственное, ради чего он нужен: собирать им
ничего не придётся. Пакета `libstdc++-dev` без номера версии не существует —
под этим именем живёт виртуальный пакет с шестью поставщиками, и apt на нём
отказывает.

### Проверка

```bash
clang++ --version
cmake --version
ninja --version
```

В первой строке вывода clang стоит его версия, и она должна быть 19
или новее. И отдельно то, ради чего ставился `g++`:

```bash
echo '#include <print>' | clang++ -std=c++23 -x c++ -fsyntax-only -
```

Молчание означает, что заголовок нашёлся. Ошибка `file not found` — библиотека
всё ещё старая.

**Подвох на LTS постарше.** В Ubuntu 24.04 пакет `clang` без номера — это
clang 18, и комплект такой сборкой собираться откажется. Там clang ставится
номером, а имя без номера создаётся отдельно:

```bash
sudo apt install clang-19 libstdc++-14-dev cmake ninja-build git gdb
sudo update-alternatives --install /usr/bin/clang++ clang++ /usr/bin/clang++-19 100
sudo update-alternatives --install /usr/bin/clang clang /usr/bin/clang-19 100
```

Годится и любой clang новее 19-го, если он есть в репозитории системы или
подключён с [apt.llvm.org](https://apt.llvm.org/): номер в трёх строках
меняется на его.

Альтернатива libstdc++ — libc++ от LLVM: пакет `libc++-<версия>-dev` и флаг
`-stdlib=libc++` в своём пресете. Границы комплекта объявлены `extern "C"`,
поэтому готовые `libos.so` и `libedr.so` линкуются с любой из двух библиотек.

Дистрибутивы, где clang 19 или новее не поставить вовсе (Ubuntu 22.04,
Debian 12), для курса не подходят: нужна система поновее.

## macOS

Apple Silicon и Intel работают одинаково. Разница только в том, куда Homebrew
кладёт свои файлы, и команды ниже написаны так, что её не приходится знать.

### 1. Command Line Tools

```
xcode-select --install
```

Отсюда берутся системные заголовки, библиотеки и компоновщик — clang собирает
под них. Компилятор в этом наборе тоже есть, но курсу он не подойдёт: причина
в разделе «Компилятор один — clang» выше. Если Xcode установлен целиком,
отдельно ставить нечего.

### 2. Homebrew, а из него LLVM и остальное

Если Homebrew ещё нет — установщик со страницы [brew.sh](https://brew.sh/).
В конце он печатает две команды, которыми дописывает себя в PATH; их надо
выполнить, иначе `brew` не найдётся.

```
brew install llvm cmake ninja git
```

**Подвох: свой clang Homebrew в PATH не кладёт.** Это называется keg-only:
в системе уже есть компилятор с тем же именем, и подменять его молча Homebrew
не станет. Пресет `macos` вызывает компилятор по имени `clang++`, поэтому
каталог надо дописать в PATH самому — одной строкой в профиль оболочки:

```
echo "export PATH=\"$(brew --prefix llvm)/bin:\$PATH\"" >> ~/.zprofile
```

Строка устроена так, что `brew --prefix llvm` раскрывается сейчас, при записи,
и в файл попадает готовый путь: `/opt/homebrew/opt/llvm/bin` на Apple Silicon
или `/usr/local/opt/llvm/bin` на Intel. Терминал после этого открывается
заново — PATH подхватывают только новые процессы.

VS Code — с [code.visualstudio.com](https://code.visualstudio.com/),
перетаскиванием в «Программы».

### 3. Проверка

Новый терминал:

```
clang++ --version
cmake --version
ninja --version
```

Первая строка вывода `clang++` обязана начинаться с **`Homebrew clang
version`**, и версия — 19 или новее. `Apple clang version` означает, что PATH
не подхватился: шаг 2 сделан не до конца либо терминал остался прежним.

И отдельно то, ради чего нужен именно этот clang:

```
echo '#include <print>' | clang++ -std=c++23 -x c++ -fsyntax-only -
```

Молчание означает, что заголовок нашёлся, — то есть компилятор читает свою
libc++, а не системную.

**Про libc++ и почему её две.** Стандартная библиотека на macOS называется
libc++, и в системе она своя, от Apple, — заметно старее той, что приезжает
с `brew install llvm`. Заголовки clang из Homebrew берёт свои, а вот
компоноваться по умолчанию норовит с системной, и тогда сборка падает
на неразрешённых символах вроде `std::__1::__print::__vprint_unicode_posix`:
заголовок функцию объявил, а в старой библиотеке её нет. Комплект это
разруливает сам — `CMakeLists.txt` находит libc++ рядом с компилятором
и указывает её компоновщику, — так что делать ничего не нужно. Знать полезно,
если соберётесь собирать что-то своё мимо пресетов.

## macOS: Linux в контейнере

Готовых `libos.dylib` и `libedr.dylib` комплект пока не несёт: в `project/lib/`
лежат `win-x64` и `linux-x64`. Поэтому на Маке конфигурация проекта
заканчивается отказом CMake «Комплект не несёт границ под mac-arm64», и это
не ошибка установки, а отсутствующий файл: линковать нечего.

Пока каталога `lib/mac-arm64` нет, работа на Маке идёт в Linux-контейнере.
Комплект в нём тот же, пресеты те же — `linux`, `debug`, `asan`, `strict`, —
а границы берутся из `lib/linux-x64`. Файлы при этом правятся на Маке любым
редактором: каталог курса контейнеру монтируется, а не копируется в него.

Сам контейнер описан в курсе, каталогом `.devcontainer/`. Компилятор,
CMake, Ninja и gdb уже в образе, ставить внутри него ничего не нужно, и Homebrew
с LLVM из раздела «macOS» тоже не понадобятся: компилятор живёт в контейнере.

### 1. Docker Desktop

Установить [Docker Desktop](https://www.docker.com/products/docker-desktop/),
затем включить Settings → General → «Use Rosetta for x86/amd64 emulation
on Apple Silicon». Образ курса — x86-64, на Apple Silicon он идёт через
эмуляцию, и с Rosetta она в разы быстрее, чем стандартный qemu. На Intel Mac
включать нечего: там образ идёт как есть.

### 2. Открыть курс в контейнере

Понадобится расширение **Dev Containers**
(`ms-vscode-remote.remote-containers`). Дальше — открыть в VS Code корень
репозитория курса, тот, где лежат `lectures/`, `practice/` и `project/`,
и выполнить Ctrl+Shift+P → **Dev Containers: Reopen in Container**. Первая
сборка образа занимает несколько минут, дальнейшие открытия мгновенны.

**Подвох:** если каталог `.vscode` уже создан копией `vscode-macos`, его надо
удалить до этого. Задачи macos-набора вызывают пресеты `macos` и `debug-macos`,
а в контейнере их нет — система там Linux. Набор под Linux контейнер создаёт
сам, если каталога `.vscode` не существует.

Дальше всё как в разделе «Порядок работы в VS Code» для Linux: шаг 4, задача
«занятие», конфигурирует проект, Ctrl+Shift+B собирает, F5 запускает
под отладчиком.

### 3. То же из терминала, без VS Code

Из корня репозитория курса:

```
docker build -t nano-edr .devcontainer
docker run --rm -it -v "$PWD":/course -w /course nano-edr bash
```

Внутри — обычные команды курса из каталога `project/`:

```
cd project
cmake --preset linux -D NANO_EDR_LESSON=1.1
cmake --build --preset linux
ctest --preset linux
./build/linux/nano-edr scenarios/phishing_macro.log
```

### Что знать про эмуляцию

- Сборка идёт медленнее нативной. Заметно, но занятию это не мешает.
- Каталоги сборки у пресетов разные: `project/build/linux` в контейнере
  и `project/build/macos` от попытки собрать на Маке. Друг другу они
  не мешают, удалять ничего не нужно.
- Санитайзеры под эмуляцией курс не проверял. Если пресет `asan`
  собирается, а программа падает на старте сообщением про shadow memory, —
  это ограничение эмуляции, а не ваша ошибка: напишите преподавателю.

| `ms-vscode.cmake-tools` | конфигурация, сборка, тесты, пресеты | да | — | да |
| `ms-vscode.cpptools` | отладчик; на Windows разбор кода выключен, на Linux он его и ведёт | да | да | — |
| `vadimcn.vscode-lldb` | отладчик CodeLLDB — на macOS он вместо C/C++ | — | — | да |

Искать их по одному не нужно: нужные перечислены в заготовке настроек,
и VS Code предложит их сам — это шаг 2 порядка работы ниже.

**Наборы настроек устроены по-разному.** Windows-набор ведёт работу через
CMake Tools: пресеты, профиль, сборка и тесты выбираются командами палитры,
а разбор кода отдан clangd. macos-набор устроен так же и отличается одним —
отладчиком: там CodeLLDB. Linux-набор обходится без CMake Tools —
конфигурация, сборка и очистка сделаны задачами, а разбор кода ведёт C/C++
по `c_cpp_properties.json`. Отсюда развилки в шагах ниже.

**Обязательны только clang, CMake и Ninja.** На них собирается проект, и все
команды курса даны так, что выполняются из терминала; редактор поверх них
выбирается свободно, вплоть до другой IDE. Два из трёх заменяемы по одному:

- вместо **clangd** разбор кода может вести C/C++ от Microsoft или любой
  другой языковой сервер. Тогда в `settings.json` надо вернуть ему разбор:
  `"C_Cpp.intelliSenseEngine": "default"` — windows-набор выключает его как раз
  потому, что двух разборов сразу не бывает (правило ниже). Linux-набор
  так и устроен, там менять нечего; в macos-наборе C/C++ не стоит вовсе,
  и выключать нечего;
- вместо **CMake Tools** — те же пресеты из терминала, `cmake --preset`
  и `cmake --build --preset`: шаги 3–7 порядка работы сводятся к двум
  командам, они разобраны в [`project/README.md`](project/README.md).
  Linux-набор этим и пользуется, только командами не из терминала, а из задач.

Третье — **отладчик**, и он у каждой системы свой: на Windows и Linux
конфигурации в `launch.json` написаны под отладчик из C/C++, на macOS —
под CodeLLDB. Без своего расширения отладка тоже возможна: `lldb` или `gdb`
из терминала работают с тем же бинарём, — но F5 в VS Code перестанет
запускаться.

**Правило: два разбора кода одновременно не работают.** clangd и C/C++ читают
файл каждый сам и дают два набора подчёркиваний, нередко разных. Поэтому
в каждом наборе разбор ведёт кто-то один: в windows-наборе clangd, а у C/C++
разбор выключен настройкой; в linux-наборе наоборот — clangd не ставится
вовсе; в macos-наборе разбор у clangd, а C/C++ не ставится, поэтому
и выключать нечего. Расширение C/C++ нужно в windows- и linux-наборах:
отладчик берётся из него. В macos-наборе эту роль играет CodeLLDB.

## Порядок работы в VS Code

Шаги идут в том порядке, в каком их делают. Первые четыре — один раз
за занятие, остальные — сколько угодно раз за вечер.

**1. Забрать курс и открыть его.**

```
git clone <репозиторий курса>
cd cpp_course
cp -r vscode-windows .vscode   # Linux: vscode-linux, macOS: vscode-macos
code .
```

Третья строка создаёт рабочие настройки редактора: в репозитории они лежат
заготовками по системам — `vscode-windows/`, `vscode-linux/`
и `vscode-macos/`, — а рабочим каталогом становится копия своей. Команда
годится любой оболочке: в PowerShell `cp` — это `Copy-Item`, а `-r`
разворачивается в `-Recurse`.
Каталога `.vscode` до этого быть не должно: если пересоздаёте, сначала
удалите старый, иначе копия ляжет внутрь него.

Сама копия не версионируется, и это нарочно. Сценарий по умолчанию и прочие
мелочи правятся под себя, в репозиторий не уезжают и конфликтом при
обновлении курса не приходят. Обратная сторона — исправления в заготовках
сами не доедут: для них копию делают заново.

Открывается корень: в одном окне и лекции, и постановки занятий, и код.
Сам проект при этом лежит в `project/`, и `CMakeLists.txt` в корне открытой
папки нет — каждый набор объясняет это по-своему. В windows- и macos-наборах
путь к проекту задан в `settings.json` ключом `cmake.sourceDirectory`, оттуда
же берётся каталог для терминала: он открывается в `project/`, потому что
команды в постановках занятий даны от него. В linux-наборе путь прописан
в каждой задаче своим `cwd`, а терминал открывается в корне репозитория.

**2. Поставить расширения.** При первом открытии VS Code предложит сам —
список лежит в `.vscode/extensions.json`. Если предложение закрылось,
его вернёт палитра команд (Ctrl+Shift+P): «Extensions: Show Recommended
Extensions».

Списки разные: в windows- и macos-наборах по три расширения, в linux-наборе
одно — C/C++. Так и задумано, см. таблицу выше.

**3. Выбрать пресет — на Windows и macOS:** Ctrl+Shift+P → **CMake: Select
Configure Preset** → `windows`, на macOS `macos`. Расширение сразу
сконфигурирует проект.

*На Linux этого шага нет.* CMake Tools там не участвует, и пресет выбирается
прямо в задаче следующего шага.

В списке пресеты подписаны — сначала имя, потом что это:

```
windows — clang x64, профиль Release
asan-windows — clang, ASan и UBSan
strict-windows — предупреждения как ошибки
msvc — сверка компилятором MSVC
Add a New Preset...
```

На macOS список свой, и `msvc` в нём нет: `macos`, `debug-macos`,
`asan-macos`, `strict-macos`.

Нужен первый; остальные понадобятся перед сдачей (шаги те же, см. «Санитайзеры
и строгая сборка»), а `msvc` в обычной работе не нужен вовсе. «Add a New
Preset…» — предложение CMake Tools создать свой пресет, оно не нужно.

Пресетов чужой системы в этом списке нет: у каждого в файле стоит условие
по ОС, поэтому на Windows не видно линуксовых и маковых, и наоборот.
Отладочного пресета на Windows тоже нет — там профиль выбирается отдельно,
на шаге 5; на macOS он в списке есть, `debug-macos`, потому что профиль там
часть пресета.

Шаг обязательный, и пропуск виден не сразу: пока пресет не выбран, CMake
Tools о проекте не знает ничего. Сборка из терминала при этом может проходить,
а F5 отвечать «No executable target was found to launch»: о целях проекта
CMake Tools знает только из конфигурации, которую запустил сам, а не из ваших
команд в терминале.

**4. Задать номер занятия:** Ctrl+Shift+P → **Tasks: Run Task** → **занятие**
→ выбрать номер (1.1 … 4.3), затем пресет.

Список пресетов здесь свой у каждой системы: на Windows `windows`,
`asan-windows`, `strict-windows`; на Linux `linux`, `debug`, `asan`, `strict`;
на macOS `macos`, `debug-macos`, `asan-macos`, `strict-macos`.

*На Windows и macOS* задача выполняет две команды подряд. Первая — `cmake`
с этим номером, ровно та, что набирают в терминале. Вторая — конфигурация,
запущенная самим CMake Tools: это расширение ведёт свой список целей и тестов
проекта и пополняет его только тогда, когда конфигурацию запустило само;
на команду из терминала оно не смотрит. Без второй команды тесты занятия
не появились бы в панели Testing.

*На Linux* команда одна — тот же `cmake`. Второй там незачем: CMake Tools
не участвует, и тесты запускаются не из панели, а из терминала (шаг 8).

От номера зависит, какие заготовки попадут на include-путь и какие наборы
выданных тестов соберутся, — конфигурация печатает результат:

```
-- занятие: 1.1
-- комплект занятия: l1.1
-- выданные тесты: 1.1
```

Значение запоминается в кэше сборки, поэтому шаг нужен один раз за занятие.

**5. Выбрать профиль — только на Windows:** **CMake: Select Build Preset** →
`windows` для `Release` или `debug-windows` для `Debug`. Отдельного списка
«Debug / Release» в VS Code нет: при работе с пресетами CMake Tools свой выбор
профиля отключает, потому что профиль — часть пресета.

*На Linux и macOS этого шага нет.* Генератор там одноконфигурационный,
и профиль задаётся пресетом: для отладки на шаге 4 выбирается `debug`
или `debug-macos`, у него свой каталог сборки — и свой номер занятия,
то есть шаг 4 для него повторяется.

**6. Собрать.** *На Windows и macOS* — F7 («CMake: Build»). *На Linux* —
Ctrl+Shift+B, это задача «сборка проекта»: она спросит пресет и вызовет
`cmake --build --preset … --parallel`. Рядом с ней в linux-наборе лежат
«clean» и «clean-all» — первая чистит цели пресета, вторая сносит `build/`
целиком; в macos-наборе из них есть вторая.

Первой строкой сборка печатает, чем собирает:

```
[1/6] собираю: Clang 19.1.5, Ninja Multi-Config
```

Строка не для красоты: каталог сборки помнит генератор и компилятор с прошлой
конфигурации, и сборка на старом каталоге пойдёт прежним компилятором, ничего
не сказав.

Собирается всё. Когда нужно что-то одно, *на Windows и macOS* есть **CMake:
Build Target**: он спросит цель и соберёт только её. Целей в проекте
несколько: `nano-edr` — сам агент, `minimal_agent` — пример из `examples/`,
плюс программы выданных тестов. Команда **CMake: Set Build Target** закрепляет
выбранную цель за F7. *На Linux* то же даёт `--target` в терминале:
`cmake --build --preset linux --target nano-edr`.

**7. Запустить или отладить.** Агенту нужен аргумент — путь к сценарию, —
и запускать его надо из корня `project/`, потому что путь относительный. И то
и другое уже прописано в заготовке.

**F5 работает во всех трёх наборах:** под отладчиком, со **списком
сценариев** — перед запуском VS Code спросит, на каком прогонять, и подставит
выбранный в аргументы. Точки останова работают, значения переменных видны.
На Linux он спросит ещё и пресет, чтобы знать, какой каталог сборки брать;
на Windows и macOS каталог берётся из пресета, выбранного на шаге 3.

Отладчик при этом разный, и на месте это заметно только по мелочам вроде
вида окна переменных: на Windows и Linux он из расширения C/C++, на macOS
это CodeLLDB. Почему так — в разделе «VS Code: расширения» выше.

Разница, о которой стоит помнить, другая. *На Windows и macOS* перед запуском
выполняется сборка, так что отлаживается всегда свежий бинарь. *На Linux* —
нет: F5 запускает то, что уже собрано, поэтому шаг 6 перед ним обязателен.

*На Windows* есть ещё два способа, оба от CMake Tools:

- **Shift+F5** («CMake: Debug») — под отладчиком, но без вопросов: сценарий
  берётся из `settings.json`, а агент открывается в отдельном окне консоли.
  Удобно, когда одно и то же гоняется много раз подряд.
- **Ctrl+Shift+F5** («CMake: Run Without Debugging») — просто запуск, вывод
  в терминале. Сценарий берётся оттуда же. Так удобнее смотреть на печать
  детектов.

*На macOS* из этих двух работает второй, Ctrl+Shift+F5: запуск без отладчика,
вывод в терминале. Отладка через CMake Tools (Shift+F5) там не заведётся —
она обращается к расширению C/C++, которого в macos-наборе нет. Под отладчиком
запускает F5, и этого достаточно.

Сценарий этим запускам задан в `.vscode/settings.json`, ключом `args` в блоке
`cmake.debugConfig`:

```json
"args": ["scenarios/phishing_macro.log"],
```

Другой сценарий прописывается туда руками — списка выбора в настройках
не объявить. Правка остаётся насовсем: `.vscode/` ваша копия, обновление
курса её не трогает. Разовый прогон всё же удобнее пускать по F5,
а `settings.json` менять тогда, когда один и тот же сценарий гоняется неделю
подряд.

В списке сценариев рядом лежат `.log` и `.cfg` одного и того же мира. `.log` —
готовый журнал событий, его агент читает файлом; это то, что нужно на первых
занятиях. `.cfg` — описание мира для симулятора, оно понадобится, когда агент
переедет на `os.h`.

Отлаживать имеет смысл отладочную сборку: на Windows это профиль из шага 5,
на Linux — пресет `debug` из шага 4, на macOS — `debug-macos` оттуда же.
В `Release` отладчик тоже запустится, но по оптимизированному коду будет
прыгать через строки, а половина переменных окажется «optimized out».

**8. Прогнать тесты.** *На Windows и macOS* — панель **Testing** (значок
пробирки). Кнопка запуска прогоняет весь набор, у каждого теста видно, прошёл
он или упал, и вывод упавшего открывается по щелчку. *На Windows* на отладочном
профиле тест можно не только запустить, но и отладить — значок с жуком рядом
с ним; тогда точка останова в вашем коде сработает на его данных.

*На Linux* панели нет: её наполняет CMake Tools. Тесты прогоняются из
терминала, из каталога `project/`:

```
ctest --preset linux
```

В начале занятия тесты **падают**, и так и должно быть: они описывают то,
чего ещё не написано.

### Что уже настроено

Каталог `.vscode/` создаётся на шаге 1 копией `vscode-windows/`,
`vscode-linux/` или `vscode-macos/`. Править его не нужно — кроме сценария
по умолчанию, если гоняется не тот, что стоит там (шаг 7).

Состав у наборов разный, и это прямое следствие того, участвует CMake Tools
или нет.

**windows-набор:**

| | |
|---|---|
| `extensions.json` | три расширения для шага 2 |
| `settings.json` | где лежит проект (`project/`) и где открывается терминал; разбор кода отдан clangd, у C/C++ выключен; агенту задан рабочий каталог, сценарий по умолчанию и отдельное окно консоли |
| `tasks.json` | задачи «занятие» (шаг 4) и «сборка перед запуском» — та же сборка, что F7, её вызывает F5 |
| `launch.json` | конфигурация отладки для шага 7 и список сценариев, из которого F5 спрашивает аргумент |

**linux-набор:**

| | |
|---|---|
| `extensions.json` | одно расширение — C/C++ |
| `c_cpp_properties.json` | разбор кода: компилятор, стандарт и путь к `project/compile_commands.json` |
| `tasks.json` | задачи «занятие» (шаг 4), «сборка проекта» (шаг 6, она же Ctrl+Shift+B), «clean» и «clean-all» |
| `launch.json` | конфигурация отладки для шага 7; спрашивает сценарий и пресет |

`settings.json` в linux-наборе нет — задавать в нём нечего: путь к проекту
прописан в каждой задаче своим `cwd`, а разбор кода настроен отдельным файлом.

**macos-набор:**

| | |
|---|---|
| `extensions.json` | три расширения для шага 2 |
| `settings.json` | где лежит проект (`project/`) и где открывается терминал; агенту задан рабочий каталог и сценарий по умолчанию |
| `tasks.json` | задачи «занятие» (шаг 4), «сборка перед запуском» — та же сборка, что F7, её вызывает F5, — и «clean-all», сносящая `build/` целиком |
| `launch.json` | конфигурация отладки CodeLLDB для шага 7 и список сценариев, из которого F5 спрашивает аргумент |

Разбор кода в macos-наборе не настраивается ничем: его ведёт clangd,
а тот читает `compile_commands.json`, и `c_cpp_properties.json` ему не нужен —
это файл расширения C/C++, которого здесь нет.

Навигация заводится сама, но не раньше первой сборки: и clangd, и C/C++ читают
`compile_commands.json`, а его копию в корень `project/` кладёт сборка. То есть
переходы по определениям появляются после шага 6. Если clangd запустился
раньше — «clangd: Restart language server».

### Санитайзеры и строгая сборка

Приёмка занятий требует чистого прогона под санитайзерами (критерий К1)
и сборки без предупреждений. Это те же восемь шагов, только выбирается другой
пресет: на Windows и macOS — на шагах 3 и 4, на Linux — на шаге 4.

| | |
|---|---|
| `asan-windows`, `asan`, `asan-macos` | ASan и UBSan |
| `strict-windows`, `strict`, `strict-macos` | предупреждения как ошибки |

**Номер занятия им нужен свой.** Кэш свой у каждого каталога сборки,
а у этих пресетов каталоги отдельные — поэтому шаг 4 повторяется с их именем.
То же и для отладочных сборок на Linux и macOS: профиль там задаётся при
конфигурации, отладка идёт пресетом `debug` или `debug-macos`, и номер занятия
задаётся ему отдельно.

Санитайзеры ловят и то, что MSVC не поймал бы никогда: ASan даёт обращение
за границу буфера и использование освобождённой памяти с точным файлом
и строкой, UBSan — переполнение знакового, сдвиг на слишком много,
разыменование невыровненного указателя.

**Что внутри санитайзерного пресета.** На Linux и macOS внутри один ключ —
`NANO_EDR_SANITIZE` — и профиль `Debug`; всё остальное делает clang сам.
На Windows пресет задаёт статическую версию
CRT (`CMAKE_MSVC_RUNTIME_LIBRARY`) и собирает профиль `RelWithDebInfo`.
Рантайм санитайзеров в LLVM собран под статический CRT, и весь остальной код
обязан быть собран так же, иначе компоновка падает с `/failifmismatch:
mismatch detected for 'RuntimeLibrary'`, а у профиля `Debug` к этому добавилось
бы расхождение по `_ITERATOR_DEBUG_LEVEL`. Пресет задаёт CRT сразу всем
конфигурациям, поэтому расходиться нечему ни в одной из них.

Профиль при этом выбран не ради компоновки, а ради скорости: файл и строку
в отчётах даёт `-g`, который санитайзерная сборка включает при любом профиле,
а `-O0` под ASan только замедляет прогон. Набирать это руками не нужно —
в пресете уже записано; знать полезно, если будете делать свой вариант.

### То же из терминала

Всё, что делают шаги 4–8, — три команды. Номер занятия дописывается ключом
и запоминается в кэше, дальше он не набирается:

```
cmake --preset windows -D NANO_EDR_LESSON=1.1
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`, на macOS — `macos`. Для отладочной
сборки — `debug-windows` на Windows, пресет `debug` на Linux, `debug-macos`
на macOS; для санитайзеров и строгой сборки — `asan-windows` / `asan` /
`asan-macos` и `strict-windows` / `strict` / `strict-macos`.

## Готово, когда

Две команды в каталоге `project/` проходят без ошибок. На Windows и macOS
терминал VS Code там и открывается; на Linux он открывается в корне
репозитория, и до `project/` надо дойти самому:

```
cmake --preset windows -D NANO_EDR_LESSON=1.1
cmake --build --preset windows
```

и агент запускается на сценарии:

```
./build/windows/Release/nano-edr scenarios/phishing_macro.log
```

На Linux — `--preset linux` и `./build/linux/nano-edr`, на macOS —
`--preset macos` и `./build/macos/nano-edr`, а в Linux-контейнере — те же,
что на Linux; это те же команды и пути,
что в постановках занятий. Запускать из корня `project/`: пути к сценариям
относительные.

Тесты занятия при этом **падают** — окружение настроено тогда, когда они
запускаются и честно показывают, чего не хватает, а не когда они зелёные.

## Если не работает

| Что видно | В чём дело |
|---|---|
| `clang++ : The term 'clang++' is not recognized` | каталог clang не в PATH (шаг 1 раздела «Windows») либо терминал открыт до правки PATH |
| `No CMAKE_CXX_COMPILER could be found` | пресеты всех трёх систем вызывают компилятор одним именем — `clang++`, — и по этому имени его не нашлось. На Windows и macOS каталог компилятора не в PATH: шаг 1 раздела «Windows», шаг 2 раздела «macOS». На Linux имени без номера версии может не быть вовсе — см. подвох в разделе «Linux» |
| `CMAKE_MAKE_PROGRAM is not set` или CMake не находит генератор | Ninja не установлен либо его каталог не в PATH; на Linux — `apt install ninja-build`, на macOS — `brew install ninja` |
| `no member named 'print' in namespace 'std'` | стандартная библиотека старая: на Linux нужна libstdc++ 14 или новее, её приносит пакет `g++`, на Windows — Build Tools новее 17.10, на macOS собирается компилятором Apple вместо Homebrew (см. следующую строку) |
| `generator : Ninja Multi-Config Does not match the generator used previously: Visual Studio 17 2022` | каталог сборки остался от старой версии комплекта, где `windows` собирался MSVC: удалить `build/` и сконфигурировать заново |
| В выводе сборки `MSBuild version …` и строка `собираю: MSVC …` | то же самое, но замечается не при конфигурации, а при сборке: `cmake --build` берёт генератор и компилятор из каталога сборки, а не из пресета. Удалить `build/`, сконфигурировать заново |
| `/failifmismatch: mismatch detected for 'RuntimeLibrary'` или `_ITERATOR_DEBUG_LEVEL` | санитайзеры собираются своим пресетом мимо `asan-windows`, без статического CRT: рантайм ASan в LLVM собран под него, см. раздел «Санитайзеры и строгая сборка» |
| `No executable target was found to launch` при F5 (Windows) | CMake Tools не сконфигурировал проект: не выбран пресет — это шаг 3 («CMake: Select Configure Preset»). Сборка из терминала здесь не помогает: о целях проекта CMake Tools знает только из своей конфигурации |
| F5 не находит программу (Linux) | бинаря нет: linux-набор перед запуском не собирает, шаг 6 обязателен. На Windows и macOS такого не бывает — там F5 сначала собирает. Проверьте и пресет — путь в `launch.json` собирается из него, `build/<пресет>/nano-edr` |
| Под Linux запуск не стартует, ошибка про терминал | отдельное окно консоли `cppdbg` открывает системным терминалом, и там, где его нет (WSL без графики, сервер по SSH), запуск срывается. В linux-наборе `"externalConsole"` уже `false`; если правили — верните, вывод пойдёт в панель Debug Console |
| Не найти, где переключить Debug и Release | с пресетами этого списка нет. На Windows профиль задаёт build-пресет, шаг 5 — «CMake: Select Build Preset»; на Linux и macOS — сам пресет конфигурации, `debug` вместо `linux` и `debug-macos` вместо `macos` |
| Разбор кода жалуется на ненайденные заголовки, переходы не работают | проект ещё не собран: копия `compile_commands.json` появляется в корне `project/` при сборке. Собрать, затем «clangd: Restart language server» либо «C/C++: Reset IntelliSense Database» |
| Два набора подчёркиваний, иногда противоречащих друг другу | стоят и clangd, и C/C++, и оба разбирают файл. В windows-наборе разбор C/C++ выключает `settings.json` — значит `.vscode/` не создан (шаг 1) или открыт не корень репозитория. В linux-наборе лишний clangd, в macos-наборе — C/C++; лишнее расширение надо отключить |
| В палитре нет пресетов, «No configure presets» (Windows) | без `.vscode/settings.json` CMake Tools ищет проект в корне открытой папки, а `CMakePresets.json` лежит в `project/`. Создать `.vscode/` копией заготовки и открыть корень репозитория; что видит сам CMake, печатает `cmake --list-presets` из `project/` |
| `Не найдена библиотека: .../os.dll`, `.../libos.so`, `.../libos.dylib` | комплект не несёт границ под вашу платформу: собранные `os` и `edr` лежат в `lib/win-x64`, `lib/linux-x64`, `lib/mac-arm64` и `lib/mac-x64`. Обновите клон через `git pull`; если нужного каталога нет и после этого — напишите преподавателю, сборка под платформу это один прогон скрипта. На Маке до этого работают в Linux-контейнере — раздел «macOS: Linux в контейнере» |
| Тесты не появились ни в панели, ни в `ctest` | не задан номер занятия (шаг 4, задача «занятие») — без него тестов нет вовсе. Если задан, а панель на Windows или macOS пуста, CMake Tools нужна своя конфигурация: «CMake: Configure». На Linux панели нет вовсе, тесты гоняются `ctest --preset` |
| `clang … слишком старый` при конфигурации (Linux) | по имени `clang++` нашлась версия старее 19-й: в Ubuntu 24.04 пакет `clang` без номера это 18-й. Поставить clang номером и создать имя без номера — подвох в разделе «Linux» |
| `clang … слишком старый` при конфигурации, в выводе `Apple clang version` (macOS) | собирается компилятором Apple, а он для C++23 не годится. Нужен clang из Homebrew и его каталог в PATH — шаг 2 раздела «macOS». Проверка: `clang++ --version` в новом терминале должен начинаться с `Homebrew clang version` |
| `Undefined symbols: std::__1::__print::__vprint_unicode_posix` (macOS) | сборка идёт с заголовками libc++ от Homebrew, а компонуется с системной. Пресеты комплекта это учитывают, поэтому причина одна из двух: собираете своим пресетом мимо комплекта либо каталог сборки остался от прежней конфигурации — удалите `build/` и сконфигурируйте заново |
| `brew: command not found` | установщик Homebrew печатает в конце две команды, дописывающие его в PATH, и их надо выполнить; затем открыть терминал заново |
| На macOS VS Code не находит `clang++`, хотя в терминале он есть | VS Code, запущенный из Dock, профиль оболочки не читает и PATH из `~/.zprofile` не видит. Открывать через `code .` из терминала — так делает шаг 1 |
| Вместо русского текста в выводе кракозябры | старый `cmd.exe` работает в кодировке 866: `chcp 65001` либо терминал VS Code и Windows Terminal, где UTF-8 по умолчанию |
