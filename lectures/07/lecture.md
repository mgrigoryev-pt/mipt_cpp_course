# Лекция 7. Полиморфизм и виртуальные функции

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему».

## 0. О чём эта лекция

Это вторая лекция про наследование, и она про то, ради чего наследование чаще всего и делается — **полиморфизм**. На прошлой лекции мы научились писать «класс `Dog` наследуется от `Animal`», понимаем layout, multiple inheritance и ромбовидную проблему. Но пока в нашей иерархии нет способа сказать «дайте мне любое животное, я попрошу его издать звук, и каждое издаст свой» — всё ещё статически связано.

Сегодня мы:

- Разберём касты в иерархии — upcast и downcast.
- Введём виртуальные функции — главный механизм полиморфизма в C++.
- Обсудим абстрактные классы как способ описать интерфейс.
- Разберём важную ошибку — забытый виртуальный деструктор.
- Посмотрим на `dynamic_cast`, а устройство vtable соберём руками на обычном C++.
- В конце — `enum class` как современная замена `enum`.

После этой лекции у вас будут все инструменты, чтобы писать «классические» OOP-программы на C++. Иерархия — на прошлой лекции; динамика поведения — здесь.

## 1. Касты при наследовании

В прошлой лекции мы видели **upcast** — приведение указателя/ссылки к базовому типу:

```cpp
class Animal { /* ... */ };
class Dog : public Animal { /* ... */ };

Dog d;
Animal* pa = &d;     // upcast, неявный
Animal& ra = d;      // upcast, неявный
```

Это работает, потому что `Dog` **является** `Animal` (subtyping). Адреса совпадают — `Animal` лежит в начале объекта `Dog`. Это **безопасный** каст, компилятор разрешает его автоматически при `public` наследовании.

### Downcast — обратно вниз

Обратное приведение — от базы к наследнику — компилятор **не** делает автоматически:

```cpp
Animal* pa = get_some_animal();
Dog* pd = pa;                          // CE: implicit cast Animal* → Dog* запрещён
Dog* pd = static_cast<Dog*>(pa);       // компилируется, но опасно
```

Компилятор не может на этапе компиляции проверить, **действительно ли** `pa` указывает на `Dog`. Если на самом деле там `Cat`, `static_cast` молча даст битый указатель. Любая операция через `pd` — UB.

`static_cast` для downcast уместен только если вы **уверены**, что объект действительно того типа. Иначе нужен `dynamic_cast` — он проверяет в рантайме (см. далее).

В хорошо спроектированном коде downcast встречается **редко**. Обычно вместо «проверим, что это `Dog`, и вызовем `bark`» лучше иметь виртуальную функцию `sound()`, которая для `Dog` возвращает `"woof"`.

## 2. Виртуальные функции

Теперь к главному — полиморфизму.

Без `virtual`:

```cpp
class Animal {
public:
    void sound() { std::print("???\n"); }
};

class Dog : public Animal {
public:
    void sound() { std::print("woof\n"); }
};

Animal* a = new Dog();
a->sound();      // "???", не "woof"
```

Это и есть **статическое связывание**. Компилятор выбирает функцию **на этапе компиляции** по типу указателя — `Animal*` — а не по реальному объекту. Это иногда удобно для оптимизации, но не то, что обычно нужно для полиморфизма.

### С `virtual` — динамическое связывание

```cpp
class Animal {
public:
    virtual void sound() { std::print("???\n"); }
};

class Dog : public Animal {
public:
    void sound() override { std::print("woof\n"); }
};

Animal* a = new Dog();
a->sound();      // теперь "woof"
```

`virtual` включает **динамическое связывание**: выбор функции происходит в рантайме, по **реальному типу** объекта. Это и есть полиморфизм.

Виртуальные функции работают через **vtable** — таблицу указателей на функции. Каждый объект полиморфного класса несёт скрытый указатель на эту таблицу. В разделе 7 мы соберём такую таблицу руками, без единого `virtual`.

## 3. `override` и `final`

### `override`

`override` — ключевое слово (точнее, contextual identifier, появилось в C++11), которое говорит компилятору: «я уверен, что это переопределение виртуальной функции из базы». Если переопределения нет — CE:

```cpp
class Animal {
public:
    virtual void sound();
};

class Dog : public Animal {
public:
    void sound() override { /* ... */ }     // ok, переопределение
    void sound(int) override { /* ... */ }  // CE: в Animal нет sound(int)
    void Sound() override { /* ... */ }     // CE: опечатка
};
```

`override` не меняет семантику программы — без него `void sound()` в наследнике тоже переопределяла бы виртуальную. Но **без `override`** опечатка вроде `Sound` или несовпадение типа аргумента молча создаёт новую функцию вместо переопределения — баг, который сложно отловить.

**Привычка профессионального C++:** всегда писать `override` на переопределённых функциях. Бесплатная защита от опечаток.

### `final`

`final` запрещает дальнейшее переопределение функции или наследование от класса:

```cpp
class Dog : public Animal {
public:
    void sound() final { /* ... */ }      // никакой Puppy не переопределит sound
};

class Husky final : public Dog {};        // от Husky нельзя наследоваться
```

Применяется редко — в основном чтобы зафиксировать архитектуру и иногда дать компилятору возможность **devirtualize** вызов (если он знает, что переопределений больше нет — может вызвать напрямую без vtable). В обычном прикладном коде встречается не часто.

## 4. Абстрактные классы

**Чисто виртуальная функция** — это виртуальная функция без реализации в базе:

```cpp
class Shape {
public:
    virtual double area() const = 0;     // = 0 делает функцию чисто виртуальной
    virtual ~Shape() = default;
};
```

Синтаксис `= 0` после объявления — «реализации нет, переопределяй». Класс **с хотя бы одной чисто виртуальной функцией** называется **абстрактным**.

Абстрактный класс **нельзя создать** напрямую:

```cpp
Shape s;                       // CE: cannot instantiate abstract class
Shape* p = new Shape();        // CE
```

Зато можно создать **наследников**, которые переопределили все чисто виртуальные методы:

```cpp
class Circle : public Shape {
    double r_;
public:
    Circle(double r) : r_(r) {}
    double area() const override { return 3.14 * r_ * r_; }
};

Shape* p = new Circle(5);      // ok
std::print("{}\n", p->area()); // 78.5
```

Абстрактные классы используются как **интерфейсы** — описание контракта без реализации. Это аналог `interface` в Java или `abstract class` в Python с `ABC`. Принимая `Shape*` или `Shape&`, функция говорит: «дайте мне что-то, что умеет `area()`».

### Где это нужно на практике

Фигуры удобны для объяснения механизма, но плохо отвечают на вопрос «зачем». Разберём пример, который ближе к настоящему коду.

Система обнаружения атак устроена так: есть поток **событий** с машины (запустился процесс, открылся файл, установилось соединение) и есть набор **правил детектирования**, каждое из которых умеет сказать про событие «это подозрительно». Устроены правила по-разному: одно сверяет имя процесса со списком, второе смотрит на цепочку родительских процессов, третье считает частоту событий за окно времени, четвёртое дёргает внешнюю репутационную базу. Общего кода у них почти нет.

Зато у них есть общий **контракт**:

```cpp
class Rule {
public:
    virtual bool Matches(const Event& e) const = 0;
    virtual std::string_view Name() const = 0;
    virtual ~Rule() = default;
};
```

И теперь весь движок проверки — это несколько строк:

```cpp
std::vector<std::unique_ptr<Rule>> rules;

void Check(const Event& e) {
    for (const auto& rule : rules) {
        if (rule->Matches(e)) Alert(rule->Name());
    }
}
```

Обратите внимание на два свойства этого кода, которых нельзя добиться без виртуальных функций.

Во-первых, `std::vector<std::unique_ptr<Rule>>` хранит объекты **разных типов** в одном контейнере. Вектор гомогенен — в нём лежат указатели одного типа `Rule*`, а вот то, на что они указывают, у каждого элемента своё. Без наследования и виртуальности пришлось бы держать отдельный контейнер на каждый вид правила и отдельно их обходить.

Во-вторых, `Check` не упоминает ни одного конкретного правила. Добавление нового вида детекта — это новый класс-наследник плюс одна строка регистрации; функция `Check` не меняется. Именно этого мы и добиваемся, когда говорим «программируем против интерфейса»: точки расширения находятся там, где добавляется код, а не там, где он правится.

Если вам показалось, что то же самое можно сделать шаблонами — верно, часто можно, и на лекциях 8–9 мы увидим, как. Разница в моменте выбора: шаблон требует знать набор правил на этапе компиляции, виртуальные функции позволяют собрать его **во время выполнения** — например, прочитав список включённых правил из конфигурации. Когда состав известен только в рантайме, альтернатив виртуальности практически нет.

### Чисто виртуальные с реализацией

Допустимо (и иногда полезно) дать чисто виртуальной функции **тело**:

```cpp
class Shape {
public:
    virtual double area() const = 0;
};

double Shape::area() const { return 0; }   // ok, Shape всё равно абстрактный
```

Класс по-прежнему абстрактный. Наследники могут вызвать `Shape::area()` явно, через квалифицированное имя. Применение редкое — например, чтобы дать наследникам «default implementation», но всё равно потребовать явно её активировать.

## 5. Виртуальный деструктор

Это, пожалуй, самая важная практическая ошибка, которую нужно избежать в иерархии классов.

### Опасная ситуация

```cpp
class Animal {
public:
    ~Animal() { /* НЕ virtual */ }
};

class Dog : public Animal {
    std::unique_ptr<Buffer> buf_;
public:
    ~Dog() { /* должен освободить buf_, но... */ }
};

Animal* a = new Dog();
delete a;        // вызовется только ~Animal(), не ~Dog()!
```

При `delete a` компилятор смотрит на тип указателя (`Animal*`). Деструктор `Animal` — не виртуальный, поэтому вызов **статический**: запускается `~Animal()` и ничего больше. Деструктор `Dog` **не вызывается**. Поле `buf_` не освобождается. Утечка ресурсов. Технически — UB (стандарт говорит, что `delete` через указатель базы на наследника без виртуального деструктора — UB).

### Решение

```cpp
class Animal {
public:
    virtual ~Animal() = default;
};

class Dog : public Animal {
public:
    ~Dog() override { /* ... */ }
};

Animal* a = new Dog();
delete a;        // теперь вызовутся ~Dog() и затем ~Animal()
```

Виртуальный деструктор сам становится частью vtable, и `delete` через базовый указатель ищет реальный деструктор через таблицу.

### Жёсткое правило

**Если в классе есть хотя бы одна виртуальная функция — деструктор должен быть виртуальным.** Без исключений.

Часто пишут просто `virtual ~Base() = default;` — без полей и аллокаций деструктор тривиален, нужно просто пометить его виртуальным.

Если класс **не предназначен** для наследования и полиморфизма — деструктор может оставаться невиртуальным (это нормальный случай для большинства классов, которые «просто хранят данные»).

## 6. `dynamic_cast`

`dynamic_cast` — единственный **безопасный** способ downcast. Он использует RTTI (Run-Time Type Information) для проверки реального типа объекта:

```cpp
Animal* a = get_some_animal();

Dog* d = dynamic_cast<Dog*>(a);
if (d) {
    d->bark();                       // ok, это действительно Dog или наследник
} else {
    /* a указывает не на Dog */
}
```

Если `a` реально указывает на `Dog` (или класс-наследник `Dog`) — `dynamic_cast` возвращает указатель. Иначе — `nullptr`. Обязательная проверка результата на null.

### Со ссылкой

Для **ссылок** `dynamic_cast` не может вернуть `nullptr` (ссылки не бывают пустыми), поэтому он **бросает** `std::bad_cast`:

```cpp
try {
    Dog& d = dynamic_cast<Dog&>(*a);
    d.bark();
} catch (const std::bad_cast&) {
    /* a — не Dog */
}
```

### Требования

`dynamic_cast` работает только для **полиморфных** классов — у которых есть хотя бы одна виртуальная функция (включая виртуальный деструктор). Без virtual-функции RTTI не генерируется, и `dynamic_cast` будет CE.

### Когда использовать

В **хорошо спроектированном** OOP-коде `dynamic_cast` встречается **редко**. Обычно правильнее иметь виртуальную функцию, которая делает нужное для каждого типа, и не приводить тип вообще.

`dynamic_cast` уместен, когда:

- Нужно реализовать **visitor** или RTTI-механизм
- Интероперабельность с библиотекой, которая возвращает базовый тип
- Гетерогенная коллекция с гетерогенной обработкой (вынужденно)

Если в вашем коде много `dynamic_cast` — это сигнал, что **дизайн стоит пересмотреть**. Скорее всего, можно заменить серию downcast на одну виртуальную функцию.

## 7. Таблица вызовов руками

`virtual` — не магия компилятора и не отдельная подсистема рантайма. Механизм, который за ним стоит, целиком выражается на обычном C++: структура с указателями на функции плюс указатель на такую структуру в самом объекте. Соберём его руками — после этого поведение виртуальных функций перестаёт быть чем-то, что надо запоминать.

Указатели на функции разбирались на лекции 3, здесь они основной инструмент.

### Шаг 1. Таблица методов

Опишем «поведение» из двух операций — `sound` и `human_age`. Таблица методов — это обычная структура, все поля которой являются указателями на реализации:

```cpp
struct Animal;                      // нужен для сигнатур в таблице

struct AnimalOps {                  // таблица методов
    const char* (*sound)(const Animal* self);
    int (*human_age)(const Animal* self);
};

struct Animal {
    const AnimalOps* ops;           // первое поле — указатель на таблицу
    const char* name;
    int age_years;
};
```

Первым полем объекта лежит указатель на таблицу, дальше — обычные данные. Порядок здесь не случаен: он позволяет добраться до таблицы, зная только адрес объекта.

### Шаг 2. Две реализации

```cpp
const char* dog_sound(const Animal*) { return "woof"; }
int dog_human_age(const Animal* self) { return self->age_years * 7; }
constexpr AnimalOps kDogOps{dog_sound, dog_human_age};

const char* bird_sound(const Animal*) { return "tweet"; }
int bird_human_age(const Animal* self) { return self->age_years * 5; }
constexpr AnimalOps kBirdOps{bird_sound, bird_human_age};
```

`kDogOps` и `kBirdOps` — по одной таблице на «вид», а не на объект. Сколько бы собак вы ни создали, таблица `kDogOps` останется одна.

Параметр `self` — это `this`, написанный руками: через него реализация добирается до полей объекта (`dog_human_age` им пользуется). Там, где данные объекта не нужны, имя параметра можно опустить — как в `dog_sound`.

### Шаг 3. Вызов через таблицу

```cpp
void describe(const Animal* a) {
    std::print("{}: {}, по-человечески {}\n",
               a->name, a->ops->sound(a), a->ops->human_age(a));
}

int main() {
    Animal dog{&kDogOps, "Sharik", 3};
    Animal bird{&kBirdOps, "Kesha", 3};
    describe(&dog);      // Sharik: woof, по-человечески 21
    describe(&bird);     // Kesha: tweet, по-человечески 15
}
```

`describe` не знает, собака перед ней или птица, и не содержит ни одной проверки типа. Она делает три шага: берёт из объекта указатель на таблицу, из таблицы — указатель на функцию, вызывает его и передаёт сам объект. Это уже полноценная динамическая диспетчеризация, и слова `virtual` в коде нет.

### То же самое на `virtual`

```cpp
class Animal {
public:
    Animal(const char* name, int age_years) : name_(name), age_years_(age_years) {}
    virtual ~Animal() = default;
    virtual const char* sound() const = 0;
    virtual int human_age() const = 0;
    const char* name() const { return name_; }
protected:
    const char* name_;
    int age_years_;
};

class Dog : public Animal {
public:
    Dog(const char* name, int age) : Animal(name, age) {}
    const char* sound() const override { return "woof"; }
    int human_age() const override { return age_years_ * 7; }
};

class Bird : public Animal {
public:
    Bird(const char* name, int age) : Animal(name, age) {}
    const char* sound() const override { return "tweet"; }
    int human_age() const override { return age_years_ * 5; }
};

void describe(const Animal& a) {
    std::print("{}: {}, по-человечески {}\n", a.name(), a.sound(), a.human_age());
}
```

Вывод у обеих программ одинаковый. Разница только в том, кто пишет таблицы и обращения к ним.

**Правило:** `virtual` — это ровно та конструкция, которую мы собрали руками, только таблицы генерирует компилятор, а `self` он подставляет сам как `this`.

### vtable и vptr

Терминология: таблицу, которую компилятор создаёт для каждого полиморфного класса, называют **vtable**; скрытое поле-указатель на неё внутри объекта — **vptr**. В ручной версии это `AnimalOps` и `Animal::ops`.

```
объект Dog:         vtable Dog:
[ vptr       ] ─► [ &Dog::~Dog, &Dog::sound, &Dog::human_age ]
[ name_      ]
[ age_years_ ]
```

Вызов `a.sound()` компилируется примерно в `(*a.vptr)[slot_of_sound](&a)` — загрузка vptr из объекта, загрузка адреса функции из таблицы, косвенный вызов. Те же три шага. Это и называется **dispatch**.

Отличия настоящей vtable от нашей непринципиальны: компилятор сам нумерует слоты, заполняет `vptr` в конструкторе базового класса и хранит рядом с таблицей служебные данные для RTTI и `dynamic_cast`.

### Сколько это стоит: `sizeof`

```cpp
struct Plain {
    int age_years;
    void sound() const {}
};

struct Polymorphic {
    int age_years;
    virtual void sound() const {}
    virtual ~Polymorphic() = default;
};

std::print("{} {}\n", sizeof(Plain), sizeof(Polymorphic));   // 4 16
```

`Plain` — четыре байта, ровно одно поле: обычные методы места в объекте не занимают. `Polymorphic` — шестнадцать: восемь байт `vptr`, четыре байта поля и четыре байта padding до выравнивания в 8 (правила выравнивания — с лекции 6).

Ключевое здесь — **таблица одна на класс, а в объекте только указатель на неё**. Добавьте в `Polymorphic` ещё девять виртуальных функций: вырастет таблица, а `sizeof` останется 16. Миллион полиморфных объектов — это миллион одинаковых указателей и одна таблица на всех.

### Цена вызова

- **Память:** +8 байт на объект на 64-битной системе. Для класса с парой `int` это утроение размера, для класса на сотню байт — незаметно.
- **Время:** одна дополнительная косвенность. Адрес функции сначала читается из таблицы. Предсказатель переходов на современных CPU почти всегда угадывает цель, так что сам вызов дёшев.
- **Inlining:** главная потеря. Адрес функции известен только в рантайме, значит вызов нельзя заинлайнить, а вместе с инлайнингом отваливаются оптимизации, которые он открывает, — свёртка констант, устранение проверок, векторизация цикла.

**Подвох:** «виртуальный вызов медленный» — утверждение не про сам вызов, а про барьер для оптимизаций вокруг него. В горячем цикле дорого обходится именно это.

Даже с учётом барьера это **намного дешевле**, чем в Java или Python, где виртуально почти всё. В C++ виртуальность только там, где явно написано `virtual`.

### Devirtualization

Если компилятор может доказать реальный тип объекта, он заменяет вызов через таблицу прямым — это **devirtualization**:

```cpp
Dog d{"Sharik", 3};
d.sound();          // тип известен точно → прямой вызов, можно заинлайнить
```

Помогает `final` (раздел 3) и создание объекта рядом с местом вызова. Но как только объект приходит по `Animal&` из другой единицы трансляции, доказывать нечего, и вызов остаётся косвенным. Полагаться на devirtualization в дизайне не стоит: это оптимизация, а не гарантия.

## 8. `enum` и `enum class`

В заключение лекции — небольшая, но важная тема.

### Классический `enum` (наследие C)

```cpp
enum Color { Red, Green, Blue };

Color c = Red;
int x = Red;          // ok: неявно конвертится в int
```

Три проблемы:

1. **Имена попадают в окружающий scope.** `Red`, `Green`, `Blue` теперь — глобальные имена. Если в другом `enum` тоже есть `Red` — конфликт имён.
2. **Неявная конверсия в `int`.** `Color` смешивается с числами, потеря типобезопасности.
3. **Размер не контролируется.** Компилятор выбирает размер сам, между `int` и достаточным, чтобы вместить все значения.

### `enum class` (C++11)

```cpp
enum class Color { Red, Green, Blue };

Color c = Color::Red;
int x = Color::Red;            // CE: no implicit conversion
int y = static_cast<int>(Color::Red);    // ok, явно
```

Преимущества:

- **Scoped.** Обращение `Color::Red` — имена не загрязняют окружающий scope.
- **Strong typed.** Не конвертится неявно в `int`. Нельзя случайно подставить `Color` туда, где ждут `int`.
- **Underlying type контролируется:** `enum class Color : uint8_t { ... }` — задаём, какой именно тип под капотом.

**Правило в новом коде:** используйте `enum class`, не `enum`. Старый `enum` оставляйте только если интероперабельность с C-API требует. Преимуществ у обычного `enum` перед `enum class` практически нет.

## Итоги

- **Касты в иерархии:** upcast (`Derived*` → `Base*`) неявный, downcast только через `dynamic_cast` для полиморфных классов.
- **Виртуальные функции** дают полиморфизм во время выполнения. Всегда пишите `override`. `final` запрещает дальнейшее переопределение.
- **Чисто виртуальные** (`= 0`) делают класс **абстрактным** — нельзя создать напрямую.
- **Виртуальный деструктор обязателен**, если в классе есть любая виртуальная функция. Без исключений.
- **`dynamic_cast`** — безопасный downcast. Признак, что дизайн стоит пересмотреть, если их много.
- **vtable + vptr** — механизм, который собирается руками на обычном C++: структура с указателями на функции плюс указатель на неё первым полем объекта. `virtual` делает ровно это.
- **Таблица одна на класс**, в объекте только указатель на неё: `sizeof` растёт на 8 байт независимо от числа виртуальных функций.
- **Цена вызова** — одна дополнительная косвенность и невозможность заинлайнить; второе обычно дороже первого. Devirtualization случается, но не гарантирована.
- **`enum class`** — единственная форма enum, которую стоит писать в новом коде.
