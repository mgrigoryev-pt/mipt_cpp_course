# Лекция 15. Умные указатели и основы многопоточности

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему». Это последняя лекция курса.

## 0. О чём эта лекция

На лекции 2 мы познакомились с RAII — как с лекарством от ручных `new`/`delete`. Формулировка была такая:

> Ресурс владеется объектом. Деструктор освобождает его автоматически — при любом выходе из области видимости, включая выход по исключению.

Тогда речь шла исключительно про **память**: `unique_ptr` вместо `new`/`delete`, и на этом всё. Но обратите внимание, как сформулирован принцип — в нём нет слова «память». Там сказано «ресурс».

Сегодня мы проверим, насколько далеко эта идея заходит. И обнаружим, что она **универсальна**: работает для памяти, для мьютексов, для потоков, для файлов — для всего, что нужно захватить и потом обязательно отпустить.

На лекции 2 `unique_ptr` и `shared_ptr` были готовыми инструментами. Теперь, когда есть move-семантика, шаблоны и type erasure (намёком из лекции 10), можно посмотреть, как они устроены внутри. Вторая половина лекции — базовая многопоточность: стандартная библиотека даёт всё, что нужно для корректного concurrent-кода.

Темы:

- Устройство `unique_ptr`: RAII над указателем, move-only, custom deleter.
- `shared_ptr`: control block, счётчик ссылок, стоимость.
- `make_shared` / `make_unique` и их ограничения.
- `weak_ptr`, циклические ссылки, `enable_shared_from_this`.
- Запуск потоков: `std::thread`, `std::jthread`, `stop_token`.
- Синхронизация: `std::mutex`, RAII-обёртки блокировок, deadlock, `scoped_lock`.
- Ожидание событий: `std::condition_variable`.
- Асинхронность: `std::future`, `std::promise`, `std::async`.
- `thread_local`.

К концу лекции вы должны:

- Понимать устройство `unique_ptr` и `shared_ptr` (control block, счётчик ссылок). Всё, чтобы разобрать их устройство, уже есть: move-семантика (лекция 11), шаблоны (лекции 8–9), [перегрузка](../glossary.md#overload) (overloading) операторов (лекция 5).
- Знать, когда `weak_ptr` нужен и как им пользоваться.
- Уметь запустить поток, защитить общее состояние, дождаться события.
- Видеть за умными указателями, блокировками и `jthread` одну общую идею, а не две несвязанные темы.
- Понимать, что осталось за рамками курса: атомарные операции, модель памяти, lock-free.

## 1. `unique_ptr` — устройство

На лекции 2 мы пользовались `std::unique_ptr` как «коробочкой», которая сама вызывает `delete`. Теперь посмотрим, как она устроена:

```cpp
template <typename T>
class UniquePtr {
    T* ptr_ = nullptr;
public:
    explicit UniquePtr(T* p) : ptr_(p) {}
    ~UniquePtr() { delete ptr_; }

    T& operator*()  const { return *ptr_; }
    T* operator->() const { return ptr_; }
    T* get()        const { return ptr_; }
};
```

Это [RAII](../glossary.md#raii) (resource acquisition is initialization) над одним указателем. Конструктор берёт [сырой указатель](../glossary.md#raw-pointer) (raw pointer), деструктор вызывает `delete`. Между ними — методы доступа `*`, `->`, `get()`. Никакой магии — это **обычный шаблонный класс** в духе того, что мы писали на лекциях 5 и 8.

### Move-only

Главное свойство `unique_ptr` — **только один [владелец](../glossary.md#ownership)** (ownership). Копирование запрещено:

```cpp
UniquePtr(const UniquePtr&) = delete;
UniquePtr& operator=(const UniquePtr&) = delete;
```

Если разрешить копирование — два объекта получат один и тот же указатель, при разрушении дважды вызовут `delete` — [double free](../glossary.md#double-free) (повторное освобождение памяти), [UB](../glossary.md#ub) (undefined behavior).

Но **перемещать можно** — мы знаем [move-семантику](../glossary.md#move-semantics) (move semantics) с лекции 11:

```cpp
UniquePtr(UniquePtr&& other) noexcept : ptr_(other.ptr_) {
    other.ptr_ = nullptr;        // зануляем источник
}

UniquePtr& operator=(UniquePtr&& other) noexcept {
    if (this != &other) {
        delete ptr_;              // освобождаем своё
        ptr_ = other.ptr_;        // забираем чужое
        other.ptr_ = nullptr;     // зануляем источник
    }
    return *this;
}
```

Это и есть «уникальное владение» = **move-only тип**. Прямое применение [правила пяти](../glossary.md#rule-of-three) (rule of five) из лекции 11.

Дополнительно `unique_ptr` имеет [специализацию](../glossary.md#specialization) (specialization) `unique_ptr<T[]>` для массивов (вызывает `delete[]` вместо `delete`). На уровне базы — это «есть и работает».

### Custom deleter

Реальный `std::unique_ptr` принимает **второй** шаблонный параметр — тип [deleter](../glossary.md#deleter)'а:

```cpp
template <typename T, typename Deleter = std::default_delete<T>>
class unique_ptr;
```

`std::default_delete` это просто [функтор](../glossary.md#functor) (function object), который вызывает `delete`. Но можно подставить **свой** deleter — полезно для не-`new` ресурсов:

```cpp
auto close_file = [](FILE* f) { if (f) std::fclose(f); };
std::unique_ptr<FILE, decltype(close_file)> file(std::fopen("x", "r"), close_file);
// файл закроется автоматически
```

Это та же RAII-идея, но deleter знает, **как** освобождать. Для файлов это `fclose`, для сетевых хендлов — `close`, для GPU-объектов — соответствующее API. Идея — превратить любой ресурс в RAII-управляемый.

В прикладном коде часто пишут собственные wrapper-классы поверх `unique_ptr` с предзаданным deleter'ом — это даёт чистый интерфейс. Подробности по custom-deleter, включая [type erasure](../glossary.md#type-erasure) (по-русски — стирание типа) deleter'а в `shared_ptr`, в курс не входят.

## 2. `shared_ptr` и control block

`shared_ptr` поддерживает **разделяемое владение** — несколько объектов-указателей на один и тот же объект, и объект живёт, пока есть **хотя бы один** владелец:

```cpp
auto a = std::make_shared<int>(42);
{
    auto b = a;        // refcount = 2
    auto c = a;        // refcount = 3
}                      // b и c уничтожены → refcount = 1
// объект жив, пока есть a
```

### Внутреннее устройство

`shared_ptr` хранит **два** указателя: на сам объект и на **[control block](../glossary.md#control-block)** (по-русски — блок управления):

```
   shared_ptr<T>
   ┌──────────┐
   │  T*    ──┼──────────────────────► T object
   │  ctrl* ──┼──┐                     ┌────────┐
   └──────────┘  │                     │ data   │
                 ▼                     └────────┘
        ┌─────────────────┐
        │ strong refcount │
        │ weak refcount   │
        │ deleter         │
        │ allocator       │
        └─────────────────┘
            Control Block
```

Control block содержит:

- **[счётчик ссылок](../glossary.md#reference-count)** (reference count, на схеме strong) — сколько `shared_ptr` сейчас владеют объектом
- **счётчик слабых ссылок** (weak) — сколько `weak_ptr` ссылаются (об этом дальше)
- **deleter** (через type erasure) — как удалять объект
- **[аллокатор](../glossary.md#allocator)** (allocator) — как удалять память control block

Когда копируется `shared_ptr` — копируются оба указателя плюс инкремент счётчика ссылок. При уничтожении — декремент. Когда **strong** = 0 — объект удаляется. Когда **strong** и **weak** оба = 0 — удаляется сам control block.

### Стоимость

- **Размер:** `sizeof(shared_ptr)` обычно 16 байт (два указателя), у `unique_ptr` — 8.
- **Аллокации:** обычно две — отдельно объект (через `new T(...)`) и отдельно control block.
- **Счётчик ссылок [атомарный](../glossary.md#atomic) (atomic)** — чтобы копирование между потоками было [потокобезопасным](../glossary.md#thread-safety) (thread safety). Каждый инкремент счётчика — атомарная операция, она дороже обычного инкремента.

Это означает: **`shared_ptr` нужен только когда реально нужно разделяемое владение**. Если хватает уникального — используйте `unique_ptr` (быстрее, меньше памяти, проще).

### Когда `shared_ptr` действительно нужен

- Объект используется в **нескольких независимых контекстах**, и кто его удалит — заранее непонятно.
- Объект **возвращается** из фабрики, и время его жизни определяется потребителем.
- Подписчики, обозреватели, кэши с долговременным владением.

В обычном прикладном коде `shared_ptr` встречается **гораздо реже**, чем `unique_ptr`. Если в вашем коде половина — `shared_ptr`, скорее всего, дизайн стоит пересмотреть.

## 3. `make_shared` vs `make_unique`

`std::make_shared<T>(args...)` и `std::make_unique<T>(args...)` — стандартные способы создания [умного указателя](../glossary.md#smart-pointer) (smart pointer).

### `make_shared`

```cpp
auto p1 = std::shared_ptr<T>(new T(args));   // ОК, но не лучший вариант
auto p2 = std::make_shared<T>(args);          // предпочтительный вариант
```

`make_shared` лучше двумя вещами:

1. **Одна аллокация вместо двух.** В первом случае `new T(args)` — одна аллокация, потом `shared_ptr` делает вторую под control block. В случае `make_shared` компилятор размещает объект и control block рядом в **одном** блоке памяти. Это быстрее, меньше фрагментации, лучше [локальность](../glossary.md#cache-locality) (cache locality).

2. **[Exception safety](../glossary.md#exception-safety)** (по-русски — безопасность исключений) в выражениях типа:
   ```cpp
   f(std::shared_ptr<T>(new T(...)), risky());
   ```
   До C++17 порядок вычисления аргументов был [unspecified](../glossary.md#unspecified) — компилятор мог вычислить `new T(...)`, затем `risky()` (которая бросила исключение), и только потом обернуть в `shared_ptr`. Между `new` и обёртыванием была «дыра», где сырой указатель мог [утечь](../glossary.md#memory-leak) (memory leak). В `make_shared(...)` выделение памяти и создание владельца происходят внутри одного вызова: промежутка между `new` и конструктором `shared_ptr` нет — утечки нет. С C++17 стало спокойнее: порядок аргументов по-прежнему unspecified, но вычисление одного аргумента больше не вправе перемежаться с вычислением другого — `risky()` не может вклиниться между `new` и конструктором `shared_ptr`. Привычка всё равно осталась.

### `make_unique`

`make_unique<T>(args...)` (появилось в C++14) — то же самое для `unique_ptr`. Те же выигрыши по exception safety. Аллокация одна (control block у `unique_ptr` нет — она лишняя).

**Правило:** всегда `make_shared` / `make_unique`. Голый `new T` внутри конструктора умного указателя — устаревший стиль.

### Когда `make_shared` не подходит

```cpp
auto p = std::make_shared<int>(42);
std::weak_ptr<int> w = p;
p.reset();    // объект уничтожен...
              // ...но память НЕ освобождена, пока жив weak_ptr!
```

`make_shared` кладёт control block и объект в одну аллокацию. Деструктор объекта вызывается при нулевом счётчике ссылок, но саму **память** освободить можно только когда уничтожится control block — а он жив, пока есть хоть один `weak_ptr`.

Для очень больших объектов с долгоживущими `weak_ptr` это может быть проблемой — память «зависает» до окончания weak_ptr'ов. В таком случае — `std::shared_ptr<T>(new T(...))` (две аллокации, но объект освобождается сразу).

В обычном коде эта проблема не возникает. Знать стоит — но 99% времени `make_shared` правильный выбор.

### Подводный камень: приватный конструктор

Ещё одна неочевидная ситуация — `make_shared` (или `make_unique`) **не сработает**, если конструктор класса приватный, даже изнутри самого класса:

```cpp
class Widget {
    Widget(int x) : x_(x) {}      // private
public:
    static std::shared_ptr<Widget> create(int x) {
        return std::make_shared<Widget>(x);    // CE
    }
    int x_;
};
```

`std::make_shared<T>` — это **свободная функция** из стандартной библиотеки, а не метод или `friend` вашего класса. Внутри она делает что-то вроде `new T(forward<Args>(args)...)`. Из контекста этой функции `T` приватный конструктор недоступен — [CE](../glossary.md#ce) (compilation error).

Это иногда сюрприз: вызов `make_shared` идёт из метода `Widget::create`, и кажется, что доступ к приватному конструктору должен быть. Но в момент **вычисления `make_shared`** мы уже находимся внутри тела стандартной библиотечной функции, у которой никаких особых прав на `Widget` нет.

Обходные пути:

1. **Сделать конструктор публичным.** Простейшее решение, если приватность не критична.
2. **Passkey idiom** — добавить параметр-«ключ» в публичный конструктор:
   ```cpp
   class Widget {
       struct PrivateKey {};
   public:
       Widget(PrivateKey, int x) : x_(x) {}
       static std::shared_ptr<Widget> create(int x) {
           return std::make_shared<Widget>(PrivateKey{}, x);
       }
   };
   ```
   `PrivateKey` — приватный тип, создать его снаружи нельзя. Конструктор формально публичный, но вызвать его без `PrivateKey` нельзя.
3. **Откатиться на `std::shared_ptr<Widget>(new Widget(x))`** — две аллокации вместо одной, но проще:
   ```cpp
   static std::shared_ptr<Widget> create(int x) {
       return std::shared_ptr<Widget>(new Widget(x));
   }
   ```
   `new Widget(x)` происходит внутри метода `Widget::create` — доступ к приватному конструктору есть.

Самый чистый — passkey idiom, но он многословный. Чаще ограничиваются вариантом 3.

## 4. `weak_ptr` — циклические ссылки

Главная проблема `shared_ptr` — **циклические ссылки**:

```cpp
struct Node {
    std::shared_ptr<Node> next;
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->next = a;     // цикл!
```

При выходе из [области видимости](../glossary.md#scope) (scope): счётчик ссылок `a` уменьшается до 1 (внутренняя ссылка `b->next` всё ещё держит), счётчик `b` уменьшается до 1 (`a->next` держит). Ни один не дойдёт до 0. **Утечка**, хотя мы использовали умные указатели.

### Решение — `weak_ptr`

`weak_ptr` **не инкрементирует** счётчик ссылок. Он только инкрементирует счётчик слабых ссылок, чтобы control block не удалился, пока есть кто-то наблюдающий:

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node>   prev;   // не держит prev живым
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->prev = a;     // weak — не цикл
```

Теперь циклов нет: `a` держит `b` через `next`, но `b` не держит `a` через `prev`.

### Доступ через `lock()`

`weak_ptr` сам по себе — это не указатель, через него нельзя сделать `*` или `->`. Чтобы получить актуальный `shared_ptr` (если объект ещё жив), нужен `lock()`:

```cpp
std::weak_ptr<Node> w = a;

if (auto sp = w.lock()) {
    sp->method();      // объект жив, можем пользоваться
} else {
    // объект уже уничтожен
}
```

`lock()` **атомарно** проверяет, что счётчик ссылок > 0, и возвращает `shared_ptr` (либо пустой, если объект мёртв). Атомарность важна: между «проверить, что жив» и «получить shared_ptr» в многопоточном коде объект может умереть. `lock()` решает это одной операцией.

### `enable_shared_from_this`

Иногда внутри метода нужно получить **`shared_ptr` на сам объект**. Наивная попытка:

```cpp
class Widget {
public:
    std::shared_ptr<Widget> self() {
        return std::shared_ptr<Widget>(this);   // ОПАСНО
    }
};
```

Это создаст **новый** control block, отдельный от того, через который объект изначально управляется. В итоге будет два control block'а на один объект — double free, UB.

Правильный способ — наследоваться от `std::enable_shared_from_this`:

```cpp
class Widget : public std::enable_shared_from_this<Widget> {
public:
    std::shared_ptr<Widget> self() {
        return shared_from_this();
    }
};

auto w = std::make_shared<Widget>();
auto same = w->self();    // same и w делят один control block
```

`shared_from_this()` находит существующий control block (через внутренний `weak_ptr` в базе) и возвращает `shared_ptr`. Требование: объект уже должен управляться `shared_ptr` к моменту вызова — иначе исключение `bad_weak_ptr`.

Применение: подписки на [колбэки](../glossary.md#callback) (callback), где объект должен «передать ссылку на себя», но не «потерять контроль».

## 5. `std::thread` и `std::jthread`

Мы разобрали RAII применительно к памяти. Но вспомним формулировку принципа: «ресурс владеется объектом, деструктор освобождает». Про память там ничего не сказано.

Что ещё бывает ресурсом, который нужно обязательно отпустить?

- **Поток** — перед уничтожением его нужно дождаться (`join`) или отвязать (`detach`).
- **[Мьютекс](../glossary.md#mutex)** (mutex) — после захвата нужно отпустить (`unlock`), иначе всё встанет.
- **Файловый дескриптор, сокет, соединение с БД, транзакция** — всё это захватывается и обязано освобождаться.

Проверим идею на потоках и мьютексах. И тут нас ждёт интересное: стандартная библиотека сначала сделала это **неправильно**, а исправилась только через девять лет — в C++20.

C++11 стандартизировал многопоточность в составе языка. До этого приходилось пользоваться платформенными API (pthread на Linux, WinAPI на Windows) — несовместимыми между собой. Сейчас в стандартной библиотеке есть создание потоков (`std::thread`, `std::jthread`), синхронизация (`std::mutex`, `std::lock_guard`/`scoped_lock`/`unique_lock`, `std::condition_variable`) и асинхронность (`std::future`, `std::promise`, `std::async`). Атомарные операции (`std::atomic<T>`) и [модель памяти](../glossary.md#memory-model) (memory model, `std::memory_order`) в курс не входят.

Запуск потока:

```cpp
#include <thread>

void worker(int id) {
    std::print("worker {}\n", id);
}

int main() {
    std::thread t(worker, 1);
    t.join();          // ждём окончания

    std::thread t2([](int x) { std::print("lambda {}\n", x); }, 42);
    t2.join();
}
```

`std::thread` принимает [callable](../glossary.md#callable) (вызываемый объект) плюс аргументы (через [variadic templates](../glossary.md#variadic) из лекции 9) и запускает их в новом потоке.

А теперь главное. Поток — это ресурс: его нужно дождаться перед уничтожением объекта. Что делает деструктор `std::thread`, если вы забыли `join()`?

```cpp
{
    std::thread t(worker, 1);
}   // деструктор вызывает std::terminate() — программа падает
```

**Падает.** Это ровно то, чего не должно происходить с RAII-объектом: деструктор не освобождает ресурс, а обрушивает программу.

### Почему так вышло

Может показаться, что это недоработка. На самом деле это осознанное решение, и у него есть логика. Что мог бы делать деструктор?

- **Молча делать `join()`** — то есть блокироваться. Тогда выход из области видимости внезапно занимает секунды или минуты, причём в неочевидном месте. Сюрприз по времени.
- **Молча делать `detach()`** — поток продолжает работать с объектами, которые уже разрушаются. Сюрприз по данным, причём с UB.
- **Падать громко** — программист обязан явно сказать, чего он хочет.

Стандарт выбрал третье: лучше немедленное падение, чем тихое ожидание неизвестной длины — а если ожидаемый поток сам ждёт текущий, то и [deadlock](../glossary.md#deadlock) (потоки ждут друг друга по кругу), — или порча памяти. Решение защитимое, но с точки зрения RAII `std::thread` — **не** RAII-обёртка. Тип управляет ресурсом, но не освобождает его.

### `join()` vs `detach()`

- **`join()`** — блокирующее ожидание окончания потока. После него объект освобождает свои ресурсы.
- **`detach()`** — «отвязать» поток. Он продолжит работать в фоне, но объект больше им не управляет.

`detach` используется редко: обычно вы хотите дождаться результата, а не потерять контроль над потоком.

### `std::jthread` (C++20) — RAII восстановлен

Через девять лет после C++11 в стандарт добавили то, чем `thread` должен был быть с самого начала:

```cpp
{
    std::jthread t(worker, 1);
}   // деструктор сам делает join()
```

Буква `j` — от *joining*. Одна буква, и тип наконец ведёт себя как положено RAII-обёртке: захватил в конструкторе, отпустил в деструкторе.

Как решили дилемму из предыдущего раздела? Добавили **[кооперативную отмену](../glossary.md#cooperative-cancellation)** (cooperative cancellation): `jthread` в деструкторе сначала просит поток остановиться, и только потом ждёт. Так что ожидание в деструкторе перестаёт быть неопределённо долгим — если поток написан правильно, он завершится быстро.

Плюс `jthread` умеет принимать `std::stop_token`:

```cpp
std::jthread t([](std::stop_token stop) {
    while (!stop.stop_requested()) {
        do_work();
    }
});

t.request_stop();   // попросить остановиться (поток сам решит, как реагировать)
// в деструкторе jthread автоматически request_stop() + join()
```

`stop_token` — механизм кооперативной отмены. Поток сам периодически проверяет `stop_requested()` и решает, как корректно завершиться. Принудительной остановки потока в C++ нет — это сознательное решение, чтобы избежать утечек и поломанных инвариантов.

**Правило:** в новом коде используйте `jthread`, не `thread`.

## 6. `std::mutex` — защита общего состояния

С потоками мы увидели закономерность: ресурс есть, а RAII-обёртки сначала не было. С мьютексами история повторяется почти буквально — и это не совпадение, а общее свойство «низкоуровневых» примитивов: они дают механизм, а безопасную обёртку приходится строить отдельно.

Сначала о том, зачем мьютекс вообще нужен. Когда несколько потоков обращаются к одной переменной, и хотя бы один из них пишет — это **[гонка данных](../glossary.md#data-race)** (data race):

```cpp
int counter = 0;   // shared

void inc() {
    for (int i = 0; i < 100000; ++i) {
        ++counter;     // race: read-modify-write не атомарен
    }
}

std::jthread t1(inc), t2(inc);
// результат < 200000 — некоторые ++ потерялись
```

`++counter` это три операции: чтение, инкремент, запись. Между ними другой поток может вклиниться и тоже прочитать — оба прочитают одно и то же, оба запишут одно и то же. Один инкремент потеряется.

Гонка данных — это **UB** в C++. Стандарт не обещает ничего конкретного.

### Защита через `std::mutex`

```cpp
int counter = 0;
std::mutex m;

void inc() {
    for (int i = 0; i < 100000; ++i) {
        m.lock();
        ++counter;
        m.unlock();
    }
}
```

`m.lock()` блокирует мьютекс — если кто-то его уже держит, ждём. `m.unlock()` отпускает. Между `lock` и `unlock` гарантирован эксклюзивный доступ — это **[критическая секция](../glossary.md#critical-section)** (critical section).

### RAII-обёртки блокировок: `lock_guard`

Ручной `lock()` / `unlock()` — это ровно та же ошибка, что ручные `new` / `delete` на лекции 2. Достаточно одного раннего выхода:

```cpp
m.lock();
do_something();        // а если бросит исключение?
m.unlock();            // эта строка не выполнится
```

Мьютекс останется захваченным навсегда. Любой следующий поток, который его попросит, встанет намертво — **deadlock**. И заметьте: программа не упадёт с понятной ошибкой, она просто зависнет.

Лечение то же, что для памяти — RAII:

```cpp
void inc() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock(m);   // m.lock() в конструкторе
        ++counter;
    }                                           // m.unlock() в деструкторе
}
```

С C++17 благодаря [CTAD](../glossary.md#ctad) — [выводу аргументов](../glossary.md#deduction) шаблона класса (class template argument deduction) — можно короче:

```cpp
std::lock_guard lock(m);
```

`lock_guard` — самая частая и самая дешёвая RAII-обёртка [блокировки](../glossary.md#lock) (lock). Если не нужно ждать (`wait`) на [условной переменной](../glossary.md#condition-variable) (condition variable) и не нужно отпускать-захватывать мьютекс руками — используйте `lock_guard`.

### Несколько мьютексов и deadlock

Если поток держит **несколько** мьютексов одновременно, появляется новый класс ошибок — deadlock:

```cpp
std::mutex m1, m2;

// Thread 1                          // Thread 2
{                                    {
  std::lock_guard l1(m1);              std::lock_guard l1(m2);
  std::lock_guard l2(m2);              std::lock_guard l2(m1);
  /* ... */                            /* ... */
}                                    }
```

T1 захватил `m1`, ждёт `m2`. T2 захватил `m2`, ждёт `m1`. Никто не двигается. Программа висит.

Классическая защита — **всегда захватывать мьютексы в одном и том же порядке**. Если все потоки сначала берут `m1`, потом `m2` — deadlock невозможен.

### `std::scoped_lock` (C++17)

`std::scoped_lock` — RAII-обёртка, захватывающая **несколько** мьютексов одновременно, с алгоритмом захвата, исключающим deadlock:

```cpp
{
    std::scoped_lock lock(m1, m2);   // захватываются все сразу
    /* ... */
}
```

Внутри `scoped_lock` использует упорядочивание или `try_lock` с откатом — гарантирует, что deadlock невозможен, даже если разные потоки передадут мьютексы в разном порядке.

**Правило:** несколько мьютексов захватывают только через `scoped_lock`, а не вложенными `lock_guard`.

### RAII как универсальный принцип

Здесь стоит остановиться и зафиксировать промежуточный итог. Лекция началась с определения RAII из лекции 2 — resource acquisition is initialization — и с замечания, что слова «память» в нём нет. Теперь понятно, зачем это было нужно.

| Ресурс | RAII-обёртка | Что делает деструктор |
|---|---|---|
| Память (один владелец) | `unique_ptr` | `delete` |
| Память (много владельцев) | `shared_ptr` | `--refcount`, при нуле — `delete` |
| Мьютекс | `lock_guard`, `scoped_lock` | `unlock()` |
| Поток | `jthread` (C++20) | `request_stop()` + `join()` |
| Файл | `std::fstream` | `close()` |
| Сокет, соединение с БД, GPU-буфер | ваш класс | ваш `~T()` |

Три наблюдения:

1. **RAII — не про память.** Память — самый частый случай, но принцип общий: любой ресурс с парой «взять / отдать» просится в обёртку с конструктором и деструктором.
2. **Отсутствие RAII там, где ресурс есть, — это баг дизайна, а не особенность.** История `std::thread` → `std::jthread` это прямо показывает: девять лет ушло на то, чтобы починить одно решение.
3. **RAII отвечает только на вопрос «как освободить».** Синхронизация — «как дождаться» — это отдельная задача, и решается она отдельными механизмами: `condition_variable`, `future`, `atomic`.

Третье наблюдение и определяет остаток лекции. RAII отвечает на вопрос «как гарантированно освободить ресурс» исчерпывающе — для памяти, мьютексов, потоков, файлов, чего угодно. Но у многопоточности есть второй вопрос, на который RAII ответа не даёт:

> **Как дождаться, пока что-то произойдёт?**

Поток-потребитель должен спать, пока в очереди нет данных, и проснуться, когда они появятся. Деструкторы здесь ни при чём — освобождать нечего, нужно наоборот, ждать.

## 7. `std::condition_variable` — ожидание

Первый механизм — условная переменная, `std::condition_variable`. Классический паттерн её применения называется **[producer-consumer](../glossary.md#producer-consumer)** (по-русски — производитель-потребитель), и это ровно та схема, по которой устроен почти любой агент сбора данных.

Разберём, откуда она берётся. Читать события из системы должен **один** поток: источник телеметрии обычно один, и параллельно из него читать либо нельзя, либо бессмысленно. А вот обрабатывать события — проверять правилами, обогащать, писать в хранилище — можно во многих потоках, и это как раз то, что нужно масштабировать. Значит, между чтением и обработкой нужен буфер: очередь, в которую один поток пишет, а несколько читают.

И сразу видна проблема, которую не решить мьютексом. Что делать рабочему потоку, когда очередь пуста? Крутиться в цикле, проверяя её снова и снова, — значит жечь процессор ровно в те моменты, когда работы нет; для агента, у которого главное требование «будь незаметным», это худший из возможных вариантов. Нужно **спать**, пока данных нет, и просыпаться, когда они появились. Именно это умеет `condition_variable`.

```cpp
std::mutex m;
std::condition_variable cv;
std::queue<Event> q;
```

```cpp
// Producer — поток, читающий события из системы:
{
    std::lock_guard lock(m);
    q.push(event);
}
cv.notify_one();        // разбудить ждущий поток

// Consumer — рабочий поток:
std::unique_lock lock(m);
cv.wait(lock, [&]{ return !q.empty(); });   // спим, пока пусто
Event e = std::move(q.front()); q.pop();
```

Обратите внимание на `std::move` в последней строке — это ровно тот случай из лекции 11, для которого move-семантика и придумана: элемент очереди сейчас будет удалён через `pop()`, копировать его незачем.

### Нюансы

- **`unique_lock`** (не `lock_guard`) — `cv.wait` временно отпускает мьютекс и захватывает обратно. `lock_guard` не умеет отпускать/захватывать заново.
- **Лямбда-предикат обязателен** — для защиты от **[ложных пробуждений](../glossary.md#spurious-wakeup)** (spurious wakeups). Поток может «проснуться» без `notify` (это разрешено стандартом — особенность OS). С предикатом `cv.wait` сам проверит и заснёт обратно, если данные ещё не готовы.
- **`notify_one()`** будит один ждущий поток, **`notify_all()`** — всех.

Использование condition_variable нетривиально, в нём легко допустить ошибку. Если задача попадает в один из стандартных паттернов (producer-consumer, barrier) — часто есть более высокоуровневая альтернатива: `std::counting_semaphore`, `std::barrier`, `std::latch` (все C++20).

## 8. `std::future` / `std::promise` / `std::async`

Часто нужна асинхронность не «запусти потоки и синхронизуй сам», а более простая модель: **запусти задачу, получи хендл на её результат**. Для этого есть future / promise / async.

### `std::async`

Самая удобная форма:

```cpp
#include <future>

std::future<int> f = std::async(std::launch::async, [] {
    std::this_thread::sleep_for(std::chrono::seconds(1));
    return 42;
});

// ... тем временем делаем что-то параллельно ...

int result = f.get();      // блокируется до готовности
```

`std::async` создаёт поток (политика `std::launch::async`), запускает функцию в нём, возвращает `future<R>` — хендл на будущий результат типа `R`. Через `f.get()` получаем результат (блокируется, если ещё не готов).

Без флага `std::launch::async` стандарт разрешает выполнение **в момент `get()`** (ленивое) — что часто не то, что хочется. Поэтому пишите `std::launch::async` явно.

Если задача бросила исключение — оно прокинется в `f.get()`. Удобно.

### `std::promise` + `std::future`

Низкоуровневая форма — «один поток обещает значение, другой ждёт»:

```cpp
std::promise<int> p;
std::future<int> f = p.get_future();

std::jthread producer([&p] {
    p.set_value(42);       // выставляем значение из другого потока
});

int x = f.get();           // получаем (блокируется, если ещё нет)
```

`set_exception(...)` пробросит исключение в `get()`. Тот же контракт, что у `async`.

`promise`/`future` — это «канал» одного значения, без копирования через очередь. Полезно, когда нужно вернуть результат из колбэка или обработчика события.

## 9. `thread_local`

Иногда нужна переменная, у которой **каждый поток своя копия**:

```cpp
thread_local int local_counter = 0;

void f() {
    ++local_counter;          // каждый поток инкрементит свою копию
    std::cout << local_counter << '\n';
}
```

[Время жизни](../glossary.md#lifetime) (lifetime) такой переменной — **вся жизнь потока**, а не только функции. Каждый поток получает свою независимую копию при первом обращении.

Применения:

- **Локальный state без мьютекса** — логгеры, профайлеры с локальными буферами.
- **Кэши, специфичные для потока** — например, кэш парсера регулярных выражений.
- **Random number generators:** `thread_local std::mt19937 rng;` — каждый поток имеет свой генератор, без блокировок.

Подвох: время жизни — **вся жизнь потока**. Если поток долго живёт, переменная тоже жива всё это время. Это нормально для счётчиков и RNG; для больших структур данных может быть проблемой.

## 10. Что осталось за рамками курса

Базы из этой лекции **достаточно**, чтобы писать **корректный** concurrent-код. Правила:

- Любой доступ к **shared mutable state** — под мьютексом (или через `atomic`).
- Мьютекс захватывается только через RAII-обёртку, никогда руками.
- Ожидание событий — через condition_variable + предикат.
- Асинхронность — через future / async.
- Несколько мьютексов — только через `scoped_lock`.
- Потоки — `jthread`, если нет причины использовать `thread`.

Всё это живёт на уровне «мьютекс + ожидание». Ниже есть ещё один слой, на котором оно реализовано, — и он за рамками курса:

- **`std::atomic<T>`** — операции без мьютекса, для базовых типов. Атомарный инкремент в десятки раз быстрее защищённого мьютексом.
- **`std::memory_order`** — модель памяти C++. Sequential consistency / acquire-release / relaxed. Когда какое использовать.
- **[Lock-free](../glossary.md#lock-free) структуры данных** — очереди, стеки, [хеш-таблицы](../glossary.md#hash-table) (hash tables) без мьютексов.
- **Параллельные алгоритмы** — `std::sort(std::execution::par, ...)` для параллельной сортировки.
- **[Корутины](../glossary.md#coroutine) (coroutines, C++20)** — обзорно, как альтернатива потокам для I/O-bound задач.

Здесь разобран рабочий минимум для прикладного кода; полный объём темы — это отдельный курс.

## Итоги

- **`unique_ptr`** — RAII над одним указателем, move-only тип, нулевые накладные расходы. Второй шаблонный параметр — custom deleter, через него в RAII заворачивается любой ресурс.
- **`shared_ptr`** — разделяемое владение через control block: счётчик ссылок, счётчик слабых ссылок, deleter, аллокатор. Два указателя, атомарный счётчик ссылок, обычно две аллокации. Берите его только там, где владение действительно разделяемое.
- **`make_shared` / `make_unique`** — умолчание вместо голого `new`. Ограничения: одна аллокация задерживает освобождение памяти при живых `weak_ptr`, и приватный конструктор через них не вызвать (passkey idiom или `shared_ptr<T>(new T(...))`).
- **`weak_ptr`** — разрывает циклические ссылки, не держит объект живым; доступ только через `lock()`.
- **`enable_shared_from_this`** — единственный корректный способ получить `shared_ptr` на `this`.
- **`std::jthread`** (C++20) вместо `std::thread`: авто-`join` в деструкторе плюс `stop_token` для кооперативной отмены.
- **`std::mutex` и RAII-обёртки блокировок** — `lock_guard` по умолчанию, `unique_lock` там, где нужно отпускать мьютекс, `scoped_lock` для нескольких мьютексов сразу. Гонка данных — это UB.
- **`std::condition_variable`** — ожидание события: `unique_lock` плюс обязательный лямбда-предикат против ложных пробуждений.
- **`std::future` / `std::promise` / `std::async`** — асинхронная задача и хендл на её результат; исключения пробрасываются в `get()`.
- **`thread_local`** — своя копия переменной в каждом потоке, живёт всю жизнь потока.
