# Лекция 4. Введение в ООП

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему».

## 0. О чём эта лекция

Прошлые три лекции были про язык на уровне «отдельных переменных и функций» — типы, память, указатели, ссылки, передача параметров. Сегодня мы переходим к **классам** — основному инструменту C++ для создания собственных типов.

В отличие от Java или Python, классы в C++ — это **не** обязательная парадигма. Многие хорошие программы на C++ написаны в стиле, далёком от классической OOP: с упором на value semantics, шаблоны и свободные функции. Но классы остаются центральным языковым механизмом — `std::vector`, `std::string`, `std::unique_ptr` — это всё классы.

К концу лекции вы должны уметь написать собственный класс с конструктором, деструктором, парой методов, и иметь представление о том, какие из этих частей язык сгенерирует за вас (правило нуля, трёх и пяти).

## 1. ООП — основные термины

ООП традиционно строится вокруг четырёх идей:

1. **Абстракция** — отделить «что делает» от «как реализовано».
2. **Инкапсуляция** — спрятать внутренности класса за публичным интерфейсом.
3. **Наследование** — переиспользовать поведение через отношение «is-a».
4. **Полиморфизм** — один интерфейс — разное поведение в зависимости от реального типа.

C++ **поддерживает** все четыре, но **не навязывает** ни одного. Можно писать классы без наследования (часто это и лучше). Можно писать без виртуальных функций. И часто это даже предпочтительно. В идиоматичном современном C++ опираются на три альтернативные идиомы, которые мы будем подробно встречать дальше — здесь обозначим их кратко.

**Value semantics** — это когда объекты ведут себя как обычные значения, как `int`. Их создают на стеке или как поля, передают по значению или по ссылке, копируют и перемещают. Без `new`, без указателей-на-объект «потому что так в Java делают». `std::vector<int> v;` — это объект-значение, у него нет «двух владельцев», он просто живёт там, где объявлен, и аккуратно умирает. Java вынуждает большинство объектов жить в куче через ссылки. C++ — нет, и в большинстве случаев это эффективнее и проще для понимания владения.

**Composition over inheritance** — «композиция вместо наследования». Если класс `Car` использует класс `Engine`, обычно правильно держать `Engine engine_;` как поле, а не наследоваться от `Engine`. Композиция гибче (можно поменять `engine_` в рантайме), не создаёт жёстких иерархий, и не имеет проблем многократного наследования. Наследование уместно, когда между классами реально есть отношение «is-a» с замещением — например, `class Square : public Shape`.

**Generic programming** — обобщённое программирование через шаблоны. Например, `std::sort` умеет сортировать **любые** типы с операцией `<`, не зная заранее, какие именно. Это решает ту же задачу, что виртуальные функции в Java («один код работает с разными типами»), но **на этапе компиляции** — без накладных расходов во время выполнения и без необходимости общего базового класса. Шаблоны мы начнём разбирать на лекциях 8–9.

Для базы важно понимать классические OOP-термины — это словарь языка. А как именно их применять в архитектуре своего кода — отдельный вопрос, который мы будем обсуждать по ходу курса.

## 2. Структуры и классы

### `struct` в C

В чистом C `struct` — это просто набор полей:

```c
struct Point {
    int x;
    int y;
};

struct Point p = {3, 4};
printf("%d %d\n", p.x, p.y);
```

Данные, и ничего больше. Никаких методов, никакой инкапсуляции.

### `class` и `struct` в C++

В C++ `class` и `struct` — **почти** одно и то же. Оба могут иметь:

- поля и методы
- конструкторы и деструкторы
- модификаторы доступа `public` / `private` / `protected`
- наследование от других классов

**Единственная** разница — модификатор доступа по умолчанию:

```cpp
class A { int x; };       // x — private
struct B { int x; };       // x — public
```

И то же самое для наследования (об этом — на лекции 6).

### Соглашение о применении

Поскольку технически они эквивалентны, в проектах используется **соглашение**, помогающее читателю кода понять намерение:

- **`struct`** — для «просто наборов данных»: POD-структур, конфигов, координат, пар, троек. У них все поля публичны, нет инвариантов, конструкторов либо нет, либо они тривиальны.
- **`class`** — для всего остального: классов с состоянием, инкапсуляцией, методами, инвариантами.

Этого соглашения придерживается, например, Google C++ Style Guide и большинство больших C++-проектов.

## 3. Поля, методы, `this`

### Объявление и определение

```cpp
class Point {
public:
    void print() const {
        std::print("({}, {})\n", x_, y_);
    }

    int x_ = 0;
    int y_ = 0;
};
```

Поля — это переменные, принадлежащие объекту. Методы — это функции, имеющие доступ к полям этого объекта.

C++11 разрешил **инициализаторы полей по умолчанию** прямо в объявлении: `int x_ = 0`. Раньше это можно было делать только в конструкторе. Это сильно упростило типичный код — теперь не нужен явный конструктор для «обнули все поля».

Методы можно определять внутри класса (тогда они автоматически `inline`) или вне — через `ClassName::`:

```cpp
class Point {
public:
    void print() const;
    int x_ = 0, y_ = 0;
};

void Point::print() const {
    std::print("({}, {})\n", x_, y_);
}
```

Размещение внутри класса удобно для коротких методов и шаблонов. Размещение вне — для длинных методов: уменьшает время компиляции, не «утаскивает» зависимости заголовочного файла во все его пользователи.

### Указатель `this`

В каждом методе доступен скрытый указатель `this` — на текущий объект:

```cpp
class Point {
public:
    void set_x(int x) {
        x_ = x;                  // эквивалент this->x_ = x;
        this->y_ = 0;            // явно через this
    }
    int x_, y_;
};
```

`this` имеет тип `Point*` в обычном методе и `const Point*` в `const`-методе. В современном коде явный `this->` пишут только когда:

- нужно отличить поле от параметра: `x_ = x`
- внутри шаблонного класса (там без `this->` иногда не компилируется из-за зависимых имён — об этом на лекции 8)

С C++23 появилась альтернатива — **deducing this**, который заменяет неявный `this` явным шаблонным параметром. В курс он не входит.

### Class scope

Внутри методов класса видны **все** его поля и методы — даже `private`. Это называется class scope:

```cpp
class Counter {
public:
    void inc() { ++count_; }              // ok: count_ private, но мы внутри класса
    int get() const { return count_; }
private:
    int count_ = 0;
};

Counter c;
c.inc();
std::print("{}\n", c.get());      // 1
// c.count_;                       // CE: private снаружи
```

Это и есть **инкапсуляция**: публичный интерфейс (методы `inc`/`get`), скрытое состояние (`count_`). Можно поменять реализацию (заменить `int` на `std::atomic<int>`, добавить логирование, и т.д.) — пользователи класса этого не заметят.

## 4. Модификаторы доступа

```cpp
class Widget {
public:                          // доступно всем
    void show();

protected:                       // доступно классу и наследникам
    int internal_state_;

private:                         // доступно только классу
    void helper_();
    int counter_;
};
```

`protected` подробно разберём при наследовании. Сейчас важно правило:

- **Поля — по умолчанию `private`.** Пользователь класса не должен знать о его внутренностях.
- **Методы — `public` только те, которые нужны вне класса.** Вспомогательные методы — `private`.

Это снижает связанность кода и даёт свободу менять реализацию без ломки клиентов.

### `friend`

`friend`-объявление даёт **другому классу или функции** доступ к `private` членам:

```cpp
class Account {
    int balance_ = 0;
    friend void audit(const Account& a);
};

void audit(const Account& a) {
    std::print("balance: {}\n", a.balance_);   // ok: friend
}
```

Зачем нужен `friend`:

- Перегрузка операторов в виде свободных функций (лекция 5). Например, `operator<<` для вывода в поток обычно нуждается в доступе к `private`.
- Тесно связанные классы (например, итератор, реализованный отдельным классом, нуждается в доступе к внутренностям контейнера).
- В тестах — иногда полезно, но это часто запах: если тест нуждается в `friend`, может, дизайн стоит пересмотреть.

`friend` **ломает инкапсуляцию** — поэтому используется экономно. Большие проекты выработали практику: «`friend` только когда нет нормальной альтернативы».

## 5. Конструкторы

### Основы

**Конструктор** — специальный метод, который вызывается при **создании** объекта. Имя совпадает с именем класса, возвращаемого типа нет:

```cpp
class Point {
public:
    Point(int x, int y) : x_(x), y_(y) {}
    int x_, y_;
};

Point p(3, 4);          // вызвался конструктор Point(int, int)
Point p2{3, 4};         // brace-init, эквивалент
```

Конструкторов может быть несколько — это обычная перегрузка функций по параметрам.

### Список инициализации

`: x_(x), y_(y)` — **список инициализации**. Поля инициализируются **до** входа в тело конструктора.

В теле их тоже можно «инициализировать», но это уже не инициализация, а **присваивание** уже созданному объекту:

```cpp
// плохо:
Point(int x, int y) {
    x_ = x;        // x_ к этому моменту уже default-инициализировано
    y_ = y;
}

// хорошо:
Point(int x, int y) : x_(x), y_(y) {}
```

Для встроенных типов разница мала. Но для типов с конструкторами разница принципиальная — вариант с присваиванием вызывает сначала default-конструктор, потом `operator=`. Иногда default-конструктор просто не существует (например, у ссылочного поля, поля-константы или класса без default-конструктора), и тогда инициализация в теле — **CE**.

**Правило:** инициализируйте поля в списке инициализации, не в теле конструктора.

Порядок инициализации полей **определяется порядком их объявления в классе**, не порядком в списке инициализации. Если они разные — компилятор обычно предупредит (`-Wreorder`).

### Default-конструктор

Конструктор без аргументов:

```cpp
class Point {
public:
    Point() : x_(0), y_(0) {}
    int x_, y_;
};

Point p;        // вызывается Point()
```

Если **не объявлен ни один** конструктор — компилятор сгенерирует default-конструктор автоматически. Он будет инициализировать поля их default-конструкторами (если у поля есть инициализатор `int x_ = 0;` — тем значением).

Если объявлен **любой** конструктор — компилятор автогенерацию default-а отменяет. Нужно явно попросить:

```cpp
Point() = default;
```

Это сообщает компилятору «сгенерируй сам». Без этого `Point p;` стало бы CE.

### Делегирующие конструкторы

Один конструктор может вызывать другой:

```cpp
class Point {
public:
    Point(int x, int y) : x_(x), y_(y) {}
    Point() : Point(0, 0) {}              // делегирует к Point(int, int)

    int x_, y_;
};
```

Удобно, чтобы избежать дублирования логики инициализации между несколькими перегрузками. Делегирование — **только в списке инициализации, и без других элементов в нём**: вызов делегирующего конструктора должен быть единственным.

### Конструктор копирования

Специальная форма — конструктор от ссылки на тот же тип:

```cpp
class Buffer {
public:
    Buffer(const Buffer& other) : size_(other.size_), data_(new int[other.size_]) {
        std::copy(other.data_, other.data_ + size_, data_);
    }
    // ...
};

Buffer a(...);
Buffer b = a;        // вызывается копирующий конструктор
```

Если не определить, компилятор сгенерирует «копирование по полям» (member-wise copy). Для классов, владеющих ресурсами (например, динамической памятью), это обычно неправильно — два объекта получают один и тот же указатель, при разрушении дважды освобождают.

Полное правило нуля, трёх и пяти — на лекции 11. Сейчас запомните: **если вы написали деструктор, нужный для освобождения ресурса — нужно подумать про конструктор копирования**.

### `explicit`

По умолчанию **конструктор с одним аргументом** работает как **неявное преобразование**:

```cpp
class Wrapper {
public:
    Wrapper(int x) : x_(x) {}
};

void f(Wrapper w);
f(42);              // ok: int → Wrapper неявно
```

Иногда это удобно (`std::string s = "hello";` — неявно из `const char*`). Часто — нет: типы случайно «склеиваются», аргумент функции получает не тот тип, который вы имели в виду.

С `explicit` неявные преобразования запрещены:

```cpp
class Wrapper {
public:
    explicit Wrapper(int x) : x_(x) {}
};

f(42);              // CE
f(Wrapper(42));     // ok
```

**Правило:** конструкторы с одним аргументом помечайте `explicit`, кроме случаев, когда неявное преобразование действительно желательно. С C++20 есть условный `explicit(condition)` — пригодится в шаблонах.

### `= default` и `= delete`

Современный способ управлять автогенерируемыми функциями:

```cpp
class Point {
public:
    Point() = default;                       // явно: сгенерируй default
    Point(const Point&) = default;           // явно: сгенерируй копирование
};

class NonCopyable {
public:
    NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;    // запретить копирование
};
```

`= default` особенно нужен, когда вы объявили **другой** конструктор и компилятор автоматический default уже не генерирует. `= delete` — для типов, которые семантически не должны копироваться: `std::unique_ptr`, mutex'ы, файловые дескрипторы.

Старый трюк (объявить копирующий конструктор `private` без определения) — пережиток C++03. В новом коде только `= delete`.

### Что делать, если конструктор не может создать объект

На лекции 3 в таблице «когда исключение, а когда код возврата» была строка, которую мы тогда оставили без объяснения: «конструктор не смог создать объект — исключение, другого канала нет». Теперь конструкторы разобраны, и можно объяснить, почему это не стилистическое предпочтение, а свойство языка.

У конструктора **нет возвращаемого значения**. Совсем — это не «он возвращает `void`», а «в его сигнатуре нет места для типа результата». Значит, механизм «вернуть код ошибки» физически недоступен. Остаётся исключение:

```cpp
class Port {
public:
    explicit Port(int value) : value_(value) {
        if (value < 1 || value > 65535) {
            throw std::invalid_argument("port out of range: " + std::to_string(value));
        }
    }
    int value() const { return value_; }
private:
    int value_;
};
```

Можно возразить: а нельзя ли обойтись без исключения — запомнить факт неудачи в поле и завести метод `is_valid()`? Технически можно, и в старом коде так делали. Но посмотрите, во что это превращает тип. Объект существует, но пользоваться им нельзя; каждый метод обязан начинаться с проверки флага; каждый пользователь обязан помнить про `is_valid()` и вызывать его сразу после создания. Забыл проверить — работаешь с мусором. По сути, вы вернулись к проблеме кодов возврата из лекции 3, только в худшем виде: проигнорировать проверку теперь ещё легче, потому что она вообще не выглядит как проверка ошибки.

Исключение из конструктора устроено принципиально иначе, и здесь важна одна деталь языка:

```cpp
Port p(70000);        // бросило — переменной p не существует
```

Если конструктор бросил, **объект не считается созданным**. Из этого следуют два практических вывода. Первый: деструктор такого объекта **не вызовется** — нечего разрушать, конструктор не завершился. Второй: те поля и базовые классы, которые успели проинициализироваться до броска, будут корректно разрушены — их деструкторы уже отработали в рамках раскрутки стека. То есть частично построенный объект не оставляет мусора, если, конечно, его поля сами владеют ресурсами через RAII, а не через сырые указатели.

Отсюда важное следствие для классов, владеющих ресурсами вручную. Такой конструктор небезопасен:

```cpp
class Bad {
public:
    Bad(size_t n) : a_(new int[n]), b_(new int[n]) {}   // если второй new бросит — первый утёк
    ~Bad() { delete[] a_; delete[] b_; }
private:
    int *a_, *b_;
};
```

Если второй `new` бросит `std::bad_alloc`, деструктор `~Bad` не вызовется (объект не создан), а первый блок уже выделен — утечка. С `std::unique_ptr` вместо сырых указателей проблема исчезает сама: `a_` — полноценное поле, его деструктор отработает.

Сформулируем правило:

> **Правило:** конструктор либо создаёт полностью корректный объект, либо бросает исключение. Промежуточного состояния «объект есть, но пользоваться нельзя» быть не должно.

Есть и обратная сторона, о которой стоит знать: если создание объекта может **штатно** не удаться — например, файл может отсутствовать, и это нормальная ситуация, — то бросать исключение из конструктора при каждом таком случае неудобно. В этой ситуации конструктор делают приватным, а рядом кладут статический фабричный метод, возвращающий `std::optional` или `std::expected`. Как это выглядит, увидим на лекции 14, когда появятся эти типы.

## 6. Деструкторы

**Деструктор** вызывается при **уничтожении** объекта. Имя — `~ClassName`, без аргументов и без возвращаемого типа:

```cpp
class Buffer {
public:
    Buffer(size_t n) : data_(new int[n]) {}
    ~Buffer() { delete[] data_; }
private:
    int* data_;
};
```

В деструкторе принято освобождать ресурсы — именно за счёт деструкторов и работает **RAII**, который мы разбирали на лекции 2.

### Порядок ctor/dtor

```cpp
class Inner { ~Inner() { std::print("~Inner\n"); } };
class Outer { Inner i_; ~Outer() { std::print("~Outer\n"); } };

{ Outer o; }
// ~Outer
// ~Inner
```

Порядок:

- **Конструкторы:** базовый класс → поля (в порядке объявления) → тело конструктора
- **Деструкторы:** тело деструктора → поля (в обратном порядке) → базовый класс

Это полностью симметрично и **детерминировано**.

### Правило нуля, трёх и пяти

**Правило нуля:** если для класса автогенерированных функций достаточно — **ничего не пишите**. Не пишите ни деструктор, ни копирующий конструктор, ни operator=. Компилятор справится.

Большая часть классов идиоматичного C++ соответствуют правилу нуля, потому что они состоят из полей с уже правильным поведением (`std::vector`, `std::string`, `std::unique_ptr` — у них всё уже правильно реализовано).

**Правило трёх** (классическое): если вы написали один из {деструктор, копирующий конструктор, operator=}, скорее всего нужны все три. Они логически связаны: владение ресурсом требует и освобождения, и правильного копирования.

**Правило пяти**: с появлением move-семантики (C++11) к трём добавились move-конструктор и move-присваивание. Подробно — на лекции 11.

Практически: пишите свой деструктор только если **класс сам владеет ресурсом**, который нужно явно освободить. И тогда сразу же думайте про копирование/перемещение.

## 7. `const`-методы и `static`

### `const`-методы

```cpp
class Counter {
public:
    int get() const { return count_; }     // const-метод
    void inc() { ++count_; }                // обычный метод
private:
    int count_ = 0;
};

const Counter c;
c.get();           // ok
c.inc();           // CE: cannot call non-const method on const object
```

`const`-метод объявляется добавлением `const` после списка параметров. Внутри него:

- `this` имеет тип `const ClassName*`
- Нельзя менять поля объекта (компилятор проверит)
- Можно вызывать только другие `const`-методы

Делайте `const` все методы, которые **только читают** состояние. Это часть интерфейса — пользователь видит, что метод не меняет объект.

В классах часто бывают **парные** методы — `const` и не-`const` версии:

```cpp
const T& at(size_t i) const { return data_[i]; }
T& at(size_t i)              { return data_[i]; }
```

Так устроен `operator[]` у `std::vector` и `std::map`. С C++23 это дублирование убирается через deducing this, но он в курс не входит.

### `mutable`

Иногда нужно изменить поле в `const`-методе — например, обновить кэш или счётчик обращений:

```cpp
class Cache {
public:
    int get(int key) const {
        ++stats_.queries;
        // ...
    }
private:
    mutable Stats stats_;
};
```

`mutable` снимает с поля «защиту» `const`-метода. Применяется для **«логически const»** операций — таких, которые меняют только не наблюдаемое снаружи состояние (кэш, статистика, ленивая инициализация). Если поле меняет наблюдаемое состояние — `mutable` это запах: метод просто не `const`.

### Статические поля и методы

`static`-поле принадлежит **классу**, а не каждому объекту:

```cpp
class Widget {
public:
    static int total_count;
};

int Widget::total_count = 0;     // определение, в .cpp

++Widget::total_count;
```

До C++17 определение `static`-поля приходилось класть отдельно в `.cpp`. С C++17 можно объявить `inline static` и инициализировать прямо в классе:

```cpp
class Widget {
public:
    inline static int total_count = 0;     // ok с C++17
};
```

`static`-метод не имеет `this` — он работает на уровне класса, без привязки к экземпляру:

```cpp
class MathUtils {
public:
    static int square(int x) { return x * x; }
};

int r = MathUtils::square(5);
```

Применения: фабричные методы (`MyClass::create(...)`), утилиты, не зависящие от конкретного экземпляра, синглтоны (с большой осторожностью).

## 8. Агрегатная инициализация и designated initializers

### Что такое агрегат

**Агрегат** в C++ — это класс/структура, которая:

- не имеет пользовательских конструкторов
- не имеет `private` нестатических полей
- не имеет виртуальных функций
- не имеет приватного / защищённого наследования

Примеры:

```cpp
struct Point {                    // агрегат
    int x;
    int y;
};

struct Config {                    // агрегат
    std::string host;
    int port;
    bool verbose;
};
```

### Aggregate initialization

Для агрегатов работает инициализация списком:

```cpp
Point p = {3, 4};
Point p2{3, 4};
```

Поля заполняются **в порядке объявления**. Можно опустить часть — оставшиеся получат значения по умолчанию (нули для встроенных типов, default-конструктор для классов).

```cpp
Config c{"example.com"};   // host задан, port = 0, verbose = false
```

### Designated initializers (C++20)

C++20 позволил указывать имена полей явно:

```cpp
Config c{
    .host = "example.com",
    .verbose = true,
};   // port остаётся default-значением
```

Преимущества:

- Не нужно помнить **порядок** полей в структуре
- Можно опустить любые поля, не только последние
- Код **самодокументируется** — читая `.host = "x"`, видишь, какое именно поле задаётся

Ограничения:

- Поля должны указываться **в том же порядке**, что в объявлении. `Config{.port = 80, .host = "x"}` — CE.
- Только для **агрегатов**: класс с конструктором так инициализировать нельзя.
- Нельзя в одной фигурной скобке смешивать designated и обычные позиционные.

**Правило:** для агрегатов с двумя и более полями в новом коде предпочтительны designated initializers. Это убирает целый класс багов вида «перепутал порядок параметров».

Для классов с инвариантами (нетривиальная логика конструктора) — обычные конструкторы, без агрегатной инициализации.

## Итоги

- ООП термины (абстракция, инкапсуляция, наследование, полиморфизм) — словарь, который C++ поддерживает, но не навязывает. Современный код часто строится вокруг value semantics и шаблонов.
- **`class` vs `struct`** — только модификатор доступа по умолчанию. Соглашение: `struct` для просто-данных, `class` для классов с поведением.
- **`this`** — указатель на текущий объект внутри метода. Явно пишут редко.
- **Class scope:** методы класса видят все его поля и методы, включая `private`.
- **Модификаторы доступа:** поля — `private` по умолчанию. `friend` редко.
- **Конструкторы:** список инициализации (не присваивание в теле), default-конструктор (компилятор сгенерирует или попросите `= default`), делегирующие, копирующий, `explicit` для single-arg, `= default` / `= delete`.
- **Деструкторы:** освобождают ресурсы в обратном порядке. **Правило нуля, трёх и пяти** — большинство классов соответствуют правилу нуля.
- **`const`-методы**, `mutable` для логически const, `static`-поля и методы.
- **Aggregate init + designated initializers (C++20)** — стандартный способ инициализации структур-настроек.
