# Лекция 8. Шаблоны: введение

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему».

## 0. О чём эта лекция

Шаблоны — одна из самых **мощных** и одновременно одна из самых **сложных** частей C++. На них построены `std::vector`, `std::map`, `std::function`, `std::optional`, алгоритмы STL, и почти весь современный generic C++. Без шаблонов невозможно писать обобщённый код, который работает с разными типами без потери производительности.

Сегодня мы возьмём основу — синтаксис, модель компиляции, перегрузку, специализацию, non-type параметры, dependent names. На следующей лекции добавим variadic templates и fold expressions. Что лежит глубже — SFINAE, концепты, ranges, метапрограммирование — в курс не входит.

Подача намеренно практическая: доказывать Тьюринг-полноту системы типов здесь не нужно (она действительно такая, это просто следствие). Важнее показать, что и как пишут в реальном коде.

## 1. Зачем нужны шаблоны

В C, если нужна одна и та же функция для разных типов, приходится либо дублировать код, либо использовать макросы:

```cpp
int max_int(int a, int b)       { return a > b ? a : b; }
double max_d(double a, double b){ return a > b ? a : b; }
```

С шаблонами один код работает с любым типом:

```cpp
template <typename T>
T max_val(T a, T b) { return a > b ? a : b; }

max_val(3, 5);       // T = int
max_val(3.0, 5.0);   // T = double
max_val(std::string{"a"}, std::string{"b"});   // T = std::string
```

Важно понимать: шаблоны — это **не runtime-механизм**. Они не делают полиморфизм через виртуальные функции или интерпретатор. Шаблоны — это **инструкции компилятору**: «когда тебе понадобится `max_val` для типа `T`, сгенерируй её вот так». Это происходит на этапе **компиляции**.

В результате `max_val(3, 5)` и `max_val(3.0, 5.0)` — это **две разные функции** в бинарнике. Это называется **инстанцирование шаблона**.

Преимущества:

- **Нулевые накладные расходы.** Никаких виртуальных вызовов, никакого type erasure в рантайме.
- **Compile-time проверка типов.** Если `T` не поддерживает оператор `>` — ошибка на этапе компиляции, а не runtime exception.
- **Один код для всех типов.** DRY на уровне языка.

Цена:

- **Больше времени компиляции** — компилятор реально генерирует код для каждого использования.
- **Бóльший бинарник** — несколько инстанциаций одного шаблона = несколько функций в бинарнике.
- **Сложные ошибки.** Если шаблон используется неправильно, ошибки могут быть очень длинными (об этом — в разделе про концепты).

## 2. Шаблонные функции

Базовый синтаксис:

```cpp
template <typename T>
T add(T a, T b) {
    return a + b;
}
```

`template <typename T>` объявляет шаблонный параметр-тип. `typename` — ключевое слово, говорящее «параметр это тип». Существует исторический синоним `class T` — означает ровно то же самое (название обманчивое, `T` не обязан быть классом).

Использование:

```cpp
add(2, 3);              // T = int, выведено из аргументов
add<double>(2, 3);      // T = double, указали явно (int преобразуется)
add<int>(2.0, 3.0);     // T = int, double обрежется до int
```

Компилятор **выводит** тип из аргументов, если может. Если нет — нужно указать явно через `<...>`.

### Несколько параметров

```cpp
template <typename T, typename U>
auto pair_sum(T a, U b) {
    return a + b;
}

pair_sum(1, 2.5);   // T = int, U = double, результат — double (по правилам promotion)
```

Можно использовать тот же параметр несколько раз — это значит «все эти места должны быть одного типа»:

```cpp
template <typename T>
void swap_(T& a, T& b) {
    T tmp = a; a = b; b = tmp;
}
```

При вызове `swap_(1, 2.0)` будет CE — компилятор не может одновременно вывести `T = int` (из первого аргумента) и `T = double` (из второго).

### Когда нужно указать тип явно

Когда тип не выводится из аргументов:

```cpp
template <typename T>
T parse_number(const std::string& s);

parse_number<int>("42");      // ok, T = int
parse_number("42");           // CE: T не выводится
```

`T` здесь только в возвращаемом типе. Из аргументов вывести нельзя, поэтому указываем явно.

Также — когда хотим принудительно использовать конкретный тип, отличный от выведенного.

## 3. Шаблонные классы

```cpp
template <typename T>
class Stack {
public:
    void push(const T& x) { data_.push_back(x); }
    T pop() { T top = data_.back(); data_.pop_back(); return top; }
    size_t size() const { return data_.size(); }
private:
    std::vector<T> data_;
};

Stack<int> s_int;
Stack<std::string> s_str;
```

Несколько важных замечаний.

**`Stack<int>` и `Stack<std::string>` — это разные типы.** Они не имеют общего родителя. Нельзя написать `Stack<int>& ref = s_str;` — это разные классы, никак не связанные. Поэтому шаблоны называют **compile-time полиморфизмом**: общее «поведение» определено в шаблоне, но в рантайме каждый набор параметров — отдельный тип.

### Методы вне класса

Если определяете метод **снаружи** класса — нужно повторить шаблонную часть:

```cpp
template <typename T>
class Stack {
public:
    void push(const T& x);
};

template <typename T>            // ← здесь повторяем шаблонную часть
void Stack<T>::push(const T& x) {
    data_.push_back(x);
}
```

Имя метода — `Stack<T>::push`. То есть класс — `Stack<T>` (с указанием параметра), затем `::push`. Если параметров несколько — все нужны: `Pair<T, U>::set`.

Это синтаксически громоздко, и поэтому многие методы шаблонных классов определяются прямо внутри класса (это автоматически делает их `inline`).

## 4. CTAD — вывод параметров класса (C++17)

Заметьте асимметрию: для **функций** компилятор выводит `T` из аргументов автоматически (`add(2, 3)` — и он понял, что `T = int`), а для **классов** до C++17 приходилось писать параметр руками:

```cpp
std::vector<int> v{1, 2, 3};            // <int> обязательно
std::pair<int, double> p{1, 2.0};       // <int, double> обязательно
```

Это выглядело непоследовательно: информации для вывода достаточно (аргументы конструктора её содержат), но язык ей не пользовался. C++17 эту асимметрию убрал — появился **CTAD** (Class Template Argument Deduction):

```cpp
std::vector v{1, 2, 3};                 // CTAD: vector<int>
std::pair  p{1, 2.0};                   // CTAD: pair<int, double>
std::tuple t{1, 2.0, "x"};              // tuple<int, double, const char*>
std::array a{1, 2, 3};                  // array<int, 3> — и размер тоже выведен
```

### Как это работает

Компилятор берёт все конструкторы шаблонного класса и строит из них **неявные deduction guides** — набор «функций-кандидатов», по которым и происходит вывод параметров ровно так же, как для обычной шаблонной функции. Для большинства классов этого достаточно, и ничего писать не нужно:

```cpp
template <typename T>
struct Wrapper {
    T value;
};

Wrapper w{42};        // CTAD: Wrapper<int>
```

### Пользовательские deduction guides

Иногда параметр класса **не выводится** из аргументов конструктора напрямую. Классический случай — конструктор принимает пару итераторов, а параметр класса — тип элемента:

```cpp
template <typename T>
class Container {
public:
    template <typename It>
    Container(It begin, It end);        // T нигде не упомянут!
    // ...
};
```

Из `Container(v.begin(), v.end())` компилятор не может вывести `T` — в конструкторе есть только `It`. Тогда пишут **явный guide**:

```cpp
template <typename It>
Container(It, It) -> Container<typename std::iterator_traits<It>::value_type>;

std::vector<int> v;
Container c(v.begin(), v.end());        // Container<int>
```

Синтаксис читается так: «если конструктор вызван с двумя аргументами типа `It`, то класс — `Container<value_type от It>`». Именно так устроены guides у стандартных контейнеров.

Пользовательские deduction guides — инструмент **авторов библиотек**. В прикладном коде они почти не встречаются: там достаточно неявных. Знать полезно, чтобы понимать чужой код и не пугаться странного синтаксиса со стрелкой.

### Когда CTAD не срабатывает

Пара практических оговорок:

- **Нельзя вывести часть параметров.** Либо все, либо ни один: `std::pair<int> p{1, 2.0};` — CE.
- **Не работает для алиасов** (до C++20). `template <typename T> using Vec = std::vector<T>;` — `Vec v{1,2,3}` до C++20 не компилировалось.
- **Осторожно с `auto` и копированием.** `std::vector v2{v1};` даст не `vector<vector<int>>`, а копию `v1` — сработает copy-конструктор, а не конструктор от initializer_list. Это редкий, но неприятный сюрприз.

## 5. Алиасы и шаблонные константы

### Шаблонные алиасы (C++11)

Можно создавать «сокращения» для шаблонных типов:

```cpp
template <typename T>
using Vec = std::vector<T>;

Vec<int> v;            // эквивалент std::vector<int>
```

Полезно для:

- Сокращения длинных имён (`std::vector<std::pair<std::string, int>>` → `Pairs`)
- Связывания нескольких типов в один alias
- В type traits — почти все хелперы в стандартной библиотеке имеют форму `*_t`:
  ```cpp
  // в стандарте:
  template <typename T>
  using remove_const_t = typename remove_const<T>::type;
  ```

### Шаблонные константы (C++14)

```cpp
template <typename T>
constexpr T pi = T(3.1415926535897932385L);

double d = pi<double>;       // 3.14... в double
float  f = pi<float>;        // в float (с потерей точности)
```

Это удобный способ выразить «константа, тип которой зависит от параметра». В стандарте такая форма используется для `*_v` хелперов:

```cpp
// в стандарте:
template <typename T, typename U>
constexpr bool is_same_v = is_same<T, U>::value;
```

С этим вы будете встречаться постоянно при работе с type traits.

## 6. Модель компиляции шаблонов

Понимание этой части — ключ к чтению ошибок шаблонов.

### Два прохода

C++ компилирует шаблоны в **два прохода**:

1. **Первый проход** — при чтении определения шаблона. Проверяется синтаксис, имена, **не зависящие** от шаблонных параметров.
2. **Второй проход** — при **инстанцировании**, когда компилятор знает конкретный `T`. Проверяются зависимые от `T` имена.

```cpp
template <typename T>
void f() {
    syntax_error;        // CE на первом проходе — синтаксис плохой
    T::value;            // не проверяется до инстанцирования
}

// эта строка не вызовет ошибку, пока никто не сделает f<...>():
template void g();       // декларирует, но не использует

f<int>();                // вот здесь начинаются проблемы с T::value (если int::value нет)
```

Из этого следует контринтуитивный факт: **ошибки в шаблоне часто появляются не в файле, где он объявлен, а в файле, где он используется**. И конструкции «вверху ошибки» относятся к **месту использования**, потом к нескольким уровням инстанцирования, и только в самом низу — к строке в самом шаблоне.

Это и есть «template error spew» — простыни ошибок, которые так сложно читать. Концепты (C++20) сильно улучшают эту ситуацию.

### Шаблоны живут в заголовках

Чтобы инстанцировать шаблон, компилятор должен видеть **его определение** (не просто объявление, как у обычных функций).

```cpp
// header.h
template <typename T>
void f(T x) { /* тело */ }
```

```cpp
// main.cpp
#include "header.h"
int main() { f(42); }     // тело f должно быть видно здесь
```

Это означает, что **определения шаблонов** обычно живут **в заголовочных файлах**, не в `.cpp`. Альтернатива — **явная инстанциация**, но она используется редко и в курсе не покрывается.

Прямое следствие — добавление шаблонов в заголовок увеличивает время компиляции **всех** включающих этот заголовок файлов. В больших проектах это серьёзная проблема. Современная попытка её решить — **модули** C++20, но они пока широко не поддерживаются.

## 7. Перегрузка шаблонов

Шаблонную функцию можно перегружать обычной, шаблонной с другими параметрами, и более специализированной:

```cpp
void f(int x)         { std::print("int\n"); }              // 1
template <typename T>
void f(T x)           { std::print("template T\n"); }        // 2
template <typename T>
void f(T* x)          { std::print("template T*\n"); }       // 3

f(42);          // 1: обычная функция предпочтительнее шаблона
f(42.0);        // 2: T = double
int* p = nullptr;
f(p);           // 3: T = int*, более специализированный шаблон
```

Правила разрешения перегрузки шаблонов:

1. Если есть **обычная (не-шаблонная) функция**, удовлетворяющая аргументам — она выигрывает у шаблона.
2. Среди шаблонов **более специализированный** выигрывает у менее специализированного. `void f(T*)` более специализирован, чем `void f(T)`, потому что `T*` — это уже не любой `T`, а только указатель.
3. Если есть ничья — CE «ambiguous call».

Эти правила — упрощённая версия overload resolution. Полный алгоритм — отдельная тема, которая всплывает редко.

## 8. Специализация шаблонов

### Полная специализация

Когда нужна **отдельная реализация для конкретных параметров**:

```cpp
template <typename T>
struct TypeName { static constexpr const char* name = "?"; };

template <>
struct TypeName<int> { static constexpr const char* name = "int"; };

template <>
struct TypeName<double> { static constexpr const char* name = "double"; };

TypeName<int>::name;       // "int"
TypeName<char>::name;      // "?"
```

Синтаксис `template <>` (пустые угловые скобки) означает «полная специализация». Внутри — указываем конкретное значение параметра в `<>` после имени класса.

Полная специализация работает и для **функций**, и для **классов**.

### Частичная специализация

**Только для классов!** Часть шаблонных параметров фиксируется, часть остаётся свободной — это и есть «частично»:

```cpp
template <typename T, typename U>
struct Encoder { /* general implementation */ };

// частичная: U зафиксирован как string, T всё ещё свободный
template <typename T>
struct Encoder<T, std::string> { /* T-to-string encoder */ };

// полная: оба параметра зафиксированы
template <>
struct Encoder<int, std::string> { /* int-to-string, specifically */ };
```

При использовании компилятор выбирает «самую специфичную» подходящую специализацию:

```cpp
Encoder<double, std::string>   // частичная (T = double, U = string)
Encoder<int,    std::string>   // полная (точнее частичной)
Encoder<int,    int>           // primary template (никакая спец. не подошла)
```

«Специфичность» — это отношение «один паттерн строго уже другого». Полная специализация всегда специфичнее любой частичной. Частичная с двумя зафиксированными параметрами — специфичнее частичной с одним. И так далее.

Через эти паттерны строится **большая часть type traits**, **SFINAE**, многие фичи стандартной библиотеки. Писать такое с нуля в курсе не понадобится, а узнавать в чужом коде — да.

Пример с одним параметром тоже работает и часто встречается:

```cpp
template <typename T>
struct IsPointer { static constexpr bool value = false; };

template <typename T>
struct IsPointer<T*> { static constexpr bool value = true; };
```

Здесь `T*` — это паттерн «указатель на что-то». Если шаблонный аргумент имеет такую форму — выбирается специализация, где `T` — это «то, на что указатель».

### Для функций — только полная специализация

```cpp
template <typename T>
T abs_val(T x);

template <>
int abs_val(int x);       // полная специализация для T = int

template <typename T>
T* abs_val(T* x);         // НЕ частичная специализация — новый шаблон-перегрузка
```

Третья строка **компилируется**, но это **не** частичная специализация (их для функций не существует), а **отдельный шаблон, который участвует в перегрузке** наравне с первым. Работает по правилам разрешения перегрузки: более специализированный шаблон побеждает менее (мы это видели в разделе 6).

Это правило плохо известно — многие думают, что синтаксис `T* abs_val(T*)` создаёт partial specialization для первого шаблона. Это не так. Это новый шаблон, который участвует в overload resolution.

На практике для функций «частичная специализация» обычно не нужна — её роль играет перегрузка шаблонов, и она часто даже лучше: участвует в обычных правилах overload resolution и работает с разрешением по аргументам, а не по типу самого шаблона.

## 9. Шаблонные аргументы по умолчанию

Шаблонным параметрам можно дать значения по умолчанию:

```cpp
template <typename T = int>
struct Container {
    T value;
};

Container<> c1;            // T = int
Container<double> c2;      // T = double
```

Они могут зависеть от **предыдущих параметров**:

```cpp
template <typename T, typename Alloc = std::allocator<T>>
class vector { /* ... */ };
```

Так устроены практически все контейнеры STL: `std::vector<T>` это на самом деле `std::vector<T, std::allocator<T>>`, а `std::map<K, V>` — `std::map<K, V, std::less<K>, std::allocator<std::pair<const K, V>>>`. Устройство аллокаторов в курс не входит.

## 10. Non-type template parameters

В шаблон можно передать не только тип, но и **значение**:

```cpp
template <typename T, size_t N>
class Array {
public:
    T data[N];
    constexpr size_t size() const { return N; }
};

Array<int, 5> a;       // массив из 5 int на стеке
```

Так устроен `std::array<T, N>`. `N` — это **число**, известное на этапе компиляции, и `Array<int, 5>` и `Array<int, 6>` — это **разные типы**.

### Что разрешено как non-type параметр

- Целочисленные типы: `int`, `size_t`, `bool`, `char`, любые из `<cstdint>`
- Указатели и ссылки на функции / глобальные объекты (с особенностями)
- `enum`-значения
- С C++20 — почти любые «structural types»: пользовательские структуры со всеми `constexpr`-доступными полями

```cpp
template <bool LoudErrors>
class Logger { /* ... */ };

Logger<true> verbose;     // одна инстанциация
Logger<false> silent;     // другая
```

### Что не разрешено

- `float`, `double` — до C++20 нельзя; с C++20 в составе structural types можно
- `std::string` (это не trivially-copyable) — нельзя как non-type параметр
- Указатели на временные объекты, объекты с автоматическим временем жизни

Хороший приём — `bool` non-type параметры для compile-time переключения поведения класса. Это позволяет компилятору соптимизировать неактивную ветку до нуля.

## 11. Зависимые имена

В шаблонном коде часто возникает ситуация: имя зависит от `T`, и компилятор на первом проходе **не знает**, что это — тип или значение.

```cpp
template <typename T>
void f() {
    T::value_type x;     // CE: parser doesn't know what T::value_type is
}
```

С точки зрения парсера, `T::value_type` это просто «что-то из `T`». Это может быть:

- Тип (`typedef int value_type;` или `using value_type = int;`)
- Статический член (`static int value_type;`)
- Шаблонный класс (`template <...> struct value_type;`)

Компилятор по умолчанию считает, что **это значение**, не тип. Поэтому `T::value_type x;` парсится как «умножение `T::value_type` на `x`» (как `value * x`) — что синтаксически неправильно.

### `typename` disambiguator

Чтобы сказать «это тип», используется ключевое слово `typename`:

```cpp
template <typename T>
void f() {
    typename T::value_type x;     // ok: parser теперь знает, что это тип
}
```

Это часто нужно при работе со стандартными контейнерами:

```cpp
template <typename Container>
void g(Container& c) {
    typename Container::iterator it = c.begin();
    // ...
}
```

Без `typename` будет CE «`Container::iterator` does not name a type».

С C++20 во многих случаях `typename` стал необязательным — компилятор научился сам распознавать, когда контекст требует тип. Но для кода, который должен компилироваться и старыми компиляторами, лучше оставлять.

### `template` disambiguator

Аналогичная проблема — когда зависимое имя это **шаблонный метод**:

```cpp
template <typename T>
void f(T t) {
    t.template foo<int>();    // ← template нужно, иначе CE
}
```

Без `template` парсер пытается интерпретировать `t.foo<int>` как «сравнение `t.foo` с `int`, потом `>`». С `template` — «шаблонный метод `foo` с параметром `int`».

Это та же история, что с `typename`: синтаксические подсказки парсеру.

### Правило

Если в шаблонном коде вы используете что-то из `T::...`, и это **тип** — пишите `typename`. Если это **шаблонный метод/класс** — пишите `template`. В обычном коде, где `T` известен, эти слова не нужны — но и не вредят.

## 12. Концепты — упоминание (C++20)

Главная боль шаблонов исторически — ошибки. Если код шаблона использует что-то, что у `T` не поддерживается, компилятор выдаёт огромную простыню из глубины инстанцирования.

```cpp
template <typename T>
T sum(const std::vector<T>& v) {
    T result{};
    for (auto x : v) result += x;
    return result;
}

struct NoAdd {};
sum<NoAdd>(...);   // ошибка простыней на 100+ строк
```

C++20 решает эту проблему через **концепты** — способ выразить требования к `T` явно:

```cpp
template <std::integral T>
T add(T a, T b) { return a + b; }
```

Если ограничение не выполнено — компилятор пишет читаемое сообщение: «`T` должен удовлетворять concept `std::integral`».

Концепты — большая отдельная тема, и целиком она в курс не входит. Сейчас знайте, что эта возможность есть, и встретив `std::integral T` или `std::ranges::range R` в чьём-то коде — будете понимать, что происходит.

## 13. `constexpr` — упоминание

Шаблонные функции часто **вычислимы на этапе компиляции**, если их пометить `constexpr`:

```cpp
template <typename T>
constexpr T square(T x) { return x * x; }

constexpr int x = square(5);    // 25, вычислено компилятором
int y = square(42);              // тоже работает, в рантайме
```

`constexpr`-функция может выполняться на компиляции, если все аргументы — `constexpr`. Иначе работает в рантайме как обычная функция.

К C++20 значительная часть `<algorithm>`, `<numeric>` и даже `std::vector` стали `constexpr`. Это позволяет писать **на C++ программы, работающие во время компиляции** — `constexpr`-метапрограммирование.

Полный разбор `constexpr`, `consteval`, `constinit` и виртуальных `constexpr`-функций остаётся за рамками курса.

## Итоги

- **Шаблон** — инструкция компилятору, как генерировать код для каждого набора параметров. Это compile-time механизм.
- **Инстанцирование** — генерация конкретной функции/класса для конкретных параметров.
- **Шаблонные функции, классы, алиасы, константы** — все эти формы есть в языке. Алиасы (`using`) и константы (`constexpr T name`) активно используются в type traits.
- **Двухпроходная компиляция:** ошибки часто всплывают в месте использования, а не в месте определения шаблона.
- **Шаблоны живут в заголовках** — это следствие модели инстанцирования.
- **Перегрузка:** не-шаблон лучше шаблона, более специализированный шаблон лучше менее.
- **Специализация:** полная для функций и классов, частичная — **только для классов**. Для функций вместо частичной — перегрузка шаблонов.
- **Аргументы по умолчанию** работают и для шаблонов, могут зависеть от предыдущих.
- **Non-type template parameters** — целые типы и значения. Каждое значение → отдельный тип.
- **Dependent names:** `typename` если это тип, `template` если шаблонный метод.
- **Концепты (C++20)** делают ошибки шаблонов читаемыми. Подробный разбор — за рамками курса.
- **`constexpr`-шаблоны** — большая часть стандартной библиотеки сейчас `constexpr`.
