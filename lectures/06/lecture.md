# Лекция 6. Наследование

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему».

## 0. О чём эта лекция

Это вторая лекция про классы. На лекции 4 мы научились их **создавать**: поля, методы, конструкторы, деструкторы, агрегатная инициализация. На лекции 5 — **давать им поведение в выражениях** через перегрузку операторов. Сегодня — **строить из классов иерархии**, чтобы один класс мог переиспользовать функциональность другого.

Сразу два предупреждения. Во-первых, в современном C++ наследование используется **реже**, чем в Java или Python; чаще предпочитают композицию или шаблоны. Мы это обсудим в первом разделе. Во-вторых, **multiple inheritance** и **виртуальное наследование** — особенности именно C++, в большинстве других OOP-языков их нет. Они существуют не как «крутые фичи», а как ответ на конкретные ситуации.

К концу лекции вы должны:

- Уметь объявить класс-наследник, понимать модель доступа.
- Знать, в каком порядке вызываются конструкторы и деструкторы, как передавать аргументы в конструктор базы.
- Понимать раскладку объекта в памяти при одиночном и множественном наследовании, и почему `static_cast` в multiple inheritance может сдвигать указатель.
- Понимать суть ромбовидной проблемы и роль виртуального наследования.

**Виртуальные функции и полиморфизм** — следующая лекция. Здесь мы говорим только про устройство иерархии, без `virtual`-методов.

## 1. Идея наследования

Наследование позволяет одному классу получить **поля и методы другого**:

```cpp
class Animal {
public:
    void breathe() { std::print("breathing\n"); }
    int age = 0;
};

class Dog : public Animal {
public:
    void bark() { std::print("woof\n"); }
};

Dog d;
d.breathe();   // унаследовано
d.bark();      // своё
d.age = 5;     // унаследованное поле
```

`Dog` — это **подтип** `Animal`. Где работает `Animal` — работает `Dog`. Это и есть отношение **«is-a»**.

### Когда наследование уместно

Наследование оправдано в двух случаях:

1. **Подмена типов (subtyping).** Функция принимает `Base*`, передаём `Derived*`, всё работает. На этом построен полиморфизм — следующая лекция.
2. **Расширение интерфейса.** Производный класс **добавляет** новые методы или **меняет поведение** существующих. Без `virtual` — только добавляет; с `virtual` — может менять.

В **большинстве остальных** случаев композиция (объект как поле) лучше:

```cpp
class Engine { /* ... */ };

class Car {
    Engine engine_;          // композиция: Car HAS an Engine
};
```

vs.

```cpp
class Car : public Engine { /* ... */ };   // наследование: Car IS an Engine
```

Второе обычно неверно: машина не является двигателем, она его использует. Композиция гибче (можно заменить `engine_` в рантайме), не создаёт жёстких иерархий, не имеет проблем multiple inheritance.

**Правило:** «is-a» — наследование, «has-a» — композиция. Когда сомневаетесь — берите композицию. С чисто практической стороны: композиция меньше связывает классы, и потом проще менять архитектуру.

## 2. Модификаторы наследования

```cpp
class Dog : public    Animal { /* ... */ };
class Dog : protected Animal { /* ... */ };
class Dog : private   Animal { /* ... */ };
```

Модификатор указывает, **с какой стороны** становятся видны члены базы через наследник. Это влияет на то, что **снаружи** наследника может делать пользователь его кода.

Внутри самого `Dog` все члены `Animal` (кроме `private`) видны независимо от модификатора наследования. Поэтому модификатор — это про **внешний интерфейс**, не про внутренний доступ.

### Таблица «что становится с членами»

| Член `Animal` | `public` наследование | `protected` | `private` |
|---|---|---|---|
| `public` | `public` в `Dog` | `protected` | `private` |
| `protected` | `protected` | `protected` | `private` |
| `private` | недоступен | недоступен | недоступен |

Два ключевых наблюдения:

1. **`private`-члены базы всегда недоступны наследнику** — независимо от модификатора наследования. Они принадлежат только базе.
2. Модификатор наследования **только понижает** видимость. Через `public` наследование `private`-член не станет публичным.

### Какой когда

- **`public`** — почти всегда. Это «is-a» в обычном смысле. `Dog` — это публичный `Animal`, его можно использовать везде, где ожидается `Animal&`.
- **`protected`** — редко. Идея «наследовать реализацию, но не интерфейс»: пользователю `Dog` не нужно знать, что он `Animal`, но `Dog`-наследники этим пользуются.
- **`private`** — практически никогда. Эквивалент композиции через поле, но синтаксически уродливее.

В обычном прикладном коде вы пишете `public` в 99% случаев. Если ставите что-то другое — задумайтесь, не подойдёт ли композиция лучше.

### Дефолт-модификатор

```cpp
class A : B { /* private наследование, частая ошибка */ };
class A : public B { /* то, что обычно хотят */ };
```

У `class` без модификатора наследование **`private`** по умолчанию. У `struct` — **`public`**. Это та же история, что с членами: `class` всё прячет, `struct` всё показывает.

**Привычка:** всегда писать `public` явно. Не полагайтесь на дефолт — это слишком тонкая разница, на ней постоянно ошибаются.

## 3. Расположение в памяти

Объект наследника содержит **полную копию** базы плюс свои поля:

```cpp
class A { int a; };
class B : public A { int b; };

sizeof(B);                  // 8
```

Раскладка в памяти:

```
[ A::a ][ B::b ]
  0-3    4-7
```

Базовый класс **в начале** объекта. Это важно — даёт возможность смотреть на `B*` как на `A*` без сдвига указателя.

### С учётом выравнивания

```cpp
class A { int a; };              // 4 байта, align 4
class B : public A { double b; };// 8 байт, align 8

sizeof(B);                       // 16
```

Раскладка:

```
[ A::a ][ padding ][   B::b   ]
  0-3      4-7        8-15
```

Padding появляется, потому что `double` требует выравнивания 8, а после `int a;` мы стоим на адресе 4. Это те же правила выравнивания, что и в одной структуре с полями `int a; double b;`. Подробный разбор правил выравнивания выходит за рамки курса.

### Upcast: указатель базы на наследника

Поскольку `A` лежит в начале `B`, указатель на `A` совпадает по адресу с указателем на `B`:

```cpp
B b;
A* pa = &b;       // ok при public наследовании
A& ra = b;        // то же со ссылкой
pa->a;            // ok: A знает про свои поля
// pa->b;         // CE: A не знает про B::b
```

Этот **неявный upcast** работает только при `public` наследовании — иначе компилятор запретит, потому что снаружи `B` не публично «является» `A`. С `private` наследованием вы можете upcast'ить **внутри** `B` (там видимость есть), но не снаружи.

С указателями и наследованием связано целое семейство кастов — обычные (`static_cast`) для compile-time преобразований и `dynamic_cast` для рантайм-проверки. Подробно — на следующей лекции, когда добавим виртуальные функции.

### Срезка

Указатель и ссылка на базу работают безобидно: они просто *смотрят* на объект, ничего не копируя. А вот присваивание **по значению** ведёт себя принципиально иначе:

```cpp
B b;
A a = b;          // компилируется без единого предупреждения
```

Разберём, что здесь произошло, опираясь на только что разобранный layout. Переменная `a` имеет тип `A`, а значит занимает ровно `sizeof(A)` байт. В объекте `b` подобъект `A` лежит в начале, и копирующий конструктор `A` знает только про свои поля — он скопирует их и остановится. Всё, что добавлял `B`, в `a` просто не поместилось и было **отрезано**.

Это явление называется **срезкой** (object slicing). Ключевой момент, который делает её опасной: с точки зрения языка ничего плохого не произошло. Компилятор промолчит, программа не упадёт, `a` — совершенно корректный объект типа `A`. Просто это уже не тот объект, который вы копировали.

Сформулируем причину одной фразой: **указатель и ссылка смотрят на объект, значение копирует ровно свой размер**. Пока вы работаете через `A*` или `A&`, объект остаётся собой; как только он попал в переменную типа `A`, от него осталась только базовая часть.

Отсюда — два места, где срезка реально кусается.

**Первое: передача в функцию.**

```cpp
void handle(A a);          // срежет любого наследника
void handle(const A& a);   // не срежет
```

Именно поэтому на лекции 3, обсуждая четыре способа передачи, мы говорили: полиморфные объекты передают по `const&`. Тогда аргументом была экономия на копировании; теперь видно, что дело не только в ней.

**Второе: ловля исключений.** На лекции 3 было сказано «исключения ловят по `const&`» и обещано объяснить, почему. Вот объяснение:

```cpp
try {
    throw std::invalid_argument("bad port");
} catch (std::exception e) {          // срезка!
    std::print("{}\n", e.what());     // напечатает generic-текст базового класса
}
```

Брошен был `std::invalid_argument`, а поймали по значению базового `std::exception` — копия получилась базовой, и вся конкретика потерялась. Проверить это можно за минуту: первый вариант печатает родовое `std::exception`, второй — переданный текст `bad port`. Исправление — одна пара символов:

```cpp
} catch (const std::exception& e) {   // ссылка: объект остался собой
```

Небольшая, но приятная оговорка: конкретно для `catch` компиляторы научились предупреждать — GCC и Clang выдают `-Wcatch-value`, если ловить полиморфный тип по значению. А вот про обычное `A a = b;` не предупредит никто: там срезка может быть и вполне намеренной, и отличить её от ошибки компилятор не в состоянии.

**Правило:** объекты полиморфных иерархий передают, хранят и ловят по ссылке или указателю. По значению — только когда вы точно знаете конкретный тип и хотите именно копию.

## 4. Порядок конструкторов и деструкторов

При создании объекта-наследника конструкторы вызываются в строгом порядке:

```cpp
class A {
public:
    A() { std::print("A()\n"); }
    ~A() { std::print("~A()\n"); }
};

class B : public A {
public:
    B() { std::print("B()\n"); }
    ~B() { std::print("~B()\n"); }
};

{ B b; }
// A()
// B()
// ~B()
// ~A()
```

Порядок конструкторов: **база → поля наследника → тело конструктора наследника**.
Порядок деструкторов: **обратный** — тело деструктора наследника → поля → база.

### Передача аргументов в конструктор базы

Если у базы **нет default-конструктора**, нужно вызвать её конструктор явно, в списке инициализации:

```cpp
class A {
public:
    A(int x) : x_(x) {}
    int x_;
};

class B : public A {
public:
    B(int x, int y) : A(x), y_(y) {}    // вызываем A(int)
    int y_;
};

B b(1, 2);     // A::x_ = 1, B::y_ = 2
```

Вызов конструктора базы пишется **в списке инициализации** наследника, **до** своих полей. Если не написать — компилятор попробует вызвать default-конструктор базы, и если его нет — CE.

### Полный порядок при создании `Derived`

1. Виртуальные базы (если есть, см. дальше)
2. Обычные базы — **в порядке объявления** `class D : A, B, C { }` (то есть `A` → `B` → `C`)
3. Поля `Derived` — **в порядке объявления в классе** (не в порядке в списке инициализации!)
4. Тело конструктора `Derived`

Деструкторы — **зеркально обратный** порядок. Полностью симметрично и детерминированно. Полезное упражнение — мысленно проиграть для класса с двумя базами и тремя полями.

## 5. Множественное наследование

В отличие от Java или Python (где нет multiple inheritance в чистом виде), C++ разрешает наследоваться **от нескольких классов**:

```cpp
class Walker  { public: void walk() { std::print("walk\n"); } };
class Swimmer { public: void swim() { std::print("swim\n"); } };

class Duck : public Walker, public Swimmer {};

Duck d;
d.walk();
d.swim();
```

Главный use case — **миксины**: независимые наборы функциональности комбинируются в один класс. Класс `Duck` получает способность ходить от `Walker` и плавать от `Swimmer`. В Java это были бы `interface` + composition; в C++ — обычные базовые классы.

Базовая идея простая. Сложности начинаются, когда классы-базы пересекаются (см. ромб ниже) или когда нужно понять layout.

### Порядок ctor с несколькими базами

При создании `Duck` базы конструируются **в порядке объявления** в списке наследования:

```cpp
class Duck : public Walker, public Swimmer { /* ... */ };
// 1. Walker()
// 2. Swimmer()
// 3. Duck::Duck() тело
// Деструкторы — обратно.
```

**Порядок в списке инициализации не имеет значения** — компилятор всё равно вызовет в порядке объявления. И в списке инициализации можно перечислить базы в любом порядке.

### Расположение в памяти

```cpp
class A { int a; };
class B { int b; };
class C : public A, public B { int c; };

sizeof(C);   // 12
```

Layout:

```
[ A::a ][ B::b ][ C::c ]
  0-3    4-7    8-11
```

Базы лежат **подряд**, в порядке объявления. После них — собственные поля наследника.

### Подвох: upcast в multiple inheritance сдвигает указатель

Это важное следствие layout — у одиночного наследования такого нет:

```cpp
C c;
A* pa = &c;       // pa == &c (адрес 0)
B* pb = &c;       // pb == &c + 4 (адрес 4!)
```

`A` лежит в начале объекта `C` (адрес 0), а `B` — на смещении 4 (после `A`). Поэтому `static_cast<B*>(&c)` не просто меняет тип указателя — он **сдвигает значение** на смещение `B` внутри `C`.

В одиночном наследовании этого не было: указатель на `A` совпадал с указателем на `B`, потому что `A` лежала в начале. В multiple inheritance это работает только для **первой** базы; для остальных компилятор молча сдвигает указатель при касте.

Это не баг — это следствие layout. Просто помните: при работе с multiple inheritance касты между базами и наследником **могут менять значение указателя**.

## 6. Ромбовидное наследование

Когда у двух промежуточных классов общая база — получается **ромб**:

```cpp
class Animal { public: int id; };
class Walker  : public Animal { /* ... */ };
class Swimmer : public Animal { /* ... */ };
class Duck    : public Walker, public Swimmer {};
```

Структура:

```
       Animal
       /    \
   Walker  Swimmer
       \    /
        Duck
```

Проблема: в объекте `Duck` теперь **две копии** `Animal` — одна пришла через `Walker`, одна через `Swimmer`. Они независимы.

### Что ломается

```cpp
Duck d;
d.id = 5;          // CE: ambiguous, какая копия id?

d.Walker::id = 5;  // нужно явно: id из Walker-ветки
d.Swimmer::id = 6; // другая копия
```

Это **редко** то, что мы хотим. Обычно `Animal` должен быть один — у одной утки одно `id`. Кроме семантической неоднозначности, это и лишняя память (две копии всех полей `Animal`).

## 7. Виртуальное наследование

Чтобы базовый класс был **один** в ромбе, наследование от него помечается `virtual`:

```cpp
class Animal { public: int id; };
class Walker  : virtual public Animal { /* ... */ };
class Swimmer : virtual public Animal { /* ... */ };
class Duck    : public Walker, public Swimmer {};

Duck d;
d.id = 5;       // ok, теперь одна копия Animal
```

`virtual` стоит на **обоих** промежуточных классах. Это говорит компилятору: «в финальном классе пусть будет одна общая `Animal`».

### Цена и почему его избегают

- **Лишний уровень индирекции** при доступе к виртуальной базе. Компилятор хранит указатель на «реальное место» базы в объекте.
- **Конструктор виртуальной базы вызывается из самого нижнего класса** (`Duck`), а не из промежуточных. Это делает иерархию хрупкой: добавляешь промежуточный класс — надо переписывать вызовы.
- Сложнее layout, сложнее кастовать.

В **реальном** прикладном коде ромбовидное наследование избегают как класс. Если кажется, что оно нужно — обычно стоит:

- Заменить промежуточный класс на интерфейс (чисто виртуальная база без полей)
- Использовать композицию вместо части наследований
- Пересмотреть дизайн

Виртуальное наследование встречается в основном в **библиотечном** коде (классический пример — иерархия потоков `iostream`). В прикладном — почти никогда.

## Итоги

- **«is-a» — наследование, «has-a» — композиция.** В сомнении — композиция.
- **Модификаторы наследования:** `public` (99% случаев), `protected` (редко), `private` (почти никогда). Дефолт у `class` — `private`, у `struct` — `public`; всегда пишите явно.
- **Layout:** база в начале, потом поля наследника, плюс выравнивание.
- **Срезка:** копирование наследника в переменную базового типа отрезает всё, что добавил наследник, — молча. Полиморфные объекты передают и ловят по ссылке или указателю.
- **Порядок ctor:** базы (по объявлению) → поля (по объявлению в классе) → тело. Dtor — обратно. Базу с параметрами вызывают в списке инициализации.
- **Multiple inheritance:** базы лежат подряд в памяти. Upcast между базами может сдвигать значение указателя.
- **Ромб:** две копии общей базы, обычно нежелательно. Решается `virtual` наследованием, но в реальном коде его избегают.
