## 0. О чём эта лекция

Прошлая лекция была про память и указатели — низкоуровневые механики. Эта лекция — про инструменты, которые превращают эти механики в **выразительный код**. Функции с перегрузкой и аргументами по умолчанию, ссылки как замена «по указателю», правильная работа с `const`, четыре способа преобразовать тип в современном C++ — и, в финале, вопрос, который до сих пор оставался за скобками: что делает функция, когда не может выполнить то, ради чего её позвали.

Последний раздел стоит здесь не случайно. Разговор об ошибках даст недостающее обоснование прошлой лекции: вы увидите, что RAII и умные указатели — не удобство, а единственный способ не терять ресурсы, когда по коду ходят исключения.

К концу лекции вы должны:

- уметь перегружать функции и понимать, как компилятор выбирает перегрузку;
- различать ссылку и указатель и осознанно выбирать один из четырёх способов передачи аргумента;
- правильно применять `const` и знать, какой каст в какой ситуации уместен;
- уметь сообщить об ошибке из функции обоими базовыми механизмами и объяснить, почему в присутствии исключений ручной `delete` некорректен.

## 1. Функции

### Основы

Функция — именованный блок кода с типами параметров и возвращаемым типом:

```cpp
int add(int a, int b) {
    return a + b;
}
```

`void` означает «функция не возвращает значения». `return` без аргумента (или его отсутствие в конце) допустимы для `void`-функций.

### Объявление и определение

Полезно различать:

```cpp
int add(int a, int b);          // объявление (прототип)

int add(int a, int b) {         // определение
    return a + b;
}
```

Объявление сообщает компилятору сигнатуру функции — её можно вызывать. Определение — собственно тело. Обычно объявления складывают в заголовочные файлы (`.h`), а определения — в исходники (`.cpp`).

В программе функция должна быть **определена ровно один раз** (One Definition Rule). Если её случайно определить дважды — будет ошибка линковки.

### Аргументы по умолчанию

```cpp
void greet(const std::string& name, bool loud = false) {
    if (loud) std::print("HELLO, {}!\n", name);
    else      std::print("Hello, {}.\n", name);
}

greet("Anna");          // loud = false
greet("Anna", true);    // loud = true
```

Несколько правил:

- Значения по умолчанию идут **только подряд справа**. Нельзя `void f(int a = 0, int b)` — `b` должен быть либо тоже с умолчанием, либо левее `a`.
- Объявляются **в заголовочном файле**, где находится прототип. В `.cpp`-определении умолчания не повторяются.
- Не путать с **перегрузкой**: значения по умолчанию — это та же функция, просто с возможностью опустить аргументы. Перегрузка — две разные функции.

### Перегрузка функций

В C++ можно иметь несколько функций с одним именем — компилятор выберет нужную по типам аргументов:

```cpp
int max(int a, int b)         { return a > b ? a : b; }
double max(double a, double b){ return a > b ? a : b; }

max(3, 5);       // вызовется int-версия
max(3.0, 5.0);   // вызовется double-версия
```

Важная деталь — **возвращаемый тип в сигнатуру для перегрузки не входит**:

```cpp
int f();
double f();      // CE: redefinition
```

Это исторически: если бы возврат участвовал, выражение `f()` в контексте `auto x = f();` стало бы амбивалентным.

### Разрешение перегрузки

Когда вы вызываете функцию, компилятор проходит примерно такой алгоритм:

1. Собрать все видимые функции с этим именем — это **набор кандидатов**.
2. Для каждого кандидата посмотреть, как привести **тип каждого аргумента** к типу параметра. Есть иерархия преобразований: точное совпадение лучше всего, неявные конверсии хуже, пользовательские конверсии — ещё хуже.
3. Найти **наилучшего кандидата**. Если их два одинаковых — ошибка `ambiguous call`.

```cpp
void f(int);
void f(double);
f(5);          // f(int) — точное совпадение
f(5.0);        // f(double) — точное
f(5.0f);       // CE: float конвертируется и в int, и в double одинаково
```

Полные правила раскрываются на лекции 8, когда добавятся шаблоны (там они становятся гораздо хитрее).

### Указатель на функцию

Функция имеет адрес и может храниться в указателе:

```cpp
int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

int (*op)(int, int) = add;
std::print("{}\n", op(2, 3));   // 5

op = sub;
std::print("{}\n", op(2, 3));   // -1
```

Синтаксис тяжёлый — `int (*op)(int, int)` читается как «`op` — указатель на функцию, принимающую `(int, int)` и возвращающую `int`». В современном коде вместо этого используются **лямбды** и `std::function` (лекция 10) — они выразительнее, поддерживают захват состояния и удобнее в шаблонах.

### `inline`

`inline` исторически означало «подставь тело функции по месту вызова, чтобы избежать накладных расходов на вызов». Современные компиляторы решают это сами, на основе профиля и эвристик.

В сегодняшнем C++ **главное значение `inline`** — это разрешение определять функцию в **заголовочном файле**, не нарушая ODR. Без `inline` определение функции в `.h`, которое попадает в несколько `.cpp`, привело бы к ошибке линковки. С `inline` — компилятор «договаривается» с линкером оставить одну копию.

```cpp
// utils.h
inline int square(int x) { return x * x; }
```

Шаблонные функции и `constexpr`-функции **автоматически inline** в этом смысле. Также методы, определённые внутри тела класса.

### `constexpr` — упоминание

```cpp
constexpr int factorial(int n) {
    return n <= 1 ? 1 : n * factorial(n - 1);
}

constexpr int f5 = factorial(5);   // вычислено на этапе компиляции
```

`constexpr` функция **может** быть вычислена на этапе компиляции — если все её аргументы известны компилятору. Если нет — выполнится в рантайме как обычная функция.

Полный разбор `constexpr` (и более новых `consteval`, `constinit`) выходит за рамки курса. Сейчас запомните практическое правило: **если функцию реально можно вычислить на компиляции — пишите `constexpr`**. Это даёт компилятору больше свободы и не накладывает ограничений.

## 2. Ссылки

### Что это

**Ссылка** — это второе имя для существующего объекта. После создания она навсегда привязана к своему объекту:

```cpp
int x = 5;
int& y = x;        // y — другое имя для x

y = 10;
std::print("{}\n", x);   // 10
```

В отличие от указателя, ссылку **нельзя «переадресовать»**. Запись `y = z;` — это не «теперь y ссылается на z», а «положи значение z в x».

С точки зрения сгенерированного кода ссылка обычно реализуется как указатель — но **семантически** это не указатель, а синоним объекта.

### Сравнение с указателями

| | Ссылка `T&` | Указатель `T*` |
|---|---|---|
| Может быть пустой | нет | да (`nullptr`) |
| Должна быть инициализирована | да | нет |
| Можно «переадресовать» | нет | да |
| Синтаксис доступа | как обычная переменная | через `*` и `->` |
| Можно сделать массив | нет | да |

**Правило выбора:**

- объект **гарантированно существует**, и метод не нужно «менять цель» → ссылка
- объект может **отсутствовать**, или нужно «менять цель» → указатель (или `std::optional`)

### Пример: `swap`

Классический пример пользы ссылок:

```cpp
void swap_bad(int a, int b) {
    int tmp = a; a = b; b = tmp;   // меняет копии — оригиналы не задеты
}

void swap_good(int& a, int& b) {
    int tmp = a; a = b; b = tmp;
}

int x = 1, y = 2;
swap_good(x, y);
std::print("{} {}\n", x, y);   // 2 1
```

В стандартной библиотеке для этого есть `std::swap`. И впоследствии у нас появится более эффективная версия через move-семантику.

### Возврат ссылки из функции

Иногда удобно возвращать **ссылку**, чтобы вызывающий получил «прямой доступ» к объекту:

```cpp
int& first(std::vector<int>& v) {
    return v[0];
}

std::vector<int> v = {1, 2, 3};
first(v) = 42;
std::print("{}\n", v[0]);   // 42
```

Так устроены, например, `operator[]` у `std::vector` и `std::map` — они возвращают ссылку на элемент, чтобы можно было `v[i] = x` или `m[key] = value`.

### Опасность: dangling reference

Главная ошибка — вернуть ссылку на **локальную переменную**:

```cpp
int& bad() {
    int x = 5;
    return x;        // UB: x умрёт по выходу из функции
}

int& y = bad();
std::print("{}\n", y);   // UB
```

`x` живёт на стеке функции `bad()`. По её возврату стек уже не валиден, и ссылка указывает в никуда. Современные компиляторы предупреждают про это (флаг `-Wreturn-local-addr`), но не во всех ситуациях ловят.

Возвращать ссылку безопасно только на то, что **переживёт** возврат:

- элемент контейнера, который пришёл по ссылке (как в `first(v)` выше)
- статическую или глобальную переменную
- поле объекта, чей жизненный цикл вы понимаете

## 3. Константы и способы передачи в функцию

### `const` на значениях

```cpp
const int x = 5;
x = 10;        // CE
```

`const` запрещает менять переменную после инициализации. Применяется для:

- констант времени компиляции
- параметров, которые функция обещает не менять
- защиты инвариантов класса (через `const`-методы — лекция 4)

**Не путать `const` и `constexpr`.** `const` — нельзя менять. `constexpr` — известно на компиляции (и автоматически даёт `const`). Каждый `constexpr` это `const`, но не наоборот.

### `const` с указателями

Здесь есть две вещи, и они независимы:

```cpp
const int* p1 = &x;        // указатель на const int
int* const p2 = &x;        // const-указатель на (не-const) int
const int* const p3 = &x;  // и то, и то
```

- Через `const int*` нельзя **писать** в объект, но указатель можно переприсваивать.
- Через `int* const` можно писать, но переприсваивать указатель — нельзя.

Этот раздел был на прошлой лекции, повторяем — это часто путает.

### `const` с ссылками

```cpp
int x = 5;
const int& cr = x;     // ссылка на const int
// cr = 10;            // CE
x = 10;                // ok: сам x не const
std::print("{}\n", cr);   // 10 — cr видит новое значение
```

Через `const&` нельзя писать, но **изменения оригинала видны**. Это самая распространённая форма ссылки в API C++: передача больших объектов по `const&` — стандартный способ «дай мне это, я не буду его менять».

«const-ссылка на const-объект» (`const int& const ref`) бессмысленно — ссылку всё равно нельзя переадресовать. Поэтому такого не пишут.

### Четыре способа передачи в функцию

```cpp
void by_value(std::string s);              // 1. по значению (копия)
void by_ref(std::string& s);               // 2. по ссылке (можно менять)
void by_const_ref(const std::string& s);   // 3. по const-ссылке (только читать)
void by_ptr(std::string* s);               // 4. по указателю (может быть nullptr)
```

Какой когда:

- **По значению** — для маленьких типов (`int`, `double`, `char`, типы размером с указатель и меньше). А также когда нужна **независимая копия** для модификации внутри функции, не задевая аргумент.
- **По ссылке `T&`** — когда функция **меняет** переданный объект. Пример: `swap`, `sort`.
- **По `const T&`** — самый частый вариант для **больших** объектов в режиме чтения. Не копирует, не даёт менять. Стандартный способ принимать `std::string`, `std::vector`, пользовательские классы.
- **По указателю `T*`** — когда аргумент **может отсутствовать** (передаётся `nullptr`). Также для совместимости с C-API.

Подсказка: для маленьких типов `void f(const int& x)` — антипаттерн. Передача по значению дешевле, чем по `const&` (ссылка под капотом обычно реализуется как указатель — лишний уровень индирекции).

Move-семантика (лекция 11) добавит пятый способ — `T&&` для перемещения rvalue. Тогда мы вернёмся и пересмотрим этот список.

### Продление жизни временного

Обычно временный объект (rvalue) живёт **до конца полного выражения**:

```cpp
std::string make() { return "hello"; }

std::print("{}\n", make().size());
// временный std::string существует, пока вычисляется size(),
// разрушается в точке с запятой
```

Если временный привязывается к **`const&` или к rvalue-ссылке `&&`** — его жизнь **продлевается** до жизни самой ссылки:

```cpp
const std::string& s = make();    // временный продлён до конца блока
std::print("{}\n", s);            // ok, объект жив
```

Это уникальная возможность ссылок: они «удерживают» временный объект на время своей жизни. На этом основаны многие идиомы — например, передача `make_string()` напрямую в функцию, принимающую `const&`.

### Подвох: продление не транзитивно

```cpp
struct Wrapper { const std::string& s; };

Wrapper w{ make() };     // временный s НЕ продлевается
std::print("{}\n", w.s); // UB: dangling reference в поле
```

Продление работает **только** для прямой привязки в виде `const T& ref = tmp;`. Если временный объект попадает внутрь структуры через конструктор, то к моменту, когда вы из этой структуры обратитесь к ссылочному полю — временный уже умер.

**Правило:** не храните `const&` поля на временные объекты. Если объект должен жить дольше, чем выражение его создания — используйте обычное поле (с копией) или `unique_ptr`/`shared_ptr`.

## 4. Касты

В C++ есть четыре именованных оператора преобразования типов:

- `static_cast<T>(x)` — «обычные» преобразования
- `reinterpret_cast<T>(x)` — переинтерпретация битов
- `const_cast<T>(x)` — снятие/добавление `const`
- `dynamic_cast<T>(x)` — для полиморфных иерархий, лекция 7

И ещё C-style cast `(T)x` — наследие C. **В новом коде не пишите.**

### `static_cast`

Самый частый и самый безопасный из четырёх. Используется для:

- преобразований между числовыми типами (`int → double`, `double → int`)
- приведения в иерархии классов «снизу вверх» (производный → базовый) и иногда «сверху вниз», когда вы уверены в типе
- преобразования через `void*`

```cpp
double d = 3.14;
int i = static_cast<int>(d);          // 3 (отбрасывает дробную часть)

int a = 1, b = 3;
double r = static_cast<double>(a) / b;   // 0.333..., а не 0

void* p = &i;
int* pi = static_cast<int*>(p);       // void* → int*
```

`static_cast` проверяется компилятором: семантически бессмысленные преобразования (например, `int*` → `double*` или `float*` → `int*` напрямую) запрещены. Это и хорошо: бессмысленное приведение часто означает баг.

### `reinterpret_cast`

«Возьми эти биты и интерпретируй как другой тип, не трогая значения».

```cpp
int x = 0x41414141;
char* p = reinterpret_cast<char*>(&x);
std::print("{} {} {} {}\n", p[0], p[1], p[2], p[3]);
// 65 65 65 65 — биты x, прочитанные побайтово как 'A'-ы
```

Применения — на низком уровне:

- сериализация в массив байтов и обратно
- работа с memory-mapped регистрами в embedded
- type punning (с большой осторожностью — иногда это UB по правилу strict aliasing)

**В 99% обычного прикладного кода `reinterpret_cast` не нужен.** Если вы пишете его — поставьте под вопрос «точно нет другого способа?». В большинстве случаев способ есть: `static_cast` через `void*`, или `std::bit_cast` (C++20) для копии битов.

### `const_cast`

Снимает или добавляет `const`:

```cpp
void legacy_api(char* s);     // C-API, не помечена const

void modern_wrapper(const std::string& s) {
    legacy_api(const_cast<char*>(s.c_str()));
}
```

**Ключевое правило:** если оригинальный объект был объявлен `const`, снять у него `const` и записать в него — **UB**:

```cpp
const int x = 5;
int& nc = const_cast<int&>(x);
nc = 10;                       // UB
```

Применение `const_cast` оправдано почти исключительно для интероперабельности с C-API, которые **на самом деле не пишут** в переданные данные, но **забыли** пометить параметр `const`. Если вы не уверены — лучше скопировать и передать копию.

### Почему C-style cast плохой

```cpp
double d = 3.14;
int i = (int)d;
```

Внешне C-style cast выглядит компактно. Под капотом он пробует выполнить, по порядку:

1. `const_cast`
2. `static_cast`
3. `static_cast` + `const_cast`
4. `reinterpret_cast`
5. `reinterpret_cast` + `const_cast`

Первый вариант, который скомпилируется, и применяется. Проблема в том, что **вы не видите, какой именно**. Опечатка в типе или забытый `const` могут превратить безобидный `(int*)x` в `reinterpret_cast`, и компилятор смолчит. C++-касты подсветят эту ошибку.

**Правило:** в новом коде C-style cast — индикатор кода, написанного до 2000-х, или людьми, не знающими C++. Не пишите.

### Function-style cast

В дополнение к C-style cast есть ещё **функциональная запись**:

```cpp
int i = int(3.14);             // эквивалент (int)3.14
auto p = Point(3, 4);          // вызов конструктора Point
std::string s = std::string("hi");   // вызов конструктора string
```

Граница между «приведением» и «вызовом конструктора» в этой записи размыта — синтаксис у них общий. На практике различие важное:

- Для **скалярных типов** `T(x)` — это синоним C-style cast. Со всеми его проблемами (выбирает любой из пяти видов C++-каст, без подсветки).
- Для **классов** `T(x)` — это **вызов конструктора**, и это нормальный, идиоматичный C++. Конструкция `std::string("hello")` — не плохой стиль, это просто создание объекта.

То есть правило «не пишите C-style cast» формально касается и `int(x)` для скаляров. На практике конструкция `int(x)` встречается в коде — выглядит чище C-style. Но если вы видите `int(complex_expression)` — подумайте, не сообщить ли явно через `static_cast<int>(...)`, что именно происходит.

### Brace-init форма `T{x}`

C++11 добавил третью форму — с фигурными скобками:

```cpp
int i1 = int(3.14);     // ok, молча отбрасывает дробную часть
int i2 = int{3.14};     // CE: narrowing conversion from 'double' to 'int'

int i3 = int{3};        // ok
char c = char{1000};    // CE: 1000 не влезает в char
```

Запись `T{x}` запрещает **сужающие преобразования** (narrowing). Компилятор подсветит, что вы случайно теряете точность. Если усечение действительно нужно — пишите явно `static_cast<int>(x)`.

Brace-init работает не только для cast, но и для инициализации переменных и членов класса:

```cpp
int x{5};          // эквивалент int x = 5;
double d = 1.0;
int y{d};          // CE: narrowing
```

С точки зрения «правил выживания»: если нужно преобразование с запретом сужающих (narrowing) преобразований — brace-инициализация `int{x}`. Если хотите явное усечение — `static_cast<int>(x)`. C-style `(int)x` и `int(x)` для скаляров — не пишите.

### Сводка

| Каст | Когда |
|---|---|
| `static_cast` | «обычные» преобразования: между числами, в иерархии, через `void*` |
| `reinterpret_cast` | сериализация, биты, низкий уровень — редко |
| `const_cast` | снятие `const` для C-API — почти никогда |
| `dynamic_cast` | полиморфные иерархии — лекция 7 |
| C-style `(T)x` | не пишем |

Если не уверены, какой каст выбрать — `static_cast`. Он самый безопасный и в большинстве случаев именно то, что нужно.

## 5. Как функция сообщает об ошибке

Весь разговор о функциях до этого момента строился на молчаливом допущении: функция получает аргументы и возвращает результат. Пора это допущение снять, потому что в реальном коде оно нарушается постоянно.

```cpp
int parse_port(const std::string& s);   // а если s = "abc"?
double divide(double a, double b);      // а если b == 0?
std::string read_file(const char* p);   // а если файла нет?
```

Ни в одном из этих случаев вернуть нечего. И, что важно, ни один из них не является ошибкой программиста, которую поймает компилятор: строка приходит от пользователя, делитель считается в рантайме, файл мог быть удалён между проверкой и открытием. С точки зрения лекции 1 это не CE — это ситуация, которая случается во время работы программы и с которой надо что-то делать.

Вопрос, на который надо ответить: **по какому каналу функция сообщит вызывающему, что не справилась?**

В C++ таких каналов исторически два — возвращаемое значение и исключения. Есть и третий, современный (`std::optional`, `std::expected`), но он требует шаблонов, поэтому подробно разберём его на лекции 14. Сегодня — два базовых, которых достаточно, чтобы писать корректный код на практических заданиях.

### Способ 1: особое значение в результате

Самое прямолинейное решение — договориться, что одно из значений возвращаемого типа означает не результат, а неудачу.

```cpp
int parse_port(const std::string& s) {
    if (!is_number(s)) return -1;       // -1 = «не смог»
    return std::stoi(s);
}

int port = parse_port(argv[1]);
if (port < 0) {
    std::print("bad port\n");
    return 1;
}
```

Так устроен практически весь интерфейс операционных систем и библиотек на C: `open` возвращает `-1`, `malloc` — `nullptr`, `fopen` — `nullptr`, `strtol` кладёт признак ошибки в глобальную `errno`. Подход имеет очевидные достоинства: он ничего не стоит, работает где угодно, включая ядро и код без поддержки исключений, и поток управления в нём виден целиком — нет никакой магии, только `if`.

Достоинства перечислены не для проформы: во многих ситуациях это правильный выбор, и на лекции 14 мы увидим, где именно. Но у подхода есть четыре проблемы, и все они проявляются при росте кода.

**Проблема первая: результат и ошибка живут в одном типе.** `-1` — совершенно валидный `int`. Глядя на сигнатуру `int parse_port(const std::string&)`, вы не можете узнать, что часть диапазона зарезервирована под неудачу; это знание живёт в документации, а документацию читают не всегда.

**Проблема вторая: проверку легко забыть, и компилятор промолчит.**

```cpp
int port = parse_port(argv[1]);
connect(host, port);              // а если port == -1?
```

Этот код компилируется без единого предупреждения. Забытая проверка кода возврата — одна из самых распространённых категорий ошибок в C-коде вообще. Частично лечится атрибутом `[[nodiscard]]`, до которого мы дойдём на лекции 5.

**Проблема третья: особого значения может просто не быть.** Что вернуть из `divide`, если неудача — это деление на ноль? Любое значение `double` — валидный результат деления. Приходится менять сигнатуру: возвращать `bool`, а результат отдавать через выходной параметр:

```cpp
bool divide(double a, double b, double& out);   // работает, но читается плохо
```

Функция перестала возвращать то, что вычисляет; теперь результат приходит «сбоку», и на месте вызова уже не написать `f(divide(x, y))`.

**Проблема четвёртая, и она главная: ошибку приходится протаскивать руками через все промежуточные уровни.**

```cpp
int load_config(Config& out) {
    int rc = read_file(path, buffer);
    if (rc != 0) return rc;              // просто пробросили
    rc = parse(buffer, out);
    if (rc != 0) return rc;              // и ещё раз
    rc = validate(out);
    if (rc != 0) return rc;              // и ещё
    return 0;
}
```

Обратите внимание, что делает `load_config` с ошибкой: **ничего**. Она не может её обработать — обработчик находится этажом выше, а то и пятью этажами выше. Всё, что она делает, — передаёт ошибку дальше. И так поступает каждая функция в цепочке. Если ошибка возникла на пять вызовов вглубь, то пять функций обязаны про неё знать, иметь подходящий тип возврата и не забыть пробросить. Забыл один — ошибка потерялась молча.

### Способ 2: исключения

Исключение решает ровно эту проблему: оно позволяет сообщить о неудаче **не через возвращаемое значение** и доставить сообщение сразу тому, кто умеет с ним работать, минуя всех, кто не умеет.

```cpp
int parse_port(const std::string& s) {
    if (!is_number(s)) {
        throw std::invalid_argument("port is not a number: " + s);
    }
    return std::stoi(s);
}
```

Сигнатура снова честная: `parse_port` возвращает `int` и только `int`. Весь диапазон значений снова означает результат. Неудача идёт по отдельному каналу.

Ловят исключение так:

```cpp
try {
    int port = parse_port(argv[1]);
    connect(host, port);
} catch (const std::invalid_argument& e) {
    std::print("плохой порт: {}\n", e.what());
}
```

Три ключевых слова:

- **`throw`** — момент, когда функция сдалась. Выполнение текущей функции прекращается немедленно.
- **`try`** — блок, внутри которого мы готовы к неудаче.
- **`catch`** — обработчик: что делать, если она случилась.

Главное свойство — то, ради чего механизм и существует: **между `throw` и `catch` может быть сколько угодно вызовов, и промежуточные функции о происходящем не знают**. Пример с `load_config` схлопывается до:

```cpp
Config load_config(const std::string& path) {
    auto buffer = read_file(path);      // бросит, если файла нет
    auto config = parse(buffer);        // бросит, если формат битый
    validate(config);                   // бросит, если значения бессмысленные
    return config;
}
```

Здесь ноль строк, посвящённых пробросу ошибок, и при этом ни одна ошибка не потеряется. Обработчик стоит там, где действительно есть что делать, — например, в `main`.

### Что можно бросать и что принято

Технически бросить можно объект **любого** типа: `throw 42;` — валидный C++. На практике так не делают, потому что число не расскажет обработчику, что произошло.

Соглашение всей экосистемы: бросаем объекты, унаследованные от `std::exception`. У него есть виртуальный метод `what()`, возвращающий текстовое описание. Стандартная библиотека предоставляет готовую иерархию:

```
std::exception
├── std::logic_error          ошибка в логике программы
│   ├── std::invalid_argument     аргумент не подходит
│   ├── std::out_of_range         индекс за границами
│   └── std::domain_error         значение вне области определения
├── std::runtime_error        не получилось во время работы
│   ├── std::overflow_error
│   ├── std::range_error
│   └── std::system_error         ошибка от ОС
├── std::bad_alloc            не хватило памяти (бросает new)
└── std::bad_cast             неудачный dynamic_cast (лекция 7)
```

Деление на `logic_error` и `runtime_error` отражает разницу в природе ошибки. `logic_error` означает «программа сделала что-то бессмысленное, это баг, который можно было предотвратить проверкой». `runtime_error` означает «внешние обстоятельства не сложились: файла нет, сеть недоступна, диск полон». На практике граница иногда размыта, но ориентир полезный.

Свои типы исключений писать можно и нужно — для этого достаточно унаследоваться от подходящего стандартного. Как это делается, разберём на лекции 4, когда появятся классы.

### Почему ловят по `const&`

```cpp
catch (const std::exception& e)     // так
catch (std::exception e)            // не так
```

Причин две.

Первая: ловля по значению **копирует** объект исключения, а это лишняя работа в момент, когда программе и так плохо.

Вторая серьёзнее. Если брошен был наследник — скажем, `std::invalid_argument`, — а ловим мы по значению базового типа `std::exception`, то копия получится **базового** типа: всё, что добавлял наследник, отрежется. Это явление называется **срезкой** (slicing), подробно разберём его на лекции 6, когда дойдём до наследования. Пока достаточно правила: исключения ловят по константной ссылке, всегда.

Из того же механизма следует полезное свойство: `catch` по базовому типу ловит все производные. Обработчик `catch (const std::exception& e)` поймает любое стандартное исключение, и это разумный «последний рубеж» в `main`.

Есть ещё `catch (...)` — ловит вообще всё, включая нестандартные типы, но не даёт доступа к самому объекту. Применяется редко: на границе с C-кодом (лекция 10) и там, где нужно гарантированно не выпустить исключение наружу.

### Раскрутка стека — и зачем на самом деле нужен RAII

Теперь самое важное в этом разделе, и оно объясняет задним числом всю прошлую лекцию.

Когда происходит `throw`, программа **не прыгает** сразу в `catch`. Она аккуратно выходит из каждой функции на пути от места броска до обработчика, и на каждом шаге **разрушает локальные объекты** — вызывает их деструкторы в порядке, обратном созданию. Этот процесс называется **раскруткой стека** (stack unwinding).

Ключевое слово здесь — «объекты». Посмотрите:

```cpp
void inner() {
    std::vector<int> v(1000);     // деструктор ВЫЗОВЕТСЯ
    int* p = new int[1000];       // а delete[] — НЕТ
    throw std::runtime_error("oops");
}
```

`v` — объект, у него есть деструктор, раскрутка стека его вызовет, память освободится. `p` — сырой указатель, то есть просто число; никакого деструктора у него нет, и выделенный блок утечёт. Строка `delete[] p;`, если бы вы её написали ниже, просто не выполнится — управление до неё не дойдёт.

Вернёмся к лекции 2. Там было сказано: ручной `delete` не переживает ранний выход из функции, и в списке ранних выходов рядом с `return` и `break` упоминалось исключение. Теперь видно, почему исключение в этом списке — самый опасный пункт. `return` и `break` вы видите в коде глазами. Исключение **не видно**: строка `might_throw();` выглядит как обычный вызов, и понять, бросает ли она, можно только заглянув в её реализацию — и в реализацию всего, что она вызывает.

Отсюда следует правило, которое стоит принять как безусловное:

> **Правило:** в коде, где возможны исключения, каждый ресурс обязан лежать в объекте, который его освобождает. Ручной `delete` между `new` и концом функции — это не «плохой стиль», это утечка, которая ждёт своего исключения.

А поскольку исключения возможны почти везде (`new` бросает `bad_alloc`, `std::vector` при росте бросает, любая функция стандартной библиотеки может бросить), — это правило про весь код, а не про какой-то особый.

Обратите внимание, как две лекции сошлись. На лекции 2 RAII выглядел удобством: не надо помнить про `delete`. Теперь понятно, что это не удобство, а единственный способ вообще написать корректный код в присутствии исключений. Именно поэтому в практических заданиях курса запрещены ручные `new`/`delete` — не из вредности, а потому что правильно написать их вручную сложнее, чем кажется.

```cpp
void f() {
    auto buf = std::make_unique<int[]>(1000);
    might_throw();          // бросит — buf освободится при раскрутке
}                           // не бросит — освободится при выходе
```

Один и тот же код корректен в обоих сценариях, и думать про них по отдельности не нужно.

### Когда исключение, а когда код возврата

Общий ориентир формулируется одной фразой: **исключение — для исключительного**. Исключения не предназначены для управления обычным потоком выполнения.

| Ситуация | Механизм |
|---|---|
| Ошибка ожидаема и обрабатывается на месте вызова | код возврата |
| Ошибка редкая, а обработчик далеко по стеку | исключение |
| Нарушен контракт функции (неверный аргумент, выход за границы) | исключение |
| Конструктор не смог создать корректный объект | исключение — другого канала нет (лекция 4) |
| Горячий цикл, где «не получилось» — рядовое событие | код возврата |

Классический анти-паттерн — использовать исключение там, где ситуация нормальная. Например, функция поиска элемента в контейнере, которая бросает `not_found`, если элемента нет. Отсутствие элемента при поиске — не авария, а один из двух ожидаемых исходов, ради которого вызывающий и вызывает поиск. Такой код и медленнее, и читается хуже: `try`/`catch` вокруг каждого поиска.

Есть и второй практический аргумент против исключений, о котором стоит знать заранее: существуют области, где они **запрещены целиком** — сборка с `-fno-exceptions`. Это ядра операционных систем, embedded с жёсткими ограничениями, некоторые высокочастотные торговые системы. Там код возврата — единственный доступный механизм. Подробнее — на лекции 14.

### `noexcept`

Функцию можно пометить обещанием не бросать:

```cpp
int size() const noexcept { return size_; }
```

Это именно **обещание**, а не проверка: компилятор не станет доказывать, что тело действительно ничего не бросает. Если из `noexcept`-функции исключение всё-таки вылетит, программа немедленно завершится вызовом `std::terminate` — без раскрутки стека, без шанса что-то обработать.

Звучит сурово, но смысл в этом есть. Во-первых, компилятор может оптимизировать агрессивнее: ему не нужно готовить в этой функции инфраструктуру раскрутки. Во-вторых, и это важнее, стандартная библиотека **принимает решения** на основании `noexcept`. Самый известный случай мы разберём на лекции 11: `std::vector` при увеличении размера перемещает элементы в новый буфер, только если их move-конструктор помечен `noexcept`, — иначе он их копирует, потому что копирование можно безопасно откатить, а прерванное перемещение уже нет.

Практическое правило на сейчас: помечайте `noexcept` то, что заведомо не бросает, — простые геттеры, `swap`, деструкторы (они `noexcept` по умолчанию). Не ставьте `noexcept` «на всякий случай»: снять это обещание потом, не сломав пользователей, уже нельзя.

### Что делать на практических заданиях

Пока у нас нет `optional` и `expected` — до них доберёмся на лекции 14, — работающий минимум такой:

1. **Нарушение контракта** — бросаем: `std::invalid_argument` для неподходящего аргумента, `std::out_of_range` для выхода за границы.
2. **Ожидаемое «не получилось»**, которое вызывающий обработает сразу, — код возврата или `bool`.
3. **Любой ресурс — в RAII-обёртке.** Без исключений это была дисциплина; с исключениями это необходимость.
4. В `main` — `catch (const std::exception& e)` как последний рубеж, чтобы программа сообщала о причине падения, а не молча умирала.

## Итоги

- **Функции:** аргументы по умолчанию (только справа), перегрузка по типам параметров, `inline` для размещения определения в заголовке, `constexpr` для compile-time.
- **Ссылка** — второе имя объекта. Должна быть инициализирована, нельзя переадресовать. Используется как замена «по указателю», когда `nullptr` не нужен.
- **Четыре способа передачи:** по значению, `T&`, `const T&`, `T*`. Большие объекты в read-only режиме — `const T&`. Маленькие типы — по значению.
- **`const&` к временному** продлевает его жизнь до жизни ссылки, но **не транзитивно** — не работает для полей структур.
- **Касты:** `static_cast` (90% случаев), `reinterpret_cast` (низкий уровень), `const_cast` (только для C-API), `dynamic_cast` (позже). C-style `(T)x` не пишем.
- **Ошибки:** код возврата — для ожидаемого и обрабатываемого на месте; исключение — для исключительного и для случая, когда обработчик далеко по стеку. Бросаем наследников `std::exception`, ловим по `const&`.
- **Раскрутка стека вызывает деструкторы, но не освобождает память из `new`.** Отсюда: любой ресурс — в RAII-обёртке. Это и есть настоящая причина, по которой на лекции 2 появились умные указатели.
