# Лекция 2. Память и указатели

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему».

## 0. О чём эта лекция

В прошлый раз мы посмотрели на язык в целом и разобрали базовые типы. Сегодня мы спускаемся на уровень ниже: разбираем, как C++ работает с памятью. Это та часть языка, ради которой его обычно и выбирают — здесь у программиста есть прямой контроль, не отгороженный сборщиком мусора. Но с этим контролем приходит ответственность: вся семья классических ошибок C++-программ (segfault, утечки, use after free) живёт именно здесь.

Структура лекции — сначала фундамент (виды памяти, указатели, `new`/`delete`), потом односвязный список как первое применение указателей, массивы и `sizeof`, и в конце — самое практически важное: **RAII и умные указатели** как стандартный способ работы с динамической памятью в современном C++. Ручные `new` и `delete` вы напишете ровно один раз — на занятии 1.2, где список сначала собирается на сырых указателях, а потом переводится на `std::unique_ptr`. Смысл именно в переходе: пока не написал руками, не видно, от чего избавляет обёртка. Дальше в практических заданиях `new` и `delete` не встречаются — только `std::make_unique`, `std::make_shared`, `std::vector` и `std::array`.

## 1. Виды памяти

В C++ каждый объект живёт в одной из трёх областей памяти. От этого зависит **время жизни** объекта — то есть, когда он создаётся и когда уничтожается.

### Стек (stack)

Самая распространённая область. На стеке живут локальные переменные функций:

```cpp
void f() {
    int x = 5;        // x на стеке
    double y = 3.14;  // y тоже
}                     // в конце функции — x и y разрушаются
```

Память на стеке выделяется и освобождается **очень быстро** — это просто сдвиг регистра указателя стека. Никаких системных вызовов. Время жизни объекта **жёстко привязано** к области видимости: объект существует, пока выполнение находится внутри блока `{ }`, в котором он объявлен.

У стека есть фиксированный размер — на Linux обычно 1–8 МБ на поток. Слишком глубокая рекурсия или огромный локальный массив вызывают **stack overflow** — программа крэшится.

```cpp
void f() {
    int huge[1'000'000];   // 4 МБ на стеке — может не влезть
}
```

### Статическая память

Глобальные переменные и `static`-переменные внутри функций:

```cpp
int counter = 0;                  // глобальная — в статической памяти

void f() {
    static int call_count = 0;    // переживает между вызовами f
    ++call_count;
}
```

Такие объекты создаются **до** входа в `main` (точнее, в момент инициализации программы) и разрушаются **после** выхода из `main`. Размер фиксирован на этапе компиляции и помещается в исполняемый файл.

`static` внутри функции — отдельный паттерн. Переменная создаётся **при первом проходе** через её объявление и живёт до конца программы, сохраняя значение между вызовами функции. Удобно для счётчиков, кэшей, синглтонов.

Важное правило: **глобальных и статических переменных стоит избегать** — они затрудняют тестирование (общее состояние), мешают многопоточному коду (нужны mutex'ы), и порядок их инициализации между разными файлами не определён (Static Initialization Order Fiasco).

### Динамическая память (куча, heap)

Здесь живут объекты, временем жизни которых программист управляет **вручную**:

```cpp
int* p = new int(42);   // выделили память, p указывает на неё
// ... используем *p
delete p;               // освободили
```

Память на куче выделяется **системным аллокатором** (`malloc` / `operator new`). Это медленнее, чем стек, потому что аллокатор может искать подходящий блок, разбивать или объединять блоки, обращаться к ядру за новой памятью. Зато размер ограничен только физической памятью машины, и время жизни объекта **не привязано** к функции, в которой он создан.

```cpp
int* make_int() {
    int* p = new int(42);
    return p;            // ok: объект переживёт функцию
}
```

Цена этого контроля — ответственность. **Каждому `new` должен соответствовать ровно один `delete`**, иначе либо утечка (объект не освобождён), либо UB (освобождён дважды или использован после освобождения).

### Сравнение

| Область | Скорость | Время жизни | Размер |
|---|---|---|---|
| Стек | очень быстро | привязано к scope | ограничен (~МБ) |
| Статическая | быстро | вся программа | фиксирован |
| Куча | медленнее | управляется вручную | большой (~ГБ) |

**Правило большого пальца:** используйте стек, когда можно. Это самый быстрый и самый безопасный вариант. Куча нужна, когда:

- объект должен пережить функцию, в которой создан
- размер известен только в рантайме и слишком велик для стека
- нужно полиморфное хранение через указатели на базовый класс

## 2. Указатели

**Указатель** — переменная, хранящая адрес другого объекта в памяти. С точки зрения железа это просто 64-битное число (на 64-битных машинах). С точки зрения C++ — это типизированное значение: `int*` отличается от `double*`, и компилятор это контролирует.

### Объявление и операции

```cpp
int x = 42;
int* p = &x;      // p хранит адрес x
```

- `int*` — тип «указатель на `int`»
- `&x` — оператор «взять адрес». Работает только для lvalue (то, у чего есть адрес)

Обратная операция — **разыменование** через `*`:

```cpp
int x = 42;
int* p = &x;
std::print("{}\n", *p);   // 42 — значение по адресу p

*p = 100;                 // меняем x через указатель
std::print("{}\n", x);    // 100
```

Если `p` — указатель на тип `T`, то `*p` — выражение типа `T&` (ссылка на `T`). Со ссылками подробно — на следующей лекции.

### `nullptr`

Указатель может «не указывать ни на что» — тогда его значение `nullptr`:

```cpp
int* p = nullptr;

if (p == nullptr) { /*...*/ }
if (p) { /*...*/ }                // эквивалентно p != nullptr
```

**Разыменование `nullptr` — это UB.** Перед `*p` всегда проверяйте, что `p` валиден, либо обеспечьте это контекстом (например, инвариантом, что в данный момент функция получает не-null указатель).

До C++11 для «никуда не указывает» использовали макрос `NULL` или просто `0`. В обоих случаях это всего лишь целое число, и компилятор не мог надёжно отличить «`0` как число» от «`0` как нулевой указатель». `nullptr` — типизированный, не путается с `int(0)`, не выбирает не ту перегрузку функции. **В новом коде только `nullptr`.**

### Адресная арифметика

К указателю можно прибавлять и вычитать целые числа:

```cpp
int arr[5] = {10, 20, 30, 40, 50};
int* p = arr;        // C-array распадается до указателя на первый элемент

std::print("{}\n", *(p + 1));   // 20
std::print("{}\n", *(p + 2));   // 30
```

Сложение `p + n` сдвигает указатель **на `n * sizeof(T)` байт**, а не на `n` байт. Это удобно: `p + 1` всегда «следующий элемент того же типа».

Адресная арифметика **валидна только внутри одного массива** (включая один элемент за концом — указатель на `arr + n` корректен, но разыменовать его — UB). Сложение указателей в произвольную сторону — UB, даже если результат не разыменовывается.

### `const` и указатели

Есть три похоже выглядящих, но разных по смыслу варианта:

```cpp
const int* p1 = &x;        // указатель на const int
int* const p2 = &x;        // const-указатель на int
const int* const p3 = &x;  // и то, и то
```

- `const int*` — нельзя менять то, на что указывает (`*p1 = 10;` — CE), но указатель можно переприсваивать (`p1 = &y;` — ok)
- `int* const` — нельзя переприсваивать (`p2 = &y;` — CE), но значение менять можно (`*p2 = 10;` — ok)
- `const int* const` — нельзя ни то ни то

Правило чтения **«справа налево»** помогает:

- `int* const p` → «p это const указатель на int»
- `const int* p` → «p это указатель на int, который константный»

Альтернативная запись, в которой правило работает единообразно — `int const*` вместо `const int*`. Смысл идентичен, но порядок чтения везде один. Многие современные кодстайлы предпочитают именно эту запись.

### `void*`

`void*` — указатель без типа. Можно положить любой другой указатель, нельзя разыменовать:

```cpp
int x = 5;
void* p = &x;            // ok
// *p                    // CE: cannot dereference void*

int* px = static_cast<int*>(p);   // обратно через cast
std::print("{}\n", *px);           // 5
```

`void*` — наследие C, используется в системных API (`malloc` возвращает `void*`, `memcpy` принимает `void*`). В современном C++ обычно обходится без него: для «обобщённого хранения» есть шаблоны и `std::any`.

## 3. `new` и `delete`

`new T(args)` — выделить в куче место под объект типа `T`, сконструировать его и вернуть указатель. `delete p` — вызвать деструктор объекта и освободить память.

```cpp
int* p = new int(42);
std::print("{}\n", *p);
delete p;
```

Под капотом происходит две вещи:

1. **Аллокация** — `operator new` вызывает аллокатор (обычно `malloc`) и получает блок памяти нужного размера.
2. **Конструирование** — `placement new` запускает конструктор `T` на этом блоке. Объект готов к использованию.

`delete` делает зеркальное:

1. Вызывает **деструктор** объекта.
2. Возвращает память аллокатору.

Перегрузка `operator new` и понятие placement new — отдельная тема, связанная с аллокаторами; в этом курсе они не разбираются.

### Главные подвохи

Каждому `new` нужен ровно один `delete`. Нарушения:

**Утечка памяти.** `delete` не вызван:

```cpp
void f() {
    int* p = new int(42);
    if (something_bad) {
        return;            // утечка
    }
    delete p;
}
```

Любой ранний выход — `return` до `delete`, исключение, `break` — превращается в утечку. В долго работающей программе это приводит к росту потребления памяти и в итоге крэшу.

Стоит на минуту задержаться на словах «в долго работающей программе», потому что от этого зависит, насколько серьёзно вы будете относиться к остальной лекции. Однократно запущенная утилита, которая посчитала что-то и завершилась, может течь почти безнаказанно: процесс умер — операционная система забрала всю его память обратно. Именно поэтому в учебных задачах утечка выглядит безобидно.

Теперь возьмём программу другого класса — агент, который стоит на рабочей станции, запускается при загрузке системы и живёт до перезагрузки, то есть неделями и месяцами. Такой агент обрабатывает поток событий: запуски процессов, обращения к файлам, сетевые соединения. Пусть их скромные 20 000 в секунду, и пусть на каждом событии теряется всего 100 байт — размер небольшой структуры:

```
100 байт × 20 000 событий/с × 3600 с ≈ 7 ГБ в час
```

Через несколько часов работать на машине невозможно. Причём заметьте, в чём отдельная неприятность: виноват в этом инструмент, который машину защищает, — а значит, первое, что сделает администратор, это его отключит. Утечка в таком процессе не «мелкий дефект качества», а прямая дыра в безопасности, полученная кружным путём.

Мораль общая, не только про агенты: чем дольше живёт процесс, тем меньше у него права на утечки. Для сервера, демона или агента это право равно нулю. И ровно поэтому дальше в этой лекции мы придём к тому, что ручное управление памятью в прикладном коде писать не надо — не потому, что вы невнимательны, а потому, что при таком масштабе невнимательность стоит слишком дорого.

**Double free.** `delete` вызван дважды:

```cpp
int* p = new int(42);
delete p;
delete p;                  // UB
```

После `delete p` объекта по этому адресу больше нет, но переменная `p` всё ещё хранит тот же адрес. Повторный `delete` ломает структуры аллокатора. Чаще всего это происходит, когда **два разных указателя владеют одним объектом** — и оба пытаются его удалить.

**Use after free.** Объект использован после `delete`:

```cpp
int* p = new int(42);
delete p;
*p = 100;                  // UB
```

Иногда «работает» — память ещё не переиспользована. Иногда падает. Иногда даёт странные баги через час работы. Это один из самых популярных багов в C++-коде.

Все три категории ошибок надёжно ловятся **AddressSanitizer**'ом (`-fsanitize=address`). Этот инструмент — best friend C++-разработчика, особенно на этапе обучения.

### Массивы: `new[]` и `delete[]`

Для массивов в куче — отдельные формы:

```cpp
int* arr = new int[100];
arr[0] = 1;
arr[99] = 2;
delete[] arr;              // именно delete[]
```

**`new T[n]` обязательно идёт в паре с `delete[]`.** Перепутали — UB, потому что для массива деструктор должен вызываться `n` раз, и аллокатор тоже знает про массивный размер.

```cpp
int* a = new int[10];
delete a;                  // UB: должен быть delete[]
```

В современном C++ `new[]` руками вы не пишете — есть `std::vector` (динамический массив) и `std::array` (фиксированного размера на стеке).

## 4. Односвязный список: узлы и указатели

Цепочка узлов — простейший способ хранить растущую последовательность записей, например последние события, пришедшие с машины: сколько их будет, заранее неизвестно, а добавление новой не должно трогать уже сохранённые.

Это первая структура данных, которую имеет смысл собрать руками сразу после указателей: в ней нет ничего, кроме самих указателей и ручного освобождения памяти.

### Узел и голова

**Узел** — это значение плюс указатель на следующий узел:

```cpp
struct Node {
    int value;
    Node* next;
};
```

Список — цепочка таких узлов. Сам список хранит **только голову**, то есть указатель на первый узел; у последнего узла `next` равен `nullptr`, и это признак конца.

```
head -> [10|*] -> [20|*] -> [30|nullptr]
```

Смысл такой организации виден при сравнении с массивом. Элементы списка **не лежат подряд**: каждый узел выделяется в куче отдельно и живёт по своему адресу, а связь между ними задаётся указателями. Отсюда главное свойство: **вставка и удаление не двигают соседей**. Чтобы вставить элемент в середину, достаточно переписать пару указателей — остальные узлы остаются на своих местах, и уже взятые на них указатели остаются валидными. У массива иначе: вставка в середину сдвигает весь хвост, а рост может переселить все элементы на новый адрес, и старые указатели протухнут.

### Сырая версия: `new` и `delete` руками

Добавление в конец: создаём узел, доходим по цепочке до последнего и цепляем новый за него. Пустой список — это `head == nullptr`, поэтому функция возвращает голову: для пустого списка она меняется.

```cpp
Node* push_back(Node* head, int value) {
    Node* node = new Node{value, nullptr};
    if (head == nullptr) {
        return node;              // список был пуст: новый узел стал головой
    }
    Node* last = head;
    while (last->next != nullptr) {
        last = last->next;
    }
    last->next = node;
    return head;
}
```

Поиск хвоста здесь линейный; в настоящей реализации хвост хранят отдельным указателем, чтобы добавление было за константное время.

Обход — обычный цикл по указателю, пока не упрёмся в `nullptr`:

```cpp
for (Node* it = head; it != nullptr; it = it->next) {
    std::print("{} ", it->value);
}
std::print("\n");
```

Освобождение — тоже руками, узел за узлом. Здесь легко написать ошибку:

```cpp
void clear(Node* head) {
    while (head != nullptr) {
        Node* next = head->next;   // сохранить ДО delete
        delete head;
        head = next;
    }
}
```

**Подвох:** после `delete head` узла больше нет, и читать `head->next` — use after free. Указатель на следующий узел нужно взять заранее. Это классическая ошибка в рукописных списках, и AddressSanitizer её ловит сразу.

Полный пример:

```cpp
int main() {
    Node* head = nullptr;
    for (int i = 1; i <= 3; ++i) {
        head = push_back(head, i * 10);
    }
    for (Node* it = head; it != nullptr; it = it->next) {
        std::print("{} ", it->value);   // 10 20 30
    }
    std::print("\n");
    clear(head);                        // без этой строки — утечка всех узлов
}
```

Обратите внимание, сколько здесь ручной работы: каждому `new` нужен парный `delete`, и если между созданием и `clear` случится ранний `return` или исключение, утечёт вся цепочка целиком.

### Цена

За удобство вставки платят по двум статьям:

- **Отдельная аллокация на каждый элемент.** Аллокатор дороже сдвига указателя, и на каждый `int` в списке приходится ещё указатель — накладные расходы на элемент сравнимы с самими данными или больше.
- **Обход прыгает по памяти.** Узлы лежат где придётся, и процессор не может предсказать следующий адрес. Массив на том же количестве элементов обходится в разы быстрее просто потому, что лежит подряд. Это свойство называется локальностью, и подробно про него — на лекции 13.

Поэтому в реальном коде свой список пишут редко: берут `std::list` (тот же двусвязный список из стандартной библиотеки) или, гораздо чаще, `std::vector`. Про стандартные контейнеры и про то, какой когда выбирать, — лекция 13. Свой список имеет смысл писать ради понимания устройства и в специальных случаях, когда нужны стабильные указатели на элементы или сцепление узлов без аллокаций.

Владение здесь целиком ручное: за каждый `new` отвечает программист. Как сделать освобождение автоматическим — в разделе 8.

## 5. Массивы

В C++ есть четыре способа держать «много элементов одного типа»:

```cpp
int a[10];                       // C-style на стеке
int* b = new int[n];             // динамический (через new[])
std::array<int, 10> c;           // C++: обёртка над C-style
std::vector<int> d(n);           // C++: динамический
```

**Правило, как и с памятью:** в новом коде C-style массивов не пишите. У них две главные проблемы:

1. **Распад до указателя при передаче в функцию.** Параметр `int arr[10]` на самом деле принимает `int*` — длина теряется.
   ```cpp
   void f(int arr[10]) {
       std::print("size: {}\n", sizeof(arr));   // 8 (sizeof(int*))!
   }
   ```
   Поэтому в C принято передавать `(int* arr, size_t n)`. В C++ для этого есть `std::span<T>` — non-owning view с длиной (см. лекцию 14).
2. **Нет интерфейса.** Нельзя узнать длину, нельзя добавить элемент, нельзя проверить границы.

`std::array<T, N>` и `std::vector<T>` лишены обеих проблем — имеют методы `.size()`, итераторы, безопасный `.at()`, и нормально передаются по ссылке.

```cpp
std::array<int, 5> a = {1, 2, 3, 4, 5};
std::vector<int> v = {1, 2, 3, 4, 5};

v.push_back(6);
std::print("array size: {}, vector size: {}\n", a.size(), v.size());
```

Размер известен на компиляции — `std::array`. Иначе — `std::vector`. Никаких `int arr[1000]`.

## 6. `sizeof`

`sizeof` — оператор (не функция!), возвращающий **размер типа или объекта в байтах**.

```cpp
sizeof(int);              // 4 (обычно)
sizeof(double);           // 8
sizeof(int*);             // 8 на 64-битной системе
int x = 5;
sizeof(x);                // 4 — то же, что sizeof(int)
```

Тип результата — `size_t`. Значение известно **на этапе компиляции**, поэтому `sizeof` можно использовать в `constexpr`-контекстах и в качестве шаблонного non-type параметра.

Подвох: для контейнеров `sizeof` возвращает размер **самого объекта-контейнера**, а не его данных:

```cpp
std::vector<int> v(100);
sizeof(v);                // ~24 (3 указателя), не 400!
```

Это потому, что `vector` хранит данные в куче, а в самом объекте — только три указателя (начало, конец, capacity).

В шаблонах `sizeof` особенно полезен:

```cpp
template <typename T>
void debug() {
    std::print("size of {} = {}\n", typeid(T).name(), sizeof(T));
}
```

## 7. Variadic C-style — что это, почему не пишут

В C для функций с переменным числом аргументов был механизм `va_list`:

```cpp
#include <cstdarg>

int sum(int count, ...) {
    va_list args;
    va_start(args, count);
    int total = 0;
    for (int i = 0; i < count; ++i) total += va_arg(args, int);
    va_end(args);
    return total;
}
```

Проблемы:

- **Нет типобезопасности.** `va_arg(args, int)` верит вам на слово. Передали `double`, читаете как `int` — UB.
- **Нужно явно передавать число аргументов.** В `printf` его кодируют через форматную строку, что породило отдельный класс багов.

В C++ для переменного числа аргументов используются **variadic templates** (лекция 9) — типобезопасные, проверяемые на компиляции, без накладных расходов. Старая форма оставлена в основном для совместимости с `printf` и С-API.

## 8. RAII и умные указатели

Доходим до самой практически важной части лекции.

К этому моменту мы умеем работать с динамической памятью через `new` / `delete`. Но **писать это в реальном коде опасно**:

- забыли `delete` — утечка
- удалили дважды — крэш
- удалили и продолжили пользоваться — UB

В крупных кодовых базах эти ошибки массово возникают на стыке функций: одна выделяет, другая использует, третья удаляет, и стоит вставить раннее `return` или исключение — посередине этой цепочки — как баг готов.

Решение в C++ — переложить ответственность за освобождение **на компилятор**. Это называется **RAII**.

### Идея RAII

**RAII = Resource Acquisition Is Initialization.** Название неудачное (в нём акцент на «захвате»), но идея простая: **ресурс владеется объектом, а его освобождение происходит в деструкторе**.

```cpp
{
    SomeResourceOwner r(...);   // конструктор захватил ресурс
    use(r);
} // выход из блока — деструктор r отдал ресурс обратно
```

Деструктор вызывается **автоматически** при выходе из области видимости — независимо от того, был выход обычным `return`, исключением, или просто концом блока. Это означает, что если ресурс правильно завёрнут в RAII-объект, **забыть про освобождение невозможно**.

RAII работает для любых ресурсов:

- память (умные указатели)
- файловые дескрипторы (`std::fstream`)
- mutex'ы (`std::lock_guard`)
- сетевые соединения (обычно через библиотеки вроде Asio)
- ссылки на удалённые объекты (`shared_ptr` сам по себе)

### `std::unique_ptr`

`std::unique_ptr<T>` — RAII-обёртка над одиночным указателем. Внутри она хранит обычный `T*`, и в **своём деструкторе** вызывает `delete`.

```cpp
#include <memory>

void f() {
    auto p = std::make_unique<int>(42);
    *p = 100;
    std::print("{}\n", *p);
}   // здесь p автоматически удалит свой int
```

`std::make_unique<T>(args...)` — стандартный способ создать `unique_ptr`. Аргументы передаются в конструктор `T`. Эквивалентный, но менее предпочтительный вариант — `std::unique_ptr<T>(new T(args))`.

Доступ к значению и полям — как у обычного указателя:

```cpp
struct Point {
    int x, y;
    Point(int x, int y) : x(x), y(y) {}
};

auto p = std::make_unique<Point>(3, 4);
std::print("{} {}\n", p->x, p->y);   // 3 4
```

### Уникальное владение

Главная особенность `unique_ptr` — **только один владелец**. Его нельзя скопировать:

```cpp
auto p1 = std::make_unique<int>(42);
auto p2 = p1;                       // CE: cannot copy unique_ptr
```

Если бы копирование было разрешено, оба указателя владели бы одним объектом, и оба бы пытались его удалить — double free.

Если нужно **передать владение** другому месту — есть `std::move`:

```cpp
auto p2 = std::move(p1);            // ok: p2 владеет, p1 теперь nullptr
```

После `std::move(p1)` сам `p1` становится пустым (`nullptr`), а `p2` владеет объектом. Это и есть **move-семантика**, которую мы подробно разберём в лекции 11. Сейчас просто запомните правило: **`unique_ptr` нельзя копировать, можно перемещать через `std::move`**.

### Список на `unique_ptr` и подвох с рекурсией

Вернёмся к списку из раздела 4 и перепишем в нём владение. Там каждый узел освобождался вручную, а `clear` было легко забыть; теперь эту работу можно отдать деструктору.

Если поле `next` сделать умным указателем, освобождение становится автоматическим:

```cpp
struct Node {
    int value;
    std::unique_ptr<Node> next;
};
```

Теперь тип поля прямо говорит, кто чем **владеет**: каждый узел владеет следующим, а голову держит сам список. Сырой `Node*` в этом коде остаётся только там, где нужен невладеющий «наблюдатель» — например, при обходе.

```cpp
struct List {
    std::unique_ptr<Node> head;
};

// last — невладеющий указатель на существующий узел
void push_back(Node* last, int value) {
    while (last->next != nullptr) {
        last = last->next.get();
    }
    last->next = std::make_unique<Node>(value, nullptr);
}

int main() {
    List list;
    list.head = std::make_unique<Node>(10, nullptr);
    push_back(list.head.get(), 20);
    push_back(list.head.get(), 30);

    for (Node* it = list.head.get(); it != nullptr; it = it->next.get()) {
        std::print("{} ", it->value);   // 10 20 30
    }
    std::print("\n");
}   // цепочка освобождается сама — ни одного delete
```

Ни `delete`, ни `clear` больше не нужны: когда разрушается `list`, разрушается `head`, тот удаляет первый узел, вместе с ним — его поле `next`, и так далее.

**Подвох:** именно это «и так далее» и есть проблема. Освобождение цепочки — **рекурсия**, а не цикл:

```
~List -> ~unique_ptr(head) -> delete узел 1 -> ~Node
      -> ~unique_ptr(next) -> delete узел 2 -> ~Node -> ...
```

Глубина рекурсии равна длине списка, и каждый уровень занимает кадр на стеке. На списке из десятков тысяч узлов это переполняет стек — программа падает с segfault не в момент работы со списком, а в момент его уничтожения, что делает диагностику особенно неприятной. Оптимизатор эту рекурсию в общем случае не убирает, а в отладочной сборке — тем более.

**Правило:** если узлы владеют друг другом по цепочке, список обязан разбирать её **явным циклом в своём деструкторе**.

```cpp
struct List {
    std::unique_ptr<Node> head;

    ~List() {
        while (head != nullptr) {
            head = std::move(head->next);
        }
    }
};
```

Что здесь происходит на каждом шаге: `head->next` отдаёт владение следующим узлом переменной `head`, после чего старый первый узел удаляется — но его собственное поле `next` уже пусто, поэтому рекурсия не начинается. Цепочка разбирается по одному узлу, глубина стека постоянна.

Это и есть цена автоматического владения в связанных структурах: сами узлы освобождать больше не нужно, но за разбор цепочки по-прежнему отвечает автор списка. RAII убирает рутину, а не необходимость думать о том, как устроено владение.

### `std::shared_ptr`

Иногда нужно, чтобы **несколько мест в коде совместно владели объектом**, и он жил до тех пор, пока хоть кто-то на него ссылается. Для этого есть `std::shared_ptr<T>`.

```cpp
auto a = std::make_shared<int>(42);
auto b = a;                         // ok: счётчик ссылок = 2
std::print("{} {}\n", *a, *b);

// объект удалится, когда оба (a и b) выйдут из области видимости
```

Внутри `shared_ptr` хранится не только указатель на объект, но и указатель на **control block** — служебную структуру со счётчиком ссылок. При копировании счётчик увеличивается, при уничтожении владельца — уменьшается. Когда счётчик достигает нуля, объект и control block освобождаются.

`std::make_shared<T>(args)` предпочтительнее `std::shared_ptr<T>(new T(args))` — он делает одну аллокацию вместо двух (объект и control block кладёт рядом) и безопаснее в exception safety. Подробности — на лекции 15.

### Когда какой

- **`unique_ptr`** — по умолчанию. Уникальное владение. Нулевые накладные расходы относительно ручного `new`/`delete` — компилятор инлайнит всё.
- **`shared_ptr`** — когда **действительно** нужно разделяемое владение. Стоит дороже: атомарные операции при копировании/удалении, дополнительная аллокация под control block.

**Правило большого пальца:** всегда начинайте с `unique_ptr`. Меняйте на `shared_ptr` только когда стало ясно, что владельцев действительно несколько и непонятно, кто последний.

### Правило в этом курсе

Дальше в практических заданиях **не пишите `new` и `delete` руками** (единственное исключение — первая половина занятия 1.2, где это и есть задание). Используйте:

| Старое | Новое |
|---|---|
| `T* p = new T(args)` | `auto p = std::make_unique<T>(args)` |
| `T* p = new T[n]` | `std::vector<T> p(n)` |
| `delete p` / `delete[] p` | ничего, само освободится |

Это убирает целые классы багов (утечки, double free, use after free) **без потери производительности**. `unique_ptr` после оптимизации компилируется ровно в то же, что и ручной `new`/`delete`.

Семинаристы будут проверять — `new`/`delete` в ваших ДЗ не должно встречаться, кроме явно учебных задач из этой лекции.

Как умные указатели устроены изнутри (control block, кастомный deleter, weak_ptr) — разберём в **лекции 15**, когда у нас уже будут move-семантика и шаблоны.

## Итоги

- Память делится на три области: **стек** (быстро, scope-bound), **статическая** (вся программа), **куча** (управляется вручную, медленнее).
- **Указатель** — переменная с адресом. `&` берёт адрес, `*` разыменовывает. `nullptr` — пусто. Разыменование `nullptr` — UB.
- `const int*` vs `int* const` — три варианта, читать справа налево.
- **`new` / `delete`** — выделение и освобождение. Подвохи: утечки, double free, use after free.
- **Односвязный список** — цепочка узлов «значение + указатель на следующий»; вставка не двигает соседей, но цена — аллокация на элемент и прыжки по памяти.
- C-style массивы не пишите — используйте `std::array` / `std::vector`.
- **RAII** — ресурс владеется объектом, освобождается в деструкторе автоматически.
- **`std::unique_ptr`** — RAII над одним владельцем. Нельзя копировать, можно `std::move`.
- Если узлы связанной структуры владеют друг другом через `unique_ptr`, деструктор обязан разбирать цепочку **циклом**: рекурсивное освобождение переполнит стек.
- **`std::shared_ptr`** — RAII с разделяемым владением через счётчик ссылок.
- В практических заданиях: только `make_unique` / `make_shared` / `vector` / `array`. Ручные `new`/`delete` — один раз на занятии 1.2 и больше нигде.
