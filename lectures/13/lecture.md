# Лекция 13. Итераторы, контейнеры и алгоритмы

> Конспект к лекции для самостоятельного чтения. Слайды (`slides.md`) повторяют структуру, конспект подробнее объясняет «почему».

## 0. О чём эта лекция

К этому моменту у нас уже есть весь язык, чтобы пользоваться STL: классы, шаблоны, лямбды, move-семантика. Сегодня мы посмотрим на саму **стандартную библиотеку** — как она устроена и что из неё стоит знать в первую очередь.

STL держится на двух идеях:

- **Итератор** — обобщённый указатель в контейнер. Один интерфейс работает для всех контейнеров.
- **Алгоритм** — функция, оперирующая итераторами, а не контейнерами. Один и тот же `std::sort` работает для `vector`, `array` и пользовательской структуры.

К концу лекции вы должны:

- Понимать иерархию категорий итераторов и связь с алгоритмами.
- Знать, **какой контейнер использовать когда** — это самое практически важное.
- Уметь применять STL-алгоритмы с лямбдами (часто заменяет ручные циклы).
- Уметь ограничить рост памяти у контейнера, который живёт столько же, сколько процесс.
- Иметь общее представление о `ranges` как современной альтернативе.

**Внутреннее устройство контейнеров** (placement new в `vector::reserve`, fake node в `list`, RB-tree в `map`) в курс не входит.

## 1. Идея итератора

Итератор — это **обобщённый указатель** на элемент контейнера:

```cpp
std::vector<int> v = {1, 2, 3, 4};

for (auto it = v.begin(); it != v.end(); ++it) {
    std::cout << *it << ' ';
}
```

Базовый интерфейс:

- `begin()` — итератор на **первый** элемент.
- `end()` — итератор **за последним** (полуоткрытый интервал `[begin, end)`).
- `++it` — следующий элемент.
- `*it` — текущее значение (lvalue для большинства контейнеров).

Один и тот же интерфейс работает для **всех** STL-контейнеров. Это и есть «обобщённый указатель» — синтаксически выглядит как `T*` (`*it`, `++it`), но может быть устроен внутри как угодно.

### Полуоткрытый интервал

`[begin, end)` — стандартная конвенция. `end()` указывает **за** последний элемент, и разыменовывать его **нельзя** (UB). Это удобно по двум причинам:

- Пустой контейнер легко выразить: `begin() == end()`.
- Длина диапазона = `end - begin` (для random access итераторов).

### Зачем итераторы вообще

Алгоритмы STL работают с **итераторами**, не с контейнерами:

```cpp
std::sort(v.begin(), v.end());
std::find(v.begin(), v.end(), 3);
std::copy(src.begin(), src.end(), std::back_inserter(dst));
```

Один и тот же `sort` работает для:

- `std::vector<int>`
- `std::array<int, N>`
- Обычного C-style массива (через `std::begin`/`std::end`)
- Пользовательского контейнера, у которого есть итераторы

Алгоритм оперирует итераторами; самого контейнера ему не видно. Это и есть **обобщённое программирование** — главная идея STL.

## 2. `range-based for` под капотом

```cpp
for (auto& x : v) {
    std::cout << x << ' ';
}
```

Компилятор разворачивает это примерно в:

```cpp
auto _begin = v.begin();
auto _end = v.end();
for (auto _it = _begin; _it != _end; ++_it) {
    auto& x = *_it;
    /* тело */
}
```

Из этого следует: чтобы `range-based for` работал с вашим типом, нужно реализовать `begin()` и `end()`. Это может быть **метод класса** или **свободная функция** в том же namespace (через ADL).

### Полезные напоминания из лекции 12

Уже знакомые идиомы итерации:

```cpp
for (auto& x : v)           // работаем с элементами, можем менять
for (const auto& x : v)     // только читаем (хороший дефолт)
for (auto x : v)            // копия — для маленьких типов

for (const auto& [k, v] : map)   // structured bindings + const&
```

## 3. Категории итераторов

Не все итераторы одинаково мощные. Стандарт выделяет **категории** в виде иерархии:

```
Input / Output  →  Forward  →  Bidirectional  →  RandomAccess  →  Contiguous
```

Чем «правее», тем больше операций поддерживает.

### Что умеет каждая категория

- **Input iterator:** `*it` (только чтение, **один раз**), `++it`. Прочитал — пошёл дальше. Пример: `std::istream_iterator`.
- **Output iterator:** `*it = x` (только запись, **один раз**), `++it`. Пример: `std::ostream_iterator`, `std::back_inserter`.
- **Forward iterator:** `*it` многократно (можно перечитывать). Пример: `std::forward_list`.
- **Bidirectional iterator:** добавляет `--it`. Пример: `std::list`, `std::map`, `std::set`.
- **Random access iterator:** добавляет `it + n`, `it - n`, `it[n]`, `it1 - it2`. Пример: `std::deque`.
- **Contiguous iterator** (C++20): обещает, что данные **лежат подряд** в памяти, можно делать `&*it + n == &*(it + n)`. Пример: `std::vector`, `std::array`, обычный массив.

Алгоритмы STL требуют **минимальную необходимую** категорию. `std::sort` требует RandomAccess, поэтому для `list` (только Bidirectional) есть отдельный `list::sort()`. `std::find` принимает Input — работает практически с чем угодно.

### `iterator_traits`

В обобщённом коде иногда нужно узнать у итератора, какого типа его элементы и какая у него категория. Для этого есть `std::iterator_traits<It>`:

```cpp
template <typename It>
using value_type = typename std::iterator_traits<It>::value_type;

template <typename It>
using category = typename std::iterator_traits<It>::iterator_category;
```

Используется в реализации алгоритмов и шаблонных утилит. В прикладном коде встречается редко. С появлением `auto` и `decltype` явный `iterator_traits` нужен ещё реже.

## 4. `const`- и reverse-итераторы

У контейнеров есть несколько вариантов начальной точки:

```cpp
std::vector<int> v = {1, 2, 3};

auto it1 = v.begin();        // iterator — можно менять *it
auto it2 = v.cbegin();       // const_iterator — только читать
auto it3 = v.rbegin();       // reverse_iterator — идёт с конца
auto it4 = v.crbegin();      // const + reverse
```

### `const_iterator`

`*it` возвращает `const T&` — нельзя менять элемент. Получают через `cbegin()` / `cend()`, или просто через `begin()`/`end()` если контейнер сам `const`:

```cpp
void process(const std::vector<int>& v) {
    for (auto it = v.begin(); it != v.end(); ++it) {
        // *it = ...;        // CE: v const, итератор тоже const
    }
}
```

### `reverse_iterator`

`++` идёт **назад** по контейнеру:

```cpp
for (auto it = v.rbegin(); it != v.rend(); ++it) {
    std::cout << *it << ' ';   // 3 2 1
}
```

`rbegin()` — итератор на **последний** элемент (не за него!), `rend()` — за первым (то есть «до» первого). Внутри это обёртка над обычным итератором.

В современном коде вместо явных reverse-итераторов часто используют `std::ranges::reverse_view` (C++20) или `std::views::reverse` — `for (int x : v | std::views::reverse)`.

## 5. Последовательные контейнеры

Стандарт даёт пять последовательных контейнеров. Главное — знать их сложности и подходящие случаи.

### Таблица сложностей: последовательные

| Контейнер | `[i]` | push_back | push_front | insert middle | Память |
|---|---|---|---|---|---|
| `vector` | O(1) | O(1)\* | — | O(n) | подряд |
| `deque` | O(1) | O(1)\* | O(1)\* | O(n) | блоками |
| `list` | — | O(1) | O(1) | O(1)\*\* | связанная |
| `forward_list` | — | — | O(1) | O(1)\*\* | связанная, односторонняя |
| `array` | O(1) | — | — | — | подряд, фиксированный |

\* амортизированно (`vector` иногда перевыделяет буфер с удвоением; `deque` иногда аллоцирует новый блок — за исключением этих моментов операция дешёвая). \*\* при условии, что у вас уже есть итератор.

### `std::vector` — рабочая лошадка

Самый часто используемый контейнер C++:

```cpp
std::vector<int> v = {1, 2, 3};
v.push_back(4);          // 1 2 3 4
v.emplace_back(5);       // 1 2 3 4 5 — лучше, чем push_back с rvalue
v[0] = 10;                // без проверки границ
v.at(0) = 10;             // с проверкой, бросает out_of_range
v.front(); v.back();      // первый и последний
v.size(); v.empty();

v.reserve(100);           // зарезервировать память — не растёт до 100
v.resize(10);             // изменить размер до 10 (заполняет default)
v.clear();                // очистить
```

Под капотом — массив в куче, удвоение при росте. Итераторы — contiguous. **По умолчанию используйте `vector`** для всего, где не доказана необходимость другого. Это лучший выбор в ~90% случаев.

Внутренности `vector::reserve` (placement new, exception safety) в курс не входят.

### `std::deque`

```cpp
std::deque<int> d;
d.push_front(1);         // O(1) — главное отличие от vector
d.push_back(2);          // O(1)
d[0];                    // O(1), но **немного медленнее** vector[]
```

Внутри — массив указателей на блоки данных. Random access есть, но через дополнительный indirection. Используется, когда нужно push_front + random access (буферы сообщений, FIFO с произвольным доступом).

В обычном коде `deque` встречается редко. Но именно `deque` используется по умолчанию внутри `std::stack` и `std::queue`.

### `std::list`

Двусвязный список:

```cpp
std::list<int> l;
l.push_back(1);
l.push_front(2);
// l[0];                 // CE: нет random access
auto it = l.begin();
l.insert(it, 99);        // O(1) — главное преимущество list
l.erase(it);             // O(1)
l.splice(...);           // O(1) перенос узлов между списками
```

`list` хорош, когда:

- Частые **insert/erase в середине** при наличии уже валидного итератора (тогда O(1), а не O(n) как в vector).
- Нужно **сохранять валидность итераторов** при модификации (vector инвалидирует все при `push_back`, list — нет).
- Используется `splice` для перемещения узлов без копирования.

На практике эти случаи редки. **`list` в новом коде встречается нечасто.** Cache locality у `vector` обычно выигрывает у алгоритмической сложности `list`.

### `std::forward_list`

Односвязный список. Ещё меньше памяти на элемент (один указатель вместо двух), но только итерация вперёд. Используется в очень специфичных случаях — обычно в системном коде. В прикладном — практически никогда.

### `std::array`

```cpp
std::array<int, 5> a = {1, 2, 3, 4, 5};
a[0];                 // O(1)
a.size();             // 5 — known at compile time
a.front(); a.back();
```

Тонкая обёртка над C-style массивом. Размер — **часть типа** (`array<int, 5>` и `array<int, 6>` — разные типы).

В отличие от `int arr[5]`:

- Не «распадается» до указателя при передаче в функцию (лекция 2).
- Имеет полный интерфейс STL-контейнера (size, итераторы, at).
- Можно положить в другой контейнер (`std::vector<std::array<int, 3>>`).

В новом коде вместо `int arr[N]` всегда `std::array<int, N>`.

## 6. Ассоциативные контейнеры

Контейнеры, оптимизированные для **поиска по ключу**.

### Таблица сложностей: ассоциативные

| Контейнер | Поиск | Структура | Порядок | Память |
|---|---|---|---|---|
| `map<K,V>` | O(log n) | RB-tree | по ключу | связная |
| `set<K>` | O(log n) | RB-tree | по ключу | связная |
| `unordered_map<K,V>` | O(1)\* | hash table | нет | подряд + bucket-цепочки |
| `unordered_set<K>` | O(1)\* | hash table | нет | подряд + bucket-цепочки |

\* амортизированно, при хорошей hash-функции. Худший случай — O(n).

**Общая рекомендация — начинать с `unordered_map` / `unordered_set`**, потому что асимптотика лучше. Но «по умолчанию» здесь — упрощение, и `map` в реальной жизни часто оказывается **эффективнее**, чем кажется по таблице. Несколько случаев, когда стоит подумать дважды.

**Мало элементов.** При небольших коллекциях (десятки, сотни элементов) константный фактор `unordered_map` — вычисление хеша, разрешение коллизий, индирекции через bucket'ы — обычно проигрывает упорядоченному дереву или просто сортированному вектору. Для маленьких словарей рассматривайте `flat_map` (C++23), `map`, или даже `vector<pair<K,V>>` с линейным поиском.

**Дорогой хеш.** Если ключ сложный (длинная строка, структура, требующая хеширования нескольких полей), вычисление хеша может стоить дороже, чем `O(log n)` сравнений в `map`. Для строк длиной 100+ символов это уже актуально.

**Рехеш-спайки.** Вставка в `unordered_map` — амортизированно `O(1)`, но раз в N операций происходит **рехеш**: полное перестроение таблицы, O(n) от текущего размера. В latency-sensitive коде (HFT, real-time) эти спайки могут быть неприемлемы. У `map` вставка стабильно `O(log n)` без всплесков.

**Порядок и диапазоны.** Когда важен порядок ключей (`map` идёт в отсортированном порядке) или нужны диапазонные операции (`lower_bound`, `upper_bound`) — `map` или `set` единственный выбор.

**Кэш-локалити.** RB-tree у `map`/`set` — связанная структура, ноды разбросаны по памяти. `unordered_map` чуть лучше (массив buckets), но цепочки коллизий снова разбрасывают. **`flat_map`** (C++23) или `boost::container::flat_map` — сортированный массив пар — обычно выигрывает у обоих по локалити для маленьких и средних размеров.

Практическое правило: если коллекция маленькая или хеш дорогой — измеряйте оба варианта. Для больших коллекций со скалярными ключами почти всегда выигрывает `unordered_map`.

### `std::map`

```cpp
std::map<std::string, int> scores;
scores["Anna"] = 90;                  // вставка (или модификация, если есть)
scores["Bob"] = 85;
scores.insert({"Cara", 75});          // вставка без перезаписи

if (auto it = scores.find("Anna"); it != scores.end()) {
    std::cout << it->second;          // 90
}

for (const auto& [name, score] : scores) {     // упорядочено по name
    std::cout << name << ": " << score << '\n';
}

scores.erase("Bob");                  // удалить по ключу
```

Итераторы `map` — bidirectional, идут по ключам в отсортированном порядке (по умолчанию `std::less<K>`, можно задать свой компаратор).

**Подвох:** `scores["NotExisting"]` **создаст** запись с default-значением. Если нужно «проверить и получить» — используйте `find` или `contains` (C++20).

### Structured bindings (C++17)

В примере выше уже встретилась конструкция `[name, score]` — разберём её, потому что без неё работать с `map` неудобно.

Элемент `std::map<K, V>` — это `std::pair<const K, V>`. Если обращаться к нему напрямую, получается так:

```cpp
for (const auto& p : scores) {
    std::cout << p.first << ": " << p.second << '\n';
}
```

`p.first` и `p.second` не говорят читателю ничего о смысле — приходится держать в голове, что первое это имя, а второе балл. C++17 добавил **structured bindings** — возможность «распаковать» составной объект на именованные переменные:

```cpp
for (const auto& [name, score] : scores) {
    std::cout << name << ": " << score << '\n';
}
```

Тот же код, но имена говорят сами за себя. Это стало **стандартным способом** итерации по ассоциативным контейнерам.

**Где работает.** Распаковывать можно всё «кортежеподобное»:

```cpp
std::pair<int, std::string> p{42, "hello"};
auto [n, s] = p;                       // std::pair, std::tuple

struct Point { int x, y; };
auto [x, y] = Point{3, 4};             // агрегат с публичными полями

int arr[3] = {1, 2, 3};
auto [a, b, c] = arr;                  // массив известной длины
```

Формально работает для: `pair`/`tuple`, агрегатных структур (все поля публичные), массивов фиксированной длины, и пользовательских типов, реализовавших `std::tuple_size` + `std::get<I>` (custom binding — редкость).

**Модификаторы** те же, что у `auto` — и это важно:

```cpp
auto [k, v]        = p;    // копия обоих полей
auto& [k, v]       = p;    // ссылки на поля — изменения видны в p
const auto& [k, v] = p;    // const-ссылки, ничего не копируем
```

Для изменения значений в контейнере нужна именно ссылочная форма:

```cpp
for (auto& [name, score] : scores) {
    score += 5;            // меняет реальные значения в map
}
```

**Подвох с `map`:** ключи в `std::map<K, V>` имеют тип `const K` — менять их нельзя, иначе сломается упорядоченность дерева. Поэтому в `for (auto& [name, score] : scores)` переменная `name` будет `const std::string&` даже без явного `const` в биндинге. Это не баг, а следствие устройства контейнера.

**Второе частое применение** — функции, возвращающие пару значений. Например, `insert` у ассоциативных контейнеров возвращает `pair<iterator, bool>`:

```cpp
auto [it, inserted] = scores.insert({"Dave", 70});
if (!inserted) {
    // ключ уже был, it указывает на существующий элемент
}
```

Без structured bindings это выглядело бы как `result.second` — и снова непонятно, что означает `second`.

### `std::unordered_map`

Тот же интерфейс, что у `map`, но без порядка:

```cpp
std::unordered_map<std::string, int> scores;
scores["Anna"] = 90;          // O(1)
```

Внутри — **хеш-таблица**. Использует `std::hash<K>` для вычисления bucket'а. Для стандартных типов (`int`, `std::string`, etc.) хеш есть из коробки.

Для **своих типов** нужно специализировать `std::hash`:

```cpp
struct Point { int x, y; };

template <>
struct std::hash<Point> {
    size_t operator()(const Point& p) const noexcept {
        return std::hash<int>{}(p.x) ^ (std::hash<int>{}(p.y) << 1);
    }
};
```

`std::hash` должен быть `noexcept` — это требование стандарта.

### `std::set` и `std::unordered_set`

Те же контейнеры, только **без значения** — хранят только ключи. Полезны, когда нужно «множество уникальных элементов»:

```cpp
std::set<int> s = {3, 1, 4, 1, 5};   // {1, 3, 4, 5}
s.insert(9);
s.contains(3);       // true (C++20)

std::unordered_set<std::string> dict;
dict.insert("hello");
```

Есть мульти-версии — `multiset`, `multimap` — допускают дубликаты ключей. Используются реже.

## 7. Адаптеры контейнеров

Адаптеры — **обёртки** над другими контейнерами, ограничивающие интерфейс до конкретной семантики:

```cpp
std::stack<int> st;              // LIFO
st.push(1); st.push(2);
st.top();                        // 2
st.pop();

std::queue<int> q;               // FIFO
q.push(1); q.push(2);
q.front();                       // 1
q.pop();

std::priority_queue<int> pq;     // max-heap
pq.push(3); pq.push(1); pq.push(4);
pq.top();                        // 4
pq.pop();
```

Под капотом:

- `stack` и `queue` по умолчанию используют `deque` (можно переопределить на `vector` / `list` через шаблонный параметр).
- `priority_queue` использует `vector` плюс heap-операции из `<algorithm>`.

Адаптеры — это «спрятать всё лишнее, оставить только то, что нужно для конкретной структуры данных». В алгоритмических задачах встречаются часто.

## 8. Что использовать когда

Простой decision tree:

- **Нужен упорядоченный массив, размер растёт?** → `vector` (90% случаев).
- **Размер фиксирован, известен на этапе компиляции?** → `array`.
- **Нужен push_front + random access?** → `deque` (редко).
- **Частые insert/erase по итератору в середине?** → `list` (редко).
- **Поиск по ключу, порядок не важен?** → `unordered_map` / `unordered_set`.
- **Поиск + важен порядок ключей или диапазоны?** → `map` / `set`.
- **LIFO / FIFO / max-heap?** → `stack` / `queue` / `priority_queue`.

**Правило большого пальца:** всегда начинайте с `vector`. Менять на что-то другое — только если есть **конкретная** причина (профиль показал узкое место, нужна определённая сложность операции, специфичная семантика).

### Контейнеров на самом деле гораздо больше

Перечисленные выше — стандартные. Стандарт продолжает добавлять новые. В C++23 появились **`std::flat_map`** и **`std::flat_set`** — это, по сути, сортированный `std::vector<std::pair<K, V>>` с интерфейсом, похожим на `map`. Поиск через бинарный — `O(log n)`, но за счёт **кэш-локалити** на маленьких и средних коллекциях `flat_map` часто быстрее как `map`, так и `unordered_map`. Цена — вставка `O(n)`, потому что нужно сдвигать элементы.

Кроме стандарта, в реальном production-коде встречаются **сторонние** контейнеры — часто более быстрые для конкретных задач:

- **`absl::flat_hash_map`** (Google's Abseil) — открытая адресация, чаще быстрее `std::unordered_map` благодаря лучшей локалити.
- **`robin_hood::unordered_map`** (martinus/robin-hood-hashing) — компактная робин-худ хеш-таблица.
- **`tsl::robin_map`** / **`tsl::hopscotch_map`** — современные хеш-таблицы.
- **`boost::container::flat_map`** — предшественник `std::flat_map`, всё ещё актуален при работе на C++17/20.
- **`folly::F14Map`** (Facebook) — оптимизированная хеш-таблица.
- **`absl::btree_map`** — B-tree вместо RB-tree, лучше cache locality для упорядоченного словаря.

В большинстве случаев `std::unordered_map` и `std::map` хороши. Но в high-performance коде стоит **бенчмарчить** конкретную задачу против сторонних реализаций — выигрыш в 2-3 раза не редкость. Знать о существовании этих библиотек полезно; замер конкретной задачи — то, что делается руками и по месту.

## 9. Алгоритмы и лямбды

STL даёт сотни обобщённых алгоритмов в `<algorithm>` и `<numeric>`. Самые частые:

```cpp
std::vector<int> v = {3, 1, 4, 1, 5, 9, 2, 6};

std::sort(v.begin(), v.end());                          // 1 1 2 3 4 5 6 9
std::sort(v.begin(), v.end(), std::greater<>{});        // по убыванию
std::sort(v.begin(), v.end(), [](int a, int b) { return std::abs(a) < std::abs(b); });

auto it = std::find_if(v.begin(), v.end(),
                       [](int x) { return x > 3; });    // первый > 3

auto cnt = std::count_if(v.begin(), v.end(),
                          [](int x) { return x % 2 == 0; });

int sum = std::accumulate(v.begin(), v.end(), 0);
int prod = std::accumulate(v.begin(), v.end(), 1, std::multiplies<>{});
```

С лямбдами алгоритмы становятся **очень выразительными**. Прежде чем писать цикл руками — проверьте, нет ли уже подходящего алгоритма.

### Часто используемые

| Алгоритм | Что делает |
|---|---|
| `find(b, e, value)` | первый итератор с `*it == value` |
| `find_if(b, e, pred)` | первый итератор, для которого `pred(*it)` истинен |
| `count`, `count_if` | сколько элементов удовлетворяют условию |
| `transform(b, e, out, f)` | применить `f` к каждому, результат в `out` |
| `accumulate(b, e, init)` | сумма (или фолд с пользовательской `f`) |
| `copy_if(b, e, out, pred)` | отфильтровать в `out` |
| `any_of`, `all_of`, `none_of` | булевы проверки |
| `min_element`, `max_element` | итератор на минимум/максимум |
| `unique` | удалить подряд идущие дубликаты |
| `partition` | разделить по предикату |

Все алгоритмы принимают пару итераторов `(b, e)` — это и есть «range». Большинство возвращают итератор, по которому можно определить «где остановились».

### Почему это лучше рукописного цикла

На векторе из восьми `int` разница между алгоритмом и циклом выглядит косметической. Посмотрим на данных, чуть более похожих на настоящие: пачка событий, вычитанная агентом из системного буфера.

```cpp
struct Event {
    std::string image;
    int pid;
    bool suspicious;
};

std::vector<Event> batch = read_batch();

auto n = std::count_if(batch.begin(), batch.end(),
                       [](const Event& e) { return e.suspicious; });

bool alarm = std::any_of(batch.begin(), batch.end(),
                         [](const Event& e) { return !is_allowed(e.image); });

std::vector<Event> to_report;
std::copy_if(batch.begin(), batch.end(), std::back_inserter(to_report),
             [](const Event& e) { return e.suspicious; });
```

Сравните последнюю операцию с её рукописным эквивалентом:

```cpp
std::vector<Event> to_report;
for (size_t i = 0; i < batch.size(); ++i) {
    if (batch[i].suspicious) {
        to_report.push_back(batch[i]);
    }
}
```

Формально это то же самое, и никто не умрёт, если вы напишете так. Но у версии с алгоритмом есть три конкретных преимущества, и все три — про чтение, а не про производительность.

Во-первых, **название алгоритма говорит, что делает код, до того как вы прочитали тело**. Увидев `copy_if`, вы уже знаете: сейчас будет фильтрация, размер результата не больше исходного, порядок сохранится. Увидев `for (size_t i = 0; ...)`, вы не знаете ничего — цикл может фильтровать, а может суммировать, транспонировать или что-нибудь удалять, и придётся вчитаться, чтобы понять.

Во-вторых, в цикле есть места, где можно ошибиться, а в алгоритме их нет. Классика — `i <= batch.size()`, `++i` в неверном месте, обращение к `batch[i]` после того, как в `batch` что-то вставили. Ошибки такого рода не выдумка ради красивого аргумента; они составляют заметную долю реальных багов с выходом за границы.

В-третьих, алгоритм говорит читателю и то, чего он **не** делает. `count_if` не может изменить `batch` — он принимает элементы по `const&` и возвращает число. Рукописный цикл такой гарантии не даёт: чтобы убедиться, что он не портит контейнер по ходу, надо прочитать его целиком.

Отсюда та самая привычка: прежде чем писать цикл, потратьте десять секунд и проверьте, нет ли для этого готового алгоритма. Их в `<algorithm>` больше сотни, и половина рукописных циклов в реальном коде — это неудачно переписанный `find_if`, `copy_if` или `transform`.

### С контейнерами через итераторы

```cpp
std::vector<int> v = {1, 2, 3, 4, 5};
std::vector<int> doubled;
std::transform(v.begin(), v.end(), std::back_inserter(doubled),
               [](int x) { return x * 2; });
// doubled = {2, 4, 6, 8, 10}
```

`std::back_inserter` — output-итератор, который вызывает `push_back` у контейнера. Аналогично есть `front_inserter` (`push_front`), `inserter` (произвольная позиция).

### Бинарный поиск на отсортированном

Если диапазон **отсортирован**, линейный `find` избыточен — есть семейство бинарных:

```cpp
std::vector<int> v = {1, 3, 5, 7, 9};              // отсортирован!

auto it = std::lower_bound(v.begin(), v.end(), 5); // первый элемент >= 5
auto up = std::upper_bound(v.begin(), v.end(), 5); // первый элемент > 5
bool has = std::binary_search(v.begin(), v.end(), 5);
auto [lo, hi] = std::equal_range(v.begin(), v.end(), 5);  // сразу оба
```

`O(log n)` вместо `O(n)`. Критичное требование: **диапазон должен быть отсортирован** по тому же критерию, что используется в поиске. Если нет — поведение не определено, причём молча: функция что-то вернёт, но не то, что вы ожидаете.

`lower_bound` также используется для **вставки с сохранением порядка**:

```cpp
v.insert(std::lower_bound(v.begin(), v.end(), value), value);
```

Это, кстати, ровно то, как работает `std::flat_map` (C++23), про который мы говорили выше.

### Парадокс `remove`: почему он ничего не удаляет

Один из самых сбивающих с толку моментов STL:

```cpp
std::vector<int> v = {1, 2, 3, 2, 4};
std::remove(v.begin(), v.end(), 2);
// v == {1, 3, 4, ?, ?}  —  но v.size() всё ещё 5!
```

Почему? Вернёмся к главной идее лекции: **алгоритмы работают с итераторами, а не с контейнерами**. `std::remove` получил только пару итераторов — он физически не может изменить размер, потому что не знает, что это за контейнер и есть ли у него вообще понятие размера (а вдруг это обычный массив?).

Что `remove` реально делает: **сдвигает** «выживших» элементы в начало диапазона и возвращает итератор на новый логический конец. Всё, что за ним, остаётся в неопределённом состоянии (обычно — старые значения или moved-from объекты).

### Erase-remove idiom

Поэтому удаление в два шага: сначала алгоритм переставляет элементы, потом **метод контейнера** правит размер:

```cpp
auto new_end = std::remove(v.begin(), v.end(), 2);
v.erase(new_end, v.end());              // теперь size() == 3
```

Обычно это пишут одной строкой — та самая классическая **erase-remove idiom**:

```cpp
v.erase(std::remove(v.begin(), v.end(), 2), v.end());

v.erase(std::remove_if(v.begin(), v.end(),
                       [](int x) { return x % 2 == 0; }), v.end());
```

Эта конструкция десятилетиями встречалась в каждом C++-проекте. Выглядит она загадочно, но теперь понятно, откуда взялась: это следствие разделения «алгоритмы ↔ контейнеры».

### `std::erase` и `std::erase_if` (C++20)

В C++20 наконец добавили свободные функции, которые делают то, чего все всегда хотели:

```cpp
std::erase(v, 2);                                    // удалить все 2
std::erase_if(v, [](int x) { return x % 2 == 0; });   // удалить чётные
```

Работают для `vector`, `deque`, `list`, `forward_list`, `string`. Для ассоциативных контейнеров (`map`, `set`, `unordered_*`) есть `std::erase_if`.

**В новом коде используйте `erase_if`** — короче, понятнее, не оставляет шанса ошибиться с границами. Erase-remove idiom нужно **узнавать** при чтении существующего кода, но писать её самому больше не нужно.

## 10. Ограничение памяти в долгоживущем процессе

До сих пор мы выбирали контейнер по сложности операций. Есть ещё одно измерение выбора, которое почти не видно в учебных задачах и становится главным в реальных программах: **сколько памяти контейнер займёт через месяц работы**.

Так устроен любой долгоживущий агент, разбирающий поток событий с машины: процесс стартует один раз и работает неделями, а поток событий не кончается.

### Постановка

Программа получает бесконечный поток данных и накапливает по нему состояние: последние события, счётчики по ключам, кэш разобранных записей. Каждая отдельная вставка выглядит безобидно. Но контейнер, в который **только добавляют**, — это утечка памяти с полезной нагрузкой: формально всё достижимо и корректно освободится при выходе, фактически процесс растёт, пока его не убьёт OOM-killer.

**Правило:** если контейнер живёт столько же, сколько процесс, а данные в него приходят из потока — удаление старого должно быть частью дизайна структуры, а не оптимизацией «на потом».

Разница практическая. «На потом» означает, что политику вытеснения придётся вкручивать в уже написанный код, где выбран `std::vector`, итераторы раздаются наружу, а размер нигде не проверяется. Заложенное с самого начала ограничение — это выбор контейнера, поле «максимум» рядом с ним и одна функция обрезки.

### Две стратегии вытеснения

**По возрасту (скользящее окно).** Храним записи не старше `T`. Естественно для аналитики «что происходило за последние 5 минут»: старые данные не просто занимают место, они уже не нужны по смыслу задачи.

**По объёму (жёсткий предел).** Задаём верхнюю границу на количество записей или на байты и при переполнении вытесняем самые старые. Естественно для кэшей и буферов, где важно только «сколько мы готовы потратить».

Стратегии решают разные проблемы, и по отдельности каждая дырявая:

- Только возраст не спасает от **всплеска**: если за минуту пришёл миллион событий, окно в пять минут честно удержит все пять миллионов.
- Только объём не спасает от **медленного накопления** мусора: предел в миллион записей будет достигнут, и память останется занятой навсегда, даже если полезны из них последние сто.

**Правило большого пальца:** применяйте обе границы одновременно. Возраст задаёт смысл («данные старше T не нужны»), объём задаёт потолок («больше N мы не потратим ни при каких входных данных»).

### Почему для окна удобен `std::deque`

Скользящее окно — это добавление в конец и удаление из начала. У `std::deque` обе операции константные. У `std::vector` `push_back` тоже константный, но `erase(v.begin())` сдвигает **все** оставшиеся элементы — `O(n)` на каждое удаление, то есть квадратичное поведение на потоке.

**Подвох:** соблазн взять `vector` и «иногда» чистить его пачкой (`v.erase(v.begin(), v.begin() + k)`) работает, но требует аккуратности с индексами и всё равно копирует хвост. `deque` даёт то же поведение без ручной бухгалтерии.

Если верхняя граница известна заранее и она небольшая — стоит рассмотреть **кольцевой буфер** на `std::array<T, N>`: фиксированный размер, никаких аллокаций вообще, идеальная предсказуемость по памяти. Цена — размер нельзя изменить в рантайме, и переполнение надо обрабатывать явно.

### Пример: окно событий с двумя границами

```cpp
#include <chrono>
#include <cstddef>
#include <deque>
#include <iterator>
#include <string>
#include <unordered_map>
#include <utility>

using Clock = std::chrono::steady_clock;

struct Event {
    Clock::time_point ts;
    std::string image;
};

// Стратегия 1: по возрасту — выкидываем всё старше max_age.
void trim_by_age(std::deque<Event>& events, Clock::duration max_age) {
    const auto deadline = Clock::now() - max_age;
    while (!events.empty() && events.front().ts < deadline) {
        events.pop_front();
    }
}

// Стратегия 2: по объёму — жёсткий потолок на количество записей.
void trim_by_size(std::deque<Event>& events, std::size_t max_count) {
    while (events.size() > max_count) {
        events.pop_front();
    }
}
```

Обе функции вызываются периодически — например, раз в N обработанных событий или по таймеру:

```cpp
void on_event(std::deque<Event>& events, Event e) {
    events.push_back(std::move(e));

    using namespace std::chrono_literals;
    trim_by_age(events, 100s);
    trim_by_size(events, 32);
}
```

Записи в `deque` лежат в порядке поступления, поэтому обрезка по возрасту — это цикл `pop_front`, пока голова старая: искать по всему контейнеру не нужно.

### Вытеснение из ассоциативного контейнера

С `map` и `unordered_map` сложнее: порядка по времени в них нет, и «самый старый» приходится искать по всем элементам. Типичный подход — хранить в значении отметку последнего обращения и периодически выбрасывать всё, к чему давно не обращались:

```cpp
void evict_idle(std::unordered_map<std::string, Clock::time_point>& seen,
                Clock::duration max_idle) {
    const auto deadline = Clock::now() - max_idle;
    std::erase_if(seen, [deadline](const auto& item) {
        return item.second < deadline;
    });
}
```

`std::erase_if` (C++20) есть для всех стандартных контейнеров и делает ровно то, что нужно: проходит контейнер и удаляет подходящие элементы за один вызов.

**Подвох:** удаление во время ручного обхода — классическая ошибка. Так писать нельзя:

```cpp
for (auto it = seen.begin(); it != seen.end(); ++it) {
    if (it->second < deadline) {
        seen.erase(it);      // UB: it инвалидирован, ++it читает мусор
    }
}
```

Корректный ручной вариант использует возвращаемое значение `erase`:

```cpp
for (auto it = seen.begin(); it != seen.end(); ) {
    it = (it->second < deadline) ? seen.erase(it) : std::next(it);
}
```

`std::erase_if` снимает этот вопрос целиком — в новом коде пишите его.

### Чего периодическая чистка не гарантирует

**Инвалидация итераторов.** Удаление инвалидирует итераторы на удалённые элементы, а у некоторых контейнеров — и на остальные. У `deque` `pop_front` инвалидирует все итераторы; у `vector` `erase` инвалидирует всё от точки удаления и дальше; у `map`, `set` и хеш-таблиц страдают только удалённые элементы (плюс рехеш у неупорядоченных). Поэтому нельзя держать «долгоживущий» итератор или указатель на элемент контейнера, который чистится в фоне: сохраняйте ключ или индекс, а не итератор.

**Чистка без верхней границы не даёт гарантии.** Обрезка по возрасту раз в секунду ограничивает память только при условии, что поток медленнее чистки. Если событий приходит быстрее, чем успевает отработать очистка, между двумя её запусками контейнер вырастет — и оценка «памяти будет не больше X» перестаёт выполняться.

**Правило:** гарантию даёт только жёсткий потолок, проверяемый **в момент вставки**. Всё остальное — оптимизация среднего случая. Что делать при достижении потолка — выбрасывать самое старое, отбрасывать новое или считать переполнение ошибкой — зависит от задачи, но решение должно быть принято явно.

## 11. `ranges` — упоминание (C++20)

C++20 добавил **более удобную** форму алгоритмов:

```cpp
#include <ranges>

std::vector<int> v = {3, 1, 4, 1, 5, 9};

std::ranges::sort(v);                              // вместо v.begin(), v.end()

auto evens = v | std::views::filter([](int x) { return x % 2 == 0; });
for (int x : evens) std::cout << x << ' ';
```

Преимущества:

- Не нужно передавать `begin()` / `end()` — алгоритм принимает контейнер целиком.
- **Композиция через `|`** — функциональный pipeline-стиль.
- **Lazy evaluation** — `views::filter` не копирует данные, а строит «вид», который вычисляется при итерации.

Подробный разбор `ranges` выходит за рамки курса.

## Итоги

- **Итератор** — обобщённый указатель. `begin()`, `end()`, `++`, `*`. Полуоткрытый интервал `[begin, end)`.
- **`range-based for`** работает через `begin()`/`end()`. Пользовательские типы могут их предоставить.
- **Категории** иерархически: Input → Forward → Bidirectional → RandomAccess → Contiguous. Алгоритмы требуют минимальную категорию.
- **Последовательные:** `vector` по умолчанию, `array` для фикс. размера, `deque` для push_front, `list` редко.
- **Ассоциативные:** `unordered_map`/`set` по умолчанию, `map`/`set` если нужен порядок. На маленьких или с дорогим хешем — `map` может быть быстрее, плюс есть `std::flat_map` (C++23).
- **Адаптеры:** `stack`, `queue`, `priority_queue` — ограниченный интерфейс для конкретной семантики.
- **STL-алгоритмы + лямбды** заменяют большинство ручных циклов.
- **Контейнер, в который только добавляют, — утечка с полезной нагрузкой.** В долгоживущем процессе вытеснение старого закладывается в дизайн сразу.
- **Две границы, обе сразу:** по возрасту (скользящее окно на `deque`) и по объёму (жёсткий потолок). Только возраст не спасает от всплеска, только объём — от медленного накопления.
- **`std::erase_if`** — правильный способ удалять по условию, в том числе из `map`/`unordered_map`; ручное удаление во время обхода инвалидирует итератор.
- **Гарантию по памяти даёт только потолок, проверяемый при вставке.** Периодическая чистка ограничивает средний случай, а не максимум.
- **`ranges` (C++20)** — современный синтаксис с lazy-композицией. Подробный разбор — за рамками курса.

## Что дальше

Следующая лекция — **утилитарные типы и обработка ошибок**:

- `std::string_view`, `std::span` — non-owning views
- `std::optional`, `std::variant`, `std::expected`
- Третий подход к ошибкам и сравнение всех трёх — возвращаемся к теме лекции 3
- Ошибки на границе с C-API: коды возврата в `std::expected`
- Exception safety guarantees (basic / strong / nothrow)
- Краткое упоминание `std::error_code`
