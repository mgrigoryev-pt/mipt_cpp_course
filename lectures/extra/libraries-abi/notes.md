# Библиотеки и граница ABI

> Дополнительный материал курса: конспект для самостоятельного чтения. Слайдов к нему нет — он не читается на паре, а объясняет, что студент получил в комплекте практикума: собранные `os` и `edr` и два заголовка `extern "C"`. Опирается на материал [«Как C++ собирает программу»](../build-model/notes.md) — объектные файлы, линкер, name mangling — и на [«CMake поверх модели сборки»](../cmake-basics/notes.md).

## 0. О чём этот материал

В комплекте практикума нет исходников симулятора. Есть заголовки `include/os.h` и `include/edr.h` и по два файла на систему: `os.dll` с `os.lib` под Windows, `libos.so` под Linux. С этим можно писать агента, который вызывает функции симулятора, получает от него события и отдаёт ему детекты, — и ни разу не видеть кода по ту сторону.

Так распространяется любая закрытая библиотека, и устроено это проще, чем кажется. Но у такой поставки есть граница, которую компилятор не охраняет: чтобы две половины программы, собранные в разное время разными людьми, работали вместе, они должны совпадать не только в тексте заголовка, но и в двоичном устройстве. Это совпадение называется **ABI**, и почти всё необычное в `os.h` — `extern "C"`, коды возврата вместо исключений, буферы фиксированного размера, непрозрачный хендл — существует ради него.

К концу чтения вы должны:

- различать статическую и динамическую библиотеку и знать, что из них попадает в программу, а что нужно при запуске;
- понимать, что такое экспорт, импортная библиотека и почему DLL без экспорта бесполезна;
- различать API и ABI и приводить пример изменения, которое не ломает сборку, но ломает программу;
- объяснять, почему в интерфейсе библиотеки не передают `std::string`, не бросают исключений и не освобождают чужую память;
- читать `os.h` как набор решений, каждое из которых закрывает одну из этих проблем.

Примеры собраны clang 19 под Windows, файлы [ELF](../../glossary.md#pe-elf) (Executable and Linkable Format, формат Linux) получены им же кросс-компиляцией под Linux; таблицы экспорта и импорта сняты `llvm-readobj` и `llvm-nm` с настоящих `os.dll` и `libos.so` из комплекта.

## 1. Статическая библиотека — архив объектных файлов

Материал про модель сборки заканчивается на объектных файлах: у каждого есть машинный код и две таблицы, «предоставляю» и «требуется». **Статическая библиотека** — это просто несколько объектных файлов, сложенных в один архив. Под Windows у архива расширение `.lib`, под Linux — `.a`. Внутри ничего нового:

```
$ llvm-ar t geom.lib
geom.cpp.obj

$ llvm-nm -C geom.lib
geom.cpp.obj:
00000000 T double __cdecl area(double)
```

Когда [линкеру](../../glossary.md#linker) (linker) передают архив, он поступает с ним так же, как с отдельными объектными файлами, с одной поправкой: берёт из архива только те файлы, которые закрывают чьё-то «требуется». Остальное в программу не попадает.

Главное свойство статической библиотеки: её код **копируется** в исполняемый файл. После линковки архив больше не нужен — программа запустится на машине, где его нет.

## 2. Динамическая библиотека — ссылка вместо кода

**Динамическая библиотека** — `.dll` под Windows, `.so` под Linux — устроена наоборот. Это уже готовый исполняемый модуль, почти как программа, только без `main`. Код из неё в программу не копируется: в исполняемый файл записывается ссылка — «нужна библиотека `geom.dll`, из неё функция такая-то». Настоящий адрес подставляется при запуске.

![Слева статическая библиотека: из архива geom.lib линкер копирует объектный файл с кодом area в app.exe, и при запуске библиотека не нужна. Справа динамическая: из импортной geom.lib в app.exe попадает только таблица импорта со ссылкой на geom.dll, а код area остаётся в geom.dll и подключается при запуске; без неё программа не стартует](img/static-vs-dynamic.svg)

Ссылка видна своими глазами. Та же программа из трёх файлов, где `geom` собрана как `SHARED`:

```
$ llvm-readobj --coff-imports app.exe
  Name: geom.dll
  Symbol: ?area@@YANN@Z
  Name: MSVCP140D.dll
  Name: KERNEL32.dll
  ...
```

[Таблица импорта](../../glossary.md#import-table) (import table): из `geom.dll` нужна функция с именем `?area@@YANN@Z` — это `area(double)` после [name mangling](../../glossary.md#name-mangling) (по-русски — искажение имён), про него раздел 5. Ниже — ещё несколько библиотек, от которых зависит любая программа на C++ под Windows: стандартная библиотека C++ (`MSVCP140D.dll`, буква `D` — отладочная версия) и сама система (`KERNEL32.dll`).

Раз код остался снаружи, без библиотеки программа не запустится. Проверяется копированием `app.exe` в пустой каталог:

```
$ alone\app.exe
[exit 3221225781]
```

Ни строчки вывода, только [код завершения](../../glossary.md#exit-code) (exit code). В шестнадцатеричной записи это `0xC0000135` — «не найдена DLL». Запущенная двойным щелчком, программа показала бы окно с именем библиотеки; из терминала она просто завершается с этим кодом. Поэтому комплект после сборки кладёт `os.dll` и `edr.dll` рядом с агентом: каталог, где лежит сам `.exe`, Windows просматривает первым. На Linux так делать не нужно — путь к библиотекам записывается в исполняемый файл при сборке (раздел 9 материала про CMake).

Зачем вообще так делать, если статическая библиотека проще:

- **Одна копия на всех.** Системные библиотеки — `KERNEL32.dll`, `libc.so.6` — нужны каждой программе. Будь они статическими, каждая программа несла бы свою копию, а обновление системы требовало бы пересборки всего.
- **Замена без пересборки.** Исправленную библиотеку можно положить поверх старой, и программы подхватят её при следующем запуске. Правда, только если новая совместима со старой двоично — об этом разделы 4–6.
- **Поставка без исходников и без подробностей сборки.** Библиотеку собирают один раз, со своими флагами и своей стандартной библиотекой, а пользователи подключают готовый файл. Так поставлены `os` и `edr`.

Как именно система при запуске находит библиотеку, загружает её и вписывает адреса — отдельная тема. Здесь важно одно: ссылка записана в программе, а код — в другом файле, который обязан найтись.

## 3. Экспорт: что видно снаружи библиотеки

У статической библиотеки видно всё: линкер просто берёт объектные файлы с их таблицами. У динамической есть собственная таблица — **таблица экспорта**, — и наружу видно только то, что в неё попало. Здесь Windows и Linux ведут себя противоположно.

**Windows по умолчанию не экспортирует ничего.** Та же `geom`, собранная как `SHARED` без каких-либо пометок, собирается — а программа, которая её вызывает, нет:

```
[2/4] Linking CXX shared library geom.dll
[4/4] Linking CXX executable app.exe
FAILED: app.exe
lld-link: error: undefined symbol: double __cdecl area(double)
```

`geom.dll` существует, код `area` в ней есть, но в таблице экспорта пусто, и для программы функции нет. Чтобы функция попала в экспорт, её помечают `__declspec(dllexport)` при сборке библиотеки. Тот же заголовок подключают и пользователи, и им нужна другая пометка — `__declspec(dllimport)`. Поэтому заголовок библиотеки под Windows всегда начинается с макроса-переключателя:

```cpp
#if defined(_WIN32)
#if defined(GEOM_BUILD_SHARED)
#define GEOM_API __declspec(dllexport)  // собираем саму библиотеку
#else
#define GEOM_API __declspec(dllimport)  // подключаем готовую
#endif
#else
#define GEOM_API __attribute__((visibility("default")))
#endif

GEOM_API double area(double r);
```

`GEOM_BUILD_SHARED` задаётся только при сборке самой библиотеки: в CMake — `target_compile_definitions(geom PRIVATE GEOM_BUILD_SHARED)`, и слово `PRIVATE` здесь ровно то, что нужно (материал про CMake, раздел 4). С этим макросом в таблице экспорта появляется функция:

```
$ llvm-readobj --coff-exports geom.dll
Export {
  Ordinal: 1
  Name: ?area@@YANN@Z
}
```

**Импортная библиотека.** Рядом с `geom.dll` линкер кладёт `geom.lib` — но это не статическая библиотека из раздела 1, хоть расширение и то же. Это **импортная библиотека**: в ней нет кода, только заглушки, по которым линкер программы узнаёт, какие имена есть в DLL. Разница видна по размеру: у комплекта `os.dll` весит 137 КБ, а `os.lib` — 3,8 КБ. Внутри `os.lib` на каждую функцию по две записи:

```
$ llvm-nm os.lib
00000000 T __imp_os_init
00000000 T os_init
...
```

`__imp_os_init` — ячейка, в которую при запуске будет вписан настоящий адрес `os_init` из DLL. `os_init` — крошечная заглушка, которая прыгает по адресу из этой ячейки. Пометка `dllimport` позволяет компилятору вызывать функцию сразу через ячейку и обходиться без заглушки. Для функций это экономия одного перехода, поэтому без `dllimport` вызов тоже соберётся; для переменных, экспортированных из DLL, пометка обязательна.

У DLL без экспорта импортная библиотека тоже появляется — пустая, с одними служебными записями. Отсюда и `undefined symbol` выше, а не жалоба на отсутствующий файл.

**Linux по умолчанию экспортирует всё.** Импортной библиотеки там нет — линкер читает сам `.so`. Та же `geom.cpp`, собранная в `.so` без пометок:

```
$ llvm-nm -D libgeom.so
0000000000001280 T _Z4aread
```

Функция видна, хотя её никто не просил показывать. В большой библиотеке так наружу уезжают и все внутренние функции — они становятся частью интерфейса, их могут случайно вызвать, а компилятор лишается возможности их оптимизировать как внутренние. Поэтому библиотеки собирают с ключом `-fvisibility=hidden`, который прячет всё, и помечают нужное `__attribute__((visibility("default")))` — это ветка `#else` в макросе выше. С ключом и без пометки:

```
$ llvm-nm -D libgeom_hidden.so
libgeom_hidden.so: no symbols
```

В `os.h` макрос устроен так же, только в три состояния:

```c
#if defined(_WIN32)
#  if defined(OS_BUILD_SHARED)
#    define OS_EXPORT __declspec(dllexport)
#  elif defined(OS_USE_SHARED)
#    define OS_EXPORT __declspec(dllimport)
#  else
#    define OS_EXPORT
#  endif
#elif defined(OS_BUILD_SHARED)
#  define OS_EXPORT __attribute__((visibility("default")))
#else
#  define OS_EXPORT
#endif
```

Третье состояние — пустой макрос — для сборки симулятора статической библиотекой. `OS_USE_SHARED` студент нигде не задаёт: его раздаёт цель `os` в CMake как `INTERFACE`-определение, и он доезжает до каждого файла, который подключает `os` (материал про CMake, раздел 9). В таблице экспорта `os.dll` ровно тринадцать имён — те тринадцать функций, что объявлены в `os.h` с пометкой `OS_EXPORT`. Внутренних символов симулятора там нет.

## 4. API и ABI

**API** (application programming interface) — договор на уровне исходного текста: какие функции есть, какие у них параметры, что они возвращают. Его проверяет компилятор, читая заголовок. Если API библиотеки изменился несовместимо, код пользователя перестаёт компилироваться — неприятно, но честно.

**[ABI](../../glossary.md#abi)** (application binary interface) — договор на уровне машинного кода. Он отвечает на вопросы, которых в исходнике не видно:

- под каким именем функция лежит в таблице символов;
- **[calling convention](../../glossary.md#calling-convention)** — в каких регистрах и в каком порядке передаются аргументы, куда кладётся результат, кто снимает аргументы со стека и какие регистры обязаны пережить вызов;
- какой у структуры размер, по каким смещениям лежат поля, какое у неё [выравнивание](../../glossary.md#alignment) (alignment; лекция 6, раздел 3);
- как устроена [vtable](../../glossary.md#vtable) — таблица адресов [виртуальных функций](../../glossary.md#virtual-function) (virtual functions) — и где в объекте указатель на неё (лекция 7, раздел 7);
- как бросается и ловится исключение;
- чья [куча](../../glossary.md#heap) (heap) выделила память и кто вправе её освободить.

Библиотека и программа, собранные раздельно, обязаны совпадать во всём этом. Проверить совпадение некому: компилятор видит одну [единицу трансляции](../../glossary.md#translation-unit) (translation unit), а линкер сверяет только имена. Когда API не изменился, а ABI — изменился, сборка проходит, а программа ломается.

Пример из жизни поставщика библиотек: в новой версии в структуру добавили поле. Программа собрана со старым заголовком, библиотека — с новым:

```cpp
// info_v1.h — с ним собрана программа
struct ProcessInfo {
    int pid;
    int ppid;
};

void fill_info(ProcessInfo* out);
```

```cpp
// info_v2.h — с ним собрана библиотека: в середину добавлено поле
struct ProcessInfo {
    int pid;
    char user[8];
    int ppid;
};

void fill_info(ProcessInfo* out);
```

```cpp
// lib.cpp, собрана с info_v2.h
void fill_info(ProcessInfo* out) {
    out->pid = 4242;
    std::strcpy(out->user, "root");
    out->ppid = 1;
}

// app.cpp, собрана с info_v1.h
int main() {
    ProcessInfo info{};
    fill_info(&info);
    std::print("pid={} ppid={}\n", info.pid, info.ppid);
}
```

Имя функции в обеих версиях одно, тип параметра — «указатель на `ProcessInfo`» — тоже. Компилятор доволен каждым файлом по отдельности, линкер нашёл `fill_info`. А по памяти происходит вот что:

![Программа собрана с заголовком версии 1 и отвела под ProcessInfo восемь байт: pid и ppid. Библиотека собрана с версией 2 и пишет по своему layout шестнадцать байт: pid, восемь байт user, ppid. Всё, что дальше восьмого байта, ложится на соседние данные стека](img/abi-break.svg)

Программа отвела на стеке восемь байт, библиотека пишет шестнадцать. Собранная обычным образом, программа в этом прогоне упала, не напечатав ничего:

```
[exit 3221225477]
```

`0xC0000005` — [нарушение доступа](../../glossary.md#access-violation) (access violation): запись за концом `info` испортила что-то на стеке `main`. Под [AddressSanitizer](../../glossary.md#asan) (ASan) то же самое видно по существу:

```
ERROR: AddressSanitizer: stack-buffer-overflow on address 0x005af00ff8a8
WRITE of size 5 at 0x005af00ff8a8 thread T0
    #0 in strcpy
    #1 in fill_info(struct ProcessInfo *) lib.cpp:7
    #2 in main app.cpp:7

  This frame has 2 object(s):
    [32, 40) 'info' (line 6) <== Memory access at offset 40 overflows this variable
```

Восемь байт `info` (с 32-го по 40-й), а запись идёт с 40-го. Упасть могло и иначе, а могло не упасть вовсе и напечатать неверный `ppid` — это [UB](../../glossary.md#ub) (undefined behavior), подробнее — в материале [«Undefined behavior и его соседи»](../undefined-behavior/notes.md).

Добавить поле в конец структуры тоже нельзя: размер всё равно меняется, и память по-прежнему выделяет тот, кто знает старый размер. Изменения, которые ABI не ломают, — это добавление **новых** функций и новых типов, не задевающих старые.

**Правило:** всё, что видно в заголовке библиотеки, — часть её ABI. Если размер структуры виден пользователю, менять структуру уже нельзя.

Отсюда два приёма, которые `os.h` использует оба.

- **Непрозрачный хендл.** `typedef struct os_handle os_handle;` — тип объявлен, но не определён. Пользователь не знает его размера и не может создать такой объект сам: только получить указатель из `os_init` и вернуть его в `os_free`. Раз размер никому снаружи не известен, внутри его можно менять как угодно.
- **Номер версии.** `#define OS_API_VERSION 1` — константа в заголовке, по которой видно, против какой версии договора собран код.

Там, где структуру всё же приходится показывать — `os_process_info`, `os_event`, — она объявлена один раз и больше не меняется: `SPEC.md` разрешает расширять границу новыми функциями, но не менять существующее.

## 5. Два C++ ABI

Одно из совпадений, которых требует ABI, — имена символов. Материал про модель сборки показывает, что компилятор C++ кодирует в имя символа типы параметров — это name mangling: `double area(double)` становится `_Z4aread`. Это правило не из стандарта C++ — стандарт про имена символов не говорит ничего, — а из ABI платформы. И платформ здесь две.

Одна и та же `geom.cpp`, собранная одним и тем же clang 19 под две системы:

| | Windows | Linux |
|---|---|---|
| имя `double area(double)` в таблице | `?area@@YANN@Z` | `_Z4aread` |
| чьё это правило | ABI Microsoft (MSVC) | Itanium C++ ABI |
| кто ему следует | MSVC и clang под Windows | GCC и clang под Linux и macOS |

clang умеет оба и выбирает по целевой системе: под Windows он обязан совпадать с MSVC, иначе не смог бы пользоваться стандартной библиотекой и системными DLL, собранными MSVC. Имена — только видимая часть. [Layout](../../glossary.md#layout) (по-русски — размещение в памяти) классов с виртуальными функциями, передача объектов по значению, устройство исключений между этими ABI тоже различаются. Код, собранный под одно, с кодом под другое не линкуется и не должен.

Та же картина в таблицах импорта библиотек комплекта. `os.dll` импортирует из стандартной библиотеки Microsoft имена вида

```
??1?$basic_ostream@DU?$char_traits@D@std@@@std@@UEAA@XZ
```

а `libos.so` из стандартной библиотеки GCC — имена вида

```
_ZNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEE15_M_replace_coldEPcmPKcmm@GLIBCXX_3.4.31
```

В этом имени больше, чем кажется. После demangling (`llvm-cxxfilt`) это `std::__cxx11::basic_string<char, …>::_M_replace_cold(…)`, и в имени есть две метки ABI сразу:

- `__cxx11` — [пространство имён](../../glossary.md#namespace) (namespace), которого нет в стандарте. В 2015 году, с GCC 5, стандартная библиотека GCC поменяла устройство `std::string`, чтобы соответствовать C++11. Старый и новый варианты несовместимы двоично, и новый поместили в отдельное пространство имён, чтобы программа, собранная со старым, получала ошибку линковки, а не падение. Разница с разделом 4 ровно в этом: здесь поломку ABI превратили в разницу имён, и её увидел линкер;
- `@GLIBCXX_3.4.31` — версия символа. Библиотеке нужна `libstdc++` не старее той, в которой этот символ появился. На системе со старой `libstdc++` [загрузчик](../../glossary.md#loader) (loader) откажется запускать программу.

`extern "C"` выключает name mangling: имя в таблице становится просто именем функции. В C name mangling нет, поэтому имя `os_init` одинаково на обеих системах, у всех компиляторов:

```
$ llvm-nm -D libos.so                        $ llvm-readobj --coff-exports os.dll
0000000000007e20 T os_free                     Name: os_free
00000000000082a0 T os_init                     Name: os_init
0000000000007f20 T os_wait                     Name: os_wait
...                                            ...
```

Внутри `os.dll` — C++23 со стандартной библиотекой Microsoft, внутри `libos.so` — C++23 со стандартной библиотекой GCC. Снаружи у обоих одинаковые тринадцать имён без единого следа C++. Так `extern "C"` становится общим знаменателем: библиотеку на C++ может вызвать программа, собранная любым компилятором и на любом языке, умеющем вызывать C.

## 6. Почему через границу не передают `std::string`

Раз имена можно сделать простыми, кажется, что остальное — дело техники: объявить `extern "C" void os_set_name(std::string name)`, и готово. Так делать нельзя, и `os.h` говорит об этом прямо: «Ничего из стандартной библиотеки C++ через границу не проходит». Причин три.

**Устройство `std::string` не одинаково.** Стандарт описывает, что строка умеет, но не как она лежит в памяти. У каждой стандартной библиотеки свой layout: у библиотеки GCC строка занимает 32 байта, у libc++ из LLVM — 24. У библиотеки Microsoft размер зависит ещё и от [типа сборки](../../glossary.md#build-type) (build type) — замер на clang 19 под Windows:

```
Release:  string 32, vector<int> 24, map<int, int> 16
Debug:    string 40, vector<int> 32, map<int, int> 24
```

В отладочной сборке каждый контейнер несёт дополнительный указатель — через него работают проверки итераторов. Библиотека, собранная в Release, и программа, собранная в Debug, при передаче `std::string` по-разному понимали бы один и тот же объект — ровно как `ProcessInfo` в разделе 4.

Для статической линковки Microsoft эту ошибку ловит: заголовки стандартной библиотеки кладут в каждый объектный файл метку типа сборки, и линкер отказывается соединять несовпадающие:

```
error LNK2038: mismatch detected for '_ITERATOR_DEBUG_LEVEL': value '2' doesn't match value '0' in mix_app.o
error LNK2038: mismatch detected for 'RuntimeLibrary': value 'MDd_DynamicDebug' doesn't match value 'MD_DynamicRelease' in mix_app.o
```

Через границу DLL такая метка не проходит — там линкер видит только имена, — и защита пропадает.

**Память должна вернуться туда, откуда пришла.** `std::string` сама выделяет память под длинный текст и сама освобождает её в деструкторе. Если строку создала библиотека, а уничтожила программа, то `delete` выполнит [аллокатор](../../glossary.md#allocator) (allocator) программы над блоком, выделенным аллокатором библиотеки. Это не обязательно один и тот же аллокатор: у DLL, собранной со статической стандартной библиотекой, своя куча, а отладочная и обычная версии стандартной библиотеки Microsoft — вообще разные DLL со своими аллокаторами. Освобождение блока чужой кучей — UB.

**Правило:** память освобождает тот модуль, который её выделил. Отсюда пары `os_init` / `os_free` и `edr_init` / `edr_free`: хендл создаёт и уничтожает библиотека, программа только держит указатель.

**Строки на время вызова.** Там, где строку всё же надо передать, `os.h` передаёт `const char*` — указатель на символы, [владение](../../glossary.md#ownership) (ownership) которыми остаётся за отдавшей стороной. Для событий договор такой: строки внутри `os_event` действительны только на время вызова [колбэка](../../glossary.md#callback) (callback), нужно сохранить — копируйте. Для запросов наоборот: `os_process_info` содержит буферы фиксированного размера — `char image[OS_MAX_PATH]`, — и библиотека копирует данные в структуру, которую выделил вызывающий. Комментарий в `os.h` объясняет это одной фразой: «фиксированные буферы именно для того, чтобы вопроса о владении не возникало».

Приятное следствие, которое `os.h` тоже называет вслух: раз через границу не ходит ничего из стандартной библиотеки, у программы и библиотеки могут быть **разные** стандартные библиотеки. Агент в [пресете](../../glossary.md#preset) (preset) `debug-windows` собирается с отладочной `MSVCP140D.dll`, а `os.dll` пользуется обычной `MSVCP140.dll` — в одном процессе живут две стандартные библиотеки, и это законно, потому что ни один их объект не пересекает границу.

## 7. Исключения на границе

Исключение — тоже часть ABI: как описан бросаемый объект, как ищется подходящий `catch`, как [раскручивается стек](../../glossary.md#stack-unwinding) (stack unwinding), у Microsoft и Itanium устроено по-разному. Код на C о нём не знает вовсе. Если исключение вылетает из функции C++ и летит через кадр, скомпилированный как C или просто без поддержки исключений, раскрутка стека через этот кадр — UB.

Поэтому граница комплекта закрыта в обе стороны:

- **изнутри наружу** исключения не выходят никогда: `SPEC.md` требует, чтобы всё было поймано внутри и превращено в код возврата. Каждая функция `os.h` возвращает `os_status`;
- **снаружи внутрь** — через колбэк — тоже. Колбэк вызывается из библиотеки, и исключение из него полетело бы через её кадры. `os.h` называет это нарушением контракта и советует помечать колбэк `noexcept`, чтобы обещание было видно в коде.

`noexcept` здесь делает больше, чем документирует. Исключение, дошедшее до границы `noexcept`-функции, не летит дальше: программа вызывает `std::terminate` в этой точке. Падение громкое, но определённое — лучше, чем раскрутка через чужие кадры.

Как превратить коды возврата в `std::expected`, чтобы остальной код их не видел, — лекция 14, раздел 8. Как протащить объект с состоянием через `void* ctx` в колбэк — лекция 10, раздел 8. Обе обёртки живут **над** границей: сама граница остаётся на C.

## 8. Граница комплекта целиком

Теперь `os.h` читается как список решений, и каждое закрывает один из разделов выше.

![Граница os.h в три слоя. Сверху ваш код на C++23: RAII-хендл вместо ручного os_free, std::expected вместо os_status, лямбда через трамплин. Посередине граница extern C: проходят числа фиксированного размера, const char* на время вызова, POD-структуры с буферами фиксированного размера, непрозрачный os_handle* и код os_status, указатель на функцию и void* ctx; не проходят std::string, std::vector и прочее из std, исключения, классы с виртуальными функциями и память, которую освобождает не тот, кто её выделил. Снизу os.dll, внутри тоже C++23 со стандартной библиотекой Microsoft, но наружу из неё не выходит ничего](img/boundary.svg)

| Решение в `os.h` | Что оно закрывает | Раздел |
|---|---|---|
| `extern "C"` вокруг всех объявлений | разные схемы name mangling у компиляторов | 5 |
| макрос `OS_EXPORT` | экспорт под Windows и видимость под Linux | 3 |
| `typedef struct os_handle os_handle;` | размер объекта не виден, внутри его можно менять | 4 |
| пара `os_init` / `os_free` | память освобождает тот, кто выделил | 6 |
| `uint32_t`, `uint64_t` вместо `int`, `long` | размер числа одинаков везде | 4 |
| буферы `char[OS_MAX_PATH]` в структурах запросов | нет вопроса о владении строкой | 6 |
| `const char*` в событиях «на время колбэка» | строка не пересекает границу как объект | 6 |
| код возврата `os_status` вместо исключений | исключения не пересекают C | 7 |
| колбэк `void (*)(const os_event*, void*)` | ни `std::function`, ни лямбды C не знает | 7; лекция 10 |
| `OS_API_VERSION` | видно, против какой версии собран код | 4 |

Про `uint32_t` стоит сказать отдельно. `long` занимает 4 байта на 64-битной Windows и 8 байт на 64-битном Linux (материал про undefined behavior, раздел 3). Поле `long` в структуре границы значило бы разный layout на разных системах; [типы фиксированного размера](../../glossary.md#fixed-width) (fixed-width integer types) этот вопрос снимают.

## 9. Статическая или динамическая

| | Статическая | Динамическая |
|---|---|---|
| что попадает в программу | копия нужных объектных файлов | только ссылка: имя библиотеки и функции |
| нужна ли при запуске | нет | да — рядом с программой или по путям поиска |
| обновить библиотеку | пересобрать программу | заменить файл — если ABI не изменился |
| что видно снаружи | всё, что есть в объектных файлах | только экспорт |
| совпадение типа сборки и стандартной библиотеки | обязательно, линкер Microsoft проверяет | обязательно для всего, что пересекает границу |

Статическая библиотека проще: нечего искать при запуске, нет таблиц экспорта, не нужна дисциплина границы — если библиотека собрана тем же компилятором с теми же флагами. Динамическая нужна там, где библиотеку поставляют отдельно от программы, обновляют отдельно или делят между многими программами.

Комплект практикума — именно такой случай: `os` и `edr` собраны один раз, а агента студенты собирают разными пресетами — `windows`, `debug-windows`, `asan-windows`, — с разными типами сборки и с [санитайзером](../../glossary.md#sanitizer) (sanitizer). Одна и та же `os.dll` работает со всеми, потому что граница на C и стандартная библиотека каждой стороны остаётся при ней.

## Итоги

- Статическая библиотека — архив объектных файлов; нужное из неё копируется в программу, и при запуске она не нужна.
- Динамическая библиотека — отдельный модуль; в программу записывается ссылка в таблице импорта, и без библиотеки программа не стартует (`0xC0000135` под Windows).
- Наружу из динамической библиотеки видна только таблица экспорта. Windows по умолчанию не экспортирует ничего (`__declspec(dllexport)`), Linux — всё (`-fvisibility=hidden` плюс `visibility("default")`). Импортная `.lib` под Windows — заглушки без кода.
- API — договор по исходному тексту, его проверяет компилятор. ABI — по машинному коду: имена, передача аргументов, layout структур, исключения, аллокатор. Его не проверяет никто, и нарушение даёт собранную, но сломанную программу.
- Всё, что видно в заголовке, — часть ABI. Непрозрачный хендл прячет размер объекта; менять можно только добавлением нового.
- Схем name mangling в C++ две: Microsoft и Itanium. `extern "C"` даёт одно простое имя на всех.
- `std::string` не передают через границу: layout зависит от стандартной библиотеки, её версии и типа сборки, а память должна вернуться туда, откуда пришла.
- Исключение не пересекает C-границу ни в одну сторону; колбэк помечается `noexcept`.
- `os.h` — это набор таких решений: `extern "C"`, `OS_EXPORT`, непрозрачный хендл, пара `init` / `free`, типы фиксированного размера, буферы в структурах, коды возврата.
