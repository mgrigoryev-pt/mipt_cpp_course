# Строки и кодировки

> Дополнительный материал курса: конспект для самостоятельного чтения. Слайдов к нему нет — он не читается на паре, а разворачивает то, что лекция 1 называет одной фразой: «тема юникода в C++ исторически больная». Здесь — почему `size()` строки не равен числу букв, откуда берутся кракозябры в консоли Windows и почему файл с русским именем не открывается по `std::string`.

## 0. О чём этот материал

У текста в программе на C++ три симптома, которые встречаются всем.

- `std::string("детект").size()` равен 12, а не 6.
- Русский текст из программы в консоли Windows превращается в `╨┤╨╡╤В╨╡╨║╤В` — а иногда не превращается, и непонятно, от чего это зависит.
- Файл `журнал.log` существует, а `std::ifstream` его не открывает.

Все три — одно и то же явление: строка в C++ — это **байты**, а не буквы, и каждый участник по пути — редактор, компилятор, программа, консоль, файловая система — должен одинаково понимать, какими байтами записана какая буква. Там, где двое понимают по-разному, текст ломается.

К концу чтения вы должны:

- различать символ, кодовую точку и байт и знать, как устроен UTF-8;
- знать, что делают со строкой UTF-8 `size()`, `substr` и `std::toupper`, и чего они не делают;
- различать `char`, `char8_t`, `char16_t`, `char32_t`, `wchar_t` и знать, что из них разное на Windows и Linux;
- объяснять, где по пути от исходника до экрана текст может сломаться, и чинить каждое место;
- открывать файлы с нелатинскими именами на Windows правильно.

Примеры собраны clang 19 под Windows 11 с русской [локалью](../../glossary.md#locale) (locale); один опыт — компилятором MSVC для сравнения. Вывод консоли снят с настоящей консоли: программа читала собственный экран.

## 1. Символ, кодовая точка, байт

**Юникод** — таблица, которая каждому символу всех письменностей даёт номер: **[кодовую точку](../../glossary.md#code-point)** (code point). У буквы «д» номер `U+0434`, у латинской «a» — `U+0061`, у 🙂 — `U+1F642`. Номеров больше миллиона, и в один байт они не помещаются.

**Кодировка** — правило, по которому номер записывается байтами. Для юникода их три:

- **UTF-8** — от одного до четырёх байт на символ; латиница занимает один байт и совпадает с ASCII;
- **UTF-16** — два байта на большинство символов и четыре на редкие;
- **UTF-32** — всегда четыре байта.

До юникода каждая страна жила со своей **однобайтовой [кодовой страницей](../../glossary.md#code-page)** (code page): 256 значений, из них 128 — ASCII, остальные — местный алфавит. Для кириллицы их до сих пор две в ходу на Windows: 1251 — в программах с окнами и в файловых API, 866 — в консоли, наследство DOS. Одна и та же буква «д» записывается так:

| Кодировка | Байты «д» |
|---|---|
| UTF-8 | `d0 b4` |
| кодовая страница 1251 | `e4` |
| кодовая страница 866 | `a4` |
| UTF-16 | `34 04` (одна 16-битная [кодовая единица](../../glossary.md#code-unit) (code unit) `0x0434`) |

Прочитать байты не той кодировкой — и получится другой текст. Никакой ошибки при этом не будет: у байтов нет пометки, какой кодировкой они записаны.

## 2. UTF-8 изнутри

UTF-8 устроен так, что по каждому байту видно, чем он является.

![Строка детект в UTF-8: шесть букв, двенадцать байт, по два на букву — d0 b4, d0 b5, d1 82, d0 b5, d0 ba, d1 82. substr(0, 5) режет посреди третьей буквы: остаётся одинокий первый байт d1, на экране де и символ замены. Ниже формы байтов: 0xxxxxxx — один байт, ASCII; 110xxxxx 10xxxxxx — два байта, кириллица, греческий, диакритика; 1110xxxx и два продолжения — три байта, большинство остальных письменностей; 11110xxx и три продолжения — четыре байта, в том числе эмодзи f0 9f 99 82. Байт вида 10xxxxxx — всегда продолжение, с него буква не начинается](img/utf8-bytes.svg)

Замер на нескольких строках:

```
abc      size() =  3, кодовых точек 3
детект   size() = 12, кодовых точек 6
naïve    size() =  6, кодовых точек 5
🙂       size() =  4, кодовых точек 1
"д"            d0 b4
"🙂"           f0 9f 99 82
```

Кодовые точки считаются одной строкой: достаточно не считать байты-продолжения, у которых старшие биты `10`.

```cpp
std::size_t count_code_points(std::string_view utf8) {
    std::size_t n = 0;
    for (unsigned char c : utf8) {
        if ((c & 0xC0) != 0x80) {
            ++n;
        }
    }
    return n;
}
```

Но и кодовая точка — ещё не то, что человек называет буквой. «й» бывает записана одной кодовой точкой, а бывает двумя — «и» и отдельным знаком краткой над ней; на экране они неотличимы, а строки не равны. Эмодзи с оттенком кожи — несколько кодовых точек. Что считать одним видимым символом — **[графемой](../../glossary.md#grapheme)** (grapheme cluster), — определяют правила юникода, и их реализуют специальные библиотеки. В курс они не входят; важно знать, что `size()` считает байты, подсчёт выше — кодовые точки, а графемы — это третье число.

## 3. Что это значит для кода

Всё, что в `std::string` работает с индексами и отдельными `char`, работает с **байтами**.

**`size()` — байты.** Для ограничения длины поля в байтах это как раз то, что нужно. Для «не больше 20 символов на экране» — нет. Так же и в правиле курса про 80 колонок: `project/README.md` напоминает, что русский комментарий в UTF-8 весит вдвое больше, чем занимает на экране.

**`substr` и `[]` режут по байтам** и могут разрезать букву:

```
substr(0, 5)   d0 b4 d0 b5 d1
напечатано: [де�]
```

Последний байт `d1` — начало буквы без продолжения. Такая строка — уже не корректный UTF-8, и при выводе вместо обрывка печатается символ замены (replacement character) `�`.

**`std::toupper` — по одному байту и только ASCII:**

```
toupper: детект → детект, detect → DETECT
```

Функция получает один байт, а у кириллической буквы их два, и ни один по отдельности буквой не является. Регистронезависимое сравнение нелатинских строк — работа для библиотеки юникода.

**Поиск ASCII-разделителей безопасен.** Все байты многобайтовых последовательностей — `0x80` и выше, поэтому байт `'='`, `';'` или `','` не может оказаться внутри русской буквы. Разбор строки телеметрии вида `path=C:\Отчёты\q3.xlsx;user=иванов` по разделителям через `std::string_view` (лекция 14, раздел 2) работает на UTF-8 без изменений. Найти подстроку тоже можно обычным `find`: запись одного символа никогда не встречается внутри записи другого.

Для практикума отсюда важное следствие. `os.h` говорит, что пути сравниваются побуквенно — без приведения регистра и слешей — и что нормализация путей — задача агента. Для латиницы это `std::tolower` по байтам. Для пути с кириллицей тот же код молча ничего не сделает: `C:\Отчёты` и `C:\ОТЧЁТЫ` останутся разными строками. Контракт `os.h` кодировку строк не оговаривает; настоящий агент на Windows получал бы пути от системы в UTF-16 и переводил бы их в UTF-8 на границе.

## 4. Типы символов

| Тип | Литерал | Что в нём | Размер |
|---|---|---|---|
| `char` | `"детект"` | байты; у clang — UTF-8 | 1 байт |
| `char8_t` (C++20) | `u8"детект"` | байты UTF-8, и тип это гарантирует | 1 байт |
| `char16_t` | `u"детект"` | кодовые единицы UTF-16 | 2 байта |
| `char32_t` | `U"детект"` | кодовые точки UTF-32 | 4 байта |
| `wchar_t` | `L"детект"` | «широкий» символ платформы | 2 байта на Windows, 4 на Linux |

Замер `sizeof(wchar_t)` дал 2 под Windows; под Linux проверка `static_assert(sizeof(wchar_t) == 4)` при кросс-компиляции проходит. На Windows `wchar_t` — это UTF-16, на Linux — UTF-32. Поэтому `std::wstring` непереносим: одна и та же строка занимает разное число кодовых единиц, а 🙂 на Windows занимает **два** `wchar_t` — **[суррогатную пару](../../glossary.md#surrogate)** (surrogate pair) из двух половинок:

```
u16string(🙂).size() = 2
```

`char8_t` — самый молодой и самый неудобный. Он появился, чтобы тип строки говорил о кодировке, но стандартная библиотека почти целиком написана для `char`: `std::u8string` не передать туда, где ждут `std::string`, без копирования, и `std::print` его не принимает.

**Правило:** внутри программы текст хранится в `std::string` в UTF-8. Другие представления появляются только на границах — там, где их требует чужой интерфейс, — и переводятся туда и обратно в одном месте.

## 5. Компилятор: в какой кодировке исходник

Первое место, где текст может сломаться, — ещё до запуска. Файл `.cpp` — тоже байты, и компилятор должен знать, какой кодировкой записаны литералы в нём. Редактор курса сохраняет файлы в UTF-8. clang читает исходники как UTF-8. MSVC без указаний читает их в кодовой странице системы — на русской Windows это 1251.

Файл с одной строкой `const wchar_t* word = L"детект";`, собранный MSVC дважды:

```
cl /std:c++latest wide.cpp
wcslen(L"детект") = 12, code units: 0420 0491 0420 00b5 0421 201a 0420 00b5 0420 0454 0421 201a
sizeof("детект") - 1 = 12

cl /std:c++latest /utf-8 wide.cpp
wcslen(L"детект") = 6, code units: 0434 0435 0442 0435 043a 0442
sizeof("детект") - 1 = 12
```

Без ключа компилятор прочитал байты `d0 b4` как две буквы кодировки 1251 — «Рґ» — и честно записал в широкую строку их: двенадцать неверных кодовых единиц вместо шести. С ключом `/utf-8` — шесть правильных, `0434` это «д».

Обычная строка при этом в обоих случаях — 12 байт, те же самые: MSVC прочитал их как 1251 и записал обратно в 1251, и ошибка не видна. Поэтому такие проекты годами живут с неправильной настройкой и ломаются на первом `L"…"` или на первом символе, которого в 1251 нет.

`CMakeLists.txt` комплекта передаёт MSVC `/utf-8` вместе с предупреждениями — в цели `nano_edr_warnings` (материал [«CMake поверх модели сборки»](../cmake-basics/notes.md), раздел 4). clang ключ не нужен.

![Путь строки детект от исходника до экрана и два места, где она ломается. Файл .cpp хранит байты UTF-8. clang и MSVC с /utf-8 читают их верно, и L-литерал получает 6 символов; MSVC без ключа читает файл в 1251, и L-литерал получает 12 неверных символов — в комплекте MSVC получает /utf-8 из CMakeLists.txt. В программе строка — те же 12 байт UTF-8. std::print сама переводит текст в UTF-16 и показывается верно при любой кодовой странице; std::cout и printf отдают байты как есть, и консоль в 866 показывает ╨┤╨╡╤В╨╡╨║╤В, а после chcp 65001 — детект](img/text-path.svg)

## 6. Консоль Windows

Второе место — вывод. Консоль Windows показывает байты, прочитав их по своей **кодовой странице**, а она по умолчанию на русской системе — 866:

```
кодовая страница консоли: 866
std::print: детект
std::cout:  ╨┤╨╡╤В╨╡╨║╤В
printf:     ╨┤╨╡╤В╨╡╨║╤В
```

Одна программа выводит одну и ту же строку трижды, и на экране разное. `std::cout` и `printf` отдали консоли двенадцать байт UTF-8 как есть, консоль прочитала их как 866: байт `d0` в этой кодовой странице — символ рамки `╨`, байт `b4` — `┤`. Каждая русская буква превратилась в два символа псевдографики.

`std::print` показал правильно. По стандарту C++23, если строковые литералы программы в UTF-8 и вывод идёт в терминал, `std::print` пишет через родной для терминала интерфейс юникода. Стандартная библиотека Microsoft так и делает: переводит текст в UTF-16 и передаёт его консоли её собственной функцией для UTF-16, в обход кодовой страницы. Это ещё одна причина писать вывод через `std::print`, как это делает курс.

После `chcp 65001` — переключения консоли на UTF-8 — правильно выводят все три:

```
кодовая страница консоли: 65001
std::print: детект
std::cout:  детект
printf:     детект
```

Это и есть совет из `SETUP.md`, раздел про частые проблемы: при [кракозябрах](../../glossary.md#mojibake) (mojibake) — `chcp 65001` или терминал, работающий в UTF-8. Он нужен там, где вывод идёт байтами: через `std::cout`, `printf` или из программ, собранных не так, как курс.

**Вывод в файл или в канал** консолью не читается, и перевода нет: в файл уходят те же байты UTF-8. Кодировку должна знать программа, которая этот вывод читает. Скрипт на Python, который получает вывод через канал, по умолчанию декодирует его в кодировке системы, то есть в 1251, — и показывает кракозябры, хотя программа вывела совершенно корректный UTF-8. Лечится не в программе на C++, а в читающем скрипте: указать `encoding="utf-8"`.

На Linux этой главы почти нет: терминалы там работают в UTF-8, и байты UTF-8 из программы показываются как есть.

## 7. Пути к файлам на Windows

Третье место — файловая система. Имена файлов в NTFS хранятся в UTF-16, и у каждой функции Windows, принимающей строку, есть две версии: с суффиксом `W` принимает UTF-16, с суффиксом `A` — байты в кодовой странице системы, 1251, и переводит их в UTF-16 сама. Стандартная библиотека Microsoft для `std::ifstream` со строкой `std::string` понимает байты как 1251.

Файл `журнал.log` создан, а открыть его пытаются двумя способами:

```cpp
const std::filesystem::path path{u8"журнал.log"};
std::ofstream{path} << "запись\n";

std::ifstream by_string{std::string{"журнал.log"}};
std::ifstream by_path{path};
```

```
открыт по std::string: false
открыт по path:        true
path.u8string()        d0 b6 d1 83 d1 80 d0 bd d0 b0 d0 bb 2e 6c 6f 67
path.string()          e6 f3 f0 ed e0 eb 2e 6c 6f 67
path.native().size() = 10
```

По `std::string` файл не нашёлся: двенадцать байт UTF-8 прочитаны как двенадцать букв 1251, и вышло имя `Р¶СѓСЂРЅР°Р».log`. `std::filesystem::path`, построенный из `u8"…"`, знает, что внутри UTF-8, и хранит имя в родном для Windows виде — `native()` возвращает `std::wstring` из десяти символов. `path.string()` отдаёт имя **в кодовой странице системы**: `e6 f3 f0 ed e0 eb` — это «журнал» в 1251, а не в UTF-8. Для имени из символов, которых в 1251 нет, такого представления не существует вовсе.

**Правило:** на Windows путь к файлу строится как `std::filesystem::path` из UTF-8 — литерала `u8"…"` или `std::u8string`, — и файлы открываются по `path`. Обратно в строку UTF-8 путь превращается методом `u8string()`, а не `string()`. На Linux имена файлов — просто байты, по соглашению в UTF-8, и `std::string` работает; но код, написанный через `path`, правилен на обеих системах.

## 8. Сводка: где текст ломается и что делать

| Где | Что ломается | Что делать |
|---|---|---|
| исходник | компилятор читает файл не той кодировкой | файлы в UTF-8; MSVC — `/utf-8` (в комплекте уже) |
| строка в программе | `size()`, `substr`, `toupper` работают с байтами | хранить UTF-8 в `std::string`; помнить, что индекс — байт |
| вывод в консоль Windows | консоль читает байты по своей кодовой странице | `std::print`; для `std::cout` и `printf` — `chcp 65001` |
| чтение вывода другой программой | читатель декодирует по кодировке системы | указать читателю UTF-8 |
| имена файлов на Windows | `std::string` понимается как 1251 | `std::filesystem::path` из `u8"…"`, обратно — `u8string()` |
| граница с чужим API | чужая кодировка: UTF-16 у Windows, 1251 у старых API | переводить в одном месте, на границе |

## Итоги

- Юникод нумерует символы кодовыми точками; кодировка записывает номер байтами. UTF-8 — от одного до четырёх байт, UTF-16 — два или четыре, UTF-32 — четыре. Старые кодовые страницы — один байт, свой алфавит у каждой.
- В UTF-8 по байту видно, чем он является; байты `10xxxxxx` — продолжения. ASCII-разделители внутрь многобайтовой буквы не попадают.
- `std::string` — байты: `size()` считает байты, `substr` может разрезать букву, `std::toupper` знает только ASCII. Кодовые точки считаются просто, графемы — только библиотекой.
- `wchar_t` — 2 байта UTF-16 на Windows и 4 байта UTF-32 на Linux. Внутри программы — UTF-8 в `std::string`, остальное на границах.
- MSVC без `/utf-8` читает исходник в кодовой странице системы и портит широкие литералы; комплект этот ключ передаёт.
- Консоль Windows по умолчанию читает байты в кодировке 866. `std::print` выводит верно при любой кодовой странице, `std::cout` и `printf` — после `chcp 65001`.
- Имена файлов на Windows — UTF-16; `std::string` в пути понимается как 1251. Пути — через `std::filesystem::path` из UTF-8.
