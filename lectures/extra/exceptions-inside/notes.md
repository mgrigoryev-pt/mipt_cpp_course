# Как устроены исключения

> Дополнительный материал курса: конспект для самостоятельного чтения. Слайдов к нему нет — он не читается на паре, а показывает, что стоит за `throw`, `catch` и `noexcept` в машинном коде: почему исключение «ничего не стоит, пока его не бросили», почему бросок дорогой, что меняет `noexcept` и когда программа завершается через `std::terminate`. Листинги машинного кода здесь читаются по материалу [«Машинный код»](../asm-basics/notes.md).

## 0. О чём этот материал

Лекция 3, раздел 5, вводит исключения как канал отказа и называет главное их свойство: между `throw` и `catch` может быть сколько угодно вызовов, и промежуточные функции о происходящем не знают. Лекция 14, разделы 7–9, решает, когда исключение, а когда `std::expected`, и какие гарантии даёт функция. Обе лекции опираются на несколько утверждений, которые принимаются на веру: исключения бесплатны, пока их не бросают; бросок дорогой; `noexcept` помогает компилятору и библиотеке.

Здесь эти утверждения проверяются. Для этого достаточно заглянуть в объектный файл: промежуточные функции «не знают» об исключении, потому что знание вынесено из кода в таблицы рядом с ним.

К концу чтения вы должны:

- объяснять, как функция с локальными объектами готова к исключению, не тратя на это ни одной команды на успешном пути;
- называть две фазы броска и то, что происходит в каждой;
- знать порядок цены броска и откуда она берётся;
- объяснять три эффекта `noexcept` и показывать их на примере;
- перечислять случаи, когда вызывается `std::terminate`, и знать, раскручивается ли при этом стек;
- понимать, как исключения C++ устроены на Windows и почему это задевает AddressSanitizer.

Примеры собраны clang 19: под Linux — кросс-компиляцией в объектные файлы, которые только читались; под Windows — с запуском.

## 1. Два пути в одной функции

Функция с локальным объектом, у которого есть деструктор, и вызовом, который может бросить:

```cpp
struct Label {
    Label(int pid);
    ~Label();
};

void log_line(const Label& l);

void handle(int pid) {
    Label label{pid};  // есть деструктор
    log_line(label);   // может бросить
}
```

Если `log_line` бросит, `~Label` обязан выполниться — это [раскрутка стека](../../glossary.md#stack-unwinding) (stack unwinding) из лекции 3. Вот машинный код `handle` (clang 19, `-O2`, Linux, служебные строки убраны):

```
0000000000000000 <_Z6handlei>:
       f:   callq   Label::Label(int)
      17:   callq   log_line(Label const&)
      21:   callq   Label::~Label()
      2b:   retq
      2c:   movq    %rax, %rbx
      34:   callq   Label::~Label()
      3c:   callq   _Unwind_Resume
```

![Машинный код функции handle. Успешный путь: конструктор Label, вызов log_line, деструктор Label, возврат — ни одной команды на случай исключения. После возврата лежит landing pad: деструктор Label и _Unwind_Resume, выполняется, только если log_line бросила. Рядом таблица .eh_frame — как снять кадр handle, сколько байт стека, какие регистры восстановить, куда вернуться, — и .gcc_except_table: вызов по адресу 0x17 бросил — идти на landing pad 0x2c, catch в этой функции нет. Таблицы читает код раскрутки, а не успешный путь](img/landing-pad.svg)

Код разделён на две части.

**[Успешный путь](../../glossary.md#happy-path)** (happy path) — от начала до `retq` по адресу `0x2b`. В нём нет ни проверок «не случилось ли исключение», ни записи о том, какие объекты уже созданы. Если `log_line` вернулась нормально, функция выполняет ровно то, что написано, как если бы исключений в языке не было.

**[Landing pad](../../glossary.md#landing-pad)** (по-русски — посадочная площадка) — всё, что после `retq`. С успешного пути сюда не попасть: перед landing pad стоит возврат. Сюда управление передаёт код раскрутки, если `log_line` бросила: landing pad вызывает `~Label` и продолжает раскрутку дальше вызовом `_Unwind_Resume`.

Как код раскрутки узнаёт, что бросок из вызова по адресу `0x17` надо вести именно на `0x2c`? Из таблиц, которые компилятор положил рядом с кодом:

```
$ llvm-objdump -h handle.o
  2 .text                          00000041  TEXT
  4 .gcc_except_table              00000010  DATA
  7 .data.DW.ref.__gxx_personality_v0
 11 .eh_frame                      00000048
```

- **`.eh_frame`** описывает для каждой функции, как снять её кадр: сколько байт она заняла на стеке, где сохранила регистры, откуда взять [адрес возврата](../../glossary.md#return-address) (return address). По этой таблице код раскрутки поднимается от кадра к кадру, не выполняя ни одной команды самих функций.
- **`.gcc_except_table`** — описание обработчиков функции: какие диапазоны кода защищены, на какой landing pad идти из каждого, какие типы ловят `catch`, если они есть.
- **`__gxx_personality_v0`** — **[personality routine](../../glossary.md#personality-routine)**: функция из стандартной библиотеки, которая умеет читать `.gcc_except_table`. Код раскрутки спрашивает её в каждом кадре: «что делать здесь?».

Для сравнения — тот же файл с ключом `-fno-exceptions`:

```
  2 .text                          0000002a  TEXT
  7 .eh_frame                      00000038
```

Landing pad нет, `.gcc_except_table` нет, код на 23 байта короче. `.eh_frame` осталась: по ней стек читают ещё и отладчик, и профилировщик, и [санитайзеры](../../glossary.md#sanitizer) (sanitizers), когда печатают [стек вызовов](../../glossary.md#call-stack) (call stack).

## 2. Что происходит при `throw`

Бросок идёт в две **фазы** — стек обходится дважды.

![Стек вызовов main, load, parse, и parse бросает. Фаза 1, поиск: код раскрутки поднимается по кадрам, только читая таблицы, и в каждом спрашивает, есть ли подходящий catch; в parse и load нет, в main есть. Деструкторы в этой фазе не вызываются. Фаза 2, раскрутка: кадры снимаются сверху вниз, в каждом вызываются деструкторы локальных объектов — ~Guard в parse, ~string в load, — и управление входит в catch в main. Если фаза 1 не нашла обработчика, вызывается std::terminate, и выполнять ли перед этим фазу 2, решает реализация](img/two-phases.svg)

**Объект исключения.** `throw ParseError{…}` создаёт объект не в кадре бросающей функции — кадр сейчас будет снят, — а в отдельной памяти, которую выделяет среда выполнения. Там объект живёт, пока его не обработает последний `catch`. Поэтому `catch` по ссылке (лекция 3) законен: ссылка указывает на этот объект, а не на исчезнувший кадр.

**Фаза 1, поиск.** Код раскрутки поднимается по стеку от кадра к кадру по `.eh_frame` и в каждом кадре спрашивает personality routine, есть ли здесь `catch`, подходящий по типу. Сравнение типов идёт через [RTTI](../../glossary.md#rtti) (run-time type information) — те же сведения о типах, на которых работает `dynamic_cast` (лекция 7, раздел 6). Стек в этой фазе не меняется, деструкторы не вызываются — только чтение таблиц.

**Фаза 2, раскрутка.** Обработчик найден — теперь код раскрутки идёт по тем же кадрам второй раз и снимает их по одному. В каждом кадре он передаёт управление на landing pad, тот вызывает деструкторы и возвращает управление коду раскрутки (`_Unwind_Resume`). Дойдя до кадра с обработчиком, код раскрутки входит в `catch`.

Зачем две фазы, если можно снимать кадры сразу? Затем, что раскрутку нельзя отменить: уничтоженные объекты не вернуть. Если обработчика нет, первая фаза узнаёт это до того, как что-то разрушено, — и программа завершается через `std::terminate` в том состоянии, в каком была в момент броска. Раздел 5 показывает это на опыте.

## 3. Цена

Отсюда видно, сколько стоит каждая сторона.

**Пока не бросили — почти ничего.** Успешный путь не содержит команд для исключений. Платят местом в файле за таблицы и код landing pad и тем, что оптимизатору приходится этот код учитывать, — но не временем на каждом вызове. Отсюда название модели — **[zero-cost exceptions](../../glossary.md#zero-cost)** (по-русски — модель нулевой цены).

**Бросок — дорого.** Выделить память под объект исключения, дважды пройти по кадрам, в каждом разобрать закодированные таблицы, сравнить типы, выполнить landing pad в каждом кадре — это тысячи команд, и почти все они выполняются в функциях стандартной библиотеки и системы, а не в вашем коде. Замер: две функции, одна сообщает об отказе кодом возврата, другая — исключением; по миллиону вызовов на каждый исход, clang 19 `-O2` под Windows, i7-12700H:

| Исход | Код возврата | Исключение |
|---|---|---|
| успех | 0,6–1,2 нс | 2,4–2,5 нс (с `try`, без броска) |
| отказ | 0,7–0,8 нс | 2 170–2 706 нс (`throw` и `catch`) |

Успешный путь с исключениями и без — одного порядка: наносекунды. Отказ через исключение — в три тысячи раз дороже, чем через код возврата, и это при глубине всего в один кадр: с каждым кадром между `throw` и `catch` работы прибавляется.

Это и есть техническая основа правила из лекции 3: исключение — для исключительного. Отказ, который случается на каждом десятом событии потока, стоит превратить в код возврата или `std::expected` (лекция 14): две микросекунды на событие при миллионе событий в минуту — это две секунды процессорного времени в минуту на одни только броски.

## 4. Что меняет `noexcept`

`noexcept` действует в трёх местах.

**Вызывающему не нужен landing pad.** Если `log_line` объявлена `noexcept`, компилятор знает, что из неё ничего не вылетит, и landing pad для `~Label` в `handle` не готовит:

```cpp
void log_line(const Label& l) noexcept;
```

```
$ llvm-objdump -h handle.o
  2 .text                          0000002a  TEXT
  7 .eh_frame                      00000038
```

Ни `.gcc_except_table`, ни landing pad — код `handle` такой же, как при сборке с `-fno-exceptions`. Это то, что лекция 3 называет «компилятор может оптимизировать агрессивнее».

**Стандартная библиотека выбирает другой алгоритм.** Лекция 11, раздел 4, и лекция 14, раздел 9, объясняют, что `std::vector` при росте перемещает элементы в новый буфер, только если их [move-конструктор](../../glossary.md#move-constructor) (move constructor) `noexcept`, а иначе копирует. Подсчёт на тысяче `emplace_back`:

```
move без noexcept:       копий  2137, перемещений     0
move с noexcept:         копий     0, перемещений  2137
```

Один и тот же тип, одно и то же слово в объявлении — и две тысячи копий вместо двух тысяч дешёвых перемещений. Для типа со строкой или вектором внутри каждая копия — выделение памяти (материал [«Память процесса изнутри»](../process-memory/notes.md), раздел 4).

**На границе `noexcept`-функции исключение останавливается.** Если исключение всё-таки вылетает из тела `noexcept`-функции, дальше оно не идёт: вызывается `std::terminate`. Об этом — следующий раздел.

## 5. Когда вызывается `std::terminate`

`std::terminate` — последний рубеж: по умолчанию он вызывает `std::abort`, и программа завершается немедленно, без обработчиков `atexit` и деструкторов статических объектов (материал [«Загрузка процесса»](../process-loading/notes.md), раздел 6). Опыт — программа с объектом `Guard`, который печатает строку в деструкторе, и своим обработчиком `std::set_terminate`, чтобы было видно момент вызова:

```cpp
void from_noexcept() noexcept {
    Guard g{"внутри noexcept"};
    throw std::runtime_error("из noexcept");
}

void uncaught() {
    Guard g{"до необработанного"};
    throw std::runtime_error("никто не ловит");
}

void during_unwind() {
    ThrowingDtor t;  // деструктор бросает
    Guard g{"при раскрутке"};
    throw std::runtime_error("первое");
}
```

```
$ term.exe noexcept
  std::terminate
$ term.exe uncaught
  std::terminate
$ term.exe unwind
  ~Guard(при раскрутке)
  std::terminate
```

Три случая — три пути к `std::terminate`.

- **Исключение покидает `noexcept`-функцию.** Деструктор `Guard` не вызван: стек не раскручивался. clang предупреждает об этом ещё при сборке — `'from_noexcept' has a non-throwing exception specification but can still throw`, — но только когда `throw` стоит прямо в теле.
- **Исключение никто не поймал.** Первая фаза дошла до конца стека, не найдя обработчика. Деструктор `Guard` снова не вызван.
- **Деструктор бросил во время раскрутки.** `~Guard` уже выполнен — раскрутка шла, — а когда очередь дошла до деструктора, который бросает, в полёте оказались два исключения сразу. Язык такое не допускает. Деструкторы по умолчанию `noexcept`, и чтобы этот опыт вообще собрался, деструктору пришлось явно написать `noexcept(false)`.

В первых двух случаях деструкторы не выполнились — и это не случайность, а разрешение стандарта: раскручивать ли стек перед `std::terminate`, когда обработчик не найден или граница `noexcept` нарушена, решает реализация. Лекция 3 говорит «без раскрутки стека» — так и происходит на этой платформе, но опираться на обратное нельзя нигде.

Практическое следствие для долгоживущего процесса: необработанное исключение — не только упавшая программа, но и **невыполненные деструкторы**. Буферы не сброшены, файлы не дописаны, временные файлы не удалены. Отсюда совет лекции 3 ставить в `main` последний рубеж `catch (const std::exception& e)`: пойманное исключение раскручивает стек до `main`, и все [RAII](../../glossary.md#raii)-объекты по пути успевают отработать.

## 6. Исключения на Windows

Всё сказанное — модель, общая для платформ. Исполнение на Windows устроено иначе, чем на Linux, и одно отличие студент видит своими глазами.

**Таблицы другие.** Вместо `.eh_frame` и `.gcc_except_table` — секции `.pdata` и `.xdata` (одну из них видно в заголовке исполняемого файла в материале про загрузку, раздел 2). Та же `handle`, собранная под Windows:

```
$ llvm-readobj --unwind handle.obj
  RuntimeFunction {
    StartAddress: ?handle@@YAXH@Z
    UnwindInfo {
      Flags [ ExceptionHandler TerminateHandler ]
      UnwindCodes [
        SET_FPREG reg=RBP, offset=0x70
        ALLOC_SMALL size=120
        PUSH_NONVOL reg=RBX
        ...
      ]
      Handler: __CxxFrameHandler3
    }
  }
  RuntimeFunction {
    StartAddress: ?dtor$12@?0??handle@@YAXH@Z@4HA
    ...
```

`UnwindCodes` — то же, что `.eh_frame`: какие регистры сохранены, сколько стека занято. `__CxxFrameHandler3` — personality routine. А `?dtor$12@…` — landing pad, вынесенный в отдельный маленький кусок кода со своей записью в таблице; в Windows такие куски называются **funclet**.

**Исключение C++ — частный случай исключения системы.** В Windows есть свой механизм исключений, **[SEH](../../glossary.md#seh)** (structured exception handling), которым система сообщает о событиях вроде обращения по нулевому указателю. Бросок C++ устроен поверх него: `throw` вызывает системную функцию, которая порождает SEH-исключение с особым кодом. Это видно, если поставить на пути фильтр SEH — расширение Microsoft `__try` / `__except`, которое понимает и clang:

```
throw из C++:        код исключения 0xe06d7363
запись по nullptr:   код исключения 0xc0000005
```

`0xE06D7363` — код, которым помечено любое исключение C++ от компилятора Microsoft и совместимых с ним; три младших байта — буквы `msc` в ASCII. `0xC0000005` — [нарушение доступа](../../glossary.md#access-violation) (access violation), то самое, с которым завершается процесс при записи по чужому адресу (материал про библиотеки, раздел 4).

Два следствия.

- **`catch (...)` не ловит обращение по `nullptr`.** Опыт с `try { null_write(); } catch (...)` завершился кодом `0xC0000005`, так и не войдя в `catch`. Запись по `nullptr` — это [UB](../../glossary.md#ub) (undefined behavior); нарушение доступа — лишь то, во что оно вылилось на этой системе, и исключением C++ не является, поэтому в обычном режиме компиляции `catch` его не видит. У MSVC есть ключ `/EHa`, который это меняет; в курсе он не используется, и правильный ответ на такое падение — не поймать его, а исправить.
- **Раскрутку выполняет система.** Поиск обработчика и снятие кадров на Windows ведут функции из системных библиотек, читая `.pdata` по всему стеку. Среда [ASan](../../glossary.md#asan) (AddressSanitizer) из состава clang перехватывает часть этих функций и с раскруткой не справляется — отсюда предупреждение `project/README.md` («И кроме исключений»): под `asan-windows` пойманный `throw` роняет процесс. Ваш код здесь ни при чём, и на Linux, где раскрутку ведёт библиотека среды выполнения компилятора по `.eh_frame` — та, из которой `_Unwind_Resume` в разделе 1, — этой беды нет.

## 7. Исключения и граница библиотеки

Материал [«Библиотеки и граница ABI»](../libraries-abi/notes.md) ([ABI](../../glossary.md#abi) — application binary interface), раздел 7, запрещает исключениям пересекать границу `extern "C"`. Теперь видно почему. Код раскрутки поднимается по стеку, читая таблицы каждой функции. Кадр функции, собранной как C или с `-fno-exceptions`, либо не имеет нужных таблиц, либо имеет, но без landing pad: деструкторы в нём не выполнятся, и объекты этой функции так и не будут уничтожены. Стандарт называет это UB, и `os.h` поэтому требует от [колбэка](../../glossary.md#callback) (callback) ловить всё самому.

Обратное при этом законно: программа с исключениями линкуется с библиотекой, собранной без них, если ни одно исключение не пересекает границу. Именно так собраны `os` и `edr` — по `SPEC.md`, с `-fno-exceptions`, — а код агента исключениями пользуется.

## Итоги

- Функция готова к исключению без единой команды на успешном пути: код, который вызывает деструкторы при раскрутке, вынесен в landing pad после возврата, а сведения о кадрах и обработчиках — в таблицы: `.eh_frame` и `.gcc_except_table` на Linux, `.pdata` и `.xdata` на Windows.
- Объект исключения живёт в отдельной памяти до конца последнего `catch`.
- Бросок идёт в две фазы: поиск обработчика без изменения стека, затем раскрутка с деструкторами. Если обработчика нет, раскрутки может не быть вовсе.
- Успешный путь с исключениями стоит наносекунды, бросок — микросекунды: в опыте в три тысячи раз дороже кода возврата. Частые отказы — через код возврата или `std::expected`.
- `noexcept` убирает landing pad у вызывающих, включает перемещение вместо копирования в стандартных контейнерах и превращает вылетевшее исключение в `std::terminate`.
- `std::terminate` вызывается при исключении из `noexcept`, при необработанном исключении и при исключении из деструктора во время раскрутки. Деструкторы при этом могут не выполниться — поэтому последний `catch` стоит в `main`.
- На Windows исключения C++ — это SEH-исключения с кодом `0xE06D7363`; раскрутку ведёт система, и ASan из состава clang её не переживает. `catch (...)` не ловит нарушение доступа.
