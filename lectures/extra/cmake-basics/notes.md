# CMake поверх модели сборки

> Дополнительный материал курса: конспект для самостоятельного чтения. Слайдов к нему нет — он не читается на паре, а объясняет, что происходит, когда набираются две команды из `project/README.md`: `cmake --preset` и `cmake --build --preset`. Опирается на материал [«Как C++ собирает программу»](../build-model/notes.md): там — препроцессор, компилятор и линкер, здесь — кто и как их вызывает.

## 0. О чём этот материал

Практикум собирается CMake с первого занятия, и `SETUP.md` вместе с `project/README.md` подробно говорят, что набирать. Этого хватает, пока всё собирается. Когда перестаёт, выясняется, что непонятно главное: какая из программ ругается, что именно она помнит с прошлого раза и почему одна и та же ошибка лечится то повторной конфигурацией, то правкой кода.

Всё это следует из устройства, и устройство небольшое: CMake — не компилятор и даже не система сборки, а генератор описания для неё. Он работает в два шага, между шагами хранит кэш, а сам проект описывает целями со свойствами. Этих четырёх слов — шаг, кэш, цель, свойство — хватает, чтобы прочитать `CMakeLists.txt` комплекта целиком.

К концу чтения вы должны:

- объяснять, что делают конфигурация и сборка и когда нужен каждый из шагов;
- читать `CMakeLists.txt` из трёх целей и понимать, откуда у каждого файла флаги и пути к заголовкам;
- различать `PRIVATE`, `PUBLIC` и `INTERFACE` и выбирать нужное;
- знать, что хранится в кэше, почему номер занятия набирается один раз и как кэш сбросить;
- по тексту ошибки называть, кто её выдал: CMake, компилятор, линкер или `ctest`.

`CMakeLists.txt` комплекта студент не правит, поэтому примеры здесь — на своём проекте из трёх файлов, том же, что в материале про модель сборки. Выводы сняты с настоящих прогонов: CMake 3.28, Ninja 1.12, clang 19 под Windows.

## 1. Что остаётся от ручной сборки

Модель сборки из соседнего материала сводится к командам. Для трёх файлов их три:

```
clang++ -std=c++23 -c geom.cpp -o geom.o
clang++ -std=c++23 -c main.cpp -o main.o
clang++ geom.o main.o -o app
```

Набирать их руками можно, пока файлов три. У настоящего проекта к ним добавляется три задачи, которые руками не решаются.

**Что пересобрать.** После правки `geom.cpp` нужно заново скомпилировать только его и перелинковать. После правки `geom.h` — оба `.cpp`, потому что оба его включают. Кто включает какой заголовок, из имён файлов не видно.

**С какими флагами.** Стандарт, предупреждения, пути к заголовкам, [санитайзеры](../../glossary.md#sanitizer) (sanitizers), отладочная информация. Флаги разные у разных файлов и разные на Windows и Linux.

**В каком порядке.** Библиотека должна быть собрана раньше программы, которая с ней линкуется, а независимые файлы можно компилировать одновременно на всех ядрах.

Эти три задачи решает **[система сборки](../../glossary.md#build-system)** (build system). В курсе это Ninja: она читает файл `build.ninja` со списком «что из чего получается и какой командой», сравнивает время изменения файлов и запускает только то, что устарело. Проверяется на проекте из трёх файлов:

```
$ (правка geom.cpp)
$ cmake --build build
[1/3] Building CXX object CMakeFiles/geom.dir/src/geom.cpp.obj
[2/3] Linking CXX static library geom.lib
[3/3] Linking CXX executable app.exe

$ (правка geom.h)
$ cmake --build build
[1/4] Building CXX object CMakeFiles/geom.dir/src/geom.cpp.obj
[2/4] Linking CXX static library geom.lib
[3/4] Building CXX object CMakeFiles/app.dir/src/main.cpp.obj
[4/4] Linking CXX executable app.exe
```

Во втором случае `main.cpp` пересобран, хотя сам не менялся. Список заголовков Ninja узнаёт не из исходника, а от компилятора: в каждой команде компиляции стоит ключ `-MD`, и clang рядом с объектным файлом пишет файл `.d` — перечень всех заголовков, которые вклеил препроцессор. Система сборки с этим перечнем и сверяется.

Остаётся вопрос, кто пишет `build.ninja`. Руками его не пишут: он длинный, зависит от компилятора и платформы и меняется с каждым новым файлом. Его пишет CMake.

## 2. Два шага: конфигурация и сборка

CMake сам ничего не компилирует. Он читает описание проекта — `CMakeLists.txt` — и выдаёт описание для системы сборки. Отсюда два шага, и у каждого своя программа.

![Два шага сборки. Описание проекта — CMakeLists.txt и CMakePresets.json, их пишет человек. Шаг 1, конфигурация, cmake --preset windows: CMake читает описание и пишет каталог сборки с CMakeCache.txt и build.ninja; нужен, когда меняется описание — номер занятия, новый .cpp, пресет. Шаг 2, сборка, cmake --build --preset windows: Ninja сверяет время файлов и списки заголовков и вызывает компилятор и линкер только для устаревшего; нужен после каждой правки кода, а правка CMakeLists.txt сама запускает шаг 1](img/two-steps.svg)

**Шаг 1, конфигурация** — `cmake --preset windows`, или без [пресета](../../glossary.md#preset) (preset) `cmake -S . -B build -G Ninja`. CMake выясняет, что за компилятор установлен и какие флаги он понимает, выполняет `CMakeLists.txt` как программу и записывает в каталог сборки два главных файла: `CMakeCache.txt` — всё, что стоит запомнить до следующего раза (раздел 5), и `build.ninja` — готовые команды. Первая конфигурация занимает несколько секунд, почти все — на изучение компилятора. Повторная — десятые доли секунды: результат изучения лежит в кэше.

**Шаг 2, сборка** — `cmake --build --preset windows`. Это тонкая обёртка: CMake смотрит в каталог сборки, видит, каким генератором тот создан, и запускает `ninja`. Дальше работает только Ninja.

Отсюда простое правило, когда нужен каждый шаг. Правка кода — только шаг 2. Изменение **описания** — шаг 1: другой номер занятия, другой пресет, новый файл. Одно исключение сделано для удобства: если изменился сам `CMakeLists.txt`, Ninja замечает это и перезапускает конфигурацию сама:

```
$ (правка CMakeLists.txt)
$ cmake --build build
[0/1] Re-running CMake...
-- Configuring done (0.1s)
-- Generating done (0.0s)
ninja: no work to do.
```

Изменение, которое в `CMakeLists.txt` не записано, — ключ `-D` в командной строке, — так не подхватывается: о нём знает только команда шага 1.

**Генератор** — это то, во что CMake переводит проект. Ninja лишь один из вариантов: CMake умеет выдавать `Makefile` для make и решение Visual Studio для MSBuild. Выбирается генератор ключом `-G` или в пресете и запоминается в каталоге сборки навсегда. Попытка сменить его на ходу получает отказ:

```
CMake Error: Error: generator : Ninja Multi-Config
Does not match the generator used previously: Ninja
Either remove the CMakeCache.txt file and CMakeFiles directory or choose a different binary directory.
```

**Правило:** каталог сборки принадлежит одной конфигурации. Другой генератор, другой компилятор, другой набор санитайзеров — другой каталог. Так пресеты комплекта и устроены: у каждого свой `binaryDir` — `build/windows`, `build/asan-windows`, `build/linux`.

## 3. Цель — главное слово CMake

Проект в CMake описывается **[целями](../../glossary.md#target)** (target). Цель — то, что получается в результате сборки, вместе со всем, что нужно знать, чтобы это получить. Вот весь `CMakeLists.txt` проекта из трёх файлов:

```cmake
cmake_minimum_required(VERSION 3.21)
project(geom LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_library(geom STATIC lib/geom.cpp)
target_include_directories(geom PUBLIC lib)

add_executable(app app/main.cpp)
target_link_libraries(app PRIVATE geom)
```

Первые две строки — обязательный заголовок: какой минимальной версией CMake проект читается и на каком языке написан. Три `set` задают стандарт: C++23, строго (`REQUIRED` — отказаться от сборки, если компилятор его не знает) и без расширений компилятора. Без последней строки clang получает `-std=gnu++23` вместо `-std=c++23`, и код, который случайно опирается на расширения GCC, соберётся здесь и не соберётся у MSVC. В комплекте эти три строки стоят в начале `CMakeLists.txt`.

Дальше две цели.

- `add_library(geom STATIC lib/geom.cpp)` — библиотека `geom` из одного файла. `STATIC` значит «статическая»: архив объектных файлов, который целиком вкладывается в программу при [линковке](../../glossary.md#linker) (linking). Под Windows он называется `geom.lib`, под Linux — `libgeom.a`.
- `add_executable(app app/main.cpp)` — исполняемый файл `app`.

Видов целей немного, и все встретятся в комплекте:

| Команда | Что получается |
|---|---|
| `add_executable(имя файлы…)` | исполняемый файл |
| `add_library(имя STATIC файлы…)` | статическая библиотека |
| `add_library(имя SHARED файлы…)` | динамическая библиотека: `.dll` под Windows, `.so` под Linux |
| `add_library(имя INTERFACE)` | цель без своих файлов, только со свойствами для тех, кто её подключит |
| `add_library(имя SHARED IMPORTED)` | уже собранная кем-то библиотека: CMake её не собирает, только подключает |

У каждой цели есть **свойства**: список исходников, пути поиска заголовков, определения макросов, флаги компиляции, библиотеки для линковки. Задаются они командами с приставкой `target_`:

| Команда | Что задаёт | Во что превращается у clang |
|---|---|---|
| `target_include_directories` | где искать заголовки | `-I lib` |
| `target_compile_definitions` | макросы | `-D OS_USE_SHARED` |
| `target_compile_options` | прочие флаги компиляции | `-Wall -Wextra` |
| `target_link_libraries` | от чего цель зависит | библиотека в команде линковки и всё, что она передаёт (раздел 4) |

**Привычка профессионального C++:** всё задаётся на цели, а не на весь проект. Команды без приставки — `include_directories`, `add_compile_options` — действуют на все цели каталога сразу, и через полгода уже не понять, откуда у какого файла взялся флаг. В комплекте такая команда одна, и она осознанная: санитайзер обязан покрывать всё — и ваш код, и выданные тесты, — поэтому его флаги ставятся на весь каталог. Почему — написано комментарием над этим местом в `CMakeLists.txt`.

## 4. `PRIVATE`, `PUBLIC`, `INTERFACE`

`target_link_libraries(app PRIVATE geom)` делает больше, чем кажется. Кроме «добавь `geom.lib` в команду линковки» строка говорит: «всё, что `geom` отдаёт наружу, отдай и `app`». Что именно цель отдаёт наружу, решает слово при каждом её свойстве. Свойства, которые цель передаёт наружу, называются **[usage requirements](../../glossary.md#usage-requirements)** — требования цели к тем, кто её подключает.

![Три варианта одного свойства: путь к заголовкам lib/ у цели geom, которую app подключает одинаково. PRIVATE — только себе: geom.cpp путь видит, main.cpp не видит, и сборка app падает с 'geom.h' file not found. PUBLIC — себе и тем, кто подключил: видят оба. INTERFACE — только тем, кто подключил: сам geom путь не получает, app получает; так описываются цели без своих .cpp](img/visibility.svg)

Проверяется это на том же проекте, если `PUBLIC` у пути к заголовкам заменить на `PRIVATE`:

```
[1/4] Building CXX object CMakeFiles/geom.dir/lib/geom.cpp.obj
[2/4] Linking CXX static library geom.lib
[3/4] Building CXX object CMakeFiles/app.dir/app/main.cpp.obj
FAILED: CMakeFiles/app.dir/app/main.cpp.obj
main.cpp:3:10: fatal error: 'geom.h' file not found
```

Библиотека собралась — ей путь нужен, и она его получила. Программа — нет: путь остался при библиотеке.

**Подвох:** та же правка в проекте, где `main.cpp` лежит в одном каталоге с `geom.h`, **ничего не ломает**. `#include "…"` в кавычках сначала ищет заголовок рядом с включающим файлом и только потом по путям `-I`. Ошибка видимости прячется, пока файлы лежат вместе, и всплывает при первой перекладке по каталогам. Поэтому пример в этом разделе разнесён на `lib/` и `app/`.

Как выбирать:

- **`PRIVATE`** — свойство нужно только файлам самой цели: предупреждения, внутренние пути, макросы реализации.
- **`PUBLIC`** — нужно и цели, и тем, кто её подключает. Типичный случай — путь к заголовкам библиотеки: они включаются в её `.cpp` и в `.cpp` потребителя.
- **`INTERFACE`** — нужно только потребителям. Встречается у целей, у которых нет своих `.cpp`: библиотека из одних заголовков, готовая чужая библиотека, набор флагов.

Слово при `target_link_libraries` работает так же, и распространение идёт по цепочке. Если `core` подключает `geom` как `PUBLIC`, а `app` подключает `core`, путь `geom` доедет и до `app`: цель передаёт наружу и то, что сама получила публично.

`INTERFACE`-цель выглядит странно, пока не видно, зачем она. В комплекте их две. `nano_edr_warnings` — цель без единого файла, у которой есть только флаги `-Wall -Wextra`; кто её подключает, получает флаги. Так один список предупреждений раздаётся агенту и библиотеке из `src/` и не повторяется. Вторая — `os` и `edr`, про них раздел 8.

## 5. Имя цели или имя файла

У `target_link_libraries` есть особенность, которая стоит отдельного раздела. Если в ней написано имя, которого нет среди целей, CMake не ругается: он считает, что это имя файла библиотеки, и передаёт его линкеру как есть. Опечатка `goem` вместо `geom`:

```cmake
target_link_libraries(app PRIVATE goem)
```

Конфигурация проходит молча. Сборка падает — и вовсе не там, где ошибка:

```
FAILED: CMakeFiles/app.dir/app/main.cpp.obj
main.cpp:3:10: fatal error: 'geom.h' file not found
```

Компилятор ищет заголовок, потому что путь к нему должна была принести цель `geom`, а её никто не подключил. Если заголовок нашёлся бы и так, упал бы линкер, уже с честным текстом:

```
lld-link: error: could not open 'goem.lib': no such file or directory
```

Защита есть, и включается она одной строкой (с CMake 3.23):

```cmake
set(CMAKE_LINK_LIBRARIES_ONLY_TARGETS ON)
```

Теперь всё, что стоит в `target_link_libraries`, обязано быть целью, и ошибка приходит на шаге 1, с номером строки:

```
CMake Error at CMakeLists.txt:11 (target_link_libraries):
  Target "app" has LINK_LIBRARIES_ONLY_TARGETS enabled, but it links to:

    goem

  which is not a target.  Possible reasons include:

    * There is a typo in the target name.
```

Вторая защита — соглашение об именах. Имя с двумя двоеточиями, вида `fmt::fmt` или `GTest::gtest`, CMake всегда считает именем цели и на отсутствующую ругается при конфигурации. Поэтому сторонние библиотеки называют свои цели именно так.

## 6. Кэш: что CMake помнит между запусками

`CMakeCache.txt` в каталоге сборки — текстовый файл со строками вида `ИМЯ:ТИП=значение`. В него попадает всё, что было задано при конфигурации: генератор, путь к компилятору, [тип сборки](../../glossary.md#build-type) (build type, раздел 7) и любые переменные, объявленные в `CMakeLists.txt` как кэшируемые.

Переменная кэша объявляется так:

```cmake
set(DEMO_LESSON "" CACHE STRING "Номер занятия")
message(STATUS "занятие: '${DEMO_LESSON}'")
```

Пустая строка здесь — значение **по умолчанию**, и оно применяется только если в кэше переменной ещё нет. Четыре конфигурации подряд:

```
$ cmake -S . -B build -D DEMO_LESSON=1.3
-- занятие: '1.3'
$ cmake -S . -B build
-- занятие: '1.3'
$ cmake -S . -B build -D DEMO_LESSON=2.1
-- занятие: '2.1'
$ cmake -S . -B build
-- занятие: '2.1'
```

Ключ `-D` записывает значение в кэш, и дальше оно живёт там, пока его не заменят. Ровно так в комплекте устроен номер занятия: `NANO_EDR_LESSON` объявлен строковой переменной кэша, поэтому `-D NANO_EDR_LESSON=2.3` набирается один раз за занятие, а не при каждой конфигурации. В кэше каталога сборки он и лежит:

```
NANO_EDR_LESSON:STRING=2.3
```

У памяти есть обратная сторона: кэш помнит и то, что забыть хотелось бы. Удалили ключ из команды — значение осталось. Поменяли компилятор в переменной окружения — кэш помнит старый. Способов сброса три, от точного к грубому:

- `cmake --preset windows -U NANO_EDR_LESSON` — удалить из кэша одну переменную;
- `cmake --preset windows --fresh` (с CMake 3.24) — сконфигурировать заново с пустым кэшем;
- удалить каталог сборки целиком. Грубо, но надёжно: в нём нет ничего, что нельзя получить заново.

**Подвох:** пустой кэш забывает всё, включая генератор и компилятор. С пресетом это безопасно — пресет передаёт их заново. Без пресета нет: `cmake -S . -B build --fresh` на каталоге, который до того собирался Ninja и clang, под Windows выбрал `Building for: Visual Studio 17 2022` и компилятор MSVC — то, что CMake берёт по умолчанию, когда ему ничего не сказали. Ещё одна причина набирать команды курса пресетами.

Каталог сборки — производное от исходников и команды конфигурации. Поэтому он не хранится в git: `project/build/` записан в `.gitignore` репозитория курса.

## 7. Пресеты и типы сборки

Пресет — это записанная заранее команда шага 1. Всё, что иначе набиралось бы ключами, — генератор, каталог сборки, компилятор, переменные кэша — лежит в `CMakePresets.json` под именем. Как устроены пресеты комплекта и какой когда брать, подробно разобрано в `SETUP.md`, раздел «Что такое пресет комплекта». Здесь — только связь с тем, что уже сказано.

Наименьший полный пресет:

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "dev",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/dev",
      "cacheVariables": {
        "CMAKE_CXX_COMPILER": "clang++",
        "CMAKE_BUILD_TYPE": "Debug"
      }
    }
  ],
  "buildPresets": [{ "name": "dev", "configurePreset": "dev" }],
  "testPresets": [{ "name": "dev", "configurePreset": "dev" }]
}
```

`cmake --preset dev` равносильно `cmake -S . -B build/dev -G Ninja -D CMAKE_CXX_COMPILER=clang++ -D CMAKE_BUILD_TYPE=Debug`. Пресеты сборки и тестов лишь ссылаются на пресет конфигурации: из него они узнают каталог сборки.

**Тип сборки** (build type) — набор флагов оптимизации и отладки. Стандартных четыре: `Debug` (без оптимизаций, с отладочной информацией), `Release` (с оптимизациями, без отладочной информации), `RelWithDebInfo` (и то и другое), `MinSizeRel` (оптимизация размера). Тип сборки важен, поэтому пресеты комплекта называют его всегда явно: без явного указания CMake выбирает сам, и выбирает по-разному — на Windows с clang получается `Debug`, а на Linux тип сборки остаётся пустым, то есть без оптимизаций и без отладочной информации сразу.

Здесь же объясняется разница между пресетами на двух системах.

- **Одноконфигурационный генератор** (single-config; «конфигурацией» CMake здесь называет тип сборки, а не шаг 1) — `Ninja`, пресеты `linux`, `debug`, `asan` — выбирает тип сборки на шаге 1 переменной `CMAKE_BUILD_TYPE`. Другой тип сборки — другой каталог сборки. Поэтому на Linux отладочный пресет `debug` отдельный, и номер занятия для него задаётся заново: кэш у него свой.
- **Многоконфигурационный** (`Ninja Multi-Config`, пресет `windows`) пишет в один каталог правила сразу для всех типов сборки, а выбор откладывает до шага 2. Поэтому пресеты сборки `windows` и `debug-windows` ссылаются на один и тот же пресет конфигурации, а результат лежит в подкаталоге типа сборки: `build/windows/Release/nano-edr.exe`. По той же причине в тестовом пресете `windows` тип сборки назван явно: `ctest` иначе не знает, из какого подкаталога брать программы.

## 8. `ctest`: тест — это программа

Для CMake тест — не функция с проверками, а **программа, которую запускают и смотрят на её [код завершения](../../glossary.md#exit-code)** (exit code). Ноль — тест прошёл, не ноль — нет. Всё, что внутри, — дело программы.

```cmake
enable_testing()
add_test(NAME area_runs COMMAND app)
set_tests_properties(area_runs PROPERTIES PASS_REGULAR_EXPRESSION "^12\\.56")
```

`enable_testing()` включает тесты в каталоге, `add_test` объявляет тест с именем и командой. Здесь в роли теста выступает сама программа, а третья строка меняет критерий: вместо кода завершения — совпадение вывода с регулярным выражением. Прогон:

```
$ ctest --test-dir build
    Start 1: area_runs
1/1 Test #1: area_runs ........................   Passed    0.34 sec

100% tests passed, 0 tests failed out of 1
```

`ctest` ничего не собирает. Если программа не собралась, тест не проваливается, а **не запускается**:

```
Could not find executable D:/…/build/dev/app.exe
1/1 Test #1: area_runs ........................***Not Run   0.00 sec
```

`Not Run` вместо `Failed` — сигнал, что смотреть надо в вывод сборки, а не в код теста.

Выданные тесты комплекта устроены так же. Каждый набор — отдельная программа из файлов тестов и `doctest_main.cpp`, слинкованная с вашей библиотекой. Из `tasks/1.2/tests/CMakeLists.txt`:

```cmake
add_executable(task1_2_tests
    ${NANO_EDR_KIT_ROOT}/tests/doctest_main.cpp
    ${CMAKE_CURRENT_LIST_DIR}/list_tests.cpp
    ${CMAKE_CURRENT_LIST_DIR}/parse_tests.cpp)
target_link_libraries(task1_2_tests PRIVATE ${NANO_EDR_CORE})
add_test(NAME task1.2 COMMAND task1_2_tests)
```

Для `ctest` весь набор занятия — один тест: `task1.2`. Отдельные проверки внутри считает и печатает `doctest`, а `ctest` видит только итоговый код завершения. Поэтому ключ `-R 1.2` отбирает набор целиком: он сравнивает регулярное выражение с именами тестов `ctest`, а не с проверками внутри.

## 9. Как устроен комплект

Теперь `CMakeLists.txt` комплекта читается целиком. Вот его цели на занятии 2.3:

![Цели комплекта на занятии 2.3. Исполняемый nano-edr из src/main.cpp и программы выданных тестов task2_1_tests и task2_3_tests приватно подключают nano_edr_core — статическую библиотеку из всех src/*.cpp, кроме main.cpp, которая отдаёт наружу пути src/ и kit/include/l2.3/. Та публично подключает готовые библиотеки os и edr — они отдают наружу include/ и макросы OS_USE_SHARED и EDR_USE_SHARED — и приватно набор предупреждений nano_edr_warnings; агент тоже подключает его приватно](img/kit-targets.svg)

По порядку, как это собирается.

**Номер занятия превращается в два списка.** `-D NANO_EDR_LESSON=2.3` попадает в кэш, а `tasks/lessons.cmake` выводит из него комплект заготовок `l2.3` и наборы тестов `2.1;2.3`. Комплект добавляется к путям заголовков `nano_edr_core`, наборы подключаются командой `add_subdirectory` — каждый своим `CMakeLists.txt`, как в разделе 8. Конфигурация печатает, что получилось: `-- выданные тесты: 2.1;2.3`.

**Ваши файлы подбираются маской (glob).** Список исходников `nano_edr_core` не перечислен, а собирается командой `file(GLOB_RECURSE … CONFIGURE_DEPENDS "src/*.cpp")`. Ключ `CONFIGURE_DEPENDS` заставляет сборку при каждом запуске проверять маску заново. С Ninja это видно на проекте из трёх файлов, если положить в `src/` новый `.cpp` и запустить только шаг 2:

```
[0/2] Re-checking globbed directories...
-- GLOB mismatch!
[1/2] Re-running CMake...
-- Configuring done (0.1s)
[1/5] Building CXX object CMakeFiles/app.dir/src/geom.cpp.obj
[2/5] Linking CXX executable app.exe
```

Маска изменилась, конфигурация перезапустилась сама, новый файл собран. Документация CMake оговаривает, что так работает не с каждым генератором, поэтому правило из `project/README.md` — «новый `.cpp` в `src/` — это шаг 1» — остаётся надёжным: лишняя конфигурация стоит доли секунды.

**Пока `.cpp` нет, библиотека пустая.** На занятии 1.1 в `src/` лежит только `main.cpp`, собирать в библиотеку нечего, и `nano_edr_core` объявляется `INTERFACE`: цель существует, раздаёт пути и границы, но своих объектных файлов не имеет. Первый же ваш `.cpp` рядом с `main.cpp` делает её `STATIC`. Это решение принимается при конфигурации — ещё одна причина, по которой новый файл требует шага 1.

**Границы подключаются готовыми.** `os` и `edr` — цели вида `SHARED IMPORTED`: CMake их не собирает, а берёт из `lib/win-x64/` или `lib/linux-x64/`. Путь к `include/` и макрос `OS_USE_SHARED` у них объявлены `INTERFACE` — самим готовым библиотекам они не нужны, нужны тем, кто их подключит. `nano_edr_core` подключает их `PUBLIC`, и по цепочке из раздела 4 путь к `os.h` и макрос доезжают до агента и до каждого набора тестов. Поэтому в тестах занятия, которые включают `os.h`, никаких путей не прописано.

**Готовые `.dll` кладутся рядом с программой.** После сборки агента на Windows выполняется команда `POST_BUILD`, которая копирует `os.dll` и `edr.dll` в каталог сборки: там их ищет Windows при запуске. На Linux копировать не нужно — путь к библиотекам записывается внутрь исполняемого файла. Что будет, если библиотека не нашлась, чем динамическая библиотека вообще отличается от статической и что такое [ABI](../../glossary.md#abi) (application binary interface) — в материале [«Библиотеки и граница ABI»](../libraries-abi/notes.md). Там же, в `CMakeLists.txt` комплекта, объяснено, почему все программы собираются в один каталог.

## 10. Кто ругается

Раздел 5 материала про модель сборки учит по тексту ошибки определять этап: компилятор или линкер. С CMake этапов становится больше, но признак остаётся тем же — первая строка сообщения.

| Начало сообщения | Кто | Что обычно значит |
|---|---|---|
| `CMake Error at CMakeLists.txt:7 (…)` | CMake, шаг 1 | ошибка в описании; каталог сборки не обновлён |
| `Does not match the generator used previously` | CMake, шаг 1 | каталог сборки создан другим генератором (раздел 2) |
| `FAILED: …main.cpp.obj` и текст clang | компилятор, шаг 2 | ошибка в коде — или не приехал путь к заголовкам (разделы 4, 5) |
| `FAILED: app.exe` и `undefined symbol` (на Linux `undefined reference`) | линкер, шаг 2 | нет определения: файл не в сборке или [сигнатура](../../glossary.md#signature) (signature) разошлась |
| `FAILED: app.exe` и `could not open 'x.lib'` (на Linux `cannot find -lx`) | линкер, шаг 2 | нет файла библиотеки — часто опечатка в имени цели (раздел 5) |
| `***Not Run` | `ctest` | тестовая программа не собралась — смотреть вывод сборки |
| `***Failed` | `ctest` | программа собралась, проверка не прошла |

У Ninja строка `FAILED:` показывает, какой файл не получился, а следом — полную команду, которой его пытались получить. Команда длинная, но полезная: в ней видно, какие пути `-I` и макросы `-D` реально дошли до компилятора. Если нужного пути там нет, ошибка не в коде, а в видимости.

**Правило:** если ошибка непонятна, сначала определить, на каком шаге она случилась. Ошибка шага 1 не лечится правкой кода, ошибка шага 2 не лечится переконфигурацией — кроме случая, когда описание изменилось, а шаг 1 забыли.

## Итоги

- CMake — генератор описания для системы сборки. Компилирует не он, а Ninja вызывает компилятор и линкер, и только для устаревшего; зависимость от заголовков Ninja узнаёт от самого компилятора.
- Шагов два. Конфигурация читает `CMakeLists.txt` и пишет каталог сборки; нужна, когда меняется описание. Сборка запускает Ninja; нужна после каждой правки. Правка `CMakeLists.txt` сама запускает конфигурацию, ключ `-D` — нет.
- Каталог сборки принадлежит одной конфигурации: генератор, компилятор и тип сборки запоминаются в нём.
- Проект описывается целями: `add_executable`, `add_library` со словами `STATIC`, `SHARED`, `INTERFACE`, `IMPORTED`. Свойства задаются командами `target_…` на цели, а не на весь проект.
- `PRIVATE` — свойство только для цели, `PUBLIC` — для цели и потребителей, `INTERFACE` — только для потребителей. Свойства передаются по цепочке подключений.
- Неизвестное имя в `target_link_libraries` CMake считает файлом библиотеки, и опечатка всплывает далеко от места. Защита — `CMAKE_LINK_LIBRARIES_ONLY_TARGETS` и имена вида `пространство::цель`.
- Кэш хранит всё, что задано при конфигурации. Номер занятия набирается один раз именно поэтому. Сброс — `-U`, `--fresh` или удаление каталога сборки.
- Пресет — записанная команда шага 1. Одноконфигурационный генератор выбирает тип сборки при конфигурации, многоконфигурационный — при сборке.
- Для `ctest` тест — программа и её код завершения. `Not Run` значит «не собралось».
- Кто ругается, видно по первой строке: `CMake Error` — шаг 1, `FAILED:` — шаг 2, дальше по тексту — компилятор или линкер.
