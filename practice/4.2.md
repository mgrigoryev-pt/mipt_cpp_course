# Занятие 4.2. Ошибки на границе и конфигурация

> [Лекция 14](../lectures/14/lecture.md): `std::expected`, `std::optional`,
> `std::variant`, обработка ошибок, границы с C-API. `std::string_view`
> из той же лекции понадобится на занятии 4.3.

Здесь замыкается сквозная линия обработки ошибок, которую вы ведёте с первой
части:

| Механизм | Где появился | Зачем именно там |
|---|---|---|
| особое значение | 1.3, `FindField` → `nullptr` | «поля нет» — штатный исход, а не отказ |
| исключение из конструктора | 2.1, `OsHandle` | у конструктора нет канала для кода возврата |
| result-тип | 4.2 | отказ ожидаем, и вызывающий обязан его увидеть |

Три механизма — не три стиля. Разговор занятия: **где в агенте какой уместен
и почему на одном слое должен быть один.**

Второе содержание занятия — конфигурация. Пять занятий правила жили в коде,
и это было правильно: пока их шесть и они меняются вместе с движком, файл
конфигурации — лишний слой между вами и задачей. Теперь их десять, они
устоялись, и перекомпиляция ради одной подстроки стала дорогой. Вот тогда
и заводят конфигурацию — и вместе с ней узнают, чем за неё платят.

## Конфигурация

```bash
cmake --preset windows -D NANO_EDR_LESSON=4.2
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Что делают эти команды и откуда их
запускать — в [`project/README.md`](../project/README.md).

**Действуют семь наборов тестов: 2.1, 2.3, 3.1, 3.2, 3.3, 4.1 и 4.2.** Целиком
не снялся ни один, но из двух наборов выпадает три файла — и все три выпадения
часть содержания занятий, а не техническая деталь:

| файл | из набора | с занятия | почему |
|---|---|---|---|
| `list_tests.cpp` | 2.1 | 4.1 | односвязного списка больше нет |
| `function_tests.cpp` | 3.2 | 4.1 | своего `Function` больше нет |
| `os_handle_tests.cpp` | 2.1 | 4.2 | конструктор обёртки стал приватным |

Третий — ваш на этом занятии, и он не «устаревший тест». Он проверял, что
конструктор `OsHandle` бросает на несуществующем файле; конструктор уезжает
в приватные, и проверять там больше нечего. Контракт заменён сознательно,
значит и проверка заменяется — на тесты фабрики из набора 4.2. Цена смены
канала отказа ровно такая: один файл из пяти. Остальные четыре (событие,
разбор, условия, окно) нужны так же, как на 2.1.

Ключей для этого передавать не надо: их выводит номер занятия.

## Куда это писать

| | |
|---|---|
| `src/os_error.cpp` | новый файл: перевод кодов границы в плюсовой отказ |
| `src/os_handle.cpp` | фабрика `Open`, приватный конструктор, `expected` вместо `os_status` |
| `src/response.cpp` | ветвление по `OsErrorKind` вместо кодов чужого заголовка |
| `src/sources.h` + `.cpp` | `OsSource::Open` и перевод отказа в исключение |
| `src/event.cpp` | тип события узнаётся от куска текста конфигурации |
| `src/rule_loader.cpp` | новый файл: загрузчик правил с номерами строк |
| `src/rule_text.cpp` | **выдан готовым**: скопировать из `tasks/4.2/handout/` |
| `src/agent.h` + `.cpp` | второй вход: агент с правилами из файла |
| `src/agent_rules.h` + `.cpp` | из десяти правил в коде остаётся одно |
| `src/main.cpp` | флаг `--rules`; весь перевод отказов в код возврата |
| `rules.conf` | **новый файл в корне проекта**, рядом с `CMakeLists.txt` |

Разбор одной строки условия писать не надо — он выдан готовым:

```bash
cp tasks/4.2/handout/rule_text.cpp src/
```

Там токенизация «поле оператор значение», кавычки и слово `or`: работа
со строками, к теме занятия отношения не имеющая. Объявления лежат
в комплекте, в `rule_text.h`. Прочитать реализацию стоит — в ней два решения
формата, которые вам придётся защищать, — но переписывать её незачем.

Появление нового `.cpp` — изменение описания проекта, поэтому после
копирования нужна **пере**конфигурация. Из-за заголовков она не нужна, их
CMake не перечисляет.

## Проект

1. **`OsError` и `OsErrorKind`** — закрытое перечисление вашей обёртки.
   В нём не должно быть ни `OS_OK`, ни таймаута: успех и таймаут не отказы,
   а тип, в который нельзя положить успех, невозможно проверить не тем
   сравнением. Точный код границы остаётся в текстовом поле — наверх
   поднимается не код, а решение о том, что код значит.
2. **`os.h` заворачивается в `std::expected`.** Все статусы границы уходят
   внутрь обёртки, наружу она отдаёт `std::expected<T, OsError>`. Код
   возврата больше не расползается по вызывающим.
3. **Конструктор `OsHandle` уезжает в приватные**, рядом появляется
   статическая фабрика:

   ```cpp
   static std::expected<OsHandle, OsError> Open(const std::string& config);
   ```

   Тот самый приём, который лекция 4 анонсировала на будущее. Это **не отказ
   от решения занятия 2.1**, а другой ответ на тот же вопрос: тогда
   единственным каналом было исключение, теперь есть второй.
4. **Правило нуля превращается в правило пяти**, и это следствие мало кто
   ждёт. Фабрика возвращает объект по значению, значит нужен перемещающий
   конструктор — без него `return` не соберётся. Копирующий не подходит: он
   удалён, и удалён правильно, потому что два `os_free` на один указатель.
   Перемещение пишите через `std::exchange`: забрать и обнулить — одно
   действие, а разделённое на две строки оно однажды теряет вторую половину.
5. **Ни одного кода границы выше обёртки.** Критерий проверяется грубым
   инструментом, и это сделано намеренно:

   ```bash
   grep -rn "OS_" src/
   ```

   Вне файлов обёртки не должно находиться ничего. Последним обычно уходит
   не перечисление, а строка — печать успеха литералом. Эталоны сравниваются
   побайтово, вывод менять нельзя, поэтому литерал переезжает в маленькую
   функцию рядом с обёрткой. Функция получится неприлично мелкой, и она
   существует ровно затем, чтобы критерий читался как «ни одного», а не как
   «почти ни одного».
6. **Найдите три места, где `expected` превращается обратно в исключение.**
   Сквозной `expected` до самого `main` не проводится, и это осознанное
   решение, которое надо уметь защитить: у виртуального `Run` нет
   вызывающего, который мог бы решить иначе, а протаскивать результат через
   интерфейс ради того, чтобы в единственной точке превратить его
   в сообщение, — работа без выигрыша. Правило: **один механизм на слой;
   менять его на границе слоёв нормально, внутри слоя — нет.**
7. **`RuleLoader` читает правила из файла:**

   ```cpp
   RuleLoader::Load(path) -> std::expected<RuleSet, ConfigError>
   ```

   `ConfigError` обязан содержать **номер строки**. Конфигурация без номера
   строки в диагностике — это конфигурация, которую отлаживают перебором.
   Формат сообщения один на все отказы, и он копирует вывод компилятора:
   `rules.conf:14: неизвестный оператор startswith`.

   Два случая стоит решить осознанно. **Отказ про правило целиком указывает
   на строку заголовка правила**, а не на то место, где правило кончилось:
   человек читает про правило, а не про его границу. **Ноль означает
   «к строке не привязано»** — файла нет, файл пуст; выдумать строку было бы
   враньём.
8. **Загрузчик придирчив.** Неизвестный ключ — отказ, неизвестный
   оператор — отказ, неизвестный тип события — отказ, правило без условий —
   отказ. Ни одного «ну ладно, пропустим». Придирчивость распространяется
   и на ключи отдельных видов: `sequence` без `window_ms`, `threshold`
   с `count` больше вместимости вашего буфера отметок — тоже отказы
   с номером строки, а не правила, которые выглядят рабочими и не срабатывают
   никогда.
9. **Девять правил из десяти уезжают в `rules.conf`** — все три вида.
   Десятое остаётся в коде, и почему именно оно — ниже. Движку всё равно,
   откуда приехало правило: он видит `IRule`.
10. **Флаг `--rules <путь>`** включает чтение файла, и агент с файлом обязан
    давать на семи сценариях те же детекты и те же действия, что агент
    со встроенным набором. Сверка делается прогоном, а не рассуждением.
11. **Прогон под санитайзером.** Проверяется ровно одно, но важное:
    перемещение обёртки не освобождает хендл дважды. Тест на это есть,
    и сам по себе он ничего не ловит — его смысл в прогоне под ASan.

## Формат файла правил

Секции, знакомые по конфигурации сценария. Строка, начинающаяся с `#`
или `;`, — комментарий; пустые строки пропускаются.

```ini
[rule script_host_from_temp]
kind     = match
severity = high
match    = type is process_start
match    = image ends_with wscript.exe or image ends_with cscript.exe
match    = cmdline contains "\Temp\"
action   = kill_process
action   = quarantine_source
```

**Повторяющийся ключ означает «ещё одно», а не «вместо»:** три строки
`match` — это три условия, объединённые И; две строки `action` — два
действия.

Общие ключи у всех видов — `kind`, `severity`, `action`. Поверх них у каждого
вида свои:

| `kind` | свои ключи |
|---|---|
| `match` | `match` — одна строка условия или несколько |
| `sequence` | `first`, `second` (условия шагов), `window_ms`, `link` |
| `threshold` | `match`, `count`, `window_ms`, `key`, `idle_ms` |

Значения: `severity` — `low`, `medium`, `high`, `critical`; `link` —
`same_pid`, `child_of_prev`, `none`; `window_ms`, `count` и `idle_ms` —
целые числа; `key` — имя поля события. Имена действий — те же, что
в вашем коде с занятия 3.3. `link` можно не указывать: без него шаги
связываются по процессу, как `same_pid`.

**Условие — «поле оператор значение».** Операторы: `is` (только для поля
`type`), `equals`, `contains`, `ends_with`. Альтернативы внутри одной строки
разделяются словом `or` и означают ИЛИ. Значение с пробелами или со словом
`or` внутри — в двойных кавычках; экранирования нет.

`idle_ms` в правиле не обязателен: сколько держать счётчики по ключам —
настройка расхода памяти на конкретном хосте, и приходит она от сервера
через `edr_config_get`. Ключ в правиле её перекрывает.

Тот же формат записан в заголовке `rule_loader.h`, рядом с подписями, —
придумывать его не нужно.

## Не всё уезжает в файл, и это не недоделка

Правило с произвольным предикатом на C++ — то, которое спрашивает модель,
кто записал файл, — конфигурацией не выражается. Выразить его можно, и именно
этого делать нельзя: конфигурация, умеющая произвольные вычисления, — это
язык программирования, только хуже отлаживаемый и без компилятора.

Такие правила остаются в коде. Граница проходит там же, где всегда:
**конфигурация покрывает то, что меняется часто, код — то, что требует
выражения.** В наборе агента это одно правило из десяти, и «нельзя» здесь
настоящее: остальные девять форматом выражаются, и они уезжают.

Смешанный набор — девять правил из файла, одно из кода — не переходное
состояние, а штатное устройство.

## Готово, когда

- Ни один статус `os.h` не виден выше обёртки: `grep -rn "OS_" src/` вне
  файлов обёртки не находит ничего.
- `RuleLoader` на битой конфигурации сообщает, **что** не так и **в какой
  строке**.
- Девять правил уехали в файл, десятое осталось в коде, и на семи сценариях
  агент даёт те же детекты и те же действия, что до переезда, и проходит
  `sim_verify` по секции `[expect]`. Порядок строк `[STAT]` при этом
  разойдётся — правило из кода добавляется последним, — и это не расхождение
  результата.
- Битый или пустой `rules.conf` — отказ старта, а не «загрузим что смогли».
  Агент, стартовавший с половиной правил, выглядит работающим и не защищает.
- Перемещение обёртки границы не освобождает хендл дважды. Проверяется
  прогоном под ASan: без санитайзера этот тест проверяет только то,
  что код скомпилировался.

## Тесты

Два файла и двадцать четыре случая: девять у фабрики границы, пятнадцать
у загрузчика. Первый трогает границу: ему нужен настоящий сценарий, путь
передаётся сборкой. Второй не трогает ни диск, ни симулятор.

### Запуск тестов

Команды — те же, что в «Конфигурации». Правки в вашем `CMakeLists.txt`
не нужны: тесты линкуются с библиотекой `nano_edr_core`, а она собирается
сама из всех `.cpp` в `src/`, кроме `main.cpp`.

Наборы прошлых занятий приходят вместе с этим и обязаны проходить.

### Что именно проверяется

**Фабрика вместо конструктора.**

| тест | что сломалось бы без него |
|---|---|
| `правило пяти: копирования нет, перемещение есть` | `Open` не собирается: возвращать объект нечем |
| `конструктор недоступен снаружи` | остаётся второй путь создания, мимо проверки |
| `несуществующий файл — ошибка, а не исключение` | отказ можно не заметить |
| `перемещение не освобождает хендл дважды` | двойной `os_free` |

Четвёртый сам по себе ничего не ловит — его смысл в прогоне под
`-fsanitize=address`. Перемещающий конструктор, забывший обнулить источник,
собирается, проходит все тесты и падает на чужой машине.

Тест `отказ действия несёт вид, а не только текст` стоит отдельно. На нём
держится всё реагирование: «нет такого процесса», «номер переиспользован»
и «доступ запрещён» — три разных последствия, и различать их надо
перечислением, а не поиском подстроки в сообщении.

**Загрузчик правил.** Проверяется не то, разбирается ли правильный файл, —
это самая лёгкая часть. Проверяется, что на битой конфигурации загрузчик
**отказывает** и называет **номер строки**.

| битая строка | ожидаемый номер |
|---|---|
| неизвестный ключ (`severiti`) | строка ключа |
| неизвестный оператор (`startswith`) | строка условия |
| неизвестный тип события (`proces_start`) | строка условия |
| неизвестная важность | строка ключа |
| строка без `=`, строка вне секции | своя строка |
| правило без `kind` или без условий | строка **заголовка правила** |
| порог больше вместимости буфера отметок | строка заголовка правила |
| пустой файл, файла нет | ноль: к строке не привязано |

Последние две строки таблицы стоит прочитать вместе. Отказ про правило
целиком указывает на его заголовок, а не на место, где правило кончилось:
человек читает про правило, а не про его границу. А ноль означает честное
«строки тут нет».

Отдельно проверяется, что `слово or внутри кавычек не режет условие`. Разбор,
не знающий про кавычки, сломает `cmdline contains "a or b"` на два
бессмысленных куска и примет битое правило за исправное. Молча. Этот случай
у вас проходит с самого начала — он про выданный `rule_text.cpp`, — и стоит
он здесь затем, чтобы вы увидели, за что именно эта выдача отвечает.

### На что обратить внимание

**`expected` не отменяет исключения.** У него другая область: ожидаемый
отказ, который вызывающий обязан обработать. Нарушение контракта формата
остаётся исключением, и на вопрос «почему тут одно, а там другое» надо иметь
ответ. Короткий: у `Event` нарушен инвариант — данные битые, и делать
с этим вызывающему нечего; у `OsHandle` не открылся файл, и вызывающий обязан
сказать про это человеку внятно.

**Один взгляд на 4.2 всё-таки появляется, и только один.**
`EventTypeFromString` принимает `std::string_view`: загрузчик режет текст
конфигурации взглядами и спрашивает тип события от куска этого текста.
Заводить ради одного сравнения `std::string` означало бы аллокацию
на каждое условие в файле. Разбор самого события владения не теряет —
это тема занятия 4.3, где строки приходят из чужого потока.

**Загрузка правил из файла ослабляет проверки.** Правило в коде проверял
компилятор: опечатка в имени условия была ошибкой сборки, несуществующее
поле — ошибкой сборки. Правило в файле не проверяет никто, кроме вашего
загрузчика. Всё, что раньше ловилось на этапе компиляции, стало вашей
работой во время выполнения — отсюда и придирчивость, и номера строк.

**Тихо пропущенная строка конфигурации — это правило, которое человек
написал, а агент не применил.** Узнает он об этом после инцидента. Это
и есть довод за придирчивость, и он не эстетический.

### Если не собирается

**`'os_error.h' file not found`** — заготовки взяты из среза `l4.1`. Нужен
`l4.2`.

**`no member named 'Open' in 'nano_edr::OsHandle'`** — то же самое.

**`'rule_text.h' file not found`** — то же самое: заголовок появляется
в срезе `l4.2`.

**`undefined reference to 'nano_edr::BuildCondition'`** или
`unresolved external symbol` на `Trim`, `ParseUint`, `ParseSeverity` — файл
`rule_text.cpp` не скопирован в `src/` либо скопирован после конфигурации.
Скопируйте и переконфигурируйте.

**`calling a private constructor of class 'nano_edr::OsHandle'`** в тестах
2.1 — конфигурация осталась на прежнем занятии. С `-D NANO_EDR_LESSON=4.2`
старый файл из набора 2.1 выпадает сам.

**`ignoring return value of function declared with 'nodiscard'`** — это
не придирка компилятора, а смысл занятия: результат обязан быть посмотрен.

**Фабрика не компилируется на `return`** — не написано перемещение. См. пункт
4 задания.
