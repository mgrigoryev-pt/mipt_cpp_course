# Занятие 2.1. Переезд на `os.h`

> Лекции [4](../lectures/04/lecture.md)–[5](../lectures/05/lecture.md): классы, конструкторы, деструкторы, `static`, операторы.

Агент перестаёт читать файл и начинает получать события от системы. Файл никуда
не исчезает: он остаётся вторым источником, и это часть задания.

Появляются классы, и первым из них будет обёртка над границей C. Не случайно:
именно на ней видно, зачем нужен конструктор, который бросает.

## Конфигурация

```bash
cmake --preset windows -D NANO_EDR_LESSON=2.1
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Что делают эти команды и откуда их
запускать — в [`project/README.md`](../project/README.md).

**Наборы тестов 1.2 и 1.3 с этого занятия не подключаются, и это содержание
задания, а не поломка комплекта.** Против среза `l2.1` они бы просто
не собрались: `Event` стал классом, разбор отдаёт `EventParts` вместо `Event`,
список стал классом с приватными полями. Старые тесты проверяли типы, которых
больше нет. Проверять новые типы старыми тестами нечем, поэтому они заменены
набором 2.1 — он покрывает то же и больше.

## Куда это писать

Три новых файла в `src/` по заголовкам среза плюс свои — на агента
и на источники:

| | |
|---|---|
| `src/event.cpp` | реализации из `event.h` — событие с инвариантом |
| `src/conditions.cpp` | реализации из `conditions.h` — четыре условия |
| `src/os_handle.cpp` | реализации из `os_handle.h` — обёртка над границей |
| `src/agent.cpp` + `.h` | агент и трамплин; имя ваше |
| `src/sources.cpp` + `.h` | файловый источник и источник через границу; имя ваше |

Плюс переписываются под новые подписи три файла с прошлых занятий:
`src/parse.cpp`, `src/event_list.cpp`, `src/fields.cpp`.

Реализовать нужно всё, что объявлено в заготовках, и ровно с теми подписями:

```
Event::Event  ToString  operator<<
ParseFields  ParseEventParts  IsBlankOrComment
EventList::~EventList  PushBack  PopFront  Clear
FindField  GetRequiredField  GetIntField (две перегрузки)
IsProcessStart  IsFileWrite  IsNetConnect
PathEndsWith  CommandLineContains  NormalizePath
SeverityName  CheckRules
FieldEquals  FieldContains  FieldEndsWith  FieldInList (operator() у каждого)
OsHandle::OsHandle  ~OsHandle  Subscribe  Start  Wait  Stop
```

`size()`, `capacity()`, `empty()`, `head()`, `back()` и геттеры `Event`
написаны в заголовках — их реализовывать не надо.

`CMakeLists.txt` править не нужно: библиотека `nano_edr_core` собирается
из всех `.cpp` в `src/`, кроме `main.cpp`. Но появление новых файлов —
изменение описания проекта, поэтому после него нужна **пере**конфигурация.

**Пока этих файлов нет, набор 2.1 не собирается** — компоновщик скажет
`unresolved external symbol` (на Linux — `undefined reference`) на каждую
функцию из заготовок. Так выглядит начало занятия.

## На паре

1. **`OsHandle` — RAII-обёртка над `os_handle*`.** Конструктор зовёт `os_init`
   и **бросает**, если тот вернул ошибку. Деструктор зовёт `os_free`
   и **не бросает никогда**. Копирование — `= delete`: за указателем стоят
   открытый файл, поток и отчёт, и две обёртки над одним указателем позвали бы
   `os_free` дважды.

   Это ровно тот случай из лекции 4: у конструктора нет канала для кода
   возврата, поэтому либо корректный объект, либо исключение. Никакого
   `is_valid()`: объект, про который надо спрашивать, жив ли он, придётся
   проверять при каждом обращении, и однажды проверку забудут.
2. **Колбэк через статический метод-трамплин.** C-API принимает указатель
   на функцию и `void*`; метод класса указателем на функцию не является —
   у него есть неявный `this`. Поэтому подписываются статическим методом,
   а объект передают через `void*`, и трамплин достаёт его обратно.

   Трамплин помечается `noexcept` и внутри ловит **всё**: исключение,
   вылетевшее через границу C, — неопределённое поведение. Не «плохой стиль»,
   а UB: за границей кадры C, и раскрутка стека через них не определена.
3. **Переезд.** Агент переключается с чтения файла на подписку. Обработка
   события при этом не меняется — и если пришлось её менять, значит она была
   связана с источником сильнее, чем нужно.

   Начать стоит с `examples/minimal_agent.cpp`: полный цикл работы с границей,
   и он не только читается, но и запускается.

   ```bash
   cmake --build --preset windows --target minimal_agent
   ```

   Дальше — сам исполняемый файл из каталога сборки и любой сценарий
   из `scenarios/`.
4. **`Event` с инвариантом** вместо агрегата: приватные поля, `const`-геттеры,
   обязательные `ts` и `type` в конструкторе. «Пустого события» больше
   не существует, и это надо будет учесть в окне.

   `EventParts` при этом остаётся агрегатом без обещаний: разбор строки
   законно не удаётся, журнал пишет чужой код. Проверять в разборе, что `ts`
   число, не надо — это работа конструктора `Event`. Один вопрос проверяется
   в одном месте, иначе две проверки однажды разойдутся.
5. **`EventList` тоже класс**: поля приватные, свободные функции стали
   методами, инвариант «`size()` равен числу узлов» держит теперь сам тип,
   а не вызывающий. Заодно у `EventNode` появляется конструктор — без него
   список не собрать, потому что `Event` больше не создать пустым. Это первое
   место, где инвариант одного типа заставляет поменяться другой.
6. **`operator<<` и `Timestamp`** с `auto operator<=>(const Timestamp&) const = default`.
   `operator<<`, `ToString` и `std::format` обязаны давать **одну и ту же
   строку**: два формата одного объекта расходятся на первой правке,
   и расходятся молча.
7. **Функторы-условия** `FieldEquals`, `FieldContains`, `FieldEndsWith`,
   `FieldInList` — набор, на котором в 2.2 будут собираться правила. Это
   то, чего не умеет функция: состояние живёт в объекте, и
   `FieldEndsWith("cmdline", ".js")` с `FieldEndsWith("cmdline", ".exe")` —
   один класс и два объекта, а не две функции.

**Прочитайте `os.h` целиком, включая раздел о том, чего в нём нет.** Половина
решений этого занятия следует из контракта, а не из вашего вкуса: единственный
подписчик без отписки, строки события действительны только на время колбэка,
действия из колбэка не рекурсируют.

**Строки события живут только до возврата из колбэка.** В отладочной сборке
симулятор освобождает их сразу, так что ASan поймает использование после
возврата. Если вы сохранили `const char*` из события — вы это увидите.

**`void*` не помнит, чем он был.** Трамплин приводит контекст обратно к типу
получателя, и приводить надо ровно к тому типу, указатель на который
передавался: любой другой даст неверный адрес, и компилятор про это промолчит.

## Готово, когда

- Агент работает поверх `os.h`.
- **Старый файловый источник выбирается флагом `--file` и даёт на том же
  журнале тот же вывод, что поток через границу.** Не «остался в коде»:
  мёртвый код этому критерию удовлетворяет, а работающий второй источник —
  единственное доказательство, что обработка события не знает, откуда оно
  пришло. Сравнивать удобно под `--quiet`: там в `stdout` только детекты,
  и два прогона обязаны совпасть побайтово.
- `std::print("{}\n", event)` работает.
- **Одно испорченное событие прогон не обрывает.** Правило вправе объявить
  отсутствие обязательного поля нарушением контракта и бросить — агент это
  гасит, считает и живёт дальше. На занятии 1.3 политика была обратной, и там
  она была верной: агент читал файл и других событий не ждал. Теперь он живёт
  в потоке, и агент, умирающий от одного события, защищает хост хуже, чем
  агент, который это событие пропустил и доложил.
- **Прогон обрывает только отказ границы**, и тогда программа печатает причину
  и завершается штатно, а не падает. Коды возврата: **0** — прогон дошёл
  до конца, **1** — оборван отказом границы, **2** — работать не с чем
  (аргументы).

  Единица здесь забирает себе случай, который на 1.3 был двойкой:
  несуществующий файл. Путь теперь открывает симулятор, а `os_init` отвечает
  `OS_CONFIG_ERROR` и на битом сценарии, и на отсутствующем журнале. Отличить
  их агент не может — и не должен: спрашивать файловую систему отдельно
  значило бы завести второй источник правды о том, что уже сказала граница.
- **Прогон под санитайзером чист**: пресет `asan-windows`, на Linux — `asan`.
  На этом занятии проверка не формальная. Незакрытый `os_handle*` — утечка,
  и её не видит ни один тест: зелёный прогон означает, что хендл создался,
  а не что он освободился. Сохранённый `const char*` из события —
  использование после освобождения, и его тоже покажет только санитайзер.
  Пустой отчёт здесь и есть доказательство, что RAII написан, а не изображён.

## Тесты

Пять групп: событие с инвариантом, разбор строки, окно событий,
условия-функторы и обёртка над границей `os.h`. Тестам обёртки нужен
настоящий журнал; путь к сценариям передаёт сборка тестов, делать для этого
ничего не надо.

### Запуск тестов

```bash
ctest --preset windows
```

На Linux вместо `windows` — `linux`.

Отдельно и обязательно — прогон под санитайзером, тремя командами:

```bash
cmake --preset asan-windows -D NANO_EDR_LESSON=2.1
```

```bash
cmake --build --preset asan-windows
```

```bash
ctest --preset asan-windows
```

На Linux — `asan`.

### Что именно проверяется

Главное — **инвариант вместо проверки после создания**. Если у вас есть способ
получить `Event`, который «создался, но пользоваться нельзя», или `OsHandle`
с методом `is_valid()`, — инварианта нет, и половина тестов это покажет.

Два случая — «тысяча элементов освобождается деструктором» и «на исправном
журнале хендл создаётся и освобождается» — под обычной сборкой не проверяют
почти ничего. Они и не должны: утечку видит не тест, а санитайзер. Незакрытый
`os_handle*` обнаруживается именно так.

### На что обратить внимание

**Пустое тело деструктора списка не даёт утечки, и это ловушка.** Убрав тело
`~EventList`, легко решить, что список теперь течёт. Не течёт: поле `head_` —
`unique_ptr`, и оно разрушится само. Меняется не наличие освобождения,
а способ: вместо цикла цепочку разберёт **рекурсия** неявных деструкторов.
Тесты идут до тысячи узлов, и рекурсия их выдержит. То есть зелёный прогон
и чистый санитайзер здесь не доказывают, что деструктор написан правильно, —
смотреть надо в код.

**Трамплин тестом не поймать.** В отладочной сборке симулятор заметит
вылетевшее исключение и завершит программу, но полагаться на чужую проверку
вместо своей — плохая привычка. На паре про трамплин спросят обязательно.
