# Занятие 2.1. Переезд на `os.h`

> Лекции [4](../lectures/04/lecture.md)–[5](../lectures/05/lecture.md):
> классы, конструкторы и деструкторы, `static`, перегрузка операторов.

До сих пор агент сам открывал файл журнала. В настоящем продукте события
присылает операционная система, и с этого занятия агент получает их через
`include/os.h` — интерфейс на C между агентом и системой. Вместо настоящей
системы работает симулятор, готовая библиотека `os` из `lib/`: он проигрывает
журнал сценария так, будто события приходят с машины.

Чтение файла остаётся вторым **источником событий**. Источник — то, откуда
событие пришло; обработка — то, что агент с ним делает: проверяет правилами
и печатает детекты. Источников теперь два, обработка одна, и проверяется это
одним журналом, прогнанным двумя способами:

```
nano-edr --quiet scenarios/phishing_macro.log          # события присылает os.h
nano-edr --quiet --file scenarios/phishing_macro.log   # агент читает файл сам
```

Оба запуска обязаны напечатать одно и то же, побайтово. `--quiet`, как
с занятия 1.1, оставляет в выводе только строки детектов — их и сравнивают.

| | |
|---|---|
| **Пишете** | <ul><li>`event.cpp`, `os_handle.cpp`</li><li>агент и два источника</li></ul> |
| **Переписываете** | <ul><li>`parse.cpp`, `event_list.cpp`, `fields.cpp`</li><li>`rules.cpp`, `agent_rules.cpp`, `main.cpp`</li></ul> |
| **Выдано** | <ul><li>новые `event.h`, `os_handle.h`</li><li>изменённые `parse.h`, `event_list.h`, `fields.h` — что изменилось, сказано в начале каждого</li><li>тесты, `examples/minimal_agent.cpp`</li></ul> |
| **Сборка** | `-D NANO_EDR_LESSON=2.1` |
| **Готово** | оба источника дают один вывод на семи сценариях — [полный список](#готово-когда) |

## Развитие проекта

Шаги 1–5 — рефакторинг: код из `src/` переводится на новые заготовки, а агент
делает то же, что на 1.3. Шаги 6–10 — переезд на `os.h`.

Сразу после переконфигурации проект не собирается: код в `src/` написан под
заготовки 1.3, и компилятор находит ошибки почти в каждом файле. Каждый
из шагов 1–4 переводит на новые заготовки свои файлы, и ошибок в них
не остаётся.

Наборы тестов 1.2 и 1.3 больше не подключаются: они написаны для старых типов
и против новых заготовок не собрались бы. Их работу делает набор 2.1.

### 1. Список `EventList` становится классом

`EventList` — список последних событий с занятия 1.2. Поведение у него
прежнее, меняется только доступ: поля закрыты, функции стали методами.

| 1.2 и 1.3 | 2.1 |
|---|---|
| `EventList list; list.capacity = n;` | `EventList list(n);` |
| `ListPushBack(&list, &event)` | `list.PushBack(event)` |
| `ListPopFront(&list)` | `list.PopFront()` |
| `ListClear(&list)` | `list.Clear()` |
| `list.size`, `list.head`, `list.tail` | `list.size()`, `list.head()`, `list.back()` |

Пишете деструктор, `PushBack`, `PopFront` и `Clear`; конструктор и геттеры
уже в заголовке. У `Event` больше нет конструктора без аргументов, поэтому
узел создаётся сразу с событием: `new EventNode(event)`.

### 2. Разбор строки на новых типах

Правила разбора те же, что на 1.2. Меняется то, что разбор отдаёт:
не `Event`, а `EventParts` — [агрегат](../lectures/glossary.md#aggregate)
(aggregate) без всяких проверок. В нём две части, как и у события:

- **шапка** — строки `ts`, `type` и `pid`, общие для событий любого типа;
- **`fields`** — вектор всех остальных пар строки: `image`, `path`
  и прочие, у каждого типа события свои.

Из `EventParts` потом строится `Event` (шаг 5). Строку функции разбора
получают теперь по константной ссылке:

| 1.2 и 1.3 | 2.1 |
|---|---|
| `ParseEventLine(const std::string* line, Event* out)` | `ParseEventParts(const std::string& line, EventParts* out)` |
| — | `ParseFields(const std::string& text, std::vector<Field>* out)` |
| `IsBlankOrComment(const std::string* line)` | `IsBlankOrComment(const std::string& line)` |

Новая функция одна — `ParseFields`. Она разбирает пары `ключ=значение` и про
шапку не знает: `ts`, `type` и `pid` для неё обычные пары. `ParseEventParts`
берёт пары у неё и раскладывает по `EventParts`. Пустой текст — успех и ноль
пар; после `false` содержимое `*out` использовать нельзя.

Что `ts` — число, разбор не проверяет: это сделает конструктор `Event`
(шаг 5), и второй такой же проверки быть не должно.

### 3. Функции доступа и правила на геттерах

`fields.cpp`, `rules.cpp` и `agent_rules.cpp` переходят на геттеры из
`event.h`: `event.type()` вместо `event.type`, `event.fields()` вместо
`event.fields`, `event.raw_ts()` вместо `event.ts` — время строкой, как
в журнале. Пять правил и формат строки детекта остаются прежними.

Одно изменение в поведении: **`FindField` находит и поля шапки**. На 1.3
он искал только в `fields`, и `FindField(event, "type")` возвращал `nullptr`.
Теперь по ключам `ts`, `type` и `pid` он возвращает `raw_ts()`, `type()`
и `pid()`. `GetRequiredField` ищет там же.

### 4. Агент и файловый источник

Всё, что агент делает с одним событием, переезжает в метод `HandleEvent`
класса агента: проверить правилами, напечатать детект, положить событие
в `EventList`, учесть его в сводке. Сводка — итог, который агент с занятия 1.1
печатает в конце прогона: сколько событий всего и сколько каждого типа.
Формат её ваш, под `--quiet` её нет; с этого занятия в ней есть ещё число
пропущенных событий (шаг 9).

Чтение файла переезжает в отдельный класс-источник: он строит `Event` из каждой
строки и отдаёт агенту. Битая строка по-прежнему пропускается.

Имена классов ваши, тесты их не видят, но следующие занятия называют их так:

```cpp
class Agent {
 public:
    Agent(std::size_t window_size, bool quiet);  // из --window-size и --quiet
    void HandleEvent(const Event& event);
    void PrintSummary() const;  // сводка в конце прогона
    // ...
 private:
    EventList recent_;  // последние события, не больше window_size
    // счётчики для сводки
};

class FileSource {
 public:
    explicit FileSource(const std::string& path);
    void Run(Agent* agent);  // строка → EventParts → Event → HandleEvent
    // ...
};
```

### 5. Конструктор и печать `Event`

После шагов 1–4 ошибок компиляции нет, и сборка доходит до
[линкера](../lectures/glossary.md#linker) (linker): он не находит конструктора
`Event` — `unresolved external symbol`, на Linux `undefined reference`.
Конструктор и печать события пишутся в `src/event.cpp`.

```cpp
explicit Event(const EventParts& parts);
```

Конструктор бросает `std::invalid_argument`, если:

- `ts` пустая, не число или не помещается в `uint64_t` — слишком большое
  число не обрезается молча;
- `type` пустая.

`pid` не проверяется: он может быть пустым, потому что не у каждого события
есть процесс.

В тексте исключения должно стоять значение, которое не прошло проверку,
иначе по сообщению не понять, что не так с журналом. Например, для строки
с `ts=вчера` подойдёт `неверное время события: вчера`. Тест проверяет, что
в `what()` есть слово `вчера`.

Время хранится дважды: `ts()` — `Timestamp`, число миллисекунд для сравнений
(сравнения уже заданы в заголовке); `raw_ts()` — строка как в журнале, она
печатается в строке детекта.

Печать — три способа, одна строка, это проверяет тест:

- `ToString(event)` — формат ваш, но в строке есть `ts`, `type`, `pid` и все
  поля с ключами и значениями;
- `operator<<(out, event)` пишет ту же строку и возвращает поток (лекция 5,
  раздел 8);
- `std::format("{}", event)` и `std::print` работают через `std::formatter`,
  выданный готовым в конце `event.h`: он зовёт ваш `ToString` (специализация
  шаблона — лекция 8).

Собирайте строку только в `ToString`, а в `operator<<` выводите её результат:
формат, записанный дважды, разойдётся после первой же правки.

**Проверка.** Агент собирается и запускается как на 1.3, путь к журналу —
обычным аргументом. Вывод под `--quiet` на каждом из семи сценариев совпадает
с эталоном `tasks/2.1/tests/expected/<сценарий>.out`:

```bash
./build/linux/nano-edr --quiet scenarios/phishing_macro.log > out.txt
diff out.txt tasks/2.1/tests/expected/phishing_macro.out
```

На Windows — `./build/windows/Release/nano-edr` и `fc.exe`. Тесты пока
не собираются: линкер не находит методов `OsHandle`, это шаг 7.

### 7. Обёртка `OsHandle`

`src/os_handle.cpp`. `OsHandle` — [RAII](../lectures/glossary.md#raii)-обёртка:
она владеет хендлом, конструктор получает его от `os_init`, деструктор отдаёт
`os_free`. Остальные методы зовут по одной
функции `os.h`:

| Метод | Зовёт | При отказе |
|---|---|---|
| `OsHandle(config_path)` | `os_init` | `std::runtime_error`: вернуть код конструктору некуда |
| `~OsHandle()` | `os_free` | не бросает никогда |
| `Subscribe(callback, context)` | `os_event_subscribe` | `std::runtime_error`: отказ здесь — ошибка в коде агента |
| `Start()` | `os_start` | `std::runtime_error`, по той же причине |
| `Wait(timeout_ms)` | `os_wait` | возвращает `os_status` как есть: `OS_TIMEOUT` — обычный исход |
| `Stop()` | `os_stop` | не бросает, звать можно всегда, в том числе повторно |

Сообщение исключения из конструктора содержит путь и имя кода
из `os_status_str`. `Stop` на этом занятии никто не зовёт, но он объявлен
в заготовке — реализуйте и его.

### 8. Трамплин и источник `os.h`

`os.h` сообщает о событии [колбэком](../lectures/glossary.md#callback)
(callback): функцией, которую агент передаёт в `Subscribe`, а `os.h` зовёт
на каждое событие. Её тип:

```cpp
typedef void (*os_event_cb)(const os_event* ev, void* ctx);
```

Обработать событие должен объект агента, но обычный метод сюда не передать:
у него скрытый параметр `this`, и под указатель на функцию он не подходит.
Поэтому в агенте заводится **статический** метод ровно с этой сигнатурой
(лекция 4, раздел 7) — [трамплин](../lectures/glossary.md#trampoline)
(trampoline). В `Subscribe` передаются адрес трамплина и адрес агента;
трамплин приводит `ctx` обратно к `Agent*` через `static_cast` (лекция 3,
раздел 4) и отдаёт событие тому же `HandleEvent`, что и файловый источник.

```cpp
class Agent {
 public:
    static void Trampoline(const os_event* ev, void* ctx) noexcept;
    // ...
};

class OsSource {
 public:
    explicit OsSource(const std::string& config_path);  // создаёт OsHandle
    void Run(Agent* agent);  // Subscribe, Start, Wait в цикле
    // ...
};
```

Три требования к трамплину:

- **Исключение не выходит наружу.** Всё тело — в `try` с `catch (...)`:
  [раскрутка стека](../lectures/glossary.md#stack-unwinding) (stack unwinding)
  через код на C — [UB](../lectures/glossary.md#ub). `noexcept` без
  `catch (...)` не спасает: исключение завершит программу через
  `std::terminate`.
- **`ctx` приводится ровно к тому типу, адрес которого передан
  в `Subscribe`.** `static_cast` из `void*` ничего не проверяет.
- **Агент живёт дольше хендла.** Объявите агента раньше источника
  (`OsSource`): объекты разрушаются в обратном порядке (лекция 4, раздел 6).

Строки `os_event` — `type`, ключи и значения полей — действительны только
до возврата из колбэка. Если сохранить указатель на них и прочитать позже,
это [use-after-free](../lectures/glossary.md#use-after-free): чтение памяти,
которую `os.h` уже освободил. Поэтому трамплин сразу копирует событие:
заполняет `EventParts` и строит из него `Event`. При заполнении:

- `ts` и `pid` в `os_event` — числа, а в `EventParts` — строки
  (`std::to_string`);
- `pid`, равный 0, означает «неприменимо» — то же, что событие без `pid`
  в журнале, то есть пустую строку;
- в `fields` шапки нет: она в отдельных полях структуры.

`OsSource::Run` подписывает агента, зовёт `Start` и затем `Wait` в цикле, пока
тот возвращает `OS_TIMEOUT`. `OS_OK` — журнал кончился; любой другой код —
отказ источника (шаг 9).

В `main` появляется ключ `--file <путь>`: с ним агент читает файл сам, без
него события идут через `os.h` — как в двух командах в начале занятия.

### 9. Ошибки и коды завершения

**Одно испорченное событие не обрывает прогон.** Если обработка события
бросила исключение — `GetRequiredField` не нашёл `image` у `process_start`,
конструктор `Event` отверг `ts`, — агент ловит его, пропускает событие
и считает; число пропущенных печатается в сводке. `GetRequiredField`
по-прежнему бросает, меняется только место, где исключение ловят.

**Прогон обрывает только отказ источника.** Тогда агент печатает причину
в `stderr` и завершается с [кодом завершения](../lectures/glossary.md#exit-code)
(exit code) 1. Исключения `OsHandle` ловит `catch` в `main`, оставшийся с 1.3.

| Код | Когда |
|---|---|
| 0 | прогон дошёл до конца: `os_wait` вернул `OS_OK` или файл дочитан |
| 1 | исключение из `OsHandle`, `Subscribe` или `Start` |
| 1 | `os_wait` вернул `OS_IO_ERROR`: журнал испорчен — битая строка, нет обязательного поля или время идёт назад. В `os.h` этого кода нет, он описан в `SPEC.md` |
| 1 | с `--file` файл не открылся |
| 2 | неверные аргументы: неизвестная опция, нет пути, путь задан дважды, после `--file` нет значения |

Несуществующий файл теперь даёт 1, а не 2, как на 1.3. С `os.h` его открывает
`os_init`, отдельно проверять, есть ли файл, не нужно.

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Почему типов два: `Event` и `EventParts`

Разбор строки может не удаться: журнал пишет чужой код. Объект с инвариантом
нельзя собирать по частям из неполных данных. Поэтому разбор заполняет
агрегат без проверок, а проверяет данные только конструктор `Event`.

### Почему у `Event` и `OsHandle` нет `is_valid()`

У конструктора два исхода: готовый объект или исключение. Объект, который
создан, но пользоваться им нельзя, заставил бы каждого пользователя помнить
про проверку, а забытую проверку не видят ни компилятор, ни читающий код.
Лекция 4, раздел 5.

### Почему `Timestamp` отдельный тип

Чтобы время нельзя было по ошибке сложить с другим числом, например
с размером файла. С `uint64_t` такое компилируется молча.

### Почему копирование списка и обёртки запрещено

[Правило трёх](../lectures/glossary.md#rule-of-three) (rule of three),
лекция 4, раздел 6. Деструктор списка удаляет узлы (`EventNode`), поэтому
копирование, сгенерированное компилятором, неверно: копия получила бы те же
адреса, и каждый узел удалился бы дважды. У `OsHandle` так же: две копии позвали бы `os_free`
на одном хендле.

### Почему одно испорченное событие больше не обрывает прогон

На 1.3 агент читал готовый файл, и испорченный журнал разумно было отвергнуть
целиком. Теперь события идут потоком от системы, и агент, который
останавливается из-за одного странного события, перестаёт защищать машину.
Лучше пропустить событие и сообщить о нём.
