# Занятие 3.3. Реагирование и цена копий

> Лекция [11](../lectures/11/lecture.md): move-семантика, категории значения,
> правило пяти и правило нуля, RVO.

До сих пор агент только сообщал о детектах. С этого занятия он реагирует:
по детекту строит **план** — список действий: завершить процесс, перенести
файл в карантин, удалить файл — и исполняет его через `os.h`. На
`phishing_macro` под `--quiet` за строкой детекта появляются строки действий:

```
[DETECT] high  script_host_from_temp  ts=1730000003000 pid=1101 chain=880>1042(cmd.exe)>1101(wscript.exe)
[ACT] kill pid=1101 start=1730000003000 OS_OK
[ACT] quarantine C:\Users\max\AppData\Local\Temp\a.js -> C:\quarantine\1101-a.js OS_OK
```

несколько раз; с [move-семантикой](../lectures/glossary.md#move-semantics)
(move semantics) из лекции 11 на `phishing_macro` из 175 копий останется 5.
То же самое на отдельной программе измеряет

### 2. Счётчик копий

Счётчик — структура `CopyStats` из
[`copy_stats.h`](../project/kit/include/l3.3/copy_stats.h): одна на программу,
`copy_stats()` отдаёт её по ссылке. Счётчик выдан готовым, запись
`WindowEntry` — заготовкой:

```bash
cp tasks/3.3/handout/copy_stats.cpp src/
cp tasks/3.3/skeleton/window_entry.h src/
```

Счётчик нужно увеличивать в трёх файлах:

| Где | Какое поле счётчика |
|---|---|
| `WindowEntry` в `src/window_entry.h`: копирующие конструктор и присваивание | `window_copied` — на единицу |
| там же: перемещающие конструктор и присваивание | `window_moved` — на единицу |
| `Event(const EventParts&)` в `src/event.cpp` | `event_strings_copied` — на число строк события, `3 + 2 * parts.fields.size()` |
| `Event(EventParts&&)` там же | `event_strings_moved` — на то же число, посчитанное до `std::move(parts.fields)` |
| `MakeDetection` в `src/rule_engine.cpp`: копия события в детекте | `evidence_copied` — на единицу |

Четыре функции `WindowEntry` в заготовке объявлены, это
[специальные функции-члены](../lectures/glossary.md#special-member-functions)
(special member functions). Например, копирующий конструктор:

```cpp
WindowEntry(const WindowEntry& other)
    : ts(other.ts), type(other.type), pid(other.pid) {
    ++copy_stats().window_copied;
}
```

[Move-конструктор](../lectures/glossary.md#move-constructor) (move
constructor) и move-присваивание забирают строки через `std::move`.
Все четыре функции пишутся прямо в классе, на месте объявлений; оба
присваивания возвращают `*this`.

Чтобы проект собрался, а счётчик было видно, нужно ещё:

1. **Удалить свою `WindowEntry` из `agent.h`** и подключить там
   `"window_entry.h"`. Два разных `WindowEntry` в программе — нарушение
   [ODR](../lectures/glossary.md#odr) (One Definition Rule), о котором
   компилятор может не сказать.
2. **Заполнять запись в `HandleEvent` по полям.** Запись списком,
   `WindowEntry{…}`, с объявленными конструкторами не собирается:

   ```cpp
   WindowEntry entry;
   entry.ts = event.ts();
   entry.type = event.type();
   entry.pid = event.pid();
   window_.PushBack(entry);
   ```
3. **Положить копию события в детект.** У `Detection` появилось поле
   `evidence` — события, на которых правило сработало. В `MakeDetection`:

   ```cpp
   detection.evidence.push_back(std::make_unique<Event>(event));
   ++copy_stats().evidence_copied;
   ```

   На [шаге 4](#4-план-по-детекту) из этих событий берётся путь файла,
   который нужно удалить.
4. **Добавить флаг `--copies`.** С ним `main` после `agent.PrintSummary()`
   печатает поля счётчика, и под `--quiet` тоже:

   ```
   [COPY] строк события скопировано 150, перемещено 0
   [COPY] записей WindowEntry скопировано 20, перемещено 0
   [COPY] событий скопировано в детекты 5
   [COPY] копий всего 175
   ```

   Последнее число — `copy_stats().total()`. Последнюю строку выданный тест
   сверяет дословно, формулировка остальных ваша.

**Проверка.** Набор 3.3 пока не собирается, он соберётся на шаге 3. Соберите
только агента, как на шаге 1. Копии считайте на журнале, который агент читает
из файла сам: там событие строится из переменной, и строки копируются.
`nano-edr --quiet --copies --file scenarios/phishing_macro.log` печатает пять
строк `[DETECT]` и четыре строки `[COPY]`: 150, 20, 5 и 175.
Сохраните эти четыре строки: они сдаются с упражнением.

### 3. Перемещение вместо копии

Запись `WindowEntry` и строки события в `FileSource` копируются, хотя
оригинал после этого не нужен. Копию нужно заменить перемещением:

1. **Перегрузка `PushBack(T&& value)`** в `src/ring_buffer.h`, рядом
   с `PushBack(const T&)`. Тело то же, но присваивание —
   `= std::move(value);`. Без `std::move` выбралось бы копирующее
   присваивание: `value` — переменная с именем, то есть
   [lvalue](../lectures/glossary.md#lvalue).
2. **`HandleEvent`:** запись кладётся в окно так:
   `window_.PushBack(std::move(entry));`
3. **`FileSource`:** событие строится из `std::move(parts)`. `parts` там —
   тоже переменная с именем. Там, где событие строится из `os_event`,
   менять нечего: аргумент и так временный объект.
4. **Фабрика `MakeRule`** в `src/make_rule.h` передаёт аргументы конструктору
   правила через `std::move`:
   `std::make_unique<Rule>(id, severity, std::move(args)...)`
   ([почему не `std::forward`](#почему-фабрика-перемещает-а-не-передаёт-идеально)).

Чтобы собрался набор 3.3, скопируйте два файла: заготовку `response.cpp`
с планировщиком `ResponsePlanner` и исполнителем `Responder` и готовый
`response_plan.cpp` с планом `ResponsePlan`:

```bash
cp tasks/3.3/skeleton/response.cpp src/
cp tasks/3.3/handout/response_plan.cpp src/
```

В заготовке `response.cpp` готовы конструкторы, остальные методы пока ничего
не делают. Методы `ResponsePlanner` нужно реализовать на шаге 4,
`Responder::Execute` — на шагах 5 и 6.

### 4. План по детекту

План — `ResponsePlan` из [`response.h`](../project/kit/include/l3.3/response.h):
список действий `Action`. У действия есть вид `kind` и поля:

| `kind` | Что значит | Поля |
|---|---|---|
| `kKillProcess` | завершить процесс | `pid`; `expected_start` — время старта процесса |
| `kQuarantineFile` | изолировать файл: перенести его в каталог карантина | `path`; `to` — куда перенести |
| `kDeleteFile` | удалить файл | `path` |

Ещё у каждого действия есть `reason` — почему оно в плане.

Что делать по детекту, говорит правило. Оно называет действия именами:
строки вроде `kill_process`, добавленные через `AddAction`, приходят
в `detection.actions`. Планировщик по каждому имени добавляет в план одно или
несколько действий `Action`
([почему план строится отдельно](#почему-план-отдельно-от-исполнения)).

Весь шаг — два метода `ResponsePlanner` в `src/response.cpp`:

1. **`QuarantinePath(path, pid)`** возвращает путь файла в карантине:
   `<каталог карантина>\<pid>-<имя файла>`.

   - каталог карантина — поле `quarantine_dir_`;
   - имя файла — всё после последнего `\` в `path`;
   - для `C:\Temp\a.js` и процесса 1101 это `C:\quarantine\1101-a.js`;
   - если `quarantine_dir_` пуст, верните пустую строку.
2. **`Plan(detection)`** обходит имена из `detection.actions` по порядку:

   ```cpp
   ResponsePlan ResponsePlanner::Plan(const Detection& detection) const {
       ResponsePlan plan;
       // процесс детекта и все его потомки; процесс детекта стоит первым
       const std::vector<std::string> tree =
           model_->GetProcessTree(detection.pid);
       for (const std::string& name : detection.actions) {
           if (name == "kill_process") {
               // пункт 3
           } else if (name == "quarantine_source") {
               // пункт 4; три остальных имени — такими же ветками else if
           }
           // незнакомое имя пропускается
       }
       return plan;
   }
   ```

   План возвращается как `return plan;`, без `std::move`
   ([почему](#почему-return-plan-а-не-return-stdmoveplan)).
3. **Имя `kill_process`** добавляет в план завершение каждого процесса
   из `tree`.
   Идти нужно с конца: потомки завершаются раньше родителя.

   ```cpp
   for (std::size_t i = tree.size(); i > 0; --i) {
       const std::string& pid = tree[i - 1];
       Action action;
       action.kind = ActionKind::kKillProcess;
       action.pid = pid;
       // запись есть у каждого процесса из tree;
       // start — ноль, если запуска процесса модель не видела
       action.expected_start = model_->FindProcess(pid)->start;
       action.reason = detection.rule;
       if (pid != detection.pid) {
           action.reason += ", потомок " + detection.pid;
       }
       plan.Add(std::move(action));
   }
   ```
4. **Остальные четыре имени** добавляют в план действия с файлами.
   `reason` у каждого — `detection.rule` и текст из последнего столбца:

   | Имя в `detection.actions` | Какой файл | Откуда взять путь | `kind` | Дописать в `reason` |
   |---|---|---|---|---|
   | `quarantine_source` | из которого запущен процесс детекта | `model_->FindSpawnSource(detection.pid)`, поле `path` | `kQuarantineFile` | `, источник запуска` |
   | `quarantine_image` | образ процесса детекта | `model_->FindProcess(detection.pid)`, поле `image` | `kQuarantineFile` | `, образ процесса` |
   | `delete_dropped` | все, которые создал каждый процесс из `tree` | для каждого `pid` из `tree` — `model_->GetFilesCreatedBy(pid, true)` ([почему `true`](#почему-удаляются-только-созданные-файлы)) | `kDeleteFile` | `, принесён 1156`, где 1156 — создавший процесс |
   | `delete_evidence` | из каждого события в `detection.evidence` | `FindField(*event, "to")` у события `file_move`, `FindField(*event, "path")` у остальных | `kDeleteFile` | `, файл из детекта` |

   У действия `kQuarantineFile` поле `to` — `QuarantinePath(path, detection.pid)`.
   Например, `quarantine_source` для правила `script_host_from_temp`:

   ```cpp
   const FileRecord* source = model_->FindSpawnSource(detection.pid);
   if (source != nullptr) {
       // сюда же — проверки из пункта 5
       Action action;
       action.kind = ActionKind::kQuarantineFile;
       action.path = source->path;
       action.to = QuarantinePath(source->path, detection.pid);
       action.reason = detection.rule + ", источник запуска";
       plan.Add(std::move(action));
   }
   ```
5. **Три случая, когда действие с файлом в план не добавляется:**

   - модель или `FindField` вернули `nullptr`: источника запуска, записи
     о процессе или поля с путём нет;
   - файл системный: путь начинается с `C:\Windows\` или `C:\Program Files`,
     без учёта регистра. Такую проверку напишите сами;
   - у изоляции пустой `to`: каталог карантина не задан.

   Повторы проверять не нужно: `plan.Add` из готового `response_plan.cpp`
   не добавляет действие, цель которого (`pid` или `path`) в плане уже есть.

**Проверка.** Набор 3.3 зелёный целиком:

```bash

```

### 5. Агент печатает план

Сначала агент будет строить план на каждый детект и печатать его строками
`[PLAN]`, исполнять — на [шаге 6](#6-агент-исполняет-план). Для этого:

1. **`Responder::Execute`** в `src/response.cpp` обходит действия плана
   по порядку, пропускает повторы и печатает план. Вставьте его как есть
   и подключите `<print>`:

   ```cpp
   void Responder::Execute(const ResponsePlan& plan) {
       for (const Action& action : plan.actions()) {
           ++stats_.planned;

           // цель, по которой уже отработали: на одном процессе срабатывает
           // несколько правил
           bool repeat = false;
           for (const std::string& target : done_) {
               if (target == action.target()) {
                   repeat = true;
                   break;
               }
           }
           if (repeat) {
               ++stats_.skipped_repeat;
               continue;
           }
           done_.push_back(action.target());

           if (dry_run_ || os_ == nullptr) {
               std::print("[PLAN] {}\n", ToString(action));
               continue;
           }
           // на шаге 6 здесь действие исполняется
       }
   }
   ```

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Почему у трёх типов три ответа на правило пяти

| Тип | Сколько из пяти функций написано | Кем |
|---|---|---|
| `Event` | ни одной | компилятором: все поля копируются и перемещаются сами |
| `Detection` | ни одной, но все пять объявлены | комплектом: копирование `= delete`, остальное `= default` |
| `WindowEntry` | четыре, деструктор `= default` | вами |

`Event` — [правило нуля](../lectures/glossary.md#rule-of-three) (rule
of zero): пять функций компилятор сгенерирует сам и не забудет поле,
добавленное позже. У `Detection` копирование запрещено: копия детекта значила
бы второе сообщение на сервер о том же срабатывании. У `WindowEntry` функции
написаны руками только затем, чтобы посчитать копии.

### Почему конструктор события сначала проверяет

Если сначала забрать строки, а потом бросить исключение на неверном `ts`,
у вызывающего останутся пустые `parts`. С проверкой до перемещения
конструктор либо строит событие, либо ничего не меняет — это строгая гарантия
[exception safety](../lectures/glossary.md#exception-safety) (безопасность
исключений).

### Почему фабрика перемещает, а не передаёт идеально

Фабрика получает аргументы по значению, и после создания правила они ей
не нужны: `std::move(args)...` отдаёт их правилу без копии. `Args&&...`
и `std::forward` из
[лекции 11](../lectures/11/lecture.md#8-stdforward--отдать-дальше-тем-же-чем-получили)
убрали бы и копию при вызове фабрики, но в агенте все её аргументы
временные, и разницы нет.

### Почему план отдельно от исполнения

Если план — объект, `--dry-run` — одна проверка в `Execute`. Без плана
`if (!dry_run)` стоял бы перед каждым вызовом `os.h`, и достаточно забыть
один. Кроме того, планировщик не вызывает `os.h`, и тесты проверяют его без
симулятора.

### Почему реагирование подписано на движок

`EnableResponse` подписывает лямбду на движок, а не через `Agent::Subscribe`:
реагировать нужно и на детекты, которые подавил `DedupSink`.

### Почему `return plan`, а не `return std::move(plan)`

`plan` — локальная переменная, и компилятор строит её сразу в месте вызова:
[copy elision](../lectures/glossary.md#copy-elision), RVO. `std::move`
в `return` это отменяет, и компилятор выдаёт предупреждение
`-Wpessimizing-move`.

### Почему у действий пять имён, а не одно

Прежнее `quarantine_file` значило разное. У скриптового хоста образ
системный, и изолировать нужно скрипт, из которого он запущен, —
`quarantine_source`. У шифровальщика вредоносен сам образ —
`quarantine_image`. `kill_process` стоит первым: живой процесс держит свои
файлы открытыми, и удаление вернуло бы `OS_BUSY`.

### Почему удаляются только созданные файлы

Шифровальщик переименовывает документы: `quarterly.xlsx` становится
`quarterly.xlsx.locked`. Путь новый, и создателем модель записывает
шифровальщика. Удалить всё, что записано за процессом, значило бы удалить
документы пользователя, поэтому `delete_dropped` вызывает
`GetFilesCreatedBy(pid, true)`.

### Почему завершение требует времени старта

Номер завершённого процесса система отдаёт следующему. `os_process_kill`
с временем старта вернёт `OS_PID_REUSED`, если номер уже у другого процесса,
а с нулём завершит того, у кого номер сейчас. На `pid_reuse` номер 1042
сначала у скриптового хоста, потом у блокнота пользователя.

Потомки завершаются раньше родителя, потому что живой родитель может
запустить нового потомка.

### Почему своё событие всё равно идёт в модель

Процесс на самом деле завершён, файл на самом деле перенесён, и модель должна
об этом знать: иначе она считала бы процесс живым, а файл — лежащим
на старом месте.
