# Занятие 4.3. Асинхронный источник

> [Лекция 15](../lectures/15/lecture.md): умные указатели, `weak_ptr`,
> `std::jthread`, `mutex`, `condition_variable`, `stop_token`. Плюс
> `std::string_view` — [лекция 14](../lectures/14/lecture.md).

Одна строка в конфигурации сценария:

```ini
delivery = thread
```

Колбэки начинают приходить из другого потока. Агент, который двенадцать
занятий работал правильно, ломается — и починить его надо так, чтобы результат
на всех сценариях совпал с однопоточным.

Это последнее занятие практикума и единственное, где задание формулируется
одним изменением в чужом файле.

## Конфигурация

```bash
cmake --preset windows -D NANO_EDR_LESSON=4.3
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Что делают эти команды и откуда их
запускать — в [`project/README.md`](../project/README.md).

**Действуют восемь наборов тестов: 2.1, 2.3, 3.1, 3.2, 3.3, 4.1, 4.2 и 4.3.**
Целиком не снялся ни один; три файла из двух наборов выпали на прошлых
занятиях, и все три выпадения были частью их содержания:

| файл | из набора | с занятия | почему |
|---|---|---|---|
| `list_tests.cpp` | 2.1 | 4.1 | односвязного списка больше нет |
| `function_tests.cpp` | 3.2 | 4.1 | своего `Function` больше нет |
| `os_handle_tests.cpp` | 2.1 | 4.2 | конструктор обёртки стал приватным |

Ключей для этого передавать не надо: их выводит номер занятия.

**Здесь появляются две дополнительные сборки, и обе в своих каталогах.**
Санитайзеры несовместимы между собой — оба перехватывают одни и те же вызовы
среды выполнения, — поэтому это два прогона, а не один.

```bash
cmake --preset asan          # висящий взгляд после перехода на string_view
cmake --build --preset asan
ctest --preset asan

cmake --preset tsan          # гонки: два потока трогают одно и то же
cmake --build --preset tsan
ctest --preset tsan
```

**ThreadSanitizer работает только на Linux**, и это не упущение пресета:
среды выполнения для него под Windows нет ни у MSVC, ни у clang. Если у вас
Windows — прогон делается в WSL, и там есть своя грабля, про которую написано
в [`project/README.md`](../project/README.md): `FATAL: ThreadSanitizer:
unexpected memory mapping` лечится запуском через `setarch $(uname -m) -R`.

## Что именно ломается

Прежде чем чинить, стоит понять. Симулятор в этом режиме работает так: поток
доставки качает события свободно, не останавливается на время тика агента
и уходит вперёд дедлайна, опубликованного последним `os_wait`, — на
`thread_lookahead` событий, по умолчанию 64. Значит колбэк и тик
**действительно пересекаются**, а порядок и состав событий при этом остаются
детерминированными.

Опережение здесь не мелочь, а половина задания: всё, что вы отложите
«на потом», разберётся уже после того, как мир изменился.

Найдите, что у вас разъезжается, до того как читать дальше. Кандидаты:
счётчики, модель сущностей, состояние правил, окно, счётчик копий, `done_`
и `touched_` у реагирования.

## Куда это писать

| | |
|---|---|
| `src/sources.h` + `.cpp` | трамплин, замок, буферы разбора до цикла |
| `src/agent.h` + `.cpp` | что именно защищено замком |
| `src/parse.cpp` | разбор отдаёт `string_view`; владеющие формы — переходники |
| `src/event.cpp` | третий конструктор — из невладеющих частей |
| `src/entity_model.cpp` | записи под `shared_ptr`, родитель — `weak_ptr` |
| `src/copy_stats.cpp` | счётчики становятся атомарными |
| `src/detection.cpp` | копия детекта без улик |
| `src/reporter.cpp` | новый файл: поток отправки детектов наверх |
| `src/main.cpp` | порядок остановки: поток раньше сброса канала |

Появление нового `.cpp` — изменение описания проекта, поэтому после него нужна
**пере**конфигурация.

**Очередь событий, которую вы напишете первым пунктом, в конце удаляется.**
Это не переделка задания и не потерянный вечер: провал этой очереди —
содержание занятия, и без него всё остальное выглядит произволом.

## Проект

Первые четыре пункта идут строго по порядку. Пятый без провала четвёртого
читается как «так сказали».

1. **Напишите очередь между колбэком и обработкой.** Колбэк кладёт
   и возвращается, обработка забирает между вызовами `os_wait`, агент остаётся
   однопоточным. Классический producer-consumer, ровно лекция 15. Она пишется
   за половину пары, она собирается, и в режиме `inline` ничего не меняет.
2. **Прогоните в режиме `thread` и посмотрите, что разошлось.** Выданные тесты
   прогоняют каждый сценарий дважды, в двух режимах, и сравнивают результат
   с самим собой. Если у вас очередь, разойдутся строки `[ACT]`:

   ```
   [ACT]    kill pid=3315 ... OS_NO_SUCH_PROCESS
   [ACT]    quarantine ...   OS_NO_SUCH_FILE
   [ACT]    kill pid=1042 ... OS_PID_REUSED
   ```

   Это не гонка. Это опоздание: пока сложенное в очередь ждёт разбора,
   модельное время идёт, и процесс успевает завершиться сам, файл — переехать,
   номер — достаться другому процессу. **Правило отсюда:** реагирование —
   часть обработки события, а не фоновая работа. Отложить его на потом значит
   отложить до «поздно».
3. **Объясните, почему очередь нельзя починить рабочим потоком.** Очевидная
   починка — разбирать очередь не между вызовами `os_wait`, а в своём потоке.
   Прочитайте в `os.h` раздел про режимы доставки и скажите, что здесь
   не так. Подсказка: обещание про одновременность дано только про код
   **между** вызовами `os_wait`, а в режиме `inline` колбэк исполняется внутри
   самого `os_wait`. Отсюда правило на оба режима: **все вызовы `os.h` —
   с одного потока.**
4. **Уберите очередь: обработка остаётся на колбэке.** Контракт границы это
   прямо разрешает («ДЕЙСТВИЯ ИЗ КОЛБЭКА: разрешены»), а обратное давление
   получается само — поток доставки не двинется дальше, пока колбэк
   не вернулся.
5. **Перечислите разделяемое состояние поимённо и решите, сколько нужно
   замков.** Разделяемым остаётся состояние агента: его трогают колбэк и тик
   с главного потока. Список может выйти и коротким, и длинным — важно, чтобы
   вы могли объяснить каждую его строку и каждый замок, который завели.
6. **Прогон под ThreadSanitizer.** Уборка на тике из занятия 4.1 ходит
   по модели, которую в этот момент правит другой поток. Это самое вероятное
   место падения, и находит его санитайзер за один прогон.
7. **Счётчики копий становятся атомарными.** С занятия 3.3 счётчик —
   обычное число, и там это было правильно: писать `std::atomic` за четыре
   занятия до лекции про потоки значит чинить то, чего нет. Теперь его
   увеличивают из двух потоков. Объясните, какой порядок памяти здесь нужен
   и почему не тот, что по умолчанию.
8. **Разбор события переходит на `string_view`.** `substr` у `string_view`
   возвращает `string_view`, и весь переход сводится к смене типа
   переменной — самая наглядная иллюстрация того, чем `string_view` является.
   Владеющие формы остаются переходниками: против них стоят выданные тесты
   1.2 и 2.1, а зовут их из разбора конфигурации, где строк десяток
   на прогон.
9. **Две переменные в цикле файлового источника объявляются до цикла**, и обе
   намеренно: строка — чтобы `getline` переиспользовал буфер, части
   события — чтобы вектор внутри сохранял вместимость. Объявите их внутри
   цикла, и весь выигрыш пропадёт. Это тот редкий случай, когда «где
   объявлена переменная» перестаёт быть вопросом стиля.
10. **Третий конструктор события** — из невладеющих частей. Событие обязано
    пережить свой буфер: буфер — одна строка журнала, а событие живёт дольше.
11. **`weak_ptr` на родителя** в модели процессов. Владение вниз, наблюдение
    вверх: словарь владеет записями, ребёнок на родителя только смотрит.
    Сильная ссылка отменила бы вытеснение, а если завести ещё и список
    детей — замкнула бы цикл.

    Ловушка здесь своя: родитель разрешается на вопрос, а не на событие
    (см. `entity_model.h` с занятия 4.1). Запоминать можно только ответ,
    в котором у родителя известно время старта, — иначе заглушка зафиксирует
    неправду навсегда.
12. **Поток для отправки детектов наверх.** `std::jthread`, `stop_token`,
    `condition_variable_any`. Здесь второй поток уместен: `edr_send`
    в настоящем агенте идёт по сети, а ждать сеть на горячем пути нельзя.
    Задержка доклада безвредна — этим выход и отличается от входа.

    Отдельно подумайте, надо ли ограничивать эту очередь, и сравните ответ
    с тем, который вы дали про очередь событий.
13. **Прогон всех сценариев в двух режимах**, плюс отдельные прогоны под ASan
    и под TSan.
14. **Замерьте пропускную способность в двух режимах** на нагрузочном
    сценарии и объясните результат. Конфигурация `stress.cfg` переключается
    в `thread` той же одной строкой, которой формулируется всё занятие;
    журнал генерируется `gen_stress`, как на занятии 4.1.

    Скорее всего многопоточная версия окажется **медленнее**. Если так —
    объясните, на чём, и предложите, что с этим делать. Если быстрее — тем
    интереснее, объясните тоже. Заодно посмотрите на память: если она
    не изменилась ни на килобайт, у этого есть причина, и её надо назвать.

## Готово, когда

- Результат на всех семи сценариях в режиме `thread` совпадает с режимом
  `inline`. Проверяется выданными тестами `modes.*`, и прогонов там пять
  на сценарий: гонка — свойство прогона, а не программы.
- Под ThreadSanitizer чисто. Отдельная сборка, и только на Linux или в WSL.
- Под ASan чисто. Это главная проверка после перехода на `string_view`:
  висящий взгляд не даёт ни предупреждения, ни падения на счастливом пути.
- Парсер не аллоцирует на разбор события: части события заводятся один раз
  на цикл, а не на строку.
- Агент завершается сам, без `kill`, и без «висит на выходе иногда».
- Замков в агенте столько, сколько вы можете объяснить. «На всякий случай»
  не считается объяснением.
- Оба числа замера получены прогоном, и результат объяснён словами.

Про первый пункт: побайтовая воспроизводимость отчёта симулятор гарантирует
только для `instant` + `inline`. Здесь сравнивается вывод агента в двух
режимах на одном сценарии, и он обязан совпасть целиком — потому что
и порядок событий, и состав их симулятор сохраняет.

## Тесты

Две части, и они разного рода. Три файла на doctest — разбор без владения,
поток отправки, общее владение и атомарный счётчик. Плюс `run_modes.cmake`:
семь прогонов одного сценария в двух режимах. Это критерий занятия дословно,
и эталон для него не нужен — сравнивается ваш агент с вашим же агентом.

### Запуск тестов

Команды — те же, что в «Конфигурации». Правки в вашем `CMakeLists.txt`
не нужны: тесты линкуются с библиотекой `nano_edr_core`, а она собирается
сама из всех `.cpp` в `src/`, кроме `main.cpp`.

Сравнение режимов запускает исполняемый файл `nano-edr`; если ваш называется
иначе, передайте имя до подключения набора: `set(NANO_EDR_AGENT my_agent)`.
Без цели сравнение режимов не собирается вовсе, и сборка об этом скажет прямо:
пропустить главную проверку занятия молча нельзя.

### Что именно проверяется

**Сравнение режимов, и почему прогонов пять.** Конфигурация режима `thread`
делается из открытого сценария заменой одной строки. Дальше агент прогоняется
на обеих, и вывод обязан совпасть. Прогонов пять, и это не перестраховка:
гонка — свойство прогона, а не программы, сломанный агент совпадает в девяти
случаях из десяти, и ровно поэтому такие дефекты живут в продукте годами.
Один зелёный прогон не значит ничего.

**Если разошлись строки `[ACT]` с кодами `OS_NO_SUCH_PROCESS`,
`OS_NO_SUCH_FILE` или `OS_PID_REUSED`** — дело не в гонке, а в задержке.
Между тем моментом, когда событие пришло, и тем, когда вы на него ответили,
мир успел измениться. Смотрите, где у вас событие ждёт своей очереди.

**Если разошлось что-то другое** — скорее всего это гонка, и искать её надо
не глазами, а ThreadSanitizer: он находит её на первом прогоне и с обоими
стеками сразу.

**Разбор без владения.** Проверяется два разных утверждения, и путать их
не надо.

*Что разбирает то же самое.* Смотрящая и владеющая формы сравниваются
на одной строке поле за полем. Если у вас окажутся два разных алгоритма
разбора одного формата, они разойдутся — не сразу, а на первой правке
формата, и разойдутся молча. Владеющая форма обязана быть переходником.

*Что действительно не копирует.* Проверяется сравнением адресов: `view`
на подстроку обязан указывать внутрь исходного буфера. Это единственный
способ проверить отсутствие аллокации, не заглядывая в аллокатор.

Тест `переиспользование не оставляет следов прошлой строки` — про то, как
эту функцию положено звать: один набор частей на весь цикл. Тест `событие
из view владеет своими строками` затирает исходный буфер после
конструирования события — событие обязано это пережить.

**Поток отправки.**

| тест | что сломалось бы без него |
|---|---|
| `всё положенное уходит получателю` | часть детектов теряется под нагрузкой |
| `порядок сохраняется` | по докладу нельзя восстановить ход атаки |
| `последний детект не теряется на остановке` | остановка бросает остаток очереди |
| `Stop дожидается потока` | `flush` уходит раньше последней отправки |
| `деструктор останавливает поток сам` | программа виснет на выходе |

Третий и четвёртый стоит прочитать вместе. «Поток, которому сказали
остановиться» и «поток, который остановился» — разные состояния, и между
ними теряется ровно то, что положили последним. С `std::thread` это ловушка,
в которую попадают все; `std::jthread` существует затем, чтобы в неё нельзя
было попасть.

**Атомарный счётчик.** `счётчик копий не теряет инкрементов при работе
из двух потоков` — тот случай, где неатомарный `++` виден невооружённым
глазом: четыре потока по десять тысяч инкрементов дают не сорок тысяч,
а сколько получится. Второй тест проверяет, что счётчик по-прежнему
сравнивается с числом: выданные тесты занятия 3.3 написаны как
`CHECK(... == 0)` и обязаны собираться. Они про move-семантику, а она
на 4.3 никуда не делась.

**Слабая ссылка на родителя.** Четыре теста, и три из них — про то, чего
делать нельзя.

| тест | что он запрещает |
|---|---|
| `родитель, узнанный позже ребёнка, всё равно находится` | запоминать родителя на событии старта |
| `заглушка с нулевым стартом не запоминается` | кэшировать неполный ответ |
| `вытесненный родитель обрывает цепочку` | держать родителя сильной ссылкой |

Последний — главный. Сильная ссылка выглядит безобиднее слабой и ломает две
вещи сразу: вытеснение перестаёт освобождать память (запись выброшена
из словаря, а жива, потому что на неё смотрит ребёнок), а если кто-то заведёт
ещё и список детей — счётчики ссылок замкнутся в цикл и не дойдут до нуля
никогда. Ни то, ни другое не диагностируется ничем, кроме внимательного
чтения.

**Копия детекта без улик.** `WithoutEvidence копирует сообщение и оставляет
улики`. Детект не копируется целиком — так решено на занятии 3.2, и решено
правильно. Но положить его в очередь потока отчёта надо, а очередь владеет
тем, что в ней лежит. Выход не в том, чтобы разрешить копирование, а в том,
чтобы посмотреть, что именно уезжает наверх. Улики не уезжают: они нужны
реагированию здесь, на хосте.

### На что обратить внимание

**Счётчик копий с занятия 3.3 не атомарный.** Это известная гонка,
оставленная намеренно: до 4.3 её не было. Теперь есть, и она ваша.

**`mutex` вокруг всего — не решение, а отчёт о том, что вы не разобрались,
что именно разделяется.** Начните с того, чтобы перечислить разделяемое
состояние поимённо. Отдельно проверьте себя: если у вас получилось четыре
замка, спросите, бывает ли состояние, согласованное по одному из них
и несогласованное по другому. Модель сущностей, правила и окно меняются
одним и тем же событием.

**Тик и колбэк пересекаются по-настоящему.** Уборка на тике из занятия 4.1
ходит по модели, которую в этот момент правит другой поток. Это самое
вероятное место падения под TSan, и находит его санитайзер за один прогон —
а чтение кода не находит неделями.

**Действия реагирования уходят на границу `os.h`, и она к этому не всюду
готова.** Перечитайте в `os.h` раздел про режимы доставки и решите, с какого
потока у вас зовётся `os_process_kill`. Ответ «с любого» неверен, и почему —
написано там же.

**`string_view` не владеет, и здесь у этого своя цена.** Самая частая
ошибка — сохранить взгляд дольше, чем жив буфер. В режиме `thread` буфер
с полями события принадлежит потоку доставки и действителен только на время
колбэка: взгляд, переживший возврат, — это обращение к памяти чужого потока,
который в это время её переиспользует. Компилятор промолчит, ASan — нет.

**Выигрыш есть в файловом источнике и нет в трамплине границы.** В трамплине
заменять нечего: строки приходят из C, части собираются, событие их
**перемещает**. Перевод на взгляды сменил бы одиннадцать перемещений
на одиннадцать копий, то есть проиграл. Правило: `string_view` выигрывает
там, где буфер уже есть и владеть заново незачем; `move` выигрывает там, где
владение уже собрано и его можно передать. Вопрос «что быстрее» поставлен
неверно — они отвечают на разные вопросы.

**Счётчик копий покажет обратное, и это не регресс.** На файловом пути он
начнёт показывать копии там, где показывал перемещения. Счётчик считает
последний шаг: до 4.3 разбор заводил по строке на каждый ключ и каждое
значение, и уже потом событие их забирало — шесть с лишним конструирований
на поле, из которых счётчик видел ноль. После перехода разбор не заводит
ни одной, а событие копирует ровно по одной на строку. Расход упал, а число
на экране выросло. Не «счётчик врёт», а «счётчик отвечает на прежний
вопрос».

### Если не собирается

**`'reporter.h' file not found`** — заготовки взяты из среза `l4.2`. Нужен
`l4.3`.

**`no member named 'parent' in 'nano_edr::ProcessRecord'`** — то же самое.

**`no viable conversion from 'std::vector<Field>' to 'std::vector<FieldView>'`** —
перегрузка выбирается по типу выходного параметра, а не входного. У вас,
скорее всего, осталась одна форма разбора вместо двух.

**`undefined reference to 'pthread_create'`** — не подключены потоки.
`find_package(Threads REQUIRED)` и `Threads::Threads` к вашей библиотеке;
`-pthread` руками писать не надо, на разных системах флаг называется
по-разному.

**`'jthread' is not a member of 'std'`** — компилятор старше, чем требует
курс, либо стандарт выставлен ниже C++20.

**`ThreadSanitizer под Windows не существует`** в отказе конфигурации — так
и есть, пресет `tsan` работает на Linux и в WSL. Это не лечится флагами.

**`NANO_EDR_TSAN и NANO_EDR_SANITIZE вместе не работают`** — санитайзеры
несовместимы, нужны два каталога сборки. Пресеты `asan` и `tsan` их и делают.

**`task4_3: цель 'nano-edr' не найдена`** — ваш исполняемый файл называется
иначе. Передайте имя: `set(NANO_EDR_AGENT my_agent)`.
