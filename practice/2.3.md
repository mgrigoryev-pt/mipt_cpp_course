# Занятие 2.3. Таблица виртуальных вызовов и движок правил

> [Лекция 7](../lectures/07/lecture.md): виртуальные функции, абстрактные
> классы, виртуальный деструктор, `enum class`.

До сих пор условие, правило и источник событий были конкретными типами.
`Condition` выбирал сравнение через `switch`, агент хранил
`std::vector<MatchRule>`, а `main` выбирал между двумя источниками веткой
`if`, где каждый источник назван своим типом. На этом занятии все три места
уходят за интерфейсы — классы, в которых объявлены только
[чисто виртуальные функции](../lectures/glossary.md#pure-virtual) (pure
virtual functions). Код, который пользуется интерфейсом, не знает, с каким
наследником работает.

Это даёт две вещи, которых раньше не было: условие, составленное из других
условий, и правило с состоянием, которое ловит атаку из двух событий. На
[`phishing_macro`](../project/scenarios/phishing_macro.log) агент под
`--quiet` печатает на одну строку больше, чем в 2.2:

```
[DETECT] high  script_host_from_temp  ts=1730000003000 pid=1101
[DETECT] critical  script_host_beacon  ts=1730000004200 pid=1101
[DETECT] medium  hidden_powershell  ts=1730000006000 pid=1156
```

Вторая строка — новое правило: скриптовый хост через 1,2 секунды после
запуска открыл сетевое соединение. Такая же строка добавляется
в [`pid_reuse`](../project/scenarios/pid_reuse.log), на остальных пяти
сценариях вывод не меняется.

Набор тестов 2.2 с этого занятия не подключается: `Condition` и вектора

### 1. Условие за интерфейсом

В [`conditions.h`](../project/kit/include/l2.3/conditions.h) объявлен
интерфейс `ICondition` с одной
[виртуальной функцией](../lectures/glossary.md#virtual-function) (virtual
function) `Matches`:

```cpp
class ICondition {
 public:
    virtual ~ICondition() = default;
    virtual bool Matches(const Event& event) const = 0;
    bool operator()(const Event& event) const { return Matches(event); }
};
```

Каждый вид сравнения — свой наследник, и `Matches` в нём
[переопределяется](../lectures/glossary.md#override) (overriding) со словом
`override` ([лекция 7, раздел 3](../lectures/07/lecture.md#3-override-и-final)).
Чтобы добавить новое сравнение, пишут новый класс, а существующие
не трогают.

Четыре функтора с занятия 2.2 — `FieldEquals`, `FieldContains`,
`FieldEndsWith`, `FieldInList` — уже наследники `ICondition`. В
`src/conditions.cpp` их `operator()` нужно переименовать в `Matches`, тело
не меняется:

```cpp
// было в 2.2
bool FieldEquals::operator()(const Event& event) const { /* ... */ }

// стало
bool FieldEquals::Matches(const Event& event) const { /* ... */ }
```

Звать условие можно и через `Matches`, и как функтор.

Класс `Condition` из `src/conditions.cpp` нужно удалить: в `conditions.h`
его больше нет.

Пятое простое условие новое — `EventTypeIs(types)`, и его `Matches` нужно
написать: `true`, если `event.event_type()` — один из `types`. Это условие
сравнивает перечисления, а не строки. В [`event.h`](../project/kit/include/l2.3/event.h)
появился `EventType` — [scoped enumeration](../lectures/glossary.md#scoped-enum),
перечисление `enum class` ([лекция 7, раздел 8](../lectures/07/lecture.md#8-enum-и-enum-class)),
и метод `Event::event_type()`. Зачем перечисление, если строка уже есть, —
видно на опечатке:

```cpp
event.type() == "proces_start"                 // собирается, но всегда false
event.event_type() == EventType::kProcesStart  // ошибка: такого значения нет
```

Со строкой код собирается, и правило с такой опечаткой молча никогда
не срабатывает. С перечислением ту же опечатку останавливает компилятор.

В `src/event.cpp` нужно написать функцию:

| Функция | Что делает |
|---|---|
| `EventTypeFromString(type)` | `"process_start"` → `kProcessStart`, и так для всех семи типов из [`SPEC.md`](../project/SPEC.md); незнакомая строка → `kOther`, а не исключение |

В конструкторе `Event` нужно вызвать `EventTypeFromString` и положить
результат в поле `event_type_`. Строка типа при этом остаётся в `type()`: по `kOther`
не поймёшь, что пришло, а по строке поймёшь.

### 2. Условие из условий

Два оставшихся класса в `conditions.h` — составные условия. Они хранят
другие условия как `std::unique_ptr<ICondition>` и ничего не знают об их
типах. Их методы нужно написать в `src/conditions.cpp`:

| Метод | Что делает |
|---|---|
| `AllOf::Add(condition)`, `AnyOf::Add(condition)` | добавляет условие в конец |
| `AllOf::Matches(event)` | `true`, если все вложенные условия вернули `true`; пустой `AllOf` — `true` |
| `AnyOf::Matches(event)` | `true`, если хотя бы одно вернуло `true`; пустой `AnyOf` — `false` |

Составные условия вкладываются друг в друга: `AnyOf` может лежать внутри
`AllOf` и наоборот. Как с ними записываются правила, показано
на [шаге 5](#5-набор-правил).

### 3. Правило за интерфейсом

В [`rule.h`](../project/kit/include/l2.3/rule.h) над `RuleBase` появился
интерфейс `IRule`: `id()`, `severity()`, `Check`, `hits()` и `actions()`, все
чисто виртуальные. `IRule` — [абстрактный класс](../lectures/glossary.md#abstract-class)
(abstract class): создать его объект нельзя, можно только указатель или
ссылку на наследника ([лекция 7, раздел 4](../lectures/07/lecture.md#4-абстрактные-классы)).
`RuleBase` реализует общее, `MatchRule` наследует `RuleBase`, как в 2.2.

Меняется и то, как условие попадает в правило. В 2.2 `Condition` был одного
типа и копировался в вектор правила целиком. Теперь условия разных типов —
`FieldEquals`, `AnyOf`, `EventTypeIs`, — и в одном векторе их можно держать
только указателями на `ICondition`. Поэтому условие нужно создавать через
`std::make_unique` и передавать правилу указатель на него:

```cpp
// было в 2.2: условие копируется в правило
rule.AddCondition(Condition::Equals("type", {"process_start"}));

// стало: правило забирает указатель себе
auto is_start = std::make_unique<EventTypeIs>(
    std::vector<EventType>{EventType::kProcessStart});
rule->AddCondition(std::move(is_start));  // is_start теперь пуст
```

После `AddCondition` условие принадлежит правилу — это и называется
[владением](../lectures/glossary.md#ownership) (ownership).

В `src/rule.cpp` нужно переписать два метода `MatchRule`, остальное — как в 2.2:

| Метод | Что делает |
|---|---|
| `AddCondition(condition)` | кладёт условие в конец `conditions_`; `unique_ptr` не копируется, поэтому через `std::move` |
| `Check(event)` | `true`, если все условия вернули `true`, — тогда же зовёт `CountHit()`; у правила без условий всегда `true` |

### 4. Движок правил

Новое — движок, [`rule_engine.h`](../project/kit/include/l2.3/rule_engine.h).
Он владеет правилами и прогоняет через них событие. Его методы нужно написать
в `src/rule_engine.cpp`:

| Метод | Что делает |
|---|---|
| `AddRule(rule)` | добавляет правило в конец `rules_` |
| `ProcessEvent(event, fired)` | зовёт `Check` у каждого правила в порядке добавления и возвращает, сколько сработало. Если `fired` не `nullptr`, **дописывает** в него указатели на сработавшие правила; что там было до вызова, остаётся |

Печати в движке нет: он сообщает, какие правила сработали, а печатает агент.

### 5. Набор правил

В `src/agent_rules.cpp` пять правил с занятия 2.2 нужно переписать на новые
условия. `BuildAgentRules()` должна возвращать не вектор, а движок:

```cpp
RuleEngine BuildAgentRules() {
    RuleEngine engine;
    // engine.AddRule(...) — пять правил
    return engine;
}
```

Копировать движок нельзя, а перемещать можно: для этого в
[`rule_engine.h`](../project/kit/include/l2.3/rule_engine.h) выданы две
строки с `&&`. Что они значат, разбирается на лекции 11, к занятию 3.3.

В 2.2 «`path` заканчивается на `.locked` **или** `to` заканчивается
на `.locked`» в одно правило не помещалось, и `ransom_extension` записывался
двумя объектами. С `AnyOf` из [шага 2](#2-условие-из-условий) это одно
правило:

```cpp
auto rule = std::make_unique<MatchRule>("ransom_extension",
                                        Severity::kCritical);
rule->AddCondition(std::make_unique<EventTypeIs>(std::vector<EventType>{
    EventType::kFileCreate, EventType::kFileWrite, EventType::kFileMove}));

auto paths = std::make_unique<AnyOf>();
paths->Add(std::make_unique<FieldEndsWith>("path", ".locked"));
paths->Add(std::make_unique<FieldEndsWith>("to", ".locked"));
rule->AddCondition(std::move(paths));

rule->AddAction("quarantine_file");
engine.AddRule(std::move(rule));
```

`autostart_write` нужно собрать в одно правило так же, поэтому объектов
теперь тоже пять.

Список значений внутри одного условия — как в
`Condition::Contains("cmdline", {...})` в 2.2 — тоже нужно записать через
`AnyOf`, по условию на каждое значение:

```cpp
auto temp = std::make_unique<AnyOf>();
temp->Add(std::make_unique<FieldContains>("cmdline",
                                          "\\appdata\\local\\temp\\"));
temp->Add(std::make_unique<FieldContains>("cmdline", "%temp%"));
// ... остальные варианты пути с занятия 2.2
```

### 7. Источник за интерфейсом

В [`event_source.h`](../project/kit/include/l2.3/event_source.h) два
интерфейса. `IEventSource` — откуда берутся события, у него один метод
`Run(handler)`. `IEventHandler` — кому они отдаются. Источник знает только
`IEventHandler`, агент не знает, какой источник его вызывает.

Агента нужно сделать наследником `IEventHandler` и реализовать четыре его
метода. В комментариях — кто и когда их зовёт:

```cpp
class Agent : public IEventHandler {
 public:
    // Оба источника: пришло событие. Тело — как на шаге 6.
    void HandleEvent(const Event& event) override;

    // FileSource: пустая строка или комментарий.
    void OnSkipped() override;

    // FileSource: из строки не вышло события.
    // Трамплин: событие от os.h не удалось построить.
    void OnBroken() override;

    // OsSource: Wait вернул OS_TIMEOUT, новых событий пока нет.
    void OnTick() override;
    // ...
};
```

`OnSkipped` и `OnBroken` прибавляют по единице к своим счётчикам, и оба
счётчика нужно печатать в сводке. У `OnTick` пока пустое тело.

`FileSource` и `OsSource` нужно сделать наследниками `IEventSource`, а их
`Run(Agent*)` заменить на `Run(IEventHandler*) override`. Методы
`IEventHandler` в источниках нужно звать так:

- `FileSource::Run` зовёт `OnSkipped` на пустой строке и комментарии
  и `OnBroken`, если из строки не вышло события: разбор не удался или
  конструктор `Event` бросил исключение;
- трамплин зовёт `OnBroken`, если событие не удалось построить;
- `OsSource::Run` зовёт `OnTick` на каждом `OS_TIMEOUT`.

Например, цикл ожидания в `OsSource::Run`:

```cpp
os_status status = handle_.Wait(kWaitMs);
while (status == OS_TIMEOUT) {
    handler->OnTick();
    status = handle_.Wait(kWaitMs);
}
```

**Трамплин нужно перенести из агента в `OsSource`.** Трамплин обслуживает
границу `os.h`, то есть это часть источника. Пока он в агенте, агент знает
про `os.h`, а `OsSource` зовёт `Agent::Trampoline` и знает про агента.

Трамплин нужно сделать статическим методом `OsSource`, а в `Subscribe`
передавать указатель на `IEventHandler`. Значит, трамплин обязан привести
`ctx` к `IEventHandler*`, а не к `Agent*`:

```cpp
handle_.Subscribe(&OsSource::Trampoline, handler);  // handler — IEventHandler*

// в трамплине
IEventHandler* handler = static_cast<IEventHandler*>(ctx);
```

Это то же требование, что на занятии 2.1, а в упражнении 2.2 (часть 3) видно,
почему адрес объекта и адрес его базы бывают разными.

После переноса из `agent.h` нужно убрать `#include "os.h"`, а из файлов
источников — `#include "agent.h"`, и из заголовка, и из `.cpp`.

В `main` две ветви `if` с двумя вызовами `Run` нужно свести к одной: ветвь
только создаёт нужный источник, а `Run` зовётся один раз, через интерфейс:

```cpp
std::unique_ptr<IEventSource> source;
if (options.force_file) {
    source = std::make_unique<FileSource>(options.path);
} else {
    source = std::make_unique<OsSource>(options.path);
}
source->Run(&agent);
```

**Проверка.** Тесты `task2.1.sources.<журнал>` зелёные: они прогоняют агента
через оба источника на семи сценариях и на
[`rules_edges.log`](../project/tasks/2.1/tests/logs/rules_edges.log)
и сравнивают два вывода между собой. Если для этого шага пришлось править
движок или правила, интерфейс проведён не там.

### 8. Правило с состоянием

`SequenceRule` из [`rule.h`](../project/kit/include/l2.3/rule.h) ловит атаку
из двух событий. Пример — новое правило `script_host_beacon`: скриптовый хост
стартовал, и тот же процесс в течение 10 секунд открыл сетевое соединение.

У правила два шага, и каждый шаг — это условие:

- первый шаг — условие `first_`, в примере «старт скриптового хоста»;
- второй шаг — условие `second_`, в примере «сетевое соединение».

Правило срабатывает на событии второго шага, если перед ним было событие
первого шага и между ними прошло не больше `window_ms` миллисекунд. Если
включена связка по процессу (`same_pid_`, по умолчанию включена), у обоих
событий должен совпадать `pid`.

Пока второй шаг не пришёл, правило помнит события первого шага в векторе
`pending_`: на каждое событие — запись с его `ts_ms` и `pid`. Это и есть
состояние правила: от него зависит, сработает ли `Check` на очередном событии.

В `src/rule.cpp` заглушки `SequenceRule` нужно заменить настоящими методами:

| Метод | Что делает |
|---|---|
| `SequenceRule(id, severity, window_ms)` | передаёт `id` и `severity` в `RuleBase`, запоминает `window_ms` |
| `SetFirst(condition)`, `SetSecond(condition)` | запоминают условия первого и второго шага |

`Check(event)` нужно написать по такому алгоритму:

1. Если `first_` или `second_` не задан, вернуть `false`.
2. Удалить из `pending_` устаревшие записи: те, у которых
   `event.ts().ms - ts_ms > window_ms_`. Для них второй шаг опоздал.
3. Если событие подходит под второй шаг, найти в `pending_` запись с тем же
   `pid` (если связка выключена — любую запись). Если запись нашлась, удалить
   её, вызвать `CountHit()` и вернуть `true`.
4. Если событие подходит под первый шаг, добавить в `pending_` запись с его
   `ts_ms` и `pid`.
5. Вернуть `false`.

`true` возвращается только в пункте 3: детект — это найденная пара, и больше
ничего.

Зачем такой порядок:

- **Пункт 2** ограничивает память правила. Без него каждый скриптовый хост,
  который так и не открыл соединение, остаётся в `pending_` навсегда, и вектор
  растёт, пока работает агент.
- **Пункт 3 удаляет запись**, потому что одна пара — один детект. Если запись
  оставить, она даст детект на каждом следующем событии второго шага.
- **Пункт 3 стоит раньше пункта 4**, чтобы событие, которое подходит под оба
  шага, закрыло старую запись, а не добавило новую.

Как меняется `pending_` у `script_host_beacon` (окно 10 000 мс):

| `ts` | Событие | `pending_` после `Check` | Результат `Check` |
|---|---|---|---|
| 1000 | `process_start`, `wscript.exe`, `pid=7` | `{1000, 7}` | `false` |
| 2200 | `net_connect`, `pid=9` | `{1000, 7}` | `false`: записи с `pid=9` нет |
| 3000 | `net_connect`, `pid=7` | пусто | `true`: детект |
| 3500 | `net_connect`, `pid=7` | пусто | `false`: пару уже нашли |
| 4000 | `process_start`, `cscript.exe`, `pid=8` | `{4000, 8}` | `false` |
| 14500 | `file_write`, `pid=3` | пусто | `false`: 14500 − 4000 > 10000, запись устарела |

Шестое правило набора — `script_host_beacon`. Добавьте его в движок последним:

```cpp
auto beacon = std::make_unique<SequenceRule>("script_host_beacon",
                                             Severity::kCritical, 10000);
beacon->SetFirst(/* старт скриптового хоста: process_start,
                    image заканчивается на wscript.exe или cscript.exe */);
beacon->SetSecond(std::make_unique<EventTypeIs>(
    std::vector<EventType>{EventType::kNetConnect}));
beacon->AddAction("kill_process");
engine.AddRule(std::move(beacon));
```

`SetFirst` принимает одно условие, а у первого шага две проверки — тип события
и `image`. Их нужно собрать в `AllOf`.

**Проверка.** Тесты `SequenceRule` зелёные. В `phishing_macro` и `pid_reuse`
по сравнению с эталоном 2.1 добавилось **ровно по одной** строке
`script_host_beacon`. Две и больше — запись после детекта не удаляется.
Строка `script_host_beacon` почти на каждом событии — `Check` возвращает
`true` не только в пункте 3.

На `clean_office` появится ложный детект — его чинит

### 9. Ноль детектов на чистых сценариях

В сценариях [`clean_office`](../project/scenarios/clean_office.log)
и [`clean_build`](../project/scenarios/clean_build.log) атак нет: в первом
пользователь работает с документами, во втором собирается проект. Детект на
таком сценарии — ложный: правило приняло за атаку действия, которые атакой
не являются. Поэтому вывод на обоих сценариях должен быть пустым.

С правилом из шага 8 на `clean_office` будет ложный детект. Убрать его
помогает признак, который отличает атаку: в `phishing_macro` и `pid_reuse`
скриптовый хост запускает скрипт из временного каталога —
`...\AppData\Local\Temp\a.js` и `...\AppData\Local\Temp\b.js`. Этот же
признак проверяет правило `script_host_from_temp`.

Поэтому в первый шаг `script_host_beacon` нужно добавить третье условие:
`cmdline` содержит путь к временному каталогу. Варианты пути — те же, что
в `script_host_from_temp`:

```cpp
auto start = std::make_unique<AllOf>();
start->Add(/* тип события — process_start */);
start->Add(/* image заканчивается на wscript.exe или cscript.exe */);
start->Add(/* cmdline содержит путь к Temp, как в script_host_from_temp */);
beacon->SetFirst(std::move(start));
```

**Проверка.** На `clean_office` и `clean_build` вывод под `--quiet` пустой.
В `phishing_macro` и `pid_reuse` строка `script_host_beacon` осталась.
`lolbin_download`, `persistence` и `ransomware` совпадают с эталонами 2.1.

### 10. Цена невиртуального деструктора

Деструктор `IRule` виртуальный, и этот шаг показывает, что будет без этого.
Комплект менять нельзя, но здесь разрешена **одна временная правка**:
в [`kit/include/l2.3/rule.h`](../project/kit/include/l2.3/rule.h) уберите
слово `virtual` из строки

```cpp
virtual ~IRule() = default;
```

1. **Соберите проект** обычным пресетом. Компилятор может выдать
   предупреждение.
2. **Прогоните тесты под [санитайзером](../lectures/glossary.md#sanitizer)
   (sanitizer):**

   ```bash
   cmake --preset asan-windows -D NANO_EDR_LESSON=2.3
   cmake --build --preset asan-windows
   ctest --preset asan-windows -R "task2.3|sources"
   ```

   На Linux — пресет `asan` и `ctest --preset asan` без `-R`. На Windows
   набор ограничен, потому что под `asan-windows` падает любой пойманный
   `throw`, — подробнее в
   [`project/README.md`, «Перед сдачей»](../project/README.md#перед-сдачей).

   Санитайзер остановит прогон с отчётом `new-delete-type-mismatch`: размер
   выделенного объекта и размер освобождаемого разные. Объясните оба числа:
   что лежит в объекте `MatchRule` и что — в `IRule`.
3. **Верните `virtual`.** Тест «у интерфейса правила виртуальный деструктор»
   снова зелёный, санитайзер молчит.

## Упражнение: диспетчеризация

[`tasks/2.3/exercise/dispatch.cpp`](../project/tasks/2.3/exercise/dispatch.cpp)
— отдельная программа, с агентом не связанная. Писать ничего не надо: обе
версии готовы, работа в том, чтобы прочитать их, **предсказать на бумаге**
три вещи и потом сверить.

Похожий механизм вы уже писали на занятии 1.3. Правило там было записью
с указателем на функцию-проверку, и `CheckRules` звал её через этот
указатель:

```cpp
struct Rule {
    const char* id;
    RuleFn check;  // указатель на функцию-проверку
    Severity severity;
};

if (rules[i].check(event)) {  // какая функция вызовется, решает указатель
```

`CheckRules` не знает, какая функция стоит за `check`: это выясняется
во время работы, по значению указателя. `virtual` устроен так же. Для каждого
класса с виртуальными функциями компилятор сам заводит таблицу указателей —
[vtable](../lectures/glossary.md#vtable) (таблица виртуальных функций), —
а в каждый объект кладёт указатель на таблицу его класса. Вызов
`rule->Check(event)` идёт через эту таблицу
([лекция 7, раздел 6](../lectures/07/lecture.md#6-таблица-вызовов-руками)).

От `Rule` с занятия 1.3 это отличается двумя вещами: таблица одна на класс,
а не своя запись у каждого правила, и в функцию передаётся сам объект —
как `this`.

Упражнение собирается своей целью, как `inheritance` на занятии 2.2:

```bash
cmake --build --preset windows --target dispatch
./build/windows/Release/dispatch
```

На Linux — `--preset linux` и `./build/linux/dispatch`. Цель не зависит
от вашего кода в `src/`.

Что предсказать до запуска:

1. `sizeof` объекта с ручной таблицей и `sizeof` объекта с `virtual`.
2. Что напечатает счётчик незакрытых объектов, когда деструктор базы
   не виртуальный.
3. Что быстрее и во сколько раз.

Вопросы к коду после запуска:

- Почему таблица одна на «класс», а не одна на объект? Что было бы, если бы
  каждый объект хранил свою?
- В ручной версии `area` принимает `self` явным первым параметром. Куда он
  девается в версии с `virtual`?
- `ManualCall` делает три шага: разыменовать таблицу, взять указатель,
  позвать. Сколько из них делает `shape->Area()`?
- Что в ручной версии проверяет компилятор, а что нет? Например: можно ли
  случайно положить в таблицу квадрата функцию площади прямоугольника?
- На шаге 10 clang предупредил о невиртуальном деструкторе `IRule`, а на
  `BadBase` из упражнения молчит. Чем они отличаются?
- Если замер не показал, что `virtual` медленнее, — почему? Что должно

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Чем `IRule` отличается от `RuleBase`

`IRule` отвечает на вопрос «что правило умеет»: только чисто виртуальные
функции и ни одного поля. Это контракт, и движок разговаривает с правилами
только через него. `RuleBase` отвечает на вопрос «что у всех правил
одинаково»: идентификатор, важность, действия, счётчик. Это общий код, а не
контракт.

Меняются они по разным причинам. Правило, которому не нужен счётчик,
унаследует `IRule` напрямую. Новое поле, общее для всех правил, добавится
в `RuleBase`, и движок этого не заметит.

### Почему правила хранятся указателями

В 2.2 правила хранились `std::vector<MatchRule>`, потому что
в `std::vector<RuleBase>` от наследника доехала бы только базовая часть —
[срезка](../lectures/glossary.md#slicing) (object slicing).
`std::vector<IRule>` не собрать вовсе: `IRule` абстрактен, и объект такого
типа создать нельзя. Указатель срезать нечего, он одного размера при любом
наследнике. Поэтому движок хранит `std::vector<std::unique_ptr<IRule>>`,
и в одном векторе лежат и `MatchRule`, и `SequenceRule`.

### Почему у интерфейса виртуальный деструктор

`std::unique_ptr<IRule>` удаляет правило через указатель на `IRule`. Если
деструктор `IRule` не виртуальный, вызовется только он, а деструктор
`MatchRule` — нет: вектор условий не освободится. Сам `delete` при этом
передаёт размер `IRule`, а выделялся объект размером с `MatchRule`, —
именно это санитайзер и называет `new-delete-type-mismatch`.

**Правило:** у класса, который удаляют через указатель на базу, деструктор
базы виртуальный ([лекция 7, раздел 5](../lectures/07/lecture.md#5-виртуальный-деструктор)).
