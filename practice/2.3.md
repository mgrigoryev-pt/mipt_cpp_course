# Занятие 2.3. Таблица виртуальных вызовов и движок правил

> [Лекция 7](../lectures/07/lecture.md): виртуальные функции, абстрактные классы, виртуальный деструктор,
> `enum class`.

Кульминация второй части. Таблица указателей на функции из занятия 1.3
превращается в полиморфный движок, класс условия с переключателем разбирается
обратно на отдельные классы, а агент перестаёт знать, откуда приходят события.

## Конфигурация

```bash
cmake --preset windows -D NANO_EDR_LESSON=2.3
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Что делают эти команды и откуда их
запускать — в [`project/README.md`](../project/README.md).

**Набор тестов 2.2 с этого занятия не подключается, а 2.1 остаётся.** Предмет
набора 2.2 — `Condition` с переключателем вида сравнения и вектор правил
конкретного типа; на этом занятии не остаётся ни того, ни другого, и проверять
там нечего. Набор 2.1 наоборот обязан остаться зелёным, хотя условия
переписываются целиком: у них сохранён `operator()`, и старые тесты продолжают
звать их напрямую. Если что-то из набора 2.1 покраснело — поведение условия
изменилось вместе с его формой, а этого не требовалось.

## Куда это писать

Один новый файл в `src/`, остальные переписываются:

| | |
|---|---|
| `src/rule_engine.cpp` | реализации из `rule_engine.h` — движок |
| `src/conditions.cpp` | семь классов условий вместо одного с переключателем |
| `src/rule.cpp` | `RuleBase`, `MatchRule`, `SequenceRule` |
| `src/agent_rules.cpp` | набор правил: шесть вместо семи |
| `src/rules.cpp` | остался `SeverityName` |
| `src/agent.cpp` + `.h` | агент становится реализацией `IEventHandler` |
| `src/sources.cpp` + `.h` | два источника за одним интерфейсом; имя ваше |
| `src/main.cpp` | выбор источника — одна ветвь, дальше только интерфейс |

Реализовать нужно всё, что объявлено в заготовках, и ровно с теми подписями:

```
Matches у семи условий            AllOf::Add  AnyOf::Add
RuleBase::RuleBase  AddAction
MatchRule::MatchRule  AddCondition  Check
SequenceRule::SequenceRule  SetFirst  SetSecond  Check
RuleEngine::AddRule  ProcessEvent
SeverityName
```

`id()`, `severity()`, `hits()`, `actions()`, `CountHit()`, `condition_count()`,
`pending()`, `set_same_pid()`, `size()`, `rule()` и `operator()` написаны
в заготовках — их реализовывать не надо.

`IEventSource` и `IEventHandler` — чистые интерфейсы: реализации ваши целиком,
и имена у них ваши.

**Пока `rule_engine.cpp` не появился, набор 2.3 не собирается**: компоновщик
скажет `unresolved external symbol` (на Linux — `undefined reference`). Так
выглядит начало занятия. И помните, что появление нового файла — изменение
описания проекта, поэтому после него нужна **пере**конфигурация.

## Упражнение (40 минут)

`tasks/2.3/exercise/dispatch.cpp` — отдельная программа, собирается вручную;
команды для обеих платформ — в `README.md` рядом с ней.

Таблицу указателей на функции вы уже писали: `Rule` с полем `RuleFn`
на занятии 1.3. Вызов через сохранённый указатель вместо жёстко названной
функции — это она и есть, и ровно так устроен `virtual`. Отличий два, и оба
видны в коде: таблица здесь одна на тип, а не одна запись на правило,
и в функцию передаётся сам объект.

Писать ничего не надо, обе версии готовы. Работа в другом — прочитать их
и **предсказать на бумаге** три вещи, а потом сверить:

1. `sizeof` объекта с ручной таблицей и `sizeof` объекта с `virtual`.
2. Что напечатает счётчик незакрытых объектов, когда деструктор базы
   не виртуальный, — и почему компилятор об этом промолчал.
3. Что быстрее и во сколько раз.

После этого фраза «виртуальный вызов стоит одну косвенность» перестаёт быть
заклинанием: косвенность видна в прочитанном коде, а её цена — в числах.

Предсказание до запуска — не формальность: числа без догадки ничему не учат,
любые кажутся ожидаемыми. Ещё четыре вопроса к этому коду — в `README.md`
рядом с ним.

## Проект

1. **Условия: интерфейс вместо переключателя.** С этого стоит начать, это
   самый большой кусок занятия. `Condition` с одним `switch` по виду сравнения
   разбирается на **семь классов** за общим интерфейсом `ICondition`: пять
   простых и два составных, `AllOf` и `AnyOf`. Вектор условий теперь
   `std::vector<std::unique_ptr<ICondition>>`, и добавить восьмой вид сравнения
   значит написать восьмой класс, не тронув ни строчки в существующих.

   Составное условие — то, чего переключатель не выражал вовсе: условие,
   которое содержит другие условия и ничего не знает об их видах.

   Два следствия появятся сами. **Правил станет шесть вместо семи:** два
   смысла требовали по два правила каждый, потому что «или» выражалось только
   внутри одного поля, а с `AnyOf` каждый складывается в одно. И **одно и то
   же составное условие понадобится дважды** — записать его один раз и позвать
   из двух правил есть то, ради чего интерфейс заводился.
2. **Интерфейс правила и движок.**

   ```cpp
   class IRule {
    public:
       virtual ~IRule() = default;
       virtual const std::string& id() const = 0;
       virtual Severity severity() const = 0;
       virtual bool Check(const Event& event) = 0;   // состояние допустимо
   };
   ```

   `RuleBase` реализует общую часть, `MatchRule` наследует его. Набор правил —
   `std::vector<std::unique_ptr<IRule>>`, и это прямой ответ на вопрос
   с прошлого занятия.

   `RuleEngine` с `AddRule` и `ProcessEvent`. Печати в движке нет: он отдаёт
   список сработавших правил и умолкает, а печатает агент.
3. **Интерфейс источника.** `IEventSource` с двумя реализациями: файловый
   источник из части 1 и источник поверх `os.h`. **Агент не знает, откуда
   события** — он реализует `IEventHandler`, и в него приходят уже разобранные
   события.

   Это второй интерфейс за занятие, и он проверяет первый: если движок
   пришлось править при добавлении второго источника, значит абстракция была
   не там.
4. **`SequenceRule`** на два шага с окном и связкой `same_pid`. Первое правило
   с состоянием — то, которое таблицей указателей на функции не выражалось.
   Связка по процессу включена по умолчанию: без неё правило соединяет
   случайные события. Второй шаг за пределами окна — **не** детект, иначе
   правило однажды свяжет события, между которыми прошёл час.
5. **Вытеснение незавершённых совпадений по времени.** Правило помнит первые
   шаги, и без вытеснения эта память растёт, пока агент жив. Делается первым
   делом в `Check`, до всякой проверки.
6. **Демонстрация утечки при невиртуальном деструкторе:** убрать `virtual`,
   прогнать под санитайзером (`asan-windows`, на Linux — `asan`), прочитать
   отчёт, вернуть.
7. **Прогон на чистых сценариях и починка ложных детектов.** `clean_office`
   и `clean_build` требуют нуля детектов. Правило, которое ловит атаку
   и одновременно срабатывает на сборке проекта, — не работающее правило.
   И починка не должна стоить истинных детектов: правило, переставшее
   ошибаться потому, что перестало срабатывать вообще, не починено.

**Виртуальный деструктор в `IRule` — не украшение.** Без него `delete`
по указателю на `IRule` не вызовет деструктор наследника, и условия внутри
`MatchRule` утекут. Неприятность в том, что код при этом выглядит безупречно,
а компилятор молчит: у интерфейса в момент объявления деструктора виртуальных
функций может ещё не быть.

**`IRule` и `RuleBase` — не одно и то же.** Первый отвечает на вопрос «что
правило умеет» (контракт, только чистые виртуальные, ни одного поля), второй —
«что у всех правил одинаково» (переиспользование). Они меняются по разным
причинам, и держать их отдельно стоит именно поэтому.

**Состояние в `Check` допустимо, но у него есть размер.** `SequenceRule`
помнит незавершённые совпадения, и эта память тем больше, чем длиннее поток.
Отсюда шаг 5: без него правило работает правильно и растёт бесконечно.

**Правила проверяются и на сценариях, которых у вас нет.** Семь открытых —
не весь набор; качество считается по точности и полноте, и правило, подогнанное
под конкретный журнал, на незнакомом развалится. Поэтому первый шаг правила
стоит писать по смыслу атаки, а не по строкам, которые видно в `phishing_macro`.

## Готово, когда

- Агент работает от обоих источников без изменений в коде выше интерфейса,
  и **оба дают на одном журнале побайтово одинаковый вывод** под `--quiet`.
- **Пять сценариев из семи дают тот же вывод, что на занятии 2.2.** Условия
  и правила переписаны целиком, и это единственное доказательство, что
  перепись поведенчески тождественна. Чтобы сравнивать было с чем, снимите
  вывод всех семи сценариев под `--quiet` в файлы **до** того, как начнёте
  переписывать: `nano-edr scenarios/phishing_macro.log --quiet > before.txt`
  и так далее.
- **В `phishing_macro` и `pid_reuse` добавилось ровно по одной строке** —
  детект вашего правила на два шага. Если строк больше одной, закрытое
  совпадение не снимается, и на потоке это превратится в шум.
- На `clean_office` и `clean_build` детектов нет.
- Отчёт санитайзера при невиртуальном деструкторе вы видели своими глазами,
  а в сдаваемой версии `virtual` на месте и отчёт пуст.

## Тесты

Движок правил, полиморфные условия, правило с состоянием, интерфейсы источника
и получателя событий. Плюс набор 2.1, который остаётся подключённым.

### Запуск тестов

```bash
ctest --preset windows
```

На Linux вместо `windows` — `linux`.

### Что именно проверяется

Четыре случая проверяют `std::has_virtual_destructor_v` у четырёх интерфейсов.
Проверка компиляторная и потому дешёвая, но настоящую цену ошибки она
не показывает — её показывает шаг 6 задания.

У `SequenceRule` проверяются все три вещи, о которых легко забыть: связка
по процессу, окно и вытеснение незавершённых совпадений. Последнее — на сотне
событий; в настоящем агенте счёт был бы на миллионы.

### На что обратить внимание

**Если покраснел набор 2.1 — поведение условия изменилось вместе с формой.**
У условий сохранён `operator()`, и написанный тогда код обязан продолжать
компилироваться и давать то же самое.

**Цена интерфейса видна сразу:** `std::vector<std::unique_ptr<ICondition>>`
вместо `std::vector<Condition>` — аллокация на каждое условие и косвенность
на каждую проверку. Стоит ли она того — вопрос, на который отвечает
упражнение занятия, и ответ там может оказаться не тем, которого вы ждёте.
