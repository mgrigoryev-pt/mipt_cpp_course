# Занятие 2.3. Таблица виртуальных вызовов и движок правил

> [Лекция 7](../lectures/07/lecture.md): виртуальные функции, абстрактные
> классы, виртуальный деструктор, `enum class`.

До сих пор условие, правило и источник событий были конкретными типами.
`Condition` выбирал сравнение через `switch`, агент хранил
`std::vector<MatchRule>`, а `main` выбирал между двумя источниками веткой
`if`, где каждый источник назван своим типом. На этом занятии все три места
уходят за интерфейсы — классы, в которых объявлены только
[чисто виртуальные функции](../lectures/glossary.md#pure-virtual) (pure
virtual functions). Код, который пользуется интерфейсом, не знает, с каким
наследником работает.

Это даёт две вещи, которых раньше не было: условие, составленное из других
условий, и правило с состоянием, которое ловит атаку из двух событий. На
`phishing_macro` агент под `--quiet` печатает на одну строку больше, чем
в 2.2:

```
[DETECT] high  script_host_from_temp  ts=1730000003000 pid=1101
[DETECT] critical  script_host_beacon  ts=1730000004200 pid=1101
[DETECT] medium  hidden_powershell  ts=1730000006000 pid=1156
```

Вторая строка — новое правило: скриптовый хост через 1,2 секунды после
запуска открыл сетевое соединение. Такая же строка добавляется
в `pid_reuse`, на остальных пяти сценариях вывод не меняется.

### 1. Условие за интерфейсом

В [`conditions.h`](../project/kit/include/l2.3/conditions.h) объявлен
интерфейс `ICondition` с одной
[виртуальной функцией](../lectures/glossary.md#virtual-function) (virtual
function) `Matches`:

```cpp
class ICondition {
 public:
    virtual ~ICondition() = default;
    virtual bool Matches(const Event& event) const = 0;
    bool operator()(const Event& event) const { return Matches(event); }
};
```

Каждый вид сравнения — свой наследник, и `Matches` в нём
[переопределяется](../lectures/glossary.md#override) (overriding) со словом
`override` ([лекция 7, раздел 3](../lectures/07/lecture.md#3-override-и-final)).
Чтобы добавить новое сравнение, пишут новый класс, а существующие
не трогают.

Четыре функтора с занятия 2.2 — `FieldEquals`, `FieldContains`,
`FieldEndsWith`, `FieldInList` — уже наследники `ICondition`. Их `operator()`
переименовывается в `Matches`, тело не меняется:

```cpp
// было в 2.2
bool FieldEquals::operator()(const Event& event) const { /* ... */ }

// стало
bool FieldEquals::Matches(const Event& event) const { /* ... */ }
```

Звать условие принято через `Matches`. `operator()` написан один раз в самом
`ICondition` и оставлен для совместимости: тесты набора 2.1 зовут условия
как функторы и компилируются как прежде.

Пятое простое условие новое — `EventTypeIs(types)`: `Matches` возвращает
`true`, если `event.event_type()` — один из `types`. Оно сравнивает
перечисления, а не строки. В [`event.h`](../project/kit/include/l2.3/event.h)
появился `EventType` — [scoped enumeration](../lectures/glossary.md#scoped-enum),
перечисление `enum class` ([лекция 7, раздел 8](../lectures/07/lecture.md#8-enum-и-enum-class)),
и метод `Event::event_type()`. Зачем перечисление, если строка уже есть, —
видно на опечатке:

```cpp
event.type() == "proces_start"                 // собирается, но всегда false
event.event_type() == EventType::kProcesStart  // ошибка: такого значения нет
```

Со строкой код собирается, и правило с такой опечаткой молча никогда
не срабатывает. С перечислением ту же опечатку останавливает компилятор.

В `src/event.cpp` пишутся две функции:

| Функция | Что делает |
|---|---|
| `EventTypeFromString(type)` | `"process_start"` → `kProcessStart`, и так для всех семи типов из [`SPEC.md`](../project/SPEC.md); незнакомая строка → `kOther`, а не исключение |
| `EventTypeName(type)` | обратно: значение → строка; `kOther` → `"other"` |

Конструктор `Event` вызывает `EventTypeFromString` и кладёт результат
в поле `event_type_`. Строка типа при этом остаётся в `type()`: по `kOther`
не поймёшь, что пришло, а по строке поймёшь.

### 2. Условие из условий

Два оставшихся класса в `conditions.h` — составные условия. Они хранят
другие условия как `std::unique_ptr<ICondition>` и ничего не знают об их
типах:

| Метод | Что делает |
|---|---|
| `AllOf::Add(condition)`, `AnyOf::Add(condition)` | добавляет условие в конец |
| `AllOf::Matches(event)` | `true`, если все вложенные условия вернули `true`; пустой `AllOf` — `true` |
| `AnyOf::Matches(event)` | `true`, если хотя бы одно вернуло `true`; пустой `AnyOf` — `false` |

Составные условия вкладываются друг в друга: `AnyOf` может лежать внутри
`AllOf` и наоборот.

В 2.2 этого не хватало: «`path` заканчивается на `.locked` **или** `to`
заканчивается на `.locked`» в одно правило не помещалось, и
`ransom_extension` записывался двумя объектами. С `AnyOf` это одно правило:

```cpp
auto rule = std::make_unique<MatchRule>("ransom_extension",
                                        Severity::kCritical);
rule->AddCondition(std::make_unique<EventTypeIs>(std::vector<EventType>{
    EventType::kFileCreate, EventType::kFileWrite, EventType::kFileMove}));

auto paths = std::make_unique<AnyOf>();
paths->Add(std::make_unique<FieldEndsWith>("path", ".locked"));
paths->Add(std::make_unique<FieldEndsWith>("to", ".locked"));
rule->AddCondition(std::move(paths));

rule->AddAction("quarantine_file");
```

Список значений внутри одного условия — как в
`Condition::Contains("cmdline", {...})` в 2.2 — тоже записывается через
`AnyOf`, по условию на каждое значение:

```cpp
auto temp = std::make_unique<AnyOf>();
temp->Add(std::make_unique<FieldContains>("cmdline",
                                          "\\appdata\\local\\temp\\"));
temp->Add(std::make_unique<FieldContains>("cmdline", "%temp%"));
// ... остальные варианты пути с занятия 2.2
```

### 3. Правило за интерфейсом и движок

В [`rule.h`](../project/kit/include/l2.3/rule.h) над `RuleBase` появился
интерфейс `IRule`: `id()`, `severity()`, `Check`, `hits()` и `actions()`, все
чисто виртуальные. `IRule` — [абстрактный класс](../lectures/glossary.md#abstract-class)
(abstract class): создать его объект нельзя, можно только указатель или
ссылку на наследника ([лекция 7, раздел 4](../lectures/07/lecture.md#4-абстрактные-классы)).
`RuleBase` реализует общее, `MatchRule` наследует `RuleBase`, как в 2.2.

Меняется и то, как условие попадает в правило. В 2.2 `Condition` был одного
типа и копировался в вектор правила целиком. Теперь условия разных типов —
`FieldEquals`, `AnyOf`, `EventTypeIs`, — и в одном векторе их можно держать
только указателями на `ICondition`. Поэтому условие создаётся через
`std::make_unique`, а правилу передаётся указатель на него:

```cpp
// было в 2.2: условие копируется в правило
rule.AddCondition(Condition::Equals("type", {"process_start"}));

// стало: правило забирает указатель себе
auto is_start = std::make_unique<EventTypeIs>(
    std::vector<EventType>{EventType::kProcessStart});
rule->AddCondition(std::move(is_start));  // is_start теперь пуст
```

После `AddCondition` условие принадлежит правилу — это и называется
[владением](../lectures/glossary.md#ownership) (ownership).

В `src/rule.cpp` меняются два метода `MatchRule`, остальное — как в 2.2:

| Метод | Что делает |
|---|---|
| `AddCondition(condition)` | кладёт условие в конец `conditions_`; `unique_ptr` не копируется, поэтому через `std::move` |
| `Check(event)` | `true`, если все условия вернули `true`, — тогда же зовёт `CountHit()`; у правила без условий всегда `true` |

Новое — движок, [`rule_engine.h`](../project/kit/include/l2.3/rule_engine.h).
Он владеет правилами и прогоняет через них событие. В `src/rule_engine.cpp`:

| Метод | Что делает |
|---|---|
| `AddRule(rule)` | добавляет правило в конец `rules_` |
| `ProcessEvent(event, fired)` | зовёт `Check` у каждого правила в порядке добавления и возвращает, сколько сработало. Если `fired` не `nullptr`, **дописывает** в него указатели на сработавшие правила; что там было до вызова, остаётся |

Печати в движке нет: он сообщает, какие правила сработали, а печатает агент.

**Набор правил.** Пять правил с занятия 2.2, и объектов теперь тоже пять:
`autostart_write` складывается в одно правило так же, как `ransom_extension`
в [шаге 2](#2-условие-из-условий). `BuildAgentRules()` теперь возвращает
не вектор, а движок:

```cpp
RuleEngine BuildAgentRules() {
    RuleEngine engine;
    // engine.AddRule(...) — пять правил
    return engine;
}
```

Копировать движок нельзя, а перемещать можно: для этого в
[`rule_engine.h`](../project/kit/include/l2.3/rule_engine.h) выданы две
строки с `&&`. Что они значат, разбирается на лекции 11, к занятию 3.3.

**Агент.** Вектор правил заменяется движком, а цикл по правилам — вызовом
`ProcessEvent`:

```cpp
class Agent {
 public:
    // ...
 private:
    EventList window_;
    RuleEngine engine_;  // в конструкторе: engine_(BuildAgentRules())
    // ...
};

void Agent::HandleEvent(const Event& event) {
    std::vector<const IRule*> fired;
    engine_.ProcessEvent(event, &fired);
    for (std::size_t i = 0; i < fired.size(); ++i) {
        // строка детекта — как в 2.2, только через fired[i]->
    }
    // ...
}
```

В сводке цикл по `rules_` заменяется циклом по движку:
`engine_.rule(i).id()` и `engine_.rule(i).hits()` для `i` от 0 до
`engine_.size()`.

**Заглушки для `SequenceRule`.** Тесты набора 2.3 зовут и `SequenceRule`,
которое пишется на [шаге 5](#5-правило-на-два-шага), и без его методов
не слинкуются. Чтобы проверить шаги 1–3 сейчас, допишите в `src/rule.cpp`:

```cpp
SequenceRule::SequenceRule(const std::string& id, Severity severity,
                           uint64_t window_ms)
    : RuleBase(id, severity), window_ms_(window_ms) {}
void SequenceRule::SetFirst(std::unique_ptr<ICondition>) {}
void SequenceRule::SetSecond(std::unique_ptr<ICondition>) {}
bool SequenceRule::Check(const Event&) { return false; }
```

**Проверка.** Проект и тесты собираются, наборы 2.1 и 2.3 зелёные, кроме
тестов `SequenceRule`. Вывод под `--quiet` на всех семи сценариях совпадает
с эталонами занятия 2.1:

```bash

diff out.txt tasks/2.1/tests/expected/phishing_macro.out
```

На Windows — `./build/windows/Release/nano-edr` и `fc.exe`. В сводке правил
стало пять строк вместо семи.

### 4. Источник за интерфейсом

В [`event_source.h`](../project/kit/include/l2.3/event_source.h) два
интерфейса. `IEventSource` — откуда берутся события, у него один метод
`Run(handler)`. `IEventHandler` — кому они отдаются. Источник знает только
`IEventHandler`, агент не знает, какой источник его вызывает.

Агент становится наследником `IEventHandler` и реализует четыре его метода.
В комментариях — кто и когда их зовёт:

```cpp
class Agent : public IEventHandler {
 public:
    // Оба источника: пришло событие. Тело — как на шаге 3.
    void HandleEvent(const Event& event) override;

    // FileSource: пустая строка или комментарий.
    void OnSkipped() override;

    // FileSource: из строки не вышло события.
    // Трамплин: событие от os.h не удалось построить.
    void OnBroken() override;

    // OsSource: Wait вернул OS_TIMEOUT, новых событий пока нет.
    void OnTick() override;
    // ...
};
```

`OnSkipped` и `OnBroken` прибавляют по единице к счётчикам сводки, у `OnTick`
пока пустое тело.

`FileSource` и `OsSource` становятся наследниками `IEventSource`: их
`Run(Agent*)` превращается в `Run(IEventHandler*) override`, и зовут они
теперь методы `IEventHandler`. Например, цикл ожидания в `OsSource::Run`:

```cpp
os_status status = handle_.Wait(kWaitMs);
while (status == OS_TIMEOUT) {
    handler->OnTick();
    status = handle_.Wait(kWaitMs);
}
```

Заголовки источников больше не включают `agent.h`.

**Трамплин приводит `void*` к тому же типу, что передан в `Subscribe`.**
`OsSource::Run` теперь передаёт в `Subscribe` указатель на `IEventHandler`,
значит трамплин обязан привести `ctx` к `IEventHandler*`, а не к `Agent*`:

```cpp
handle_.Subscribe(&Agent::Trampoline, handler);  // handler — IEventHandler*

// в трамплине
IEventHandler* handler = static_cast<IEventHandler*>(ctx);
```

Это то же требование, что на занятии 2.1, а в упражнении 2.2 (часть 3) видно,
почему адрес объекта и адрес его базы бывают разными.

В `main` две ветви `if` с двумя вызовами `Run` сводятся к одной: ветвь только
создаёт нужный источник, а `Run` зовётся один раз, через интерфейс:

```cpp
std::unique_ptr<IEventSource> source;
if (options.force_file) {
    source = std::make_unique<FileSource>(options.path);
} else {
    source = std::make_unique<OsSource>(options.path);
}
source->Run(&agent);
```

**Проверка.** Тесты `task2.1.sources.<журнал>` зелёные: они прогоняют агента
через оба источника на семи сценариях и на `rules_edges.log` и сравнивают
два вывода между собой. Если для этого шага пришлось править движок или
правила, интерфейс проведён не там.

### 5. Правило на два шага

`SequenceRule` из `rule.h` — правило с состоянием. Оно ищет пару событий:
сначала первый шаг, потом второй, не позже чем через `window_ms`
и с тем же `pid`, если включена связка по процессу. Первые шаги, которые
ещё ждут второго, лежат в `pending_`.

В `src/rule.cpp` заглушки шага 3 заменяются настоящими методами:

| Метод | Что делает |
|---|---|
| `SequenceRule(id, severity, window_ms)` | передаёт идентификатор и важность `RuleBase`, запоминает окно; связка по процессу включена |
| `SetFirst(condition)`, `SetSecond(condition)` | запоминают условия первого и второго шага |

`Check(event)` делает четыре вещи, и порядок существенный:

1. Если какой-то из шагов не задан, возвращает `false`.
2. **Удаляет опоздавшие записи.** Запись в `pending_` нужна, пока второй шаг
   ещё может прийти вовремя. Например, окно — 10 000 мс, первый шаг пришёл
   с `ts=1000`. Если до `ts=11000` второго шага не было, ждать его дальше
   незачем, и на первом же событии с `ts` больше 11 000 запись удаляется.
   Без этого каждый скриптовый хост, который так и не открыл соединение,
   остаётся в `pending_` навсегда, и память правила растёт всё время, пока
   агент работает.
3. **Закрывает запись.** Если событие подходит под второй шаг и в `pending_`
   есть запись с тем же `pid` (или связка выключена), запись удаляется,
   вызывается `CountHit()`, и `Check` возвращает `true`. Одна пара — один
   детект: если запись не удалять, она даст детект на каждом следующем
   втором шаге.
4. **Добавляет запись.** Если событие подходит под первый шаг, в `pending_`
   добавляются его время и `pid`. Возвращается `false`.

Второй шаг проверяется раньше первого, чтобы событие, подходящее под оба,
закрывало уже добавленную запись, а не добавляло новую.

Шестое правило набора — `SequenceRule`. Добавьте его в движок последним:

```cpp
auto beacon = std::make_unique<SequenceRule>("script_host_beacon",
                                             Severity::kCritical, 10000);
beacon->SetFirst(/* старт скриптового хоста: process_start,
                    image заканчивается на wscript.exe или cscript.exe */);
beacon->SetSecond(std::make_unique<EventTypeIs>(
    std::vector<EventType>{EventType::kNetConnect}));
beacon->AddAction("kill_process");
engine.AddRule(std::move(beacon));
```

**Проверка.** Тесты `SequenceRule` зелёные. В `phishing_macro` и `pid_reuse`
по сравнению с эталоном 2.1 добавилось **ровно по одной** строке
`script_host_beacon`. Две и больше — запись после детекта не удаляется.

### 6. Ноль детектов на чистых сценариях

Прогоните `clean_office` и `clean_build`. На них детектов быть не должно:
правило, которое ловит атаку и заодно срабатывает на обычной работе, —
неработающее правило. Если детект есть, разберите, какое законное поведение
он поймал и чем оно отличается от атаки в `phishing_macro`.

**Проверка.** На `clean_office` и `clean_build` вывод под `--quiet`
пустой, в `phishing_macro` и `pid_reuse` новая строка на месте, остальные
пять сценариев совпадают с эталонами 2.1.

### 7. Цена невиртуального деструктора

Деструктор `IRule` виртуальный, и этот шаг показывает, что будет без этого.
Комплект менять нельзя, но здесь разрешена **одна временная правка**:
в `kit/include/l2.3/rule.h` уберите слово `virtual` из строки

```cpp
virtual ~IRule() = default;
```

1. **Прочитайте предупреждение.** Соберите проект обычным пресетом. Clang
   предупредит, что `delete` вызывается для `IRule` с невиртуальным
   деструктором, но укажет не на `rule.h` и не на ваш код, а на стандартный
   заголовок `<memory>`: удаляет правило `std::unique_ptr`. Ошибкой
   предупреждение не считается, и в длинном выводе сборки его легко
   не заметить.
2. **Прогоните тесты под [санитайзером](../lectures/glossary.md#sanitizer)
   (sanitizer):**

   ```bash
   cmake --preset asan-windows -D NANO_EDR_LESSON=2.3
   cmake --build --preset asan-windows
   ctest --preset asan-windows -R "task2.3|sources"
   ```

   На Linux — пресет `asan` и `ctest --preset asan` без `-R`. На Windows
   набор ограничен, потому что под `asan-windows` падает любой пойманный
   `throw`, — подробнее в
   [`project/README.md`, «Перед сдачей»](../project/README.md#перед-сдачей).

   Санитайзер остановит прогон с отчётом `new-delete-type-mismatch`: размер
   выделенного объекта и размер освобождаемого разные. Объясните оба числа:
   что лежит в объекте `MatchRule` и что — в `IRule`.
3. **Верните `virtual`.** Тест «у интерфейса правила виртуальный деструктор»
   снова зелёный, санитайзер молчит.

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Чем `IRule` отличается от `RuleBase`

`IRule` отвечает на вопрос «что правило умеет»: только чисто виртуальные
функции и ни одного поля. Это контракт, и движок разговаривает с правилами
только через него. `RuleBase` отвечает на вопрос «что у всех правил
одинаково»: идентификатор, важность, действия, счётчик. Это общий код, а не
контракт.

Меняются они по разным причинам. Правило, которому не нужен счётчик,
унаследует `IRule` напрямую. Новое поле, общее для всех правил, добавится
в `RuleBase`, и движок этого не заметит.

### Почему правила хранятся указателями

В 2.2 правила хранились `std::vector<MatchRule>`, потому что
в `std::vector<RuleBase>` от наследника доехала бы только базовая часть —
[срезка](../lectures/glossary.md#slicing) (object slicing).
`std::vector<IRule>` не собрать вовсе: `IRule` абстрактен, и объект такого
типа создать нельзя. Указатель срезать нечего, он одного размера при любом
наследнике. Поэтому движок хранит `std::vector<std::unique_ptr<IRule>>`,
и в одном векторе лежат и `MatchRule`, и `SequenceRule`.

### Почему у интерфейса виртуальный деструктор

`std::unique_ptr<IRule>` удаляет правило через указатель на `IRule`. Если
деструктор `IRule` не виртуальный, вызовется только он, а деструктор
`MatchRule` — нет: вектор условий не освободится. Сам `delete` при этом
передаёт размер `IRule`, а выделялся объект размером с `MatchRule`, —
именно это санитайзер и называет `new-delete-type-mismatch`.

**Правило:** у класса, который удаляют через указатель на базу, деструктор
базы виртуальный ([лекция 7, раздел 5](../lectures/07/lecture.md#5-виртуальный-деструктор)).
