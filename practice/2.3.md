# Занятие 2.3. Таблица виртуальных вызовов и движок правил

> [Лекция 7](../lectures/07/lecture.md): виртуальные функции, абстрактные классы, виртуальный деструктор,
> `enum class`.

Кульминация второй части. Таблица указателей на функции из занятия 1.3
превращается в полиморфный движок, а агент перестаёт знать, откуда приходят
события.

## Примитив (40 минут)

`tasks/2.3/exercise/dispatch.cpp` — собрать диспетчеризацию руками:

1. Структура с указателями на функции.
2. Объект с указателем на неё.
3. Вызов «метода» через таблицу.
4. Затем переписать то же самое на `virtual` и сравнить — включая `sizeof`
   объекта до и после.

После этого фраза «виртуальный вызов стоит одну косвенность» перестаёт быть
заклинанием: вы её только что написали руками.

## Проект

### Интерфейс правила

```cpp
class IRule {
 public:
    virtual ~IRule() = default;
    virtual const std::string& id() const = 0;
    virtual Severity severity() const = 0;
    virtual bool Check(const Event& event) = 0;   // состояние допустимо
};
```

`MatchRule` наследует `IRule`. Набор правил —
`std::vector<std::unique_ptr<IRule>>`, и это прямой ответ на вопрос
с прошлого занятия.

`RuleEngine` с `AddRule` и `ProcessEvent`. `enum class Severity` и `EventType`.

### Интерфейс источника

`IEventSource` с двумя реализациями: файловый источник из части 1 и `OsSource`
поверх `os.h`. **Агент не знает, откуда события.**

Это второй интерфейс за занятие, и он проверяет первый: если движок пришлось
править при добавлении второго источника, значит абстракция была не там.

## Дома

- **`SequenceRule`** на два шага с окном и связкой `same_pid`. Первое правило
  с состоянием — то, которое таблицей указателей на функции не выражалось.
- Демонстрация утечки при невиртуальном деструкторе: убрать `virtual`, прогнать
  под санитайзером, увидеть отчёт, вернуть.
- Прогон на чистых сценариях и починка ложных срабатываний.

Про последний пункт: `clean_office` и `clean_build` требуют нуля сработок.
Правило, которое ловит атаку и одновременно срабатывает на сборке проекта, —
не работающее правило.

## На что смотреть

**Виртуальный деструктор в `IRule` — не украшение.** Без него `delete`
по указателю на `IRule` не вызовет деструктор наследника, и условия внутри
`MatchRule` утекут. Неприятность в том, что код при этом выглядит безупречно.

**`IRule` и `RuleBase` — не одно и то же.** Первый отвечает на вопрос «что
правило умеет» (контракт, только чистые виртуальные, ни одного поля), второй —
«что у всех правил одинаково» (переиспользование). Они меняются по разным
причинам, и держать их отдельно стоит именно поэтому.

**Состояние в `Check` допустимо.** `SequenceRule` помнит незавершённые
совпадения. Значит у этой памяти есть размер, и он растёт. Пока это не проблема;
на финальном блоке станет.
