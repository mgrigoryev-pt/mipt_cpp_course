# Занятие 1.2. Односвязный список и разбор строки

> [Лекция 2](../lectures/02/lecture.md): указатели, память, RAII, `unique_ptr`.

Занятие добавляет к агенту два файла — разбор строки журнала и односвязный
список для [скользящего окна](../lectures/glossary.md#sliding-window)
(sliding window) последних событий — и переводит цикл в `main.cpp` на них.
На `phishing_macro` готовый агент печатает перед детектом его контекст:

```
[CTX] -2: ts=1730000001850 type=file_write pid=1042
[CTX] -1: ts=1730000002100 type=file_write pid=880
[DETECT] строка 9, признак wscript.exe: ts=1730000003000 type=process_start pid=1101 ppid=1042 image="C:\Windows\System32\wscript.exe" cmdline="wscript.exe C:\Users\max\AppData\Local\Temp\a.js" user=DESKTOP\max
```

## Конфигурация

```bash
cmake --preset windows -D NANO_EDR_LESSON=1.2
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Что делают эти команды и откуда их
запускать — в [`project/README.md`](../project/README.md).

Набор тестов 1.1 остаётся подключённым. Он сравнивает вывод под `--quiet`
с эталоном: внутренности на этом занятии переписываются целиком, а вывод
детектов меняться не должен.

## Развитие проекта

Что реализовать и с какими [сигнатурами](../lectures/glossary.md#signature)
(signature) — в [изменяемых файлах](#изменяемые-файлы); требования к списку —
в разделе [EventList](#eventlist). Тип `Event` определён в хедере
`kit/include/l1.2/event.h`: поля-строки `ts`, `type`, `pid` и вектор пар
«ключ-значение» `fields`.

1. **Выданные тесты собираются.** Заведите в `src/` два файла, `parse.cpp`
   и `event_list.cpp`, и дайте каждой из [шести функций](#изменяемые-файлы)
   тело-заглушку: `ParseEventLine` и `IsBlankOrComment` возвращают `false`,
   остальные ничего не делают. Без этого `task1_2_tests` не линкуется, и тесты
   списка и разбора не запустить по частям. После шага набор 1.2 собирается
   и красный, набор 1.1 зелёный; дальше заглушки заменяются по одной.
2. **Строка журнала целиком.** `ParseEventLine` кладёт `ts`, `type` и `pid`
   в соответствующие поля структуры, остальные пары — в вектор `fields`.
   Порядок полей в строке любой: `ts`, `type` и `pid` могут стоять в ней где
   угодно, и искать их надо по имени, а не по месту. Строка без `ts` или без
   `type` — `false`: событие без времени и без типа бесполезно. Без `pid` —
   допустима, не у всякого события есть процесс, строка `pid` в таком случае
   остаётся пустой. Событием не считаются пустая строка, строка из одних
   пробелов и табуляций и строка-комментарий — та, что начинается с `#`
   или `;` после необязательных пробелов и табуляций. `ParseEventLine`
   возвращает для них `false` и `*out` не заполняет. Проверить это проще
   всего в начале самой `ParseEventLine` — тем же `IsBlankOrComment`.
3. **Разбор пар «ключ-значение»** — прямым проходом по символам. Кавычки
   снимаются, обратный слеш внутри них — обычный символ. Пробелов между парами
   может стоять несколько, в начале и в конце строки они тоже допустимы:
   лишние пробелы пропускаются и не дают ни пустых пар, ни отказа.
   Повторяющийся ключ законен, и терять его нельзя: строку прислала система.
   Первое вхождение `ts`, `type` или `pid` занимают соответствующие поля структуры,
   второе остаётся полем в `fields`; порядок полей в `fields` — тот же, что
   в строке. Как это выглядит на конкретных строках —
   [таблица разбора](#таблица-разбора).
4. **Список хранит окно последних событий**: у него есть вместимость —
   значение `capacity`, и при переполнении самое старое событие уходит.
   Вместимость 0 означает «без ограничения».
5. **Размер окна из командной строки:** `--window-size N`, по умолчанию 64.
   Флаг задаёт `capacity` списка: столько последних событий окно хранит,
   а при переполнении самое старое уходит. Ноль — окно без ограничения.
   Строку со значением нужно сконвертировать в число: рекомендуется функция
   [`std::from_chars`](https://en.cppreference.com/cpp/utility/from_chars).
6. **Контекст детекта.** Каждый детект сопровождается двумя событиями,
   пришедшими до сработавшей строки, — время, тип, `pid`:

   ```
   [CTX] -2: ts=1730000001850 type=file_write pid=1042
   [CTX] -1: ts=1730000002100 type=file_write pid=880
   ```

   Так выглядит контекст единственного детекта в
   `scenarios/phishing_macro.log`.

   Формат и состав контекста фиксированы — их сверяет выданный тест:

   - **Место.** Строки контекста печатаются сразу перед строкой детекта.
     Если в одной строке журнала сработало несколько признаков, контекст
     печатается один раз — перед первым детектом этой строки.
   - **Состав.** Контекст — два последних события в окне, то есть два
     последних разобранных. Сработавшее событие в их число не входит:
     в окно оно кладётся после того, как контекст напечатан.
   - **Что в окно не попадает.** Комментарий, пустая строка и строка, которую
     не удалось разобрать, окна не меняют.
   - **Когда событий мало.** Печатается столько, сколько есть: одно событие
     печатается как `-1`, на пустом окне контекста нет вовсе.
   - **Под `--quiet`** в `stdout` по-прежнему нет ничего, кроме детектов:
     строк `[CTX]` там не бывает.

## Готово, когда

- Тесты списка, разбора и контекста зелёные, тесты занятия 1.1 по-прежнему
  зелёные.
- Разбор не падает ни на одном входе из [таблицы разбора](#таблица-разбора).
- На Linux: `ctest --preset asan` проходит без сообщений санитайзера,
  включая [утечки памяти](../lectures/glossary.md#memory-leak) (memory leak).
- На Windows: `ctest --preset asan-windows` проходит. Утечек он не находит
  ([почему](#на-что-обратить-внимание)), поэтому проверка здесь одна:
  прочитать свой `~EventList` и убедиться, что цикл доходит до конца цепочки.

## Справочник

### Изменяемые файлы

Два новых файла в `src/` — и `main.cpp`, который уже есть. В новых файлах —
разбор строки и реализация списка событий. В `main.cpp` — всё, что их
связывает: цикл занятия 1.1 перестаёт выдирать `type=` из строки сам и зовёт
`ParseEventLine` и `IsBlankOrComment` для каждой строки. Туда же добавляются
новая опция `--window-size` для ведения окна событий и печать контекста перед
детектом. Формат детекта не меняется.

`CMakeLists.txt` править не нужно: все `.cpp` из `src/`, кроме `main.cpp`,
подхватываются сами. Переконфигурировать проект после нового файла тоже
не нужно: сборка замечает его и перезапускает CMake сама.

Реализовать нужно всё, что объявлено в выданных заголовочных файлах (хедерах),
и ровно с теми сигнатурами:

```
ParseEventLine  IsBlankOrComment
ListPushBack  ListPopFront  ListClear  EventList::~EventList
```

Сигнатуры в хедерах редактировать нельзя, иначе не скомпилируются тесты.

Если какая-то из функций останется без реализации, при сборке будет ошибка
от [линкера](../lectures/glossary.md#linker) (linker):
`undefined symbol` с её именем (на Linux — `undefined reference`).

### EventList

Односвязный список `EventList`: узел с указателем на следующий. Узлы
выделяются через `new`, `next` — обычный указатель. `ListPushBack`,
`ListPopFront`, `ListClear` — операции над списком `EventList`.

Состояние списка — `head`, `tail` и `size`. `tail` нужен, чтобы дописывать
в конец без обхода от головы, и обнуляется вместе с `head`, когда список
опустел. `size` обязан всегда равняться числу узлов в цепочке: тесты считают
узлы обходом и сверяют с полем.

1. **Деструктор обязателен.** `~EventList` освобождает все узлы. Деструктор
   вызывается сам на любом выходе из области видимости, включая ранний
   `return`, — это [RAII](../lectures/glossary.md#raii) из лекции 2
   на своём коде.
2. **Список нельзя копировать.** Копия получит те же адреса узлов, и
   в деструкторе копии каждый узел удалится второй раз — это
   [double free](../lectures/glossary.md#double-free).
   Не присваивать список и не передавать его в функцию по значению. Запретить
   копирование по-настоящему вы научитесь на занятии 2.1, где список станет
   классом; пока это запрет на словах.
3. **Пустой список — обычный случай.** `ListPopFront` и `ListClear` на нём
   ничего не делают и ошибкой не считаются. После `ListClear` список пуст
   и годен к работе снова, а `capacity` сохраняется: вместимость — настройка,
   а не состояние.

### Таблица разбора

В таблице — строка целиком, как она приходит из журнала:

| Вход `ParseEventLine` | Результат |
|---|---|
| `ts=100 type=boot a=1 b=2` | `true`, в `fields` две пары |
| `ts=100 type=boot a=1 a=2` | `true`, две пары со значениями `1` и `2` |
| `ts=100 type=boot tag=x ts=200` | `true`, `ts` события `100`, а `ts=200` — поле в `fields` |
| `ts=100 type=boot k=a=b` | `true`, одна пара со значением `a=b` |
| `ts=100 type=ps cmdline="cmd /c wscript a.js" exit=7` | `true`, две пары; у первой значение `cmd /c wscript a.js` |
| `ts=100 type=fw path="C:\a b.js"` | `true`, одна пара со значением `C:\a b.js` |
| `ts=100 type=boot k=` | `true`, пара с пустым значением |
| `ts=100 type=boot =value` | `false` |
| `ts=100 type=boot word` | `false` |
| `ts=100 type=boot k="a b` | `false` |
| `ts=100 type=boot k="a"b` | `false` |
| `type=boot pid=1` | `false`, нет `ts` |
| `ts=100 pid=1` | `false`, нет `type` |

При `false` содержимое `*out` использовать нельзя, хотя часть полей в нём
уже может лежать.

## Тесты

Три группы: окно последних событий (`list_tests.cpp`), разбор строки журнала
(`parse_tests.cpp`) и контекст детекта — четыре случая, которые запускают
вашего агента целиком. Плюс набор 1.1, который остаётся подключённым.

Случаи контекста сравнивают **только строки `[CTX]`**, всё остальное в выводе
пропускают: формулировки сводки остаются вашими. Два случая проходят два
сценария с настройками по умолчанию, третий даёт `--window-size 1` и ждёт
одной строки контекста вместо двух, четвёртый проверяет, что под `--quiet`
строк `[CTX]` нет.

### Запуск тестов

```bash
ctest --preset windows
```

На Linux вместо `windows` — `linux`.

Отдельно и обязательно — прогон под санитайзером, тремя командами:

```bash
cmake --preset asan-windows -D NANO_EDR_LESSON=1.2
```

```bash
cmake --build --preset asan-windows
```

```bash
ctest --preset asan-windows
```

На Linux — `asan`. Пресеты комплекта собирают clang, поэтому
`-fsanitize=address,undefined` действует на обеих системах целиком — кроме
поиска утечек, которого на Windows нет
([почему](#на-что-обратить-внимание)).

### Что именно проверяется

Тесты списка проверяют граничные случаи: пустой список, один элемент, тысяча
элементов, вытеснение при переполнении. Тесты разбора наполовину состоят
из испорченных строк. Журнал пишет чужой код, и одна битая строка в нём —
обычное дело: программа, которая на такой строке падает, не доходит до конца
файла.

Тесты контекста проверяют как окно и разбор применены в `main.cpp`.

### На что обратить внимание

**Утечку и double free видит не тест, а санитайзер.** Тест «тысяча
элементов освобождается деструктором» под обычной сборкой проходит и при
потерянных узлах. Отсюда и критерий занятия — прогон под санитайзером,
а не зелёный `ctest`.

**На Windows утечки не видит и санитайзер.**
[LeakSanitizer](../lectures/glossary.md#lsan) там не работает,
и потерянные узлы не показывает ни один прогон. Обращение к освобождённому
и double free `asan-windows` ловит по-настоящему.

**Тесты сверяют поле `size` с числом узлов.** Узлы они считают обходом
цепочки.
