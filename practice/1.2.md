# Занятие 1.2. Односвязный список и разбор строки

> [Лекция 2](../lectures/02/lecture.md): указатели, память, RAII, `unique_ptr`.

Появляется первая структура данных, которую вы напишете сами, и первый тип
проекта — `Event`.

## Конфигурация

```bash
cmake --preset windows -D NANO_EDR_LESSON=1.2
cmake --build --preset windows
ctest --preset windows
```

На Linux вместо `windows` — `linux`. Что делают эти команды и откуда их
запускать — в [`project/README.md`](../project/README.md).

Набор тестов 1.1 остаётся подключённым, и это не случайность: он фиксирует
формат вывода детектов. Внутренности на этом занятии переписываются целиком,
и то, что вывод под `--quiet` остался побайтово тем же, — единственное
доказательство, что контракт не поехал.

## Куда это писать

Два новых файла в `src/`:

| | |
|---|---|
| `src/parse.cpp` | реализации из `parse.h` |
| `src/event_list.cpp` | реализации из `event_list.h` |

`CMakeLists.txt` править не нужно: библиотека `nano_edr_core` собирается
из всех `.cpp` в `src/`, кроме `main.cpp`, а выданные тесты линкуются с ней.
Но появление новых файлов — это изменение описания проекта, поэтому после него
нужна **пере**конфигурация: `cmake --preset windows -D …` ещё раз.

Реализовать нужно всё, что объявлено в заготовках, и ровно с теми подписями:

```
ParseFields  ParseEventLine  IsBlankOrComment
ListPushBack  ListPopFront  ListClear  EventList::~EventList
```

Подписи менять нельзя — против них собраны выданные тесты. Всё остальное
на ваше усмотрение: как искать кавычки, в каком порядке проверять поля,
заводить ли внутренние вспомогательные функции.

**Пока этих файлов нет, набор 1.2 не собирается** — компоновщик скажет
`unresolved external symbol` (на Linux — `undefined reference`) на каждую
из семи. Так выглядит начало занятия, а не поломка комплекта.

## Примитив (40 минут)

Односвязный список `EventList`: узел с указателем на следующий, вставка
в конец, обход, освобождение.

1. **Сначала на сырых указателях.** `new`, `delete`, `Node* next`. Цель —
   увидеть, как это устроено, и написать деструктор руками.
2. **Потом переписать владение на `std::unique_ptr`** и обсудить, что
   изменилось: где исчез `delete`, что стало с копированием, почему список
   теперь нельзя случайно скопировать.
3. **Деструктор списка — явным циклом**, а не «пусть само». Цепочка
   `unique_ptr` разбирается рекурсией: деструктор головы вызывает деструктор
   следующего узла, и глубина стека равна длине списка. На тысяче узлов это
   работает, на десятках тысяч — переполняет стек, причём в момент
   уничтожения списка, а не работы с ним. Выданные тесты доходят до тысячи
   узлов, так что рекурсивную версию они пропустят; это не значит, что она
   верна.

## Проект

1. **`struct Event`** — агрегат, ещё без методов: поля-строки `ts`, `type`,
   `pid` и вектор пар «ключ-значение».
2. **Разбор строки** на пары «ключ-значение» прямым проходом по символам,
   с учётом кавычек. `cmdline="cmd /c wscript %TEMP%\a.js"` — одно значение
   с пробелами внутри, а не три поля. Дубликаты ключей формат разрешает,
   и правило «последний выигрывает» — часть контракта: отбрасывать строку
   из-за них нельзя.
3. **Вырожденные входы разбора:** незакрытая кавычка, `=` внутри значения,
   пустой ключ, ключ без значения, пара без `=`. Разбор не падает и не строит
   событие из обрывка: он либо возвращает событие, либо честно сообщает, что
   строка битая. Битая строка и строка, которую нужно пропустить, — разные
   вещи: `ParseEventLine` вернёт `false` и на комментарий, и на обрывок,
   а отличает их только `IsBlankOrComment`.
4. **Список хранит окно последних событий**: у него есть вместимость, и при
   переполнении самое старое уходит. Окно, а не архив.
5. **Размер окна из командной строки:** `--window N`, по умолчанию 64. Ноль
   означает «без ограничения». Число разбирайте руками — `std::stoi` бросает
   исключение, а исключения это занятие 1.3.
6. **Контекст детекта.** Окно пока никто не читает, и структура, которую
   только заполняют, ничего не доказывает. Печатайте перед каждым детектом
   два последних события из окна — время, тип, `pid`:

   ```
   [CTX]    -2: ts=1730000002000 type=process_start pid=1042
   [CTX]    -1: ts=1730000003000 type=file_write    pid=1042
   ```

   Только в обычном режиме: под `--quiet` в `stdout` по-прежнему не должно
   быть ничего, кроме детектов. Список односвязный, назад по нему не пройти,
   поэтому два последних события ищутся обходом всего окна от головы.

**`std::string` по значению.** Пока за это не снимают баллы, но с занятия 1.3
будут — ссылки появляются на лекции 3. Заготовка `l1.2` принимает параметры
указателем и по значению именно поэтому: ссылок вы ещё не проходили.

## Готово, когда

- Тесты списка и разбора зелёные, тесты занятия 1.1 по-прежнему зелёные.
- Прогон под санитайзером чист: пресет `asan-windows`, на Linux — `asan`.
- Разбор не падает ни на одном вырожденном входе.

## Тесты

Две группы: окно последних событий (`list_tests.cpp`) и разбор строки журнала
(`parse_tests.cpp`). Плюс набор 1.1, который остаётся подключённым.

### Запуск тестов

```bash
ctest --preset windows
```

На Linux вместо `windows` — `linux`.

Отдельно и обязательно — прогон под санитайзером, тремя командами:

```bash
cmake --preset asan-windows -D NANO_EDR_LESSON=1.2
```

```bash
cmake --build --preset asan-windows
```

```bash
ctest --preset asan-windows
```

На Linux — `asan`, и там же полнее: у GCC и clang это ASan и UBSan, у MSVC
только ASan.

### Что именно проверяется

Тесты списка идут по границам: пустой список, один элемент, тысяча элементов,
вытеснение при переполнении. Тесты разбора наполовину состоят из испорченных
строк: журнал пишет чужой код, и агент, который на одной битой строке падает
или строит событие из обрывка, хуже, чем бесполезный — по такому обрывку
потом сработает правило.

### На что обратить внимание

**Тест «тысяча элементов освобождается деструктором» под обычной сборкой
не проверяет ничего.** Он и не должен: утечку и двойное освобождение видит
не тест, а санитайзер. Критерий занятия — чистый `-fsanitize=address,undefined`,
и зелёный `ctest` без санитайзера этого не показывает.

**Тесты считают узлы отдельно и сравнивают с полем `size`.** Поле, за которым
никто не следит, расходится с длиной цепочки на первом же вытеснении, и ловится
это только так.
