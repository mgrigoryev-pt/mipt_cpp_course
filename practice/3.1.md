# Занятие 3.1. Окно событий и комбинаторы

> Лекции [8](../lectures/08/lecture.md)–[9](../lectures/09/lecture.md):
> шаблоны, специализация, non-type параметры, variadic, fold expressions.

До сих пор все [шаблоны](../lectures/glossary.md#template) (templates)
в проекте приходили из комплекта или из стандартной библиотеки. На этом
занятии вы напишете свои: кольцевой буфер, фабрику правил и разбор поля
по типу.

**Кольцевой буфер** — массив на `N` мест, в котором новый элемент, когда
места кончились, затирает самый старый: буфер на 4 места после вставки 1, 2,
3, 4, 5, 6 хранит 3, 4, 5, 6. Память у него внутри объекта, и вставка
не обращается к [куче](../lectures/glossary.md#heap) (heap). Поэтому он заменит
односвязный список в окне агента — последних событиях, из которых агент
печатает контекст перед детектом: список выделяет память на каждое событие.

Из выданных шаблонов собирается седьмое правило, **пороговое**: оно
срабатывает, когда у одного процесса набралось 20 подходящих событий
за 10 секунд, и ловит процесс, который массово переписывает документы
пользователя. На [`ransomware`](../project/scenarios/ransomware.log) агент
под `--quiet` печатает четыре новые строки, первая из них:

```
[DETECT] critical  ransomware_mass_write  ts=1730100002410 pid=2210
```

На остальных шести сценариях новое правило не срабатывает.

### 1. Кольцевой буфер `RingBuffer<T, N>`

Скопируйте обе заготовки в `src/`:

```bash
cp tasks/3.1/skeleton/ring_buffer.h src/
cp tasks/3.1/skeleton/make_rule.h src/
```

Дальше файлы ваши. Имена методов и то, что они делают, менять нельзя:
против них собраны выданные тесты и выданный `ThresholdRule`.

В заготовке `RingBuffer` хранит `Timestamp` и годится одному пороговому
правилу: оно считает отметки времени. Но на
[шаге 3](#3-окно-агента-на-ringbuffer) на кольцевой буфер переезжает и окно
агента `window_` — последние события, из которых агент перед детектом
печатает строки `[CTX]`. В окне лежат не отметки времени, а записи
о событиях: время, тип и `pid`. Поэтому первая половина работы — сделать
буфер шаблоном `RingBuffer<T, N>`: `T` — параметр-тип, `N` —
[non-type template parameter](../lectures/glossary.md#non-type-parameter),
вместимость ([лекция 8, раздел 10](../lectures/08/lecture.md#10-non-type-template-parameters)).

```cpp
// в заготовке
class RingBuffer {
 public:
    void PushBack(const Timestamp& value);
    const Timestamp& operator[](std::size_t index) const;
    // ...
};

// стало
template <typename T, std::size_t N>
class RingBuffer {
 public:
    void PushBack(const T& value);
    const T& operator[](std::size_t index) const;
    // ...
 private:
    // приватные поля ваши
};
```

`Timestamp` во всех методах и в итераторе становится `T`. Приватные поля —
где лежат элементы, где сейчас самый старый и сколько их — выбираете вы.

Вторая половина — тела методов. Пишутся они в том же заголовке, а не
в `.cpp` ([почему](#почему-шаблон-пишется-в-заголовке)).

| Метод | Что делает |
|---|---|
| `PushBack(value)` | дописывает в конец; если буфер полон, самый старый элемент затирается |
| `Clear()` | опустошает буфер |
| `size()`, `empty()`, `full()` | сколько лежит; пуст ли; заполнен ли до `N` |
| `static capacity()` | вместимость, то есть `N`; известна на этапе компиляции |
| `operator[](index)` | элемент по логическому индексу: 0 — самый старый |
| `back()` | самый новый элемент; на пустом буфере вызывать нельзя |
| `begin()`, `end()` | обход, в том числе у `const`-объекта |

Как это выглядит на `RingBuffer<int, 4>`:

| Что сделано | `size()` | Обход | `ring[0]` | `back()` |
|---|---|---|---|---|
| только создан | 0, `empty()` | ничего | — | — |
| `PushBack` 1, 2, 3, 4 | 4, `full()` | 1 2 3 4 | 1 | 4 |
| ещё `PushBack` 5 и 6 | 4 | 3 4 5 6 | 3 | 6 |
| `Clear()`, затем `PushBack(42)` | 1 | 42 | 42 | 42 |

У итератора в заготовке три операции — `++`, `*` и `!=`, ровно то, что нужно
[range-based for](../lectures/glossary.md#range-for):

```cpp
for (const int value : ring) {  // 3 4 5 6
    // ...
}
```

Ни приватных полей, ни конструктора у итератора в заготовке нет — их
добавляете вы. Запрет менять интерфейс сюда не относится: тесты
и `ThresholdRule` получают итератор только из `begin()` и `end()`. Например,
итератор хранит указатель на буфер и логический индекс, конструктор
принимает оба, а `*` зовёт `operator[]` буфера.

Два требования, которые проверяют тесты:

- **Обход от старого к новому.** Иначе контекст детекта напечатается задом
  наперёд.
- **Ни одной аллокации, включая создание.** Тест считает обращения к куче,
  пока буфер создаётся, принимает десять тысяч вставок и обходится. Выделить
  память один раз в конструкторе тоже нельзя: такой буфер не обращается
  к куче на вставке, но при создании обращается.

**Проверка.** Агент собирается:

```bash
cmake --build --preset windows --target nano-edr
```

На Linux — `--preset linux`. Тесты набора 3.1 пока не линкуются: им нужны
тело фабрики и функции разбора поля, это шаг 2.

### 2. Фабрика `MakeRule`

[Фабрика](../lectures/glossary.md#factory) (factory) — функция, которая
создаёт объект и возвращает его. Фабрика из `src/make_rule.h` создаёт
правило любого типа и возвращает его в `std::unique_ptr`. Тот же вызов
через `std::make_unique`, как в 2.3, и через фабрику:

```cpp
// было в 2.3
auto beacon = std::make_unique<SequenceRule>("script_host_beacon",
                                             Severity::kCritical, 10000);

// через фабрику
auto beacon = MakeRule<SequenceRule>("script_host_beacon",
                                     Severity::kCritical, 10000);
```

`Rule` в вызове пишется явно, а `Args...` —
[пакет параметров](../lectures/glossary.md#parameter-pack) (parameter pack),
его компилятор [выводит](../lectures/glossary.md#deduction) (type deduction)
из аргументов. Нужно написать тело: фабрика передаёт `id`, `severity` и все
`args...` в `std::make_unique<Rule>` и возвращает результат.

**Заглушка для разбора полей.** Выданные тесты зовут ещё и функции шага 5
и без них не слинкуются. Чтобы проверить шаги 1 и 2 сейчас, заведите
`src/field_traits.cpp`:

```cpp
#include "field_traits.h"

namespace nano_edr {

bool FieldTraits<std::string>::Parse(const std::string&, std::string*) {
    return false;
}
bool FieldTraits<uint64_t>::Parse(const std::string&, uint64_t*) {
    return false;
}
bool FieldTraits<bool>::Parse(const std::string&, bool*) {
    return false;
}

}  // namespace nano_edr
```

**Проверка.**

```bash
ctest --preset windows -R 'task3\.1$' --output-on-failure
```

На Linux — `--preset linux`. В конце отчёта:

```
[doctest] test cases:  38 |  31 passed |  7 failed | 0 skipped
```

Красные семь — тесты разбора поля, до шага 5. Остальные — буфер, пороговое
правило, комбинаторы и фабрика — зелёные.

### 3. Окно агента на `RingBuffer`

**`Event` в буфер не кладётся.** `RingBuffer<Event, 256>` не соберётся:
у `Event` нет
[конструктора по умолчанию](../lectures/glossary.md#default-constructor)
(default constructor), и компилятор ответит
`no matching constructor for initialization of 'nano_edr::Event'`. Добавлять
такой конструктор не нужно ([почему](#почему-окно-не-хранит-event)).

В окно кладётся запись — только то, что нужно для печати контекста: время,
тип и номер процесса. Объявите её в `agent.h`, перед классом агента:

```cpp
struct WindowEntry {
    Timestamp ts;
    std::string type;
    std::string pid;
};
```

В агенте окно `EventList window_` нужно заменить кольцевым буфером таких
записей на 256 мест. Вместимость — константа агента, и в конструктор её
больше не передают:

```cpp
class Agent : public IEventHandler {
 public:
    static constexpr std::size_t kWindowCapacity = 256;

    explicit Agent(bool quiet);
    // ...
 private:
    RingBuffer<WindowEntry, kWindowCapacity> window_;
    RuleEngine engine_;
    // ...
};
```

В `main` агент создаётся без размера окна: `Agent agent(options.quiet);`.
Сам флаг уберёте на шаге 4.

**Контекст:**

- две последние записи окна: `window_[window_.size() - 2]`
  и `window_.back()`; если записей меньше двух — сколько есть;
- сработавшее событие в контекст не входит: в окно оно кладётся после того,
  как контекст напечатан;
- строки `[CTX]` идут сразу перед строками `[DETECT]` этого события, один
  раз, даже если сработало несколько правил.

Меняется только сама строка: в ней время, тип и `pid`, а не событие целиком,
как в 2.3. Например, на `ransomware`:

```
[CTX] -2: 1730100002110 file_move pid=2210
[CTX] -1: 1730100002200 file_write pid=2210
[DETECT] critical  ransom_extension  ts=1730100002260 pid=2210
```

Формат строки — ровно как в примере: его сверяет выданный тест.

В сводку добавьте строку о том, сколько мест окна занято, например
на `ransomware`:

```
[STAT] в окне 87 из 256 мест
```

Формулировка ваша, тесты сводку не сверяют.

**Проверка.** Тесты запускают агента на семи сценариях и сверяют строки
`[CTX]` и `[DETECT]` с эталоном, по порядку:

```bash
ctest --preset windows -R 'task3\.1\.output' --output-on-failure
```

Зелёные шесть из семи. `task3.1.output.ransomware` красный до шага 6:
в эталоне уже есть строки нового правила. Строку об окне тест не видит —
посмотрите её сами: `./build/windows/Release/nano-edr scenarios/ransomware.log`,
на Linux — `./build/linux/nano-edr`.

### 5. Разбор поля по типу

Поля события — строки, и до сих пор каждый вызывающий сам решал, что с ними
делать. В [`field_traits.h`](../project/kit/include/l3.1/field_traits.h)
выдан доступ к полю нужного типа:

```cpp
std::uint64_t pid = 0;
if (GetField<std::uint64_t>(event, "pid", &pid)) {
    // ...
}
```

`GetField` находит строку поля через `FindField` и разбирает её через
`FieldTraits<T>::Parse`. У `FieldTraits` три полные
[специализации](../lectures/glossary.md#specialization) (specialization) —
для `std::string`, `uint64_t` и `bool`
([лекция 8, раздел 8](../lectures/08/lecture.md#8-специализация-шаблонов)).
Объявлены они в комплекте, а тела `Parse` нужно написать
в `src/field_traits.cpp` вместо заглушки шага 2:

| `T` | `Parse` возвращает `true` | `Parse` возвращает `false` |
|---|---|---|
| `std::string` | всегда: строка берётся как есть | — |
| `uint64_t` | строка — непустая цепочка десятичных цифр: `"42"`, `"0"`, `"18446744073709551615"` | `""`, `"+42"`, `" 42"`, `"12ab"`, `"много"`; `"18446744073709551616"` — не помещается в `uint64_t` |
| `bool` | `"1"`, `"true"`, `"yes"` — значение `true`; `"0"`, `"false"`, `"no"` — значение `false`; регистр не учитывается, `"Yes"` тоже `true` | всё остальное: `"y"`, `"может быть"`, `""` |

При `false` значение по указателю не меняется. `GetFieldOr` выдан готовым.

Для `bool` нужно сравнение без учёта регистра — оно у вас есть в `src/text.h`
с занятия 2.2. `GetIntField` из `fields.h` трогать не нужно: он остаётся,
как был.

**Перед определением `Parse` не пишется `template <>`.** В `field_traits.h`
он уже стоит — перед самой специализацией:

```cpp
template <>
struct FieldTraits<uint64_t> {
    static bool Parse(const std::string& text, uint64_t* out);
};
```

`FieldTraits<uint64_t>` — готовый класс, а `Parse` в нём — обычная функция,
не шаблон. Поэтому в `src/field_traits.cpp` её тело пишется как у метода
обычного класса, в той же форме, что у заглушки шага 2:

```cpp
// правильно
bool FieldTraits<uint64_t>::Parse(const std::string& text, uint64_t* out) {
    // ...
}

// ошибка компиляции
template <>
bool FieldTraits<uint64_t>::Parse(const std::string& text, uint64_t* out) {
    // ...
}
```

На второй вариант clang отвечает так (у g++ текст другой):

```
error: no function template matches function template specialization 'Parse'
```

С `template <>` компилятор ищет шаблон функции `Parse`, чтобы его
специализировать, а такого шаблона нет.

**Проверка.** Та же команда, что на шаге 2, печатает `100% tests passed`.
Отчёт doctest при этом не выводится — `--output-on-failure` показывает его
только у упавших.

### 6. Порог на массовую запись

Условие нового правила собирается из выданных `AllOfStatic` и `AnyOfStatic`
из [`combinators.h`](../project/kit/include/l3.1/combinators.h). Это
комбинаторы — условия, составленные из других условий, как `AllOf`
и `AnyOf` с занятия 2.3. Разница в том, когда задаётся состав: у `AllOf` —
во время работы, вызовами `Add`; у `AllOfStatic` — при компиляции,
аргументами конструктора:

```cpp
// было в 2.3: состав собирается вызовами Add
auto start = std::make_unique<AllOf>();
start->Add(std::make_unique<EventTypeIs>(
    std::vector<EventType>{EventType::kProcessStart}));
start->Add(std::make_unique<FieldEndsWith>("image", "wscript.exe"));

// то же на шаблоне: состав задан при компиляции
std::unique_ptr<ICondition> start = MakeCondition(AllOfStatic(
    EventTypeIs({EventType::kProcessStart}),
    FieldEndsWith("image", "wscript.exe")));
```

Писать их не надо. Аргументы шаблона в вызове не написаны: их выводит
[CTAD](../lectures/glossary.md#ctad) из аргументов конструктора
([лекция 8, раздел 4](../lectures/08/lecture.md#4-ctad--вывод-аргументов-шаблона-класса-c17)).
`AllOfStatic` не наследует `ICondition`
([почему](#почему-комбинатор-не-реализует-icondition)), поэтому правилу его
передают через `MakeCondition`: она возвращает `std::unique_ptr<ICondition>`.

| Комбинатор | Возвращает `true`, если… |
|---|---|
| `AllOfStatic(c...)` | …все условия вернули `true` |
| `AnyOfStatic(c...)` | …хотя бы одно вернуло `true` |

Само правило — `ThresholdRule<N>` из [`rule.h`](../project/kit/include/l3.1/rule.h),
выдано целиком. Оно срабатывает, когда у одного значения ключа, например
`pid`, набралось `count` подходящих событий за `window_ms` миллисекунд,
и после детекта считает заново.

Седьмое правило создаётся фабрикой из шага 2 и добавляется в движок
последним, в `BuildAgentRules()`. В `agent_rules.cpp` для этого понадобятся
`#include "make_rule.h"` и `#include "combinators.h"`:

```cpp
auto mass_write = MakeRule<ThresholdRule<128>>(
    "ransomware_mass_write", Severity::kCritical,
    20,      // сколько событий
    10000,   // за сколько миллисекунд
    "pid");  // порог считается для каждого pid отдельно
mass_write->SetCondition(MakeCondition(AllOfStatic(
    EventTypeIs({EventType::kFileCreate, EventType::kFileWrite,
                 EventType::kFileMove}))));
mass_write->AddAction("kill_process");
mass_write->AddAction("quarantine_file");
engine.AddRule(std::move(mass_write));
```

`AllOfStatic` из одного условия — не ошибка: на шаге 7 к нему добавится
второе.

**Проверка.** Та же команда, что на шаге 3: `task3.1.output.ransomware`
зелёный — четыре новые строки `ransomware_mass_write`, первая — в начале
занятия. Две вместо четырёх — в условии нет `file_move`.

Красным становится `task3.1.output.clean_office`: ложный детект, его чинит
[шаг 7](#7-ноль-детектов-на-чистых-сценариях):

```
[DETECT] critical  ransomware_mass_write  ts=1730500004520 pid=1300
```

### 7. Ноль детектов на чистых сценариях

В сценариях [`clean_office`](../project/scenarios/clean_office.log)
и [`clean_build`](../project/scenarios/clean_build.log) атак нет, и детект
на них — ложный: вывод под `--quiet` должен быть пустым.

Ложный детект шага 6 даёт браузер: процесс `pid=1300` пишет свой кэш,
двадцать событий записи за 1,1 секунды. По количеству и скорости это
шифровальщик:

```
ts=1730500003400 type=file_create pid=1300 path="C:\Users\max\AppData\Local\Google\Chrome\User Data\Default\Cache\data_0"
```

Отличается то, где лежат файлы. Браузер пишет в свой каталог в `AppData`,
а шифровальщик переписывает документы пользователя —
`C:\Users\max\Documents\…` и `C:\Users\max\Desktop\…`. Поэтому в условие
нужно добавить вторую часть: путь содержит `\Documents\` или `\Desktop\`.
У `file_create` и `file_write` путь лежит в поле `path`, а у `file_move` новый
путь — в поле `to`, поэтому проверяются оба поля, условием `FieldContains`
с занятия 2.2:

```cpp
mass_write->SetCondition(MakeCondition(AllOfStatic(
    EventTypeIs({EventType::kFileCreate, EventType::kFileWrite,
                 EventType::kFileMove}),
    AnyOfStatic(FieldContains("path", "\\Documents\\"),
                FieldContains("path", "\\Desktop\\")
                /* и те же два для поля to */))));
```

Обратный слэш в строковом литерале удваивается: `"\\Documents\\"` — это
строка `\Documents\`.

**Проверка.** Та же команда, что на шаге 3: зелёные все семь. Если красный
`task3.1.output.ransomware` и строк `ransomware_mass_write` две вместо
четырёх — проверяется только `path`, а у `file_move` путь в `to`.

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Почему шаблон пишется в заголовке

Шаблон — не код, а описание семейства кода. Конкретный `RingBuffer<WindowEntry, 256>`
компилятор порождает, [инстанцируя](../lectures/glossary.md#instantiation)
(instantiation) шаблон там, где он используется, и тело ему нужно в той же
[единице трансляции](../lectures/glossary.md#translation-unit) (translation
unit). Если тела лежат в отдельном `.cpp`, единица трансляции агента видит
только объявления, и линковщик не найдёт ни одного метода
([лекция 8, раздел 6](../lectures/08/lecture.md#6-модель-компиляции-шаблонов)).

### Почему окно не хранит `Event`

Можно было бы дать `Event` конструктор по умолчанию, и `RingBuffer<Event, N>`
собрался бы. Цена — «пустое событие»: объект без времени и типа, который
каждый получатель обязан проверять после создания. От этого занятие 2.1
и избавило. Решение в другом месте: окну полное событие не требовалось
никогда, контексту нужны три значения. Выяснилось это, только когда хранить
событие целиком стало нельзя.

### Почему буфер не аллоцирует, а окно может

Ноль аллокаций — свойство буфера: его элементы лежат в самом объекте.
Но буфер не знает, что хранит. Если в записи окна лежат строки,
каждая запись может обращаться к куче сама, и тогда окно аллоцирует
на каждом событии, буфер при этом чист, а тест зелёный: он проверяет буфер
на `Timestamp`. Для этого занятия запись со строками допустима. Знать стоит
другое: «не аллоцирует» относится к контейнеру, а не ко всему, что в нём
лежит.

### Почему основной шаблон `FieldTraits` не определён

[Основной шаблон](../lectures/glossary.md#primary-template) (primary
template) `FieldTraits` объявлен и не определён, определены только три
специализации. Поэтому
`GetField<double>` не соберётся: для `double` специализации нет, а общего
разбора, на который можно было бы откатиться, не существует. Это осознанно:
ошибка компиляции лучше разбора, который молча делает что-то похожее
на правду. Новый тип — новая специализация, а не новая функция с новым
именем.

### Почему комбинатор не реализует `ICondition`

Шаблонный комбинатор нужен ради одного: внутри него нет ни аллокаций,
ни виртуальных вызовов, всё встраивается. Если бы `AllOfStatic` наследовал
`ICondition`, а вложенные условия хранились через интерфейс, вернулись бы
и косвенные вызовы, и указатели. Поэтому мост один — `MakeCondition`, и
виртуальный вызов остаётся один на весь составной комбинатор, а не на каждое
условие внутри.

Динамический `AllOf` при этом не хуже, у него другая область применения:
его состав можно собрать во время работы, например из файла.

### Почему фабрика берёт аргументы по значению

`args...` внутри фабрики — именованные переменные, то есть
[lvalue](../lectures/glossary.md#lvalue), и `std::make_unique` получает их
копии. Лишняя копия известна, и снимается она на занятии 3.3, где появятся
перемещение и идеальная передача из лекции 11.

### Почему порог считается по ключу и сбрасывается

Порог на весь хост сложил бы безобидную активность десяти процессов в один
детект и ловил бы нагрузку на машину, а не поведение процесса. Сброс после
детекта нужен по той же причине, по которой `SequenceRule` удаляет запись
из `pending_` после детекта: без него одно превышение давало бы детект
на каждом следующем событии.
