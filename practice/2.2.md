# Занятие 2.2. Условия, базовый класс правила и механика наследования

> Лекции [5](../lectures/05/lecture.md)–[6](../lectures/06/lecture.md):
> объекты с `operator()`, наследование, порядок конструкторов и деструкторов,
> размер объекта, множественное наследование.

До сих пор правило было функцией-проверкой, а его идентификатор и важность
лежали рядом, в строке таблицы правил. С этого занятия правило — объект:
в нём хранятся идентификатор, важность, условия, список действий и счётчик
срабатываний. Счётчик и есть причина переезда: функции негде помнить, сколько
раз она сработала. По счётчикам агент в конце прогона печатает, сколько
детектов дало каждое правило.

**Условие** — одна проверка поля события: «`type` равен `process_start`»,
«`image` заканчивается на `wscript.exe`». Правило срабатывает на событии, когда
все его условия для этого события дают «да».

Детекты при этом не меняются: на тех же журналах агент печатает ровно то же,
что на 2.1.

Отдельно от проекта идёт [упражнение](#упражнение-механика-наследования) о том,
как наследование устроено в памяти: порядок конструкторов, размеры объектов,
адреса баз, ромб.

### 1. Четыре условия-функтора

Условие — [функтор](../lectures/glossary.md#functor) (function object):
объект с `operator()`, который про одно событие отвечает `true` или `false`
([лекция 5, раздел 7](../lectures/05/lecture.md#7-роль-5-тип-притворщик)).
Что именно проверять — ключ поля и значение, — передаётся в конструктор
и хранится в полях объекта:

```cpp
const FieldEndsWith js_in_cmdline("cmdline", ".js");
if (js_in_cmdline(event)) {
    // ...
}
```

Классы с конструкторами объявлены в
[`conditions.h`](../project/kit/include/l2.2/conditions.h); в
`src/conditions.cpp` пишется `operator()` каждого:

| Класс | `operator()` возвращает `true`, если значение поля `key`… |
|---|---|
| `FieldEquals(key, value)` | …равно `value` целиком |
| `FieldContains(key, needle)` | …содержит `needle` |
| `FieldEndsWith(key, suffix)` | …заканчивается на `suffix` |
| `FieldInList(key, values)` | …равно одному из `values` |

Для всех четырёх:

- регистр не учитывается: `FieldEquals("type", "PROCESS_START")` возвращает
  `true` на событии `process_start`;
- поле ищется через `FindField`, поэтому работают и ключи шапки `ts`, `type`
  и `pid`;
- если поля нет, возвращается `false`, а не бросается исключение
  ([почему](#почему-условие-не-бросает));
- `FieldInList` с пустым списком значений всегда возвращает `false`.

Сравнение без учёта регистра у вас уже есть — в `PathEndsWith`
и `CommandLineContains` из `fields.cpp`. Условиям нужно три таких сравнения:
равенство, вхождение подстроки и окончание. Вынесите их функциями в свои
файлы `src/text.h` и `src/text.cpp` и вызывайте оттуда и в `fields.cpp`,
и в `conditions.cpp`: две копии одной функции разойдутся на первой же правке.

### 2. `Condition`: условие, которое кладётся в вектор

Правило хранит свои условия в векторе — это поле `MatchRule`
из [шага 3](#3-правило-rulebase-и-matchrule). Но `std::vector` хранит объекты
одного типа, а четыре функтора из шага 1 — четыре разных типа, и вектора
из них не собрать.

Поэтому в [`conditions.h`](../project/kit/include/l2.2/conditions.h) выдан
пятый класс — `Condition`, один тип на все сравнения. Какое сравнение делать,
записано в поле `match_`: это значение `enum class Match` — `kEquals`,
`kContains` или `kEndsWith`. `operator()` выбирает сравнение через `switch`
по `match_`. Решение временное: на занятии 2.3 `switch` уйдёт, а в правила
вернутся четыре отдельных класса. До тех пор функторы шага 1 в правилах
не участвуют, их проверяют только тесты.

Функторов четыре, а значений у `Match` три: для `FieldInList` отдельного
нет. Оно не нужно, потому что `Condition` сравнивает поле не с одним
значением, а со списком `values`, и возвращает `true`, если подошло любое
значение из списка:

| Функтор | То же через `Condition` |
|---|---|
| `FieldEquals("type", "file_write")` | `Condition::Equals("type", {"file_write"})` — список из одного значения |
| `FieldInList("type", {"file_create", "file_write"})` | `Condition::Equals("type", {"file_create", "file_write"})` |

Список работает и в двух других сравнениях:
`Condition::EndsWith("image", {"wscript.exe", "cscript.exe"})` возвращает
`true`, если поле `image` заканчивается на `wscript.exe` или на `cscript.exe`.

Конструктор у `Condition` закрытый. Объект создают три
[статические фабрики](../lectures/glossary.md#factory) (static factory
methods) — статические методы, которые создают объект и возвращают его
([лекция 4, раздел 7](../lectures/04/lecture.md#статические-поля-и-методы)).
Каждая фабрика записывает в `match_` своё значение:

| Создаётся | `match_` | `operator()` возвращает `true`, если значение поля `key`… |
|---|---|---|
| `Condition::Equals(key, values)` | `kEquals` | …равно одному из `values` |
| `Condition::Contains(key, values)` | `kContains` | …содержит одно из `values` |
| `Condition::EndsWith(key, values)` | `kEndsWith` | …заканчивается на одно из `values` |

Пишете три фабрики и `operator()` в том же `src/conditions.cpp`; геттеры
`match()`, `key()` и `values()` уже в заголовке. Регистр, ключи шапки, отсутствующее поле и пустой список
значений — по тем же правилам, что у функторов шага 1.

### 3. Правило: `RuleBase` и `MatchRule`

В [`rule.h`](../project/kit/include/l2.2/rule.h) два класса. `RuleBase` — то,
что есть у любого правила: идентификатор, важность, список действий и счётчик
срабатываний. `MatchRule` — [производный класс](../lectures/glossary.md#base-derived)
(derived class), или наследник, `RuleBase`: к общей части он добавляет вектор
условий.

```cpp
MatchRule rule("wscript_start", Severity::kLow);
rule.AddCondition(Condition::Equals("type", {"process_start"}));
rule.AddCondition(Condition::EndsWith("image", {"wscript.exe"}));
rule.AddAction("kill_process");

if (rule.Check(event)) {  // все условия вернули true, hits() вырос на 1
    // ...
}
```

Условия правила соединяются через И: это правило срабатывает, только если
`type` равен `process_start` **и** `image` заканчивается на `wscript.exe`.
Одного верного условия мало. «Хотя бы одно из» — это значения внутри одного
условия: `Condition::EndsWith("image", {"wscript.exe", "cscript.exe"})`
из шага 2.

Действия — имена: правилам на `process_start` дайте `kill_process`,
правилам на файлы — `quarantine_file`. На этом занятии правило их только
хранит, выполнять их агент ещё не умеет.

В `src/rule.cpp` пишется:

| Метод | Что делает |
|---|---|
| `RuleBase(id, severity)` | запоминает идентификатор и важность; действий нет, счётчик 0 |
| `AddAction(action)` | добавляет действие в конец вектора `actions_` |
| `MatchRule(id, severity)` | передаёт идентификатор и важность конструктору `RuleBase` в [списке инициализации](../lectures/glossary.md#member-initializer-list) (member initializer list) |
| `AddCondition(condition)` | добавляет условие в конец вектора `conditions_` |
| `Check(event)` | `true`, если все условия вернули `true`, — тогда же зовёт `CountHit()`; у правила без условий всегда `true` |

Геттеры `id()`, `severity()`, `hits()`, `actions()`, `conditions()` и метод
`CountHit()` уже в заголовке.

### 4. Набор правил на объектах

Пять правил те же, что на 1.3, и срабатывают на том же
([постановка 1.3](1.3.md#пять-правил)), но каждое теперь — объект `MatchRule`,
собранный из условий. Из `agent_rules.cpp` удаляются функции-проверки
и таблица правил. Из `rules.cpp` удаляется `CheckRules`, и в этом файле
остаётся одна функция — `SeverityName`.

Два отличия от 2.1, о которые легко споткнуться.

**`autostart_write` и `ransom_extension` — по два объекта `MatchRule`.**
Эти правила смотрят в разные поля в зависимости от типа события: у
`file_create` и `file_write` путь лежит в поле `path`, у `file_move` новый
путь — в поле `to`. Нужно «`path` заканчивается на `.locked` **или** `to`
заканчивается на `.locked`», а условия одного `MatchRule` соединяются только
через И. Поэтому правило записывается двумя объектами с одним
идентификатором:

```cpp
MatchRule by_path("ransom_extension", Severity::kCritical);
by_path.AddCondition(Condition::Equals("type", {"file_create", "file_write"}));
by_path.AddCondition(Condition::EndsWith("path", {".locked"}));
by_path.AddAction("quarantine_file");

MatchRule by_to("ransom_extension", Severity::kCritical);
by_to.AddCondition(Condition::Equals("type", {"file_move"}));
by_to.AddCondition(Condition::EndsWith("to", {".locked"}));
by_to.AddAction("quarantine_file");
```

В выводе их не различить: строка детекта печатает идентификатор, а он у обоих
один. `autostart_write` записывается так же.

**`script_host_from_temp` перечисляет варианты записи пути.** На 2.1
командная строка перед сравнением проходила через `NormalizePath`, а
`Condition` сравнивает поле как есть: регистр не учитывает, но `\Temp\`,
`/Temp/` и `%TEMP%` для него — разные строки. Поэтому каждый вариант
перечисляется в значениях условия:

```cpp
MatchRule rule("script_host_from_temp", Severity::kHigh);
rule.AddCondition(Condition::Equals("type", {"process_start"}));
rule.AddCondition(
    Condition::EndsWith("image", {"wscript.exe", "cscript.exe"}));
rule.AddCondition(Condition::Contains("cmdline", {
    "\\appdata\\local\\temp\\", "/appdata/local/temp/",
    "\\windows\\temp\\", "/windows/temp/",
    "%temp%", "%tmp%"}));
rule.AddAction("kill_process");
```

Строки с прямыми слешами и с `%TEMP%` есть в
[`rules_edges.log`](../project/tasks/2.1/tests/logs/rules_edges.log)
и обязаны дать детект, как на 2.1.

В `agent_rules.h` замените объявления `AgentRules()`, `AgentRuleCount()`
и пяти функций-проверок одной функцией, которая строит правила и возвращает
вектор:

```cpp
std::vector<MatchRule> BuildAgentRules();
```

### 5. Агент проверяет правила сам

`HandleEvent` с занятия 2.1 проверял событие вызовом `CheckRules`, а его
больше нет. Вместо него — цикл по правилам, которые агент теперь хранит сам:

```cpp
class Agent {
 public:
    // ...
 private:
    EventList window_;
    std::vector<MatchRule> rules_;  // в конструкторе: BuildAgentRules()
    // ...
};

void Agent::HandleEvent(const Event& event) {
    for (std::size_t i = 0; i < rules_.size(); ++i) {
        if (rules_[i].Check(event)) {
            // строка детекта — так же, как печатал CheckRules
        }
    }
    // ...
}
```

### 6. Сводка по правилам

Сводку с занятия 2.1 печатает `Agent::PrintSummary()`. В конец этого метода
добавьте цикл по `rules_`, который печатает у каждого правила идентификатор
и `hits()`. Например, на `persistence.log`:

```
правила, детектов:
  script_host_from_temp  0
  lolbin_download        0
  hidden_powershell      1
  autostart_write        2
  autostart_write        0
  ransom_extension       0
  ransom_extension       0
```

Под `--quiet` сводка, как и раньше, не печатается.

Каждый из семи объектов `MatchRule` срабатывает хотя бы на одном журнале:
на семи сценариях или на `rules_edges.log`. Если у какого-то ноль везде,
он, скорее всего, написан неверно. На одних сценариях ноль бывает и у верного
правила: например, `autostart_write` по полю `to` срабатывает только
в `rules_edges.log`.

**Проверка.** Соберите проект и запустите тесты — вторая и третья команды
из [начала раздела](#развитие-проекта). Случаи `task2.1.sources.<журнал>` прогоняют агента через
оба источника на семи сценариях и на `rules_edges.log` и сравнивают вывод
под `--quiet` с эталонами 2.1. Упавший случай печатает первую строку,
на которой вывод разошёлся.

## Упражнение: механика наследования

[`tasks/2.2/exercise/inheritance.cpp`](../project/tasks/2.2/exercise/inheritance.cpp)
— отдельная программа, с агентом не связанная.

**Сначала предсказание, потом запуск.** Прочитайте код и запишите ответы
ко всем четырём частям — на бумаге или в файле. Только после этого соберите
и запустите программу. Если запустить сначала, любой результат покажется
ожидаемым, и проверять будет нечего. Ошибиться в предсказании не страшно:
засчитывается и объяснённое расхождение.

Упражнение собирается своей целью, как `minimal_agent` на занятии 2.1:

```bash

```

На Linux — `--preset linux` и `./build/linux/inheritance`. Цель не зависит
от вашего кода в `src/`, поэтому упражнение собирается, даже пока не собирается
сам проект. Предупреждение компилятора при сборке — не ошибка: оно понадобится
в части 1.

### Часть 1. Порядок конструкторов и деструкторов

Выпишите тринадцать строк, которые программа печатает в части 1, в том
порядке, в каком ожидаете их увидеть. У `Derived` две базы и три поля,
и список инициализации перечисляет поля не в том порядке, в каком они
объявлены. Деструкторы вызываются в порядке, обратном конструкторам.

После запуска прочитайте предупреждение компилятора к конструктору `Derived`:
что именно оно сообщает и как это связано с выводом.

### Часть 2. Размеры

Предскажите `sizeof` для `First`, `Second`, `Member`, `Derived`, `Padded`,
`Packed`, `Empty`, `EmptyDerived`. Считайте для 64-битной сборки: указатель
занимает 8 байт. Объяснение — не «компилятор так решил», а какие байты где
лежат: где [выравнивание](../lectures/glossary.md#alignment) (alignment)
требует [padding](../lectures/glossary.md#padding) (выравнивающие байты)
и сколько его.

Три вопроса к результату:

- `Padded` и `Packed` состоят из одних и тех же трёх полей. Почему размеры
  разные?
- Почему `sizeof(Empty)` не ноль?
- Почему `sizeof(EmptyDerived)` не равен `sizeof(Empty) + sizeof(int)`?

### Часть 3. Приведение к базам

Программа печатает три адреса — объекта `Derived`, его базы `First` и его
базы `Second` — и сдвиг каждой базы от начала объекта. Совпадут ли все три
адреса? Если считаете, что да, объясните, где тогда лежит `First::a_`. Если
нет — предскажите сдвиг в байтах.

Два вопроса к результату:

- Чем `static_cast<Second*>(&d)` отличается
  от `reinterpret_cast<Second*>(&d)`?
- Как результат связан с требованием занятия 2.1: трамплин приводит `ctx`
  ровно к тому типу, адрес которого передан в `Subscribe`?

### Часть 4. Ромб

`DiamondPlain` наследует `LeftPlain` и `RightPlain`, а каждый из них —
`Base`. Это [ромбовидное наследование](../lectures/glossary.md#diamond)
(diamond inheritance). `DiamondVirtual` устроен так же, но `LeftVirtual`
и `RightVirtual` наследуют `Base`
[виртуально](../lectures/glossary.md#virtual-inheritance) (virtual
inheritance).

Сколько [подобъектов](../lectures/glossary.md#subobject) (subobject) `Base`
в каждом из двух классов? Какой класс больше и во сколько раз?

После запуска допишите в `main` рядом со строкой `dv.value_ = 7;` то же самое
для объекта `DiamondPlain`:

```cpp
DiamondPlain dp;
dp.value_ = 7;
```

Прочитайте сообщение компилятора, затем уберите эти строки.

## Готово, когда

- Тесты наборов 2.1 и 2.2 зелёные. В том числе `task2.1.sources.<журнал>`:
  на семи сценариях и на `rules_edges.log` детекты те же, что на 2.1,
  у обоих источников.
- Правила — объекты `MatchRule`; функций-проверок, таблицы правил
  и `CheckRules` в коде не осталось.
- Сводка в конце прогона показывает число детектов каждого правила.

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Почему правила хранятся вектором `MatchRule`

`BuildAgentRules()` возвращает `std::vector<MatchRule>`, а не
`std::vector<RuleBase>`, хотя `MatchRule` — наследник `RuleBase`.

![Объект MatchRule из двух частей копируется в ячейку размера RuleBase:
базовая часть доезжает, вектор условий перечёркнут красным](img/slicing.svg)

Вектор хранит объекты по значению, и в `std::vector<RuleBase>` каждая ячейка
размером ровно с `RuleBase`. При копировании правила в такую ячейку доезжает
только его базовая часть: идентификатор, важность, действия, счётчик. Вектору
условий места нет, и он теряется. Это [срезка](../lectures/glossary.md#slicing)
(object slicing). Компилятор о ней не предупреждает: копировать наследника
в базу законно. А вызвать `Check` у элемента такого вектора нельзя — у
`RuleBase` этого метода нет.

### Почему условие не бросает

На 2.1 правило брало поле `image` через `GetRequiredField` и на
`process_start` без `image` бросало исключение: обязательного поля нет,
событие испорчено. Условие на том же событии просто возвращает `false`. Так
лучше — отсутствие одного поля не повод прерывать проверку остальных
правил, — но отличить «поля нет» от «поле не подошло» больше нечем,
и сообщение об испорченном событии пропало. Размен сознательный, и знать
о нём полезнее, чем не заметить.
